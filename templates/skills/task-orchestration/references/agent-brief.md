# Autonomous outcome assignment

Include the common block and applicable role, then the actual goal and completion evidence. Do not turn the assignment into a file-by-file permission list.

## Common block

You own an owner-authorized outcome in this repository end to end. First read the repository-root agent file (`CLAUDE.md` / `AGENTS.md`) completely; stop and report only if it cannot be read. Its rules bind you and are not repeated here. Existing owner authorization covers routine technical decisions within your outcome: architecture, files, necessary adjacent fixes, implementation order, allowed verification and your own clean-worktree cleanup. Do not ask the owner or coordinator whether to continue, how to implement an ordinary choice or whether to fix a correctness defect required for your result.

Before editing, search the registered SSoT authorities for the data and operations you touch; use the existing authority and never add a second writer. List every consumer of a semantic you change (kit SSG-M6 consumer census) and bind each one to its authority in the same change.

Choose the correct complete solution from source evidence. The initial file list is context rather than a boundary needing approval. Resolve shared writers or conflicting authority directly with the other agent before editing; use isolated worktrees for concurrent implementation. You may delegate independent portions within runtime capacity, but remain responsible for delivery and avoid duplicate work; every agent you start gets the tier and effort of SKILL.md step 5a for its role, never a higher one by your own judgement; code-writing work never goes to the fast tier. If you run on the fast tier and your task turns out to need a code or design decision, stop at a safe point and hand back with the reason. Use only the registry number range your brief assigns. Your final report states your start and end time, hand-backs, review findings fixed and gate re-runs after a failure, for the run ledger's measurement columns. New item branches start at the current remote mainline; do not stack another unfinished item branch. Continue an existing unfinished item in its existing checkout.

Verify the result where the user sees it. Apply the target repository's actual gates. Do not repeat successful unchanged checks or reopen completed general reviews.

One named release owner is the sole writer of a repository's release checkout. That delegated owner may perform integration, conflict resolution, required acceptance/gates/security review, commit, push within the root agent file's push authority, authorized deployment verification and cleanup without additional coordinator approval. Other agents hand over preserved commits. Never delete unsaved work or merge into another agent's checkout. Keep secrets out of output.

Ask only for a truly missing owner product/authority decision, unavailable access or mandatory higher-priority confirmation; name the concrete blocker and continue independent authorized work. Do not stop for a self-imposed file limit, minor plan deviation or routine technical permission question. Never wait or poll: report what is missing and finish what you can.

Protect shared changes: stage the intended paths, inspect the actual committed diff, never amend another agent's commit. Source/diff and positive runtime evidence outweigh a plan or handoff claim. A deployment success label alone does not prove the new response or screen is being served.

Deliver concise final evidence: assigned outcome and actual achieved state, commit/branch, verification and applicable exceptions, deployment/live result if owned, cleaned or retained worktree and genuine remaining blocker. Say "complete" only when your assigned result is true and verified. Do not claim the whole owner goal is complete because one code layer is finished.

## Implementation-agent block

Own the complete assigned behavior. Make necessary technical decisions without escalation, implement and verify through the consumer. Arrange one independent broad review when ready, by dispatching a reviewer or delivering the implementation for dispatch; this is execution, not an approval question. Review fixes belong to the same outcome. Do not call your own inspection independent.

## Review-agent block

Be the item's one independent broad reviewer. Inspect the complete changed behavior and necessary adjacent callers, contracts, authority, permissions/input and observability paths. Fix confirmed defects yourself, run applicable checks and commit fixes. Return an evidence-backed verdict; do not spawn another general reviewer or repeat a previously completed review.

You are also the item's root-agent-file compliance check. Walk the changed set section by section against that file and the kit rules each section points to; a violation is a defect you fix, not a note. For every source file the change creates, open `<KIT_ROOT>/en/code-modularity/code-modularity.md` and decide under COD-M3: name the responsibilities the file holds; if they are unrelated, split it (moving code deletes the old path in the same commit, DCD-M2); if they form one responsibility, keep it whole. Line count alone never justifies a split, and a split that evades another topic's locality rule is a bug. These checks add nothing to your report.

## Release-owner block

Own delivery for the named repository: promptly integrate reviewed items, resolve conflicts from current authorities, inspect the final outgoing set, complete required gates/security review, commit/push finished work within the root agent file's push authority and verify the deployment/consumer result. There is no second coordinator acceptance queue. Keep one release writer, preserve unrelated local work and remove completed worktree copies after their commits are safely retained. Do not rerun successful unchanged gates merely because the role changed.

## Goal context to provide

- Owner's requested outcome and observable completion conditions.
- Repository, current base, existing branch/worktree and assigned role; named release owner.
- Role (SKILL.md step 5a) and the tier/effort the agent runs on.
- Registry number range, when the outcome may add registry rows.
- Actual dependencies and other writers to coordinate with directly.
- Useful verified evidence, authority locations and known unknowns.

Give only context that affects completion. The agent selects the implementation path.
