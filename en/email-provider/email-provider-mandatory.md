## **EMP-M** — Mandatory

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **EMP-M1** | All transactional email goes through one application facade (`emailService`) that delegates to the resolved `EmailProvider`. The rest of the app calls semantic methods (`emailService.sendX(...)`), never a provider SDK and never the raw `send` outside the facade. | Parallel email paths / vendor lock-in — bug (**SSG-M8**). | grep: no provider SDK import outside `*/email/adapters/`; app code calls `emailService`. |
| **EMP-M2** | Concrete providers are adapters implementing the `EmailProvider` port. The provider SDK import is confined to its adapter file. | Provider leaks into domain — bug. | Import-boundary guard (GEMP1). |
| **EMP-M3** | Provider selection is config-driven (e.g. `EMAIL_PROVIDER=ses`) and resolved in one factory / composition root. Swapping providers = change config + ensure the adapter exists; no application-code change. | Hardcoded vendor — bug; defeats the abstraction. | Single `resolveEmailProvider` reads config; no `if provider===` in domain code. |
| **EMP-M4** | The port interface and email DTOs (`SendEmailParams` / `SendEmailResult`) are provider-neutral and have one type authority. Place them in the narrowest tier that serves their consumers; expose cross-boundary types only when consumers cross that boundary ([GMR1](../monorepo/monorepo-architecture.md)). Do not include provider-specific fields in the port. | Leaky abstraction or unnecessary cross-tier coupling — bug. | Type review confirms one authority, appropriate placement, and no vendor-specific fields. |
| **EMP-M5** | Route provider failures through the application's established error policy and logging policy, preserving cause and retryability while avoiding raw provider details in user responses. | Unrouted provider error or lost observability — bug. | Error mapping is defined by the application's error authority; provider errors are not exposed raw. |
| **EMP-M6** | When email delivers verification or recovery credentials, issuance, validation, expiry, replay prevention, and rate limiting belong to the product's designated verification authority. Keep this transport from creating a parallel credential system. Coordinate rate limits across instances when the deployment can scale beyond one instance. | Brute-force, replay, or authority drift — bug. | The delivery flow calls the designated verification authority; shared rate-limit state is used where needed. |
| **EMP-M7** | Production sending requires deliverability prerequisites: verified sender domain + SPF + DKIM + DMARC; provider sandbox is not production. | Mail to spam / blocked — bug (silent user lockout). | Domain verified + DKIM/SPF/DMARC present before go-live (per adapter part). |
| **EMP-M8** | Provider credentials (API key / IAM creds) come from env / secret manager only, never in code or repo ([security](../security/README.md), [build-environment](../build-environment/README.md)). Missing required config fails fast at startup (no silent disable). | Leaked secret / silent no-send — bug. | Secret scan clean; startup config assertion. |
| **EMP-M9** | Every send carries a required `EmailType`, and the `EmailType` catalog is the single authority for email kinds. Each facade semantic method maps to exactly one type; the type is the key for audit, analytics, suppression scope, and per-type rate-limit + idempotency. Any new kind (e.g. `trial_expiring`, `subscription_expired`, `invoice`, `security_alert`) is registered in the one catalog — never an ad-hoc string at a call site. Do not pre-bloat the catalog with speculative kinds; add each when its sender lands. | Untyped / ad-hoc-string sends → no audit / no per-type controls / suppression can't scope; catalog drift — bug. | `SendEmailParams.type: EmailType` required; every kind defined in the catalog; no string-literal email kind outside it. |
| **EMP-M10** | Transactional templates have one authority, rendered app-side. Template content + data live in a single app-owned source and are rendered to final `html`/`text` by the facade before the adapter. Provider-rendered/server-side templates (e.g. SES templates) are forbidden — they re-introduce vendor lock-in and break the swap promise (**EMP-M3**). | Templates scattered across providers / lost on swap — bug (parallel SSoT, **SSG-M8**). | No `templateId`/`templateData` in the port; one template source; adapter receives only rendered body. |
| **EMP-M11** | `messageId` is app-generated and is the single correlation authority. The facade generates one `messageId` per send before dispatch; it **MUST** be globally unique and time-sortable, and is the key across the outbox row, every log line, the idempotent-send dedupe (**EDP-M2**), and bounce/complaint reconciliation (**EDP-M5**). The generation mechanism is an implementation detail (UUIDv7 / ULID / Snowflake / …) — this rule fixes the id's *properties and authority role*, never a specific library or algorithm. The provider's `providerMessageId` is stored alongside but is not the primary key (it doesn't exist until after the call and can't dedupe a retry). | No stable correlation → can't dedupe retries or match async bounces — bug. | `messageId` set before send; globally unique + sortable; logs + outbox + reconciliation all key on it. |
| **EMP-M12** | Transport ≠ authority — the email layer never owns tokens. This hub transports a code or link; it does not create, validate, store, or expire it. Those operations belong to the product's designated verification authority — one engine for every channel's codes (SMS and email), no parallel email-OTP. The facade receives an already-issued credential and only delivers it. | Parallel credential systems — bug (**SSG-M8**); the deepest SSoT leak this hub can cause. | No token generate/verify/store in `email/`; recovery/verify flows call the one verification authority; the **EMP-M6** limiter is that same SSoT. |
| **EMP-M13** | If the product restricts transactional email to a defined set of purposes, maintain one catalog for that set and document who may approve additions. The scope may differ by product; do not treat an example catalog as universal. Use type or schema validation to prevent ad-hoc kinds where the stack supports it. | Uncontrolled purpose expansion can undermine delivery controls — bug. | The catalog, its owner, and its scope are documented; sends use catalog values. |

**EMP-M8** delivery-switch application: Configured credentials do not prove that mail can be delivered — a provider can reject every send while its configuration is complete. When delivery is known to be impossible, the channel **MUST** be closed by an explicit availability switch rather than left to fail: one authority answers "can we deliver now", reading one declared setting whose absence means closed; every flow that needs delivery asks it before reading any record or issuing any code and rejects with a registered expected-category code (never "sent"); the send facade asks it again before writing a queue row, so a forgotten caller cannot produce rows that are bound to fail into crash reporting; and the client learns the same answer from a read-only projection of that authority, so it stops offering the flow. This is not the silent disable this row forbids: the closed state is declared, observable and reported to the user. A flow that has to notify the account holder inside its own commit is closed with it, because committing without the notice is the larger harm. [Consequence: Bug — users are told a code was sent that never arrives, and every queued row becomes a crash report] [Verify: review — one authority, consumed by each flow entry, the facade and the client projection]

**EMP-M12** superseded-code application: A new code may invalidate a queued older code before its TTL expires. The outbox carries only an opaque, non-secret issuance generation and the owner identity needed to ask the verification authority whether that generation is current; it does not validate the code itself. The issuer and worker serialize the per-address generation change and provider attempt through one cross-instance lease, and the worker rechecks the canonical shared-store state and the durable generation under that lease before send. A code already stale, locked, consumed or unproven at that check is terminal without provider access. A provider call with no acceptance response has an unknown outcome and is not replayed automatically: a correlation tag is not a provider idempotency key. Stated enforcement limit: an independently concurrent code *consumption* can occur after the check, and no source check proves third-party mailbox arrival order or exactly-once delivery after an irreversible request crosses the network. The client must identify the code by the most recent *request*, and operations must resolve unknown outcomes from provider evidence before any replay.

**EMP-M12**/**EDP-M4** crash-boundary application: A lease checked only before and after the action is not ownership throughout it. Renew ownership while the action runs, abort an in-flight SDK call when renewal fails, and fence each durable generation and shared-store install write on the current owner plus the exact durable generation. A provider attempt has a durable `NOT_STARTED`→`STARTED` phase transition *before* the irreversible SDK call; the due reader must select only `NOT_STARTED`, and a legacy row without a phase is unknown rather than safe to send. A known provider rejection may reset phase to `NOT_STARTED` with bounded backoff in one write. An accepted, unknown, or post-acceptance fence-lost result never resets it; the last has a distinct identity because provider acceptance is known while code validity is not. If the terminal write or delivered-row deletion fails, `STARTED` remains, preventing an automatic replay; a separate stale-`STARTED` reconciliation raises an incident without resending. Stated limit: a paused process and third-party delivery cannot be rolled back after the SDK call crosses the network; this protocol guarantees no automatic duplicate retry from our outbox, not exactly-once mailbox delivery.
