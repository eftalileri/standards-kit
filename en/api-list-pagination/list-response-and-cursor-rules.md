## **MUST** (normative) — **GAPI-M**

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **GAPI-M1** | Every in-scope list endpoint response body **MUST** match PaginationResponse shape : `items`, `total`, `hasMore`, optional `nextCursor` when cursor pagination is used (see samples file for illustrative TypeScript ) . | Bug — must not ship . | Static: the response schema requires `items`, `total` and `hasMore`, and allows `nextCursor` only for cursor paging. |
| **GAPI-M2** | `total` semantics **MUST** be documented per endpoint in the route-registration comment or the project's endpoint catalog row (exact count, estimate, or `-1` with meaning stated ) . | Contract bug . | Pass: route-registration comment or the project's endpoint catalog row or OpenAPI description field names `total` behavior . |
| **GAPI-M3** | Every list endpoint **MUST** enforce a default `limit` and a `maxLimit` (both documented ) ; requests above `maxLimit` **MUST** be rejected or clamped per [error policy](../error-policy/error-policy.md) (no silent unbounded returns ) . | Bug / DoS risk . | Static: trace default/max limit validation and the over-max rejection or clamping branch. |
| **GAPI-M4** | When GGAPI1 is NO , the implementation **MUST** use cursor-based pagination for sequential page traversal (query params `limit` + `cursor` ; response `nextCursor` when `hasMore` ) . | Bug — perf / correctness . | Pass: Code review : no `skip(`/`offset` for page number when GGAPI1 NO ; or `rg` `skip\\(|offset\\(` on handler file shows only cursor path . |
| **GAPI-M5** | When GGAPI3 is YES (skip allowed ) , offset pagination MAY use `skip`/`offset` with `limit` subject to **GAPI-M3** . | N/A if only cursor — gate routing . | Pass: Documented in route-registration comment or the project's endpoint catalog row with `limit` + `offset`/`page` params . |
| **GAPI-M6** | Cursor-based lists **MUST** document a total order : primary sort keys plus a unique tie-breaker (e.g. monotonic `_id` ) so pagination is stable . | Bug — duplicate/omitted rows across pages . | Static: the route-registration comment or the project's endpoint catalog row names sort keys and the unique tie-breaker. |
| **GAPI-M7** | Invalid or expired `cursor` **MUST** not return HTTP 200 with a silent wrong slice ; **MUST** return 4xx with a machine-readable error per [error policy](../error-policy/error-policy.md) (local minimum ) . Only an exact cursor parse/shape failure — including the `SyntaxError` produced by the canonical JSON parse seam — may be mapped to that expected BUSINESS/4xx result. An unrelated or provenance-unknown runtime throwable remains SYSTEM and must reach the global error and selected crash-reporting boundary; a broad catch must not downgrade it. The raw cursor is never emitted to observability (**SEC-M-LOG-5**). | Bug — data integrity or hidden SYSTEM failure . | Static: trace exact malformed-cursor classification, unrelated SYSTEM propagation and raw-cursor redaction. |
| **GAPI-M8** | Empty result set : `items` **MUST** be an array (length 0 ), `hasMore` **MUST** be `false`, `nextCursor` **MUST** be absent or undefined ; `total` **MUST** follow **GAPI-M2** (typically `0` for exact counts ) . | Contract bug . | Static: the empty-result branch emits an empty array, false continuation, absent cursor and documented total. |
| **GAPI-M9** | Client alignment (backend minimum ) : when `nextCursor` may be returned , the route-registration comment or the project's endpoint catalog row (or OpenAPI description ) **MUST** state the expected consumer pattern (infinite scroll vs paged `useQuery` ) and **MUST** point to the consuming project's normative guidance for its adopted client-query library (for example [TanStack Query](../tanstack-query/README.md) when used) . | Contract / integration bug . | Pass: OpenAPI / catalog text exists per endpoint with `nextCursor` ; mentions `useInfiniteQuery` or paged `useQuery` with `cursor` and `limit` params . |
| **GAPI-M10** | N+1 prevention for list handlers is governed by [**BHE-M13**](../backend-http-efficiency/set-loading-and-query-fan-out.md) (round trips **MUST NOT** grow with the set); this row adds nothing and is a pointer. | Bug — perf . | Verify per **BHE-M13**. |
| **GAPI-M11** | A list row **MUST** carry the summary fields its reader compares across rows, read through the same set-form authority the row's detail reads (the detail calls it with one id); a list that leaves those fields only on the detail route **MUST NOT** ship. Reason: the reader then opens every row's detail, and the per-item round trips move to the client — by code or by hand. | Bug — perf / client N+1 . | Review: each list column the reader scans names its set-form authority; the detail reads the same authority. |

The `nextCursor` **MUST** be built from the last row the response actually returns, never from the lookahead sentinel (**GAPI-M6** / **GAPI-N3** application). The standard way to answer `hasMore` without a second count is to fetch `limit + 1` rows: the extra row is *evidence that another row exists* and is sliced off before the response is built. If the continuation cursor is then encoded from that extra row (`rows[limit]`) while the page returns `rows[0..limit-1]`, the sentinel is skipped by construction — the next page's filter is strict-after that position, so the row is in neither page. Exactly one row disappears at every page boundary, and it disappears silently: each page is full, the count is plausible, no error is raised, and the loss is only visible to someone who knows a specific record should be in the list. Off-by-one here is not a rounding error, it is data the caller never sees. The correct anchor is the last emitted row (`page[page.length - 1]`), which the strict-after filter then excludes exactly once, as intended. The same trap has an inverse: anchoring on a row that *is* returned while the continuation filter is inclusive (`$lte` / `$gte`) repeats that row on the next page — the anchor and the comparison operator are one decision, and they are read together or not at all. [On violation: Bug — rows silently omitted from or duplicated across pages] [Verify by: single-file AST rule rejecting a cursor encoded from the lookahead index inside the `rows.length > limit` branch; a flow whose sentinel reaches the encoder through an intermediate helper needs cross-call provenance and stays with review]

The continuation predicate **MUST** be AND-composed with the base filter, never merged into it (**GAPI-M6** application). The strict-after position is itself a disjunction (`later key` OR `same key and later tie-breaker`), and a base filter often carries its own disjunction — an access or selection narrowing ("records of the selected owner", "subjects matching this phone number"). Merging the continuation object into the base filter by key assignment (spread, `Object.assign`) replaces the base disjunction with the continuation one, so the first page is correctly narrowed and every later page silently widens to the whole scope. Put the two under one conjunction — `{ <tenantKey>, $and: [baseFilter, continuation] }` — or apply the continuation as its own pipeline stage; repeat the tenant key at the top so a scoped-filter type still sees it ([**REP-N-4b**](../repository/repository-contract.md)(h)). [On violation: Bug — later pages return rows the selection excluded; user-visible, and a data exposure when the lost disjunction was an access narrowing] [Verify by: review of every cursor composition site — the merged object and the base disjunction usually live in different variables or files, so no single-file rule decides whether a merge overwrites a disjunction]

**GAPI-M7** privacy application — inspect the sort key before encoding a cursor. An opaque-looking base64 token is only an encoding: if the record key embeds a phone number or another personal identifier, the cursor discloses it even when the response is owner-scoped. Preserve the exact strict-after position with authenticated encryption and a fresh nonce per cursor, using a stable server-side, domain-separated key; reject malformed, altered, or differently scoped cursors as `INVALID_CURSOR`. The endpoint must accept every cursor it emits, including the longest valid record key. The key's semantic content and the cursor producer live in different files, so a single-file lint rule cannot prove this privacy property; review both the ID constructor and cursor encoding before release.

An encoded cursor's key type is the type of the whole stored sort key, not the type of a suffix embedded in that key. A codec change across overlapping server revisions requires a decode-first stage: every running reader must demonstrably accept the new authenticated form before any writer emits it. Retaining a legacy decoder preserves released-client compatibility but does not authenticate old unsigned tokens; without an issue-time in the old protocol, a record timestamp is not a token-expiry proof. Document the retained format, the serving-revision evidence for the emission switch, and the remaining legacy acceptance limit separately.

## **MUST NOT** (normative) — **GAPI-N**

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **GAPI-N1** | Pointer: per-item queries in a list loop are prohibited by [**BHE-M13**](../backend-http-efficiency/set-loading-and-query-fan-out.md) / [**BHE-N5**](../backend-http-efficiency/set-loading-and-query-fan-out.md). | Bug — must not ship . | Verify per **BHE-M13**. |
| **GAPI-N2** | Must not use `skip`/offset` for sequential paging when GGAPI1 is NO . | Bug — perf . | Pass: GGAPI1 review on each list endpoint ; diff shows cursor path only . |
| **GAPI-N3** | Must not ship cursor pagination without documented stable order (**GAPI-M6** ) . | Bug . | Pass: route-registration comment or the project's endpoint catalog row contains sort + tie-breaker . |
| **GAPI-N4** | **MUST NOT** use `skip` / `offset` for multi-page traversal when GGAPI2 is NO (stable ordering across pages required — cursor only). | Bug. | Pass: GGAPI2 binary review; only the `cursor` param for the next page. |
