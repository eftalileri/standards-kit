## **MUST** (normative) — IV-M

| ID         | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Consequence                                                                                                                                                                     | Verify                                                                                                                                                                                                                                                                                                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **IV-M10** | Accept a change against the bar, not against "it runs". Before a change is accepted — by its author, by a reviewer, by a gate — the question is _"is this the correct, current-best-practice way to do this?"_, measured against the standards and established practice for the stack: correctness, robustness, type-safety, security, observability, maintainability, clarity. "It works" answers a different, weaker question, and a change that clears it while falling short of the bar is not done — it is raised to the bar or it is not shipped. This applies identically to a hotfix and to a feature: urgency changes the order of work, never the standard it is judged by. Anything the change _cannot_ be measured against — because the evidence is unavailable — is named as unmeasured rather than assumed to pass.                                                                                                                                                                                                                                                                                                                                        | A repository whose quality is set by its most rushed change. Each individually-defensible shortcut lowers the floor, and the floor is what the next change is compared against. | Review: for each accepted change, the acceptance names the bar it was measured against (which rules, which practice) — not only the gate that went green.                                                                                                                                                                                       |
| **IV-M11** | Accept a change only when it is at least as good as what it replaces; losing a guarantee, validation, type-safety, abstraction, single authority, observability or coverage is a regression, and an existing solution that meets the bar is not replaced by an equal-or-worse one; when it is unclear which is better, the existing one is kept and the uncertainty stated. Retiring a check that fails the admission test ([**ENA-A1**](../enforcement-architecture/enforcement-admission.md)) is no such loss when its class keeps a stronger mechanism or a stated limit.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | A rework that buys nothing or silently removes a protection.                                                                                                                    | Review: the acceptance names what the change improves and what it removes.                                                                                                                                                                                                                                                                      |
| **IV-M12** | A production-code defect fix or authority consolidation is accepted only with a trigger proof and a proof that the normal path did not change. (a) Trigger: an exact permitted input or state and a live, reachable call path from a production entry point to the faulty branch; a hypothetical, dead, configuration-impossible or source-unreachable branch is no trigger, and without one the behaviour change is reverted. (b) Normal path unchanged: the pre-change behaviour read from `path:line`, shown equivalent after the change, with any externally observable delta limited to the trigger. (c) Preservation: for each heading the change can affect — input/output contract, cache / invalidation, wire / API compatibility — and always for authorization, tenant scope, money paths, durable writes and transaction / atomicity, and error code / status / category / retry and observability, state the invariant that holds or an evidence-backed `N/A`. A behaviour-neutral consolidation, fence or documentation change may remain only when its normal-path equivalence is shown. A retrospective review of a completed change uses the same parts. | A speculative fix or an unnoticed regression in outputs, permissions, writes, errors, cache effects, telemetry or released-client behaviour.                                    | Static inspection of the pre- and post-change trees, the call path and the preservation entries; real-run observation by read-only production measurement or endpoint probing when available, otherwise the static evidence boundary recorded; follow [**M12**](../agent-planning/agent-planning-obligations.md) and the consuming project's verification policy. Blocking: a missing trigger or an unexplained invariant loss. |
| **IV-M13** | A declined check's reason, when recorded, is one sentence inside the rule it concerns. A rule naming no check is review-held ([**ENA-GV3**](../enforcement-architecture/enforcement-admission.md)); no limit sentence is required. Where a decline is recorded, the sentence names the failed admission condition; a decline on false positives or cost states its measured count on the clean tree as one figure ("it would be noisy" without a count is not a failed condition). It **MUST NOT** grow into a measurement log, per-variant table, dated history or separate document.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | A re-argued decline, or a reason that cannot be checked.                                                                                                                        | Review.                                                                                                                                                                                                                                                                                                                                         |
| **IV-M14** | A change adds only the code its outcome needs: every added line serves a stated requirement of that outcome or a rule it must satisfy. It **MUST NOT** add speculative options, parameters, configuration, abstractions, wrappers or helpers with one caller, fallbacks for states no reachable path produces, or code kept "for later"; an existing authority is extended rather than paralleled, and code the change makes unused is deleted in the same change. Size is never a target: required correctness, validation, observability and authority work is not trimmed to shrink a diff.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Unneeded code is surface that must be read, kept consistent and secured, and it hides the lines that matter.                                                                    | Review: the independent reviewer names any added line without a requirement and removes it.                                                                                                                                                                                                                                                     |
