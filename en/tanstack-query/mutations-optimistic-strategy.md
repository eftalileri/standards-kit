## The three methods

Every mutation that changes server state implements exactly one of these. A is the default: a mutation that declares nothing is A and is held to A's obligations.

| Method | What happens | Taken when | Obligations it adds |
|--------|--------------|------------|---------------------|
| A — Server-confirmed (default) | Send → await the server → write the confirmed response through the domain's single orchestrator / registered bridge when it is sufficient (**G3**) → awaited invalidation of the families the bridge cannot cover, active queries refetched → only then close or clear the UI intent | Always, unless B or C is declared and its conditions hold; always for the flows of **MUT-N3** | **MUT-M28** (A clauses), **MUT-M13** caller choice, **MUT-M27** when the sync is correctness-required |
| B — UI-optimistic | The pending row is rendered from the mutation's own `variables` while its status is `pending` (`useMutationState` on other surfaces); nothing is written to any query cache | Declared; not a **MUT-N3** flow; the caller does not block; the in-flight change needs to be visible instantly on one surface | **MUT-M29**, **MUT-M30** |
| C — Cache-optimistic | `onMutate` writes the temporary state into the query cache, with cancel, snapshot, rollback and response bridge | Declared; not a **MUT-N3** flow; the caller does not block; and the in-flight change needs to appear instantly on more than one query key family / consumer surface or on a surface that cannot read mutation state, or a persisted / offline mutation queue must carry it across an app restart ([**UIP-M21**](ui-startup-and-persistence-boundaries.md), [**OSS-RN-M3**](../offline-sync-strategy-rn/offline-sync-strategy-rn.md)) | **MUT-M2** cancel, **MUT-M3** shape parity, **MUT-M4** bridge, **MUT-M11** snapshot + rollback, **MUT-M12** pagination shape, **MUT-M30** |

Invariant across all three — a method is never an exemption. Invalidation scope (**MUT-M6**, **MUT-M8**, **MUT-M17**), cross-entity and key-family coverage (**MUT-M20**–**MUT-M23**), registered bridges (**MUT-M22**), error surfacing (**MUT-M19**) and correctness-required post-write proof (**MUT-M27** / **G8**) are identical on every method. The method decides only where in-flight state lives, never whether the caches are reconciled. Client invalidation and refetch prove freshness because the server read runs its handler and authority read on every request ([**RDS-N14**](../redis/redis-prohibitions.md)); where a server-side derived read cache sits on that path, it must have been bumped structurally before the write response completed ([**RDS-M22**](../redis/redis-prohibitions.md)), otherwise the refetch is answered from the pre-write value.

## **MUST**

| ID | Rule |
|----|------|
| **MUT-M28** | Post-write method selection and the server-confirmed method. Every mutation that changes server state **must** implement exactly one method of the table above, chosen for this mutation in this order: (1) a flow listed in **MUT-N3** is A; (2) a caller that blocks — it awaits the result behind progress before it navigates, closes or continues — is A; (3) a change that does not need to be visible before the server answers is A; (4) otherwise B, unless the C conditions hold, then C. B and C **must** be declared in the hook's TSDoc on the **MUT-M14** line, naming the condition that admits them; an undeclared hook is A. Copying a neighbouring hook's method is not a selection. A **must**: write nothing to any query cache before the response, and hold no snapshot and no rollback (**MUT-N8**); on success, write the confirmed response through the domain's single orchestrator or registered bridge when it is sufficient (**G3**, **MUT-M4**, **MUT-M10**, **MUT-M22**) — invalidate-only while the response is bridge-sufficient is forbidden, because it makes the user wait for a refetch for nothing; await the invalidation of every family the bridge cannot cover, with active queries refetched unless **MUT-M31** applies (**MUT-M6**, **MUT-M16**, **MUT-M20**–**MUT-M23**) and the paused-query proof when the sync is correctness-required (**MUT-M27**); return or await that reconciliation from the mutation callback so `pending` covers it, inside the terminal no-throw boundary ([**COB-RN-M13**](../client-observability-rn/absorbed-defaults-and-global-nets.md)) so a reconciliation failure is reported and never turns the confirmed write into a failure; and close or clear the UI intent (modal, form, selection, submit lock) only after it settles. Whether the caller blocks behind progress while A runs is the caller's choice (**MUT-M13**). Under every method, success wording (a "created/saved" toast or card) and leaving the form **must** wait for the server's confirmation; before it the UI may show only a pending state, and a failure keeps the form with every entered value — a success shown before the answer tells the user a failed write succeeded and discards the input the retry needs. |
| **MUT-M29** | UI-optimistic (method B) obligations: The pending representation **must** be derived from that mutation's own `variables` and rendered only while its status is `pending` — read from the hook result on the calling surface, or via `useMutationState` filtered by the canonical `mutationKey` (**MUT-M14** key authority) on any other surface. TanStack Query v5 keeps `variables` in mutation state after settle (the state reducer replaces them only on the next execute), so an ungated render leaves a ghost row on screen after a failed mutation — the status gate is not optional. The pending value **must not** be written into any query cache (that is method C without its protections) and **must not** be copied into a store / second state as the pending authority (second writer — **SSG-M8**); the mutation cache is that authority. Reconciliation **must** invalidate per **MUT-M6** / **MUT-M20**–**MUT-M23** exactly as any other method, and the mutation callback **must** return / await that invalidation promise (the library awaits promises returned from mutation callbacks) so the pending representation survives until the refetch settles — otherwise a visibility gap opens between the pending row disappearing and the confirmed row arriving, the same defect **MUT-M4** forbids on the cache path. Where the surface permits repeat submits, every pending entry **must** be rendered (`useMutationState` returns an array) unless the flow locks submits (**MUT-M27**). Rollback is not applicable (nothing was written), but user-visible error feedback still is (**MUT-M19**) — a pending row that silently disappears is not feedback. |
| **MUT-M30** | An optimistic representation — method B's pending row or method C's cache entry — is displayed as authoritative while it exists. A field whose value the server derives from other fields — including money and status-derived flags — **MUST** be withheld until the server response, never recomputed client-side. The temporary representation may show input fields the user actually changed; it **MUST** represent a server-derived field it cannot truthfully copy as absence, not as a plausible number, enum member, flag, or locally re-derived formula. An optimistic delta **MUST NOT** be applied to a server-derived money aggregate: money flows are server-confirmed (**MUT-N3**). A pure count whose server rule is independent of status and money MAY be patched when rollback and invalidation remain complete. A period-filtered count may be patched only when the changed row's membership in each target period is proved using the aggregate's authoritative timezone, date basis and boundary derivation. Unknown membership means no count patch; keep the rest of the optimistic representation and reconcile the count through its server read. A status-independent count is not a period-independent count. Membership depends on cross-file server period semantics, so a future delta producer is a review obligation; the stronger repair is to write no unproved delta. |
| **MUT-M31** | Known-outcome success path — no refetch, no loader. When the server's success answer proves that the loaded cache rows already carry exactly the accepted change — a method C write whose `onMutate` cancelled no in-flight read, or a method A bridge whose acknowledgment names the exact changed rows (deleted ids, a flag set on given ids) — the success path **MUST** mark the affected families stale without refetching the active queries (`invalidateQueries` with `refetchType: 'none'`), and the write **MUST NOT** surface any loader, spinner or pull-to-refresh indicator, neither its own nor one from a refetch it caused. Window refill (a row sliding into a page the delete shortened) and server-derived counters reconcile at the next natural read (mount, focus, reconnect, push, user pull). The active queries **MUST** still be refetched when the outcome is not known at success time: a read was cancelled in `onMutate` (**MUT-M2**), a read of the same family landed after the optimistic write (its pre-write data may have overwritten it — compare the family's latest data time with the one recorded right after the write), a read of the same family is in flight when the bridge is written (its answer may predate the write), a removal emptied a loaded page whose server window has more rows (the screen would claim "nothing here"), the response does not name the changed rows, or the write failed / its outcome is uncertain (failure path). Reason: an immediate refetch of a list whose rows already show the confirmed change only flashes the list's refresh indicator and re-downloads what the user sees. The reconciliation authority takes the known/unknown answer as a required parameter (**MUT-M6**). Cache-local patches (optimistic write, bridge, rollback) **MUST** keep each entry's data time (`setQueryData(..., { updatedAt: state.dataUpdatedAt })`): a local edit is not fresher server data, and a bumped time reads as a landed fetch, so a second quick tap would refetch for the first. This narrows **MUT-M16**'s immediate active refetch and the accepted-deletion refill of **MUT-M21**; it changes no method choice (**MUT-N3** flows stay method A, except the inbox-item deletion that row names) and no invalidation coverage. |

**MUT-M30** provenance: When a consumer also diagnoses absent server-derived money fields, the optimistic writer labels the withheld field as pending in the same cache patch. A changed member's group aggregate is withheld with it; a redacted permission label never becomes pending. A detail-to-list cache bridge likewise labels an aggregate pending when the detail endpoint does not compute it; only the actual aggregate producer may label it authoritative. A diagnostic may then distinguish this temporary absence from a server contract breach without fabricating a payment result. Validate a missing provenance label on the live API response before caching it; a persisted cache row from an older client has no proof that the current server omitted the label and **must not** be reported as a live contract failure.

**MUT-M30** enforcement and stated limit: A source-level check may detect a duplicated inline derivation when its operands are explicit at the expression. A helper or rebound operands require cross-statement data-flow analysis and remain review obligations. This is the same reach boundary as [**PAY-UI-M7**](../payment-ssot/ui-binding.md); a check must state its actual scope rather than imply full coverage.

## Server-confirmed boundaries (application of **MUT-M28**)

Confirmed-write response boundary. After a server confirms a write, a separate read needed only to build a cache bridge **MUST NOT** run inside the mutation command such that its failure reclassifies the committed write as failed. Prefer a bridge-sufficient response from the write endpoint itself; sufficiency includes populated fields the existing cache consumers require, not merely the same top-level type. Do not add a fallible post-commit read to the server response path solely to make it bridge-sufficient: that moves the same false-failure defect across the wire. When the confirmed response is intentionally insufficient, skip the bridge, log why, and invalidate the affected families under **MUT-M4** / **G3**; preserve the confirmed operation result. An unexpected projection failure belongs in the established terminal no-throw observability seam. A lost response or a server failure after the write leaves the commit outcome uncertain, so the failure path **MUST** reconcile every query family that may have changed, including any family cancelled in `onMutate` (**MUT-M2**). These distinctions depend on endpoint commit semantics, population and the response contract across files, which a single-file AST cannot prove; review holds the exact command and response boundary.

Close versus erase. A command that offers both closure and record erasure **MUST** carry each scope's authority semantics into its cache behavior. If any supported scope changes or destroys money or history, the command is method A; do not apply an optimistic full-record purge to its retaining scope. A retaining close keeps its record and completed history visible and reconciles changed server-derived fields from the authority; an accepted full erasure may remove matching loaded rows from the exact tenant's registered list families before invalidation (**MUT-M21**). Never reconstruct a retained row from an insufficient acknowledgment. Terminal reconciliation uses the tenant / entity captured by the actual command or its cancellation context, never a later screen selection.

## Enforcement

Method selection needs cross-file consumer and key-family reasoning, so no single-file rule decides it; review holds **MUT-M28**. What is mechanically held:

- Method C rollback binding (**MUT-M11**): a source-level check can decide this: a proven cache write inside `onMutate` that returns a context obliges the error path (the error or settled callback's context parameter) to bind that context. The write may be inline or delegated to an imported helper; the rule resolves the helper's module and proves the write in its body, so the delegated half is not a guard's subject ([**FP-MS4**](../false-positive/mechanism-selection.md), [**FP-MS4a**](../false-positive/mechanism-selection.md), [**FP-MS8**](../false-positive/mechanism-selection.md)(b)). Neither side is decided from a name ([**FP-M32**](../false-positive/check-verification-rules.md), [**FP-M33**](../false-positive/check-verification-rules.md)). Stated limit ([**KIT-INV-8**](../authoring/kit-structural-invariants.md)): options handed to the hook as a factory call rather than an object literal are outside the rule, because the callbacks are not at the call site.
- Method C bridge: a fabricated-id optimistic row **must** be bridged on success into the same key (**MUT-M4** / **MUT-M10**). A project's check may require this; record its documented scope and limits.
- Every `useMutation` carries a canonical `mutationKey` from one name authority, which is what makes method B's cross-surface `useMutationState` read available everywhere. A project's check may require this; record its documented scope and limits.
