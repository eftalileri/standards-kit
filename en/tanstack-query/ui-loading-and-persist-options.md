Scope: The first band of the **UIP-M** family. The band split keeps the complete normative set within the authoring limits while cutting only at whole-rule boundaries inside the same UI/persist domain. The complete band set is the **Domain part files** list in [ui-persist-offline.md](ui-persist-offline.md).

Rule prefix: **UIP-M**\* — this band owns **UIP-M1**–**UIP-M17**; the second band is [ui-startup-and-persistence-boundaries.md](ui-startup-and-persistence-boundaries.md) (**UIP-M18**–**UIP-M23**).

Compliance: Violations of UIP- rules are defects; stop dependent work until fixed and do not knowingly release them — see the cross-cutting [TanStack Query standard](tanstack-query.md) (**TSQ-C4**, **TSQ-C11**).

Version compatibility: Confirm the installed `@tanstack/react-query` version supports the persist and query APIs in scope — [tanstack-query.md](tanstack-query.md) **TSQ-G1**.

References: [ui-persist-offline.md](ui-persist-offline.md) (scope, **UIP-N1**–**UIP-N7**, failure path); [error handling](../error-handling/error-handling.md); [SSOT readiness](../ssot-readiness/ssot-readiness-and-form-data.md); [mmkv](../mmkv/README.md).

## **MUST**

| ID | Rule |
|----|------|
| **UIP-M1** | Error UI: First load with no cached data: `isError` && !`data` **must** show a recoverable error surface (e.g. retry). Background refetch error while `data` exists: **must** stay non-blocking (silent or inline per [error handling](../error-handling/error-handling.md)) — no full-screen error that hides good cache. A wrapper that exposes a flattened empty array while its underlying query has no data also exposes the underlying data-presence fact. Consumers use that fact for the initial-error branch, never array truthiness or row count. A successful empty first page is cached data. For a combined required-source hook, presence covers every mandatory source; one present source does not establish readiness. Missing mandatory data with an error is recoverable failure, missing data without an error is waiting, and complete usable cache remains visible during background errors. Retry targets every failed required query. No new check is introduced: existing error/cache rules cannot infer a custom wrapper's cross-file projection or required-source set; this remains contract + review. A previous-key placeholder is not current-key data. A wrapper excludes it from required-source presence and output, or the query locally disables it when scope changes. The underlying presence fact is used to distinguish a successful empty page from a data-less failure; it is not inferred from an array's truthiness. Stated limit: data shape/projection and mandatory sources are cross-file facts. Existing scoped placeholder handling closes the exact query half; wrapper composition remains review, with no new check. |
| **UIP-M2** | A loading presentation (full-screen loader, skeleton, inline spinner, loading text, a list's loading state) **must** appear only when the surface has nothing to show: (1) persist restoring / hydration → skeleton; (2) no data and the first request in flight or gated → spinner or skeleton; (3) data present → no loader for any fetch that is not a user pull (focus, reconnect, stale mount, push, polling, prefetch, post-write reconciliation) — the data stays in place, and no row is inserted or removed above it. Each surface **must** take this decision from the one load-state authority (`initial` / `error` / `ready` / `refreshing`; `refreshing` never renders a loader), never from `isFetching`, `isRefetching`, a query's `isPending` or a local loading flag. The skeleton keeps the loaded layout's footprint. A row, menu entry or strip whose presence is gated by a server fact **must not** take that fact from a read the surface itself (or a surface mounted with it) opens: the entry is then inserted under the user after paint on every cold start. The fact comes from a persisted family, from a session-lifetime read started at session start, or — preferred for a fact that may not be persisted — rides on the session bootstrap read the readiness gate awaits, so it is known on first paint (review-held: which read a gate reaches is cross-file). A wait the user must sit through for an action they started (payment, save or submit, an irreversible action, an export) is shown on that action's own control from the blocking mutation's `pending` (**MUT-M28**), never as a screen loader; a non-blocking or optimistic write shows no loader (**MUT-M29**, **MUT-M31**); pull-to-refresh follows **UIP-M5**. A blocking gate re-read while the app is already open with no decision left to show (cleared at sign-out; an expired allow lease does not block, **FFL-RN-M5**) keeps the app tree mounted behind a touch-blocking layer and shows its loader only when the recheck outlasts a short delay; a failed recheck (offline, error) draws its retry surface on that same layer above the mounted tree; replacing the tree loses the user's place. While up, the layer **must** also consume the Android hardware back press: a touch block does not stop it, and the navigation container beneath would pop the hidden stack or open an exit confirmation above the layer. An invisible touch-blocking `View` **must** set `collapsable={false}`: with only layout styles the renderer flattens it out of the native tree and touches reach the app beneath (iOS-only props such as `accessibilityViewIsModal` do not keep it on Android). A source-level check may reject a loader, loading text or list `isLoading` opened from `isFetching` / `isRefetching` in a component file; a flag carried across files, a self-named spinner wrapper and `let` re-assignment stay in review. |
| **UIP-M3** | When persist is enabled: root **must** use `PersistQueryClientProvider` (or equivalent) with `persistOptions` (maxAge upper bound, `buster` tied to app/version), `shouldDehydrateQuery` as the single query policy gate, and an explicit `shouldDehydrateMutation` boundary. A generic query-cache persister **must** return exact `false` for every mutation: paused mutation state serializes its full variables, which may contain OTPs, tokens, or command credentials. Durable offline commands require a separate field-aware queue authority and **must not** be obtained by silently accepting TanStack's default paused-mutation dehydration. |
| **UIP-M4** | Prefetch before navigation where product requires (e.g. list → detail): `prefetchQuery` with `staleTime` consistent with detail query — not `staleTime: 0` for prefetch-only. |
| **UIP-M5** | Pull-to-refresh (where the platform supports it): **must** use debounced user intent (e.g. ≥ 2s budget between triggers), feed `refreshing` from `isFetching` but **must** show the indicator only for a fetch the user started by pulling — a background refetch (push, focus, reconnect, stale mount, post-write reconciliation) stays silent (**UIP-M2**(3)), because a programmatically shown iOS refresh control pushes the content down by its height and back, a jump Android never shows; one refresh-control authority holds that decision (a write whose outcome the cache already carries also **must not** refetch that list — **MUT-M31**) — and **must** call `refetch()` — only on screens that meet product criteria (lists/dashboards); not on form/detail/modal surfaces per product rules. |
| **UIP-M6** | Offline-first display for form-bound lists **must** align with [SSOT readiness **M9**](../ssot-readiness/ssot-readiness-rules.md): show cache when present, refresh in background, avoid indefinite full-screen block when cache could render. |
| **UIP-M7** | Logout **must** `clear` the query cache (or equivalent) so no cross-session server data leaks. |
| **UIP-M8** | Entity delete: **must** `removeQueries` (or targeted cache removal) for persisted keys when offline consistency requires — invalidate alone is not always enough for “gone” data. |
| **UIP-M9** | Error recovery UI: Full-screen / blocking error views **must** offer retry that calls `refetch()` (or mutation retry per product) — no dead-end error state without recovery path. Where one region selects among queries, the recovery callback **must** come from the same selected query result as its data and error, retaining its key, filters and enabled/readiness gates. Recovery **must** respect the existing error-policy refusal, **must not** start a duplicate while fetching or paused, and **must** leave usable cached data visible under **UIP-M1**, including expected informational errors. TanStack Query consumers join an existing fetch rather than cancel/restart it (`cancelRefetch: false`). |
| **UIP-M10** | Forbidden pattern: `if (isLoading)` → spinner alone is forbidden when **UIP-M2** requires distinguishing persistence restore, cold load, and background fetch. |
| **UIP-M11** | `persistOptions.maxAge`: each adopting project **must** set one finite upper bound in an architecture/security decision, based on persisted data families, security and privacy sensitivity, session expectations, and business requirements. A family's effective retention may be shorter or memory-only; no family may exceed the selected upper bound. When a `maxAge` or eligibility change would leave previously persisted data outside the new policy, invalidate the old blob with the appropriate buster. Align the selected bound with [MMKV retention](../mmkv/mmkv-retention-limits-and-buster.md) **MMR-M3** when MMKV backs TanStack persistence. |
| **UIP-M12** | Persist storage: When TanStack persistence is enabled, use the architecture-selected, security-approved persister and keep a single writer; do not add ad hoc parallel persist layers. Memory-only operation needs no persister. Choose a synchronous persister when the selected startup behavior requires synchronous cold-start reads; if MMKV is selected for that requirement, use its documented adapter (**MMA-M6**, **MMK-G3**) — see [mmkv](../mmkv/README.md). |
| **UIP-M13** | Memory budget: Set and document an in-memory query/cache budget suitable for the application's workload. If telemetry or profiling shows the cap is exceeded or growth is unbounded, stop shipping the affected change until eviction, a limit, or an architecture fix is documented and applied; do not assume garbage collection will solve unbounded growth. |
| **UIP-M14** | Prefetch — sibling keys of a small finite set: a paged date view (previous and next week/month) and a small fixed filter set (period tabs such as day / week / month / year for the same scope and subject) **must** read the shown key's sibling keys ahead once the shown key has data (after first paint, never competing with it), through one shared read-ahead owner, in line with **UIP-M4**. Each sibling is its own cache key, so a switch draws that key's own data; the refusal to show the previous key's data for a filter change (**CLI-M12**) is unchanged. Reason: switching then draws data instead of a skeleton. Review-held (which sets are small and finite is a product judgment). |
| **UIP-M15** | HTTP client: The shared API client **must** use a documented request timeout owned by the transport configuration, not by TanStack Query, and that configuration is the single authority for the number (server code compares against it, never restates it). Server-side counterpart (binding): any outbound provider call the server makes within that request **must** keep its worst-case duration (attempts plus backoff) provably below the client timeout — see [backend HTTP efficiency **BHE-M9**–**M11**, **BHE-N4**](../backend-http-efficiency/outbound-call-time-budget.md). Changing either timeout or a retry policy requires rechecking the total-duration bound in the same change. |
| **UIP-M16** | Feature / module normative UI documentation at the location defined by the adopting project (with Decisions / facts per [markdown authoring](../authoring/markdown-authoring.md)) may define a module-wide first-load presentation (spinner-only vs skeleton or other) that differs from **UIP-M2** defaults for that module only, provided the doc states the rule explicitly and the implementation still satisfies **UIP-M1** (error vs cache), **UIP-M9** (retry on blocking error), and **UIP-M10** (no single `isLoading` spinner alone when hydration / restore **must** be distinguished). Agents **must** read both this file and the applicable feature document — see [mobile UI patterns **MUP-C5**](../mobile-ui-patterns/mobile-ui-patterns.md) / [**MUP-M5**](../mobile-ui-patterns/mobile-ui-patterns-rules.md). |
| **UIP-M17** | Render-derivation readiness (`pending` != failed): A render-path consumer of query state (component body, `useMemo`, selector, or hook called during render) that depends on query data **must** treat `pending` and transient `error` (`isError` && !`data` on a retried / in-flight query) as not-ready — render nothing / skeleton / a contained empty state — and **must not** throw an uncaught `Error` that reaches the React error boundary. A hard thrown signal is allowed only for a resolved-but-invalid state (`isSuccess` and data present but a required field genuinely missing/invalid), and even then **must** stay contained to the affected region (**UIP-M1**) — never white-screen unrelated content. `isError` from a retried query is not a permanent failure for display. Aligns with [SSOT readiness **M1**/**M2**](../ssot-readiness/ssot-readiness-rules.md) for any multi-source derived display value (cards, rows, labels), not only forms. |

**UIP-M9** shared-prerequisite recovery: an unavailable presentation prerequisite **must** expose its authoritative closed reason instead of rendering a spinner for every unavailable state. When a region requires both a prerequisite query and a selected data query, an unusable failed prerequisite **must** retain that source's original failure and matching recovery; an unusable sibling failure **must not** disappear behind the other source's loading or unavailable presentation. Recovery targets the actually failed source under its existing enabled/hydration and registered retry policy, never a copied error or unrelated refetch. Where the same query supplies recovery, manual retry consumes the registered query retry policy at failure count zero, respects registered `retryable: false` and 429 refusal, declines a second operation while fetching or paused, and joins with `refetch({ cancelRefetch: false })`. Rendered recovery controls **must** reflect that same fetch status with disabled/busy presentation and distinguish sibling source actions by their accessible names. A usable exact-key cache remains visible during a background error. Missing scope and unresolved data are explicit unavailable states; they do not fabricate currency or amount. A shared presenter can consume these query-owned facts without becoming a classification or retry-policy authority.

**UIP-M9** local-prerequisite recovery corollary. For a blocking local-prerequisite error, rereading the same permanently unusable record is not a complete recovery path. An existing explicit user repair command may be composed into that error surface, then rerun the same failed initializer only after its actual persisted/engine outcome is acknowledged. The repair view retains its mounted operation lifetime even if memory failure metadata clears before the durable write finishes, and can admit a later prerequisite failure without requiring another error-view mount. Its prior retry and new repair controls share the pending-operation gate; neither pointer nor accessibility interaction may bypass settlement. After acknowledgement, both selection and save remain locked and the only continuation is the same initializer callback. A later callback failure **must not** relabel acknowledged repair as a failed write, automatically reapply it or fabricate application readiness: preserve the typed accepted outcome and offer continuation retry. A full-screen recovery region consumes the application's existing safe-area provider, top/bottom wrapper and scroll-content spacing authority so its actionable controls remain within system edges (**AEE-M11**/**M13**/**M14**); it does not define another inset/native policy. These are relationships among the record authority, awaited writer, error surface, current operation and callback; the existing type/API boundaries and source review hold them, and no new path-specific check is introduced.

**UIP-M11** review limit. A static check can compare a source-visible `maxAge` with the recorded upper bound, but it cannot determine whether that bound is appropriate for the persisted data, privacy/security risk, session model, or business need. Review the decision and effective runtime configuration; when values are computed or injected, inspect the resolved value. When MMKV backs TanStack persistence, also verify **MMR-M3** alignment and that the buster invalidates blobs made ineligible by a policy change.

**UIP-M1** enforcement note. A static check can flag a gate that treats an error as sufficient reason to hide data without checking whether cached data exists. Evaluate each top-level disjunct independently: a data check in a sibling `||` branch does not protect the error branch, and a negated error flag combined with a data check (`data && !isError`) is a defect, not a guard, because it closes the branch exactly when good cache exists. The same principle applies to render branches and labels. A gate that writes a sentence on missing data with no error flag is covered by [**EHX-M6**](../error-handling/error-display-ux.md). Split conditions, hoisted booleans, and cross-module control flow may be outside a single-file check and remain review obligations.

**UIP-M17** enforcement note. A lookup miss in a list-backed render is normally a stale selection or missing item, not proof that loaded data is corrupt; surface a suitable empty or unavailable state instead of throwing during render. A check may catch direct `find`-then-throw patterns or branches where a clearly invalid parsed value is thrown. Domain validity must come from the relevant schema or authority, not from a generic numeric comparison or an invented domain bound. Calls into resolvers in other modules, cross-module call graphs, and semantic validity require review. Use the project's approved verification approach for any custom check, and record its actual scope and limits.

**UIP-M17** — query readiness and exhaustive state handling. A readiness derivation that throws on an unclassified state can turn a normal query state into a render-path error. For example, a disabled query may have `isLoading === false`, `data === undefined`, and `error === null`; a readiness union that accounts only for loading, success, and error can miss that state and reach an unconditional throw. Because the throw occurs during render (for example inside a `useMemo`), an error boundary in the JSX returned by that same component is not yet mounted to contain it, and the error escapes to the root as a blank screen. An application that elsewhere treats the same state as normal “loading” has turned an expected state into a crash.

Apply these rules:

1. `enabled` is a required input to query-readiness derivation. Loading state alone cannot distinguish a disabled query from one whose request completed without data; see [SSOT readiness **M16**](../ssot-readiness/ssot-readiness-rules.md).
2. Represent unclassified states explicitly. Add a distinct union variant such as `unavailable` or `not_ready`; do not silently fall through to `ok`, and do not treat “no authority” as “the authority said no” ([**EHX-M5**](../error-handling/error-display-ux.md)). Use an exhaustive `Record<Union, …>` or `switch` so the compiler forces each consumer to handle the new variant. Show a waiting or skeleton state for not-ready data, not a lock or paywall.
3. Keep fail-loud behavior for proven invalid data. A resolved-but-invalid result (an explicitly tested invariant such as `isError === true` with `error === null`) may throw while the failure stays contained. A query state omitted from the readiness model must not throw from a pure render derivation; report it once at the hook boundary, identifying which `enabled` component is unresolved, because a single unexplained boolean makes the event indistinguishable.

Enforcement guidance: A readiness derivation should account for query enablement as well as loading and error status; unconditional throws are appropriate only when the failure condition is established. A project may add a source check for direct, file-local patterns (for example, a readiness-derivation call whose argument carries loading and error facts but no enablement fact, or a direct unconditional `throw` in a readiness-derivation body). Calls into helpers in other modules need call-graph review.
