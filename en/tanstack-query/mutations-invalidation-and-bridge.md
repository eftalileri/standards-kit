## **MUST**

| ID | Rule |
|----|------|
| **MUT-M1** | Mutation variables (user-driven input) **must** be validated with `zod` per [forms](../forms/forms.md) before submit where the stack uses shared schemas. |
| **MUT-M2** | A method C mutation's `onMutate` **must** `cancelQueries` for keys that overlap the mutation to reduce race with in-flight reads. A mutation of any method that cancels overlapping reads **must** reconcile every cancelled family on every terminal path — success, failure and unknown outcome — because a cancelled query otherwise stays on its pre-cancel data. |
| **MUT-M3** | Method C cache rows **must** match the same shape as existing cache entries for that key (no `id` vs `_id` / populated-field dualism); one shared mapper **must** feed both optimistic write and server merge when transformation exists. This applies to every row of a multi-record success response too: a frontend response row passes through the target cache's existing shared mapper and sufficiency gate before insertion. A bridge-sufficient type alone does not prove the reader's runtime shape. The cross-file mapper/reader relationship remains review-owned; a bridge-presence check does not establish row-shape parity. Shape parity includes the read path's invariants, not only the type: where a consumer resolves a displayed value through a derivation authority that fails loud on a missing field (a write-time snapshot / denormalised label the server produces), the optimistic row **must** carry that field, populated from the same source the server will read (the catalogue rows the user selected in the form) so the preview and the server row agree. An optional field in the type is not optional to the read path: the type compiles, and the row then throws during render — inside a `useMemo` or list layout that has no boundary of its own, taking the whole screen down. If the client cannot populate the field truthfully, the correct action is to write no optimistic row (fall back to the server response, log why) — never to fabricate the value and never to soften the authority into a fallback (**SSG-M8**). |
| **MUT-M4** | If optimistic entries are removed in `onSuccess`, the server response **must** be bridge-injected into the same cache when the response is sufficient; then `invalidateQueries` **must** run for server verification — no long visibility gap (empty list/card) between optimistic removal and refetch. If the response is insufficient for bridge, skip bridge, invalidate only, and report through the configured diagnostics path. The merge uses the cache's current state, not its pre-mutation rollback snapshot. A cache created by the optimistic step is a live bridge target even if no entry existed before that step. Preserve current pages, cursors, pageParams and unrelated rows; avoid duplicating a server identity already present on any loaded page. This temporal ownership question is cross-file review-bound: the type system carries context/row shape, not the ordering of concurrent cache changes. |
| **MUT-M5** | `invalidateQueries` / `refetchQueries` **must** use explicit `queryKey` or predicate — never unbounded global invalidation (**MUT-N1**). |
| **MUT-M6** | Direct impact test: Each invalidation/refetch in `onSuccess` **must** answer yes to: *After this mutation, does this query’s server data definitely change?* Maybe → do not invalidate; rely on staleTime + refetchOnMount / reconnect. The test is owed by every write path to every query DERIVED from what it writes, not only to the query it names. A server value the endpoint recomputes on read — a count, a tier, a rank, any figure the backend derives from rows the mutation just added or removed — is never listed in that mutation's own key family, and its staleness is the quietest failure a cache has: the write succeeds, the list it names refreshes, and the derived surface keeps serving the old figure until `staleTime` happens to expire. Where a consumer only reacts to the derived value changing while mounted (a banner comparing previous to current), the omission does not merely delay the surface — inside `staleTime` it makes the feature unreachable, and outside it the feature fires by accident of timing. So the coverage duty runs derivation-first: for each mutation, name the server-side derivations of the data it writes, then invalidate each one's registered key. Where several write paths share one invalidation orchestrator (**MUT-M9**) and only some of them move the derived value, the orchestrator **MUST** take the answer as a REQUIRED parameter rather than deciding it internally or defaulting it. Required, because the failure this rule prevents is an *omission*: an optional flag lets the next write path compile without ever confronting the question, which is exactly how the gap opens, whereas a required field makes the type checker refuse the call until the author answers — enforcement stronger than a lint rule and free of false positives. Internal decision is equally wrong: the orchestrator cannot see which endpoint the caller invoked. Deciding per call site also keeps the invalidation narrow — paths that leave the derivation untouched **must not** pay for a refetch (this rule's first sentence). [On violation: Bug — derived server value serves stale; a change-detecting consumer may never fire at all] [Verify by: for each mutation, the set of server-side derivations of the written data is enumerated and each has an explicit invalidate-or-declared-no-impact at the call site] |
| **MUT-M7** | Duplicate invalidation: the same query key **must not** be invalidated twice in one success path — orchestrators **must** deduplicate or merge predicates. |
| **MUT-M8** | Multi-field mutations **must** use conditional invalidation by what actually changed (e.g. financial fields vs note-only) when the endpoint updates many fields — **MUT-M6** applied per slice. |
| **MUT-M9** | Post-mutation cache updates **must** go through domain orchestrator functions documented by the adopting project's architecture; do not scatter repeated ad hoc `invalidateQueries` calls across hooks for the same domain. |
| **MUT-M10** | `setQueryData` **must not** persist fabricated or non-server rows as authoritative final state without `invalidateQueries`; bridge from mutation response is allowed, then invalidate (server wins after refetch). |
| **MUT-M11** | A method C mutation's `onError` **must** restore what its own optimistic step changed (rollback); a method A or B mutation holds no snapshot and restores nothing (**MUT-N8**). For an append-only optimistic step, restore its prior state by removing its exact inserted-row delta from the current cache, never by overwriting the whole cache with an older snapshot. Store the actually written identifiers in a required per-operation context and use a collision-resistant operation namespace; success and error cleanup share the same ownership rule, so another operation's confirmed or unfinished rows survive. Missing context after a pre-write failure owns no rows. When the operation's actor/scope lifetime has retired before a terminal callback, that callback **must not** write cache data — no snapshot restore, no bridge (a retired write resurrects removed entries, overwrites fresher data after a scope round-trip and can show rows of the previous authority, [**ZSP-M7**](../zustand/store-persist-and-module.md)); it **must** instead invalidate, in the scope captured by `onMutate`, every family `onMutate` cancelled or patched. Snapshot restore runs only while the lifetime is current. Keep `onMutate`'s cancel filters and this unwind as one shared filter list bound to the captured scope; every terminal phase (success, error, settled) **must** re-read that list in the captured scope by invalidation only — also after the lifetime retired — unless its current-lifetime reconciliation already re-reads a superset (a cancelled query that is never re-read stays stale). Return a context carrying the captured scope and that list whenever a cancel happened, even when no optimistic write followed. Tenant-targeted mutations take cancel and unwind only from the one shared authority the adopting project documents (with the snapshot restore passed in as a callback); a hook or domain module keeps at most a pure filter-list function, never its own cancel/unwind copy (**SSG-M8**). The required context and one cache patch are stronger mechanisms than a new check; whether future callers write outside that delta remains call-graph review. A mutation's command, optimistic delta and completion callbacks **must** consume one originating local operation binding. When the library can replace pending options after a UI render, prove from its installed execution path that the binding reference is captured before the first await and passed unchanged to every phase. Keep the root's mutation key, options and scope gate inspectable; a hidden options factory is not an equivalent remedy. This does not introduce a second transport/actor authority. The library-specific ordering proof remains review-owned. Exact-key parity: the optimistic read, write and rollback address the exact key a consumer subscribes to — built by the same registered factory call with the same scope arguments the reader passes. `getQueryData` / `setQueryData` / `getQueryState` match the key exactly, unlike `invalidateQueries` / `cancelQueries` / `refetchQueries`, which match by prefix: a patch written under a broader or narrower key than the reader's is a silent no-op — it reads `undefined`, skips the write, and both the optimistic view and the rollback miss what the user sees. A prefix form is a family filter, never a single-entry address, and the factory's TSDoc says so. Invalidation/cancel/refetch use that filter; `getQueriesData` discovery and `setQueriesData` family patching may also use it because each returned or patched member retains its actual full reader key. Snapshot and rollback retain those full keys and every metadata field; they never create a prefix cache entry. When a cache entry cannot be patched truthfully (**MUT-M30**), the correct fix for a dead patch is to delete it and let the server read reconcile it, not to re-key it into a plausible but partial value. |
| **MUT-M12** | Infinite query cache updates **must** preserve pagination shape (`pages` / `items`) during optimistic and bridge steps — **MUT-M4** / **MUT-M10** compatible. |
| **MUT-M13** | `mutate` vs `mutateAsync` is the caller's choice and follows the method (**MUT-M28**). Method A: the caller either calls `mutate` and continues from the success callback, or `await`s `mutateAsync` behind a progress surface when its next step needs the confirmed result (navigation into a screen that reads the written entity, an irreversible follow-up action, a receipt or legal confirmation); in both forms the UI intent closes only after the reconciliation settles. Methods B and C: the caller **must not** block — it calls `mutate` and the user continues; under C the target surfaces read the `onMutate` cache write, under B the pending representation from `useMutationState` on the canonical `mutationKey` (**MUT-M29**). A caller that needs to block takes method A. Errors **must** surface via `onError` (toast / alert) or the awaited `catch` (**MUT-M19**); method C also rolls back (**MUT-M11**). |
| **MUT-M14** | Mutation dependency map: Every exported `useMutation` hook in the adopting project's mutation modules **must** document in TSDoc which orchestrators and/or query keys it affects. A hook that invalidates one explicit key may name that key in one line. |
| **MUT-M15** | Orchestrator modules **must** expose granular sync functions (for example, `syncEntity` or `syncSummary`) — not a single “sync everything” entry that invalidates half the app (**MUT-M9**). Each sync function **must** return the `Promise` of the invalidation / refetch work it starts — never `void` it internally — and its caller **must** await or return it, because method A closes the UI intent only after that work settles (**MUT-M28**). The error path is the exception: it starts the reconciliation without returning it ([failure path](mutations-cache-sync.md#failure-path-normative)). A `Promise` return type puts the ordering obligation into the signature, where a dropped result is visible; a `void` signature hides it. |
| **MUT-M16** | Refetch policy after orchestration: Invalidate every directly affected key so inactive cache entries become stale; immediately refetch only active queries (default invalidation behavior or `{ type: 'active' }`) — except a write whose outcome the cache already carries, which marks stale without refetching (**MUT-M31**). `type: 'all'` / `refetchType: 'all'` is forbidden unless every matched inactive query has an observer-independent `queryFn` registered in `QueryClient` defaults and available at fetch time. A hook-only `queryFn` is insufficient: persisted hydration restores state/key, not function options, so forced inactive refetch can fail with `Missing queryFn`. Without that proof, critical paths use the same invalidate-all + refetch-active policy; inactive queries self-heal on mount through their canonical hook/query options. Any proved exception **must** still use a documented, minimal predicate. |
| **MUT-M17** | Invalidation and refetch **must** narrow by entity ids (for example, `entityId` or `parentId`) when the orchestrator API supports it — **MUT-M5** / **MUT-N1** alignment. |
| **MUT-M18** | When normative text in this topic changes, an audit **must** list mutation hooks whose `onSuccess` / orchestrator behavior may need updates; “rule added” ≠ “code compliant” until verified. |
| **MUT-M19** | `onError`: a method C mutation **must** roll back its own optimistic delta (**MUT-M11**); every mutation **must** surface user-visible feedback or report through the configured logging/observability boundary with the mutation name/key and error context; **must** align with [error handling](../error-handling/error-handling.md) — no empty `catch`, no silent swallow. An awaited `mutateAsync` whose `catch` is empty or comment-only is a defect; enforce it with the mechanism the adopting project documents. |
| **MUT-M20** | Cross-entity cache sync: When a mutation changes server state for entity type E — including via nested payload fields, composite endpoints, or documented side effects on a non-primary resource — `onSuccess` **must** apply the same bridge and invalidation discipline (**MUT-M4**, **MUT-M10**, **MUT-M6**) for every query key family of E as would apply to a direct mutation on E. Primary-resource-only cache sync when a secondary entity definitely changed is forbidden. |
| **MUT-M21** | Query key family coverage: For each entity type affected by a mutation, bridge `setQueryData` and `invalidateQueries` **must** enumerate all registered key factories / segments for that entity (byId, byParent, list, infinite, embed overlays) from the domain `queryKeys` module. Shared prefix between keys (e.g. same domain root + different segment) **must not** be assumed to propagate invalidation to sibling segments — each segment **must** be explicitly covered or listed in mutation TSDoc (**MUT-M14**). A cache-matching predicate **MUST** derive the key shape from the registered factory and **MUST NOT** re-spell it positionally by hand. A hand-written `key[0] === 'x' && key[1] === 'y'` chain is a *second* statement of a shape the factory already owns ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)), and its failure mode is the quietest one a cache has: a predicate whose literal sits at the wrong index simply never matches. Nothing throws, nothing logs, no type breaks, the mutation reports success — only the screen stays stale, and the gap can survive for months because the *absence* of an invalidation looks exactly like an invalidation that found nothing. The same applies to a hand-written key array passed to a matching call. Two shapes are especially prone to this: a segment written at the index the *tenant id* occupies, and a segment name that the factory never emits at all (a convenience wrapper's name rather than the canonical key it delegates to). Where the prefix already covers the family, the extra predicate is not merely wrong but redundant — delete it rather than repair it (**MUT-M7**). [On violation: Bug — silent dead predicate; the cache is never invalidated and the surface serves stale data] [Verify by: every matching predicate calls an exported predicate/key helper derived from the factory; no positional literal chain re-states a registered key family] Factory-derived helpers hold consumer root-literal comparison. Static checks may catch direct, file-local positional comparisons; whether an arbitrary index/value pair is valid against another file's factory requires cross-file analysis, and dynamic aliases and semantic equivalence of broader predicates remain review limits. |
| **MUT-M22** | Registry-linked cache bridge: When the project maintains an authority map (e.g. [SSOT registry](../ssot/ssot-registry.md) Section 1 row with a cache bridge / mutation cache owner) listing a cache bridge or post-mutation orchestrator for entity E, every mutation write path that changes E **must** invoke that registered function — including indirect / cross-entity paths (**MUT-M20**). Adding a new write path **must** update the registry consumer column in the same PR ([**SSG-R4**](../ssot/ssot-registry-rules-and-protocol.md)). |

**MUT-M11** / **MUT-M19** / **MUT-M21** application — an immutable scoped command and one reconciliation writer. Capture the originating opaque session/scope binding before invoking the mutation, not by deriving current scope again after `onMutate` has awaited. Carry it unchanged through optimistic/API/success/error phases and validate the actual outgoing config. Preserve public input/result discrimination, callback variables and stable trigger functions. After cancellation awaits, revalidate before a cache write; a retired account/tenant snapshot owns no current cache and is not restored after cleanup. Successful writes and equivalent foreground events use one registered reconciliation effect set for every affected segment. Accepted deletion patches loaded full-key lists then invalidates them; the shortened first page refills at the next natural read when the acknowledgment names the deleted ids and the page keeps rows (**MUT-M31**), otherwise active first pages are refetched; inactive entries become stale and self-heal on mount (**MUT-M16**). Preserve pagination/envelope metadata. The library's success callback may run inside the operation try: execute later assertion/cache/reporting effects through the existing terminal no-throw authority so their rejection cannot turn an accepted write into failure or trigger rollback. Definition error hooks preserve original throwable identity, validator cause and operation/family/target context through the existing observed-aware no-throw reporter; upstream ownership suppresses duplicates. Contain and report a separate rollback failure through the same authority rather than creating a detached rejected promise. The registry records the closed consumer set of such a writer (**SSG-R4**).

**MUT-M11** / **MUT-M19** application — accepted-result and original-scope terminal ownership. Keep API/domain, validation, parsing, non-success and required transformation rejection as the primary mutation failure, with its original carrier, feedback and owned optimistic rollback. After a validated result, diagnostics and success/settled dispatch consume the canonical observed-aware no-throw terminal owner; metadata reads, cache reads and secondary callbacks belong inside it. A secondary throw or rejected promise **must** remain observable under that effect's static identity, but cannot replace the accepted result, restore obsolete optimistic state or authorize another write. Independently owned cache families are attempted independently; an outer orchestrator invocation does not by itself prove isolation of every inner substep. The reconciliation is returned or awaited inside that boundary as its post-write method requires (**MUT-M28**, **MUT-M29**): its settling orders when the UI intent closes, and a failed background refetch is reported, never a success gate. Required reconciliation/readiness retains **MUT-M27**'s explicit failure/not-ready outcome and exact-state verification, and mandatory unfinished-client-state teardown remains intact. Reuse the same originating opaque assertion immediately before public API entry and later scoped publication, including rollback after a genuine request failure. When the locked SDK supplies one unique execution context to preparation, command and retries, a private reference association may index the identical returned preparation-context object; it **must not** copy actor/token/proof fields, create a new clock, recapture after an await or invent a missing-context fallback. A non-raising render/factory lifetime reader may reject a stale origin before preparation, but it does not replace the preparation's stronger authenticated-operation proof.

**MUT-M11** / **MUT-M19** / **MUT-M21** application — prepared-origin subscription ownership. A prepared command that subscribes to current origin lifetime **must** declare who releases that subscription. A private one-dispatch origin is released by its adapter after every terminal branch; an origin borrowed by several independent commands remains owned by the caller's retry intent and cannot be released by one sibling acknowledgment. Releasing a subscription **must not** convert a confirmed server result into failure. Equivalent scalar copies consume the existing actor-lifetime authority; reference equality is not a second lifetime rule. A tenant scope that changed and returned does not revive the old operation. Cache reconciliation isolates failures per affected family so a failed cancellation or bridge cannot silently skip its sibling invalidations. Opaque proof, exact schema/target binding and existing terminal no-throw APIs are stronger mechanisms than a new check; subscription/consumer ordering and complete family coverage remain cross-file review. A confirmed-create list bridge updates only a returned identity already present in the loaded raw cursor window and preserves every page/envelope field; an absent returned resource has no proved insertion position, so it is reconciled by the registered family rather than fabricated optimism or whole-list rollback. Exact server acknowledgment retires its own intent/key; an unknown result retains that key and reconciles the original families.

**MUT-M21** scope preservation: A factory-derived replacement **must** match the old predicate's tenant and segment set exactly. A broader existing family helper is not interchangeable with a narrow predicate; define a narrow helper beside the factory when needed. A strict query-key prefix may replace a positional predicate only when their matched key sets are equal.

For an accepted deletion, reader lists whose keys omit the deleted id still need their registered family prefix: remove that row from loaded pages, then invalidate for server proof. An id scan cannot reach those keys. The mutation-to-reader impact needs domain knowledge, so this coverage remains review-owned.

Before patching a matched query family, verify its cache shape for every matching key. A shared key segment can contain both flat lists and infinite pages; applying a flat-list filter to the whole segment throws after the server has already accepted the write. Narrow the factory-derived match to the affected representation, then patch and invalidate it. This cross-hook shape proof remains review-owned because a single-file AST cannot see all key consumers and their result types.
