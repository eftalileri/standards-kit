# TanStack Query — duplicate query authorities

```kit-cover
type: normative
part-of: README.md
binds: QRY obligations - a consumer must not become a second authority for what a query already owns (duplicate call site, consumer re-ordering)
open-when: shape:frontend-heavy, signal:server-state-cache, signal:ssot-authority, signal:duplicate-writer
skip-when: signal:backend-only, signal:no-server-state-change
owns: QRY-M13, QRY-M14, QRY-M15, QRY-M16, QRY-M17, QRY-N8, QRY-N9, QRY-N10
```

Part of: [queries and transforms](queries-and-transforms.md) — same QRY-\* domain, banded across three part files: that entry file, [queries-derived-form-state-and-selection.md](queries-derived-form-state-and-selection.md) and this one.

Scope: the defects in which a consumer opens a second authority for something the query path already owns — a second direct call site for an endpoint that has a `queryFn`, a consumer-side re-sort of a list whose order is part of the authority's contract, and the obligations that surround an actor-scope transition: reconciling the previous scope's cache after the actor write, stating a client-side role gate at its true strength, and keeping an invalidation set under one owner. Excluded: the hook/data path, transform resilience and the forbidden fetch patterns ([queries-and-transforms.md](queries-and-transforms.md)); selection reconciliation (**QRY-M11** / **QRY-N6**, [queries-derived-form-state-and-selection.md](queries-derived-form-state-and-selection.md)); key factories ([query-client-and-keys.md](query-client-and-keys.md)).

Compliance: as in [queries-and-transforms.md](queries-and-transforms.md) — violations are bugs; **must not** ship ([tanstack-query.md](tanstack-query.md) **TSQ-C4**, **TSQ-C11**).

## **MUST**

| ID | Rule |
|----|------|
| **QRY-M13** | One `queryFn` authority per endpoint — a second direct call site is a race, not just a duplicate request. When an endpoint's result feeds a startup/bootstrap decision (which tenant is active, which profile is loaded), every read of it **must** go through the single documented `queryFn`. A second call site issuing the request directly produces two in-flight requests at launch, which (a) can trip server rate limiting, so one of them returns incomplete or nothing, and (b) — the real defect — resolve at different moments, so the bootstrap decision races and the user lands in the wrong scope; every subsequent read and write is then correctly executed against the wrong authority. A single `queryFn` behind one query key makes this structurally impossible because the client de-duplicates concurrent reads of the same key. Only the call is restricted: imports, type references, and existence checks are unaffected. Beware a neighbouring rule that appears to cover this: a generic "no bare API calls in components" rule typically exempts the query/mutation hook directories — which is exactly where a second list-fetch is most likely to be written — so it does not close this gap; verify the exemption list before concluding the class is covered. |
| **QRY-M14** | A canonical ordering produced by an authority **must not** be re-sorted by its consumers. When a derivation returns a list together with its ordering (the order is part of the contract, often selected by a `sortMode`-style parameter), consumers **must** treat that order as authoritative and change it only through the authority's own parameter. A consumer-side `.sort(...)` is a second ordering writer (**SSG-M8**) and fails twice: the authority's ordering contract is silently disabled, and because array `sort` mutates in place, every other consumer sharing that array is reordered too — so the defect surfaces on a screen that never called `sort`. Sorting a copy is out of scope (no shared mutation). |
| **QRY-M15** | An actor-scope transition **must** reconcile the previous scope's server-state cache in the same event, positionally after the actor write. When the new actor remains authorised to read the affected scope, the canonical invalidation path marks that scope stale and refetches only under its documented policy. When the transition removes access, it **must** instead cancel in-flight old-scope requests and remove that cache; invalidating or refetching an inaccessible scope under the new actor is forbidden because it turns correct access denial into a request/error storm. Writing the actor without either reconciliation leaves old profile, settings and list data marked fresh, so the new panel can render another scope's snapshot with no error. Order is part of the obligation: reconciliation before the actor write does not discharge it because an in-flight old-scope result can repopulate the cache after the transition. Resolve both the store and the lifecycle authority by import provenance, not by name — a same-named local helper would satisfy a name-based predicate while the protection is off (**SSG-M8**). Stated limits: a single-file check may detect direct actor writes, but the same `setState({ actor })` shape occurs on many non-transition paths (login, auto-login, tenant switch, transport interceptors), an object built by spread hides the actor property from a single-file AST, and deciding which call sites remove access requires a machine-readable transition inventory and cross-module context, so that access-loss half remains review-bound. A configured check's file list is not full coverage of this rule; record its actual scope and limits. |
| **QRY-M16** | A client-side role gate is a consistency gate, not an authorisation gate — document it as what it is. A check that rejects an actor class before the UI commits to a scope (panel mode, workspace mode) is worth enforcing: without it the client draws a surface the server will refuse on every request, and the local actor record starts lying. But it **must** never be recorded — in documentation, a rule message, or a review note — as the thing that *protects the data*. The real gate is the server's actor resolver; losing the client check costs a wrongly drawn surface, not unauthorised access. Enforcement **must** also accept both legitimate shapes: a rejecting gate (test the disallowed class, stop the flow) and a verifying gate (the commit sits inside a condition that already proved the allowed class). A predicate that recognises only the rejecting shape burns the legitimate early-return path. Stated limit: such a rule sees that a gate exists, never that its constant is correct. |
| **QRY-M17** | An invalidation *set* has one owner; a consumer that already calls it **must not** also refresh one of its members inline. When an orchestrator invalidates several key families together — typically because one of them is a derivative of another — the set is the contract, not the individual keys. A call site that invokes the orchestrator *and* then hand-invalidates one member in the same body fails twice: a family added to the orchestrator later is invisible on that path, and the inline copy is usually written with a different refetch mode from the orchestrator's default, so within one event two members behave differently. The fix is never to keep the copy — it is to pass the intended mode to the orchestrator as a parameter, so every member of the set behaves alike. Scope the predicate to the copy that sits beside the orchestrator call. The broader claim — "every surface that mutates this data **must** call the orchestrator" — is an inventory assertion: whether a function is such a writer has no machine-readable marker in a single file's AST, and enforcing it broadly burns ordinary post-mutation refreshes. Keep such rules separate per key set: folding two sets into one predicate widens one while silently loosening the other. Exclude read/cancel operations (`getQueryData`, `setQueryData`, `cancelQueries`) — they are not refreshes — and exclude `predicate`-callback arms, where the targeted family could only be guessed by text matching. |

## **MUST NOT**

| ID | Rule |
|----|------|
| **QRY-N8** | Calling a bootstrap-feeding endpoint directly from a second call site instead of its single `queryFn` authority (**QRY-M13**), or re-sorting an authority-ordered list in a consumer (**QRY-M14**) — forbidden. |
| **QRY-N9** | Writing an actor scope without reconciling the previous scope's cache in the same event, placing that reconciliation before the actor write, or invalidating/refetching a scope the new actor can no longer access instead of cancelling and removing it (**QRY-M15**) — forbidden. Equally forbidden: presenting a client-side role gate as the control that protects the data (**QRY-M16**); it is a consistency gate, and recording it as an authorisation boundary hides the fact that the real gate lives on the server. |
| **QRY-N10** | Calling an invalidation orchestrator and hand-refreshing one of its member key families in the same body, or folding two distinct key sets into one predicate (**QRY-M17**) — forbidden. A differing refetch mode is not a justification for the copy; it is passed to the orchestrator as a parameter. |
