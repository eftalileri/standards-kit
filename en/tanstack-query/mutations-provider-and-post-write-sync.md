Scope: The second band of the **MUT-M** family — the five highest-consequence rows (derived read models, retry authority, irreversible provider/store commands, activation fencing, required post-write sync proof).

Rule prefix: **MUT-M**\* — this band owns **MUT-M23**–**MUT-M27**; the other bands are [mutations-invalidation-and-bridge.md](mutations-invalidation-and-bridge.md) (**MUT-M1**–**MUT-M22**) and [mutations-optimistic-strategy.md](mutations-optimistic-strategy.md) (**MUT-M28**–**MUT-M31**).

Compliance: Violations of MUT- rules are defects; stop dependent work until fixed and do not knowingly release them — [tanstack-query.md](tanstack-query.md) **TSQ-C4**, **TSQ-C11**.

## **MUST**

| ID | Rule |
|----|------|
| **MUT-M23** | Server-derived read models: A query whose server response is computed from data a mutation writes (a derived list or summary) **must** be invalidated by that mutation's invalidation authority, even when its key belongs to another entity namespace and no row of that entity was directly written. **MUT-M21** covers the mutated entity's key families; this row extends the duty to derived keys whose inputs changed. Danger sign (treat as a bug): two queries read the same server state through different derivations and only one is invalidated — the UI may combine fresh and stale values and show contradictory state or disable controls until `staleTime` expires (a defect that “fixes itself” after a delay and is therefore easy to misread as transient). When defining a domain invalidation authority, enumerate its registered key factories and justify each family that is not invalidated (**MUT-M6**). |
| **MUT-M24** | Single-owner automatic retry for replay-safe mutations: A reconciliation/idempotent mutation MAY retry automatically only when one stable action/idempotency key protects every attempt and exactly one layer owns an explicit finite attempt cap and backoff. If an HTTP response/envelope exists, only the canonical API error envelope's exact `retryable === true` fact authorizes replay; `false` or absent stops it. If no HTTP response exists at all, only the canonical structural wire-error classification `kind === 'network'` MAY authorize the same bounded same-key replay. HTTP status, free-text messages, semantic/local error-code lists, category guesses, and transport-library implementation details **MUST NOT** become parallel retry authorities. The owning caller **MUST** disable retry in lower transport layers for that request; conversely, if transport owns the budget, the caller **MUST NOT** open another one. A non-idempotent mutation **MUST NOT** gain automatic retry merely because either canonical fact is present unless an idempotency key/claim or equivalent replay-safety proof protects the write. |
| **MUT-M25** | Irreversible provider result vs backend projection: When an external store/payment/provider command succeeds but the following backend projection is unconfirmed, return and render a discriminated partial outcome (for example, provider-confirmed and activation-unconfirmed). Do not collapse the two authorities into unconditional success or report the provider operation as failed. Once the native command resolves successfully, an absent, expired, or malformed entitlement/projection in that same immediate response **MUST NOT** throw away or reclassify the provider result; preserve the result and any required transaction credential first, and let the canonical server/provider reconciliation decide activation. Recovery **MUST** replay only the idempotent backend projection with the same action key, never the irreversible provider command. A provider response indicating an existing purchase is also a reconciliation trigger: skip the provider command and run the same server-verified projection path rather than reducing it to an error message that would strand an existing entitlement. Mark an outcome active only after a runtime-validated response proves the canonical active-entitlement state; field presence or HTTP status alone is insufficient. A retry-authorized partial state follows **MUT-M24**. A terminal provider/business/system result **must** become a distinct support-required/rejected partial outcome, never “still pending.” Every subordinate credential-delivery fact (queued, blocked, not durable, cleanup pending, token unavailable) **MUST** survive activation/manual retry success in the outcome carrier and in the failure report; projection success cannot erase it. Cleanup-pending means backend acceptance is already proven but local record deletion failed, so the durable record remains for same-key cleanup replay; it is not a provider rejection. A missing provider credential is unavailable, never a fabricated queue claim. User-facing rendering follows user agency: a partial fact reaches the user only when the user must act — support is needed (blocked, or a delivery result that could not be classified) — and only such a support surface shows the canonical trace identifier. A fact that recovers by itself or belongs to the operator (queued, a deferral that sent nothing, cleanup pending, not durable, token unavailable) **MUST NOT** be shown as a warning; its report through the classification authority is then its only visibility, so a deferral is reported with its closed reason, never left silent. Silence for not-durable / token-unavailable holds only while the entitlement and the store binding are derived without that client delivery (a provider notification or server-side feed); where the client delivery is the only path, a lost credential is a support fact and is shown. The activation-unconfirmed state likewise tells the user only that the purchase completed and the plan may take a moment to appear — no queue or reconciliation wording, trace identifier or retry control — because the provider-notification projection and the same-key recovery of **MUT-M26** finish it without the user. Reason: a technical warning the user cannot act on reads as a failed payment and invites a second purchase. |
| **MUT-M26** | Post-provider activation fencing: Generate the activation idempotency key before invoking an irreversible provider command. If that command succeeds while activation remains unresolved, install one process-lifetime reconciliation block keyed by the exact authenticated subject and resource scope; its value is the exact action/product key and **MUST** be updated or cleared only by compare-and-set against that full identity. A different scope or action key **MUST NOT** overwrite or clear the block. The same key may run only one projection request at a time. Recovery may retry only the same-key backend projection and **MUST NOT** invoke the provider command again. Clear the block only after the canonical active-entitlement proof from **MUT-M25**. A typed error used to signal that this fence exists **MUST NOT** carry sensitive subject, scope, or action-key values; keep those in the authoritative process-local store and revalidate the captured scope before lookup. The error may carry only safe structural reason/trace/warning fields; logging or capturing it **must not** expose the recovery payload. When one mutation/adapter contains both the provider command and later local work, every rejection that can escape after the provider promise resolves **MUST** carry a structural provider-confirmed discriminant (without replayable credentials or a raw `cause`), so outer layers continue only the same-key projection. Preserve any already-classified delivery outcome and carry it to the **MUT-M25** rendering decision; local logging, observability, or cache failures cannot erase it. If delivery is still unknown, represent it explicitly as unknown, install the exact-key support fence, and do not invent a queued/blocked state or show generic full success. The adapter section after the provider promise resolves **MUST** itself be non-throwing or translate any escape into that discriminant; setting a success flag only after the adapter returns is insufficient. Non-authoritative analytics, refetch, cache, observability, or UI-projection work after provider success **MUST** have its own failure boundary and **MUST NOT** fall into a generic pre-provider failure handler. If canonical activation already returned, later failures **MUST** preserve that outcome and **MUST NOT** reinstall the reconciliation block. Every detached/UI-triggered recovery promise chain **MUST** end in a terminal catch that reports through the configured no-throw client-observability boundary and gives contained recovery/support feedback. |
| **MUT-M27** | Correctness-required post-write sync and action-intent lifetime: Awaiting `invalidateQueries` / `refetchQueries`, including with `throwOnError: true`, is not proof that an active query refetched: TanStack Query v5 may resolve the operation while a matched query remains `fetchStatus === 'paused'`. A correctness-required post-write orchestrator **must**, after the awaited operation, inspect the exact targeted active query family and fail loud if any matched query remains paused, preferring its canonical `fetchFailureReason` when present. The mutation **must not** announce full sync success until this inspection passes. When the flow owns user selection or an action/idempotency intent key, the complete scope+canonical fingerprint+key+pending authority **must** live at least as long as that selection/recovery intent (including child-screen/tab unmounts), reuse the exact handle for same-intent retry, and clear only after the sync proof. A hook-local/ref pending flag or key reset by remount is insufficient when the selection survives elsewhere. `onMutate` **must** acquire the exact fingerprint intent and set pending before any request-side await; `mutationFn` and every automatic retry **must** resolve that same key. A terminal error may release pending while preserving the exact key, and exact success may clear pending+intent only after required sync. Each terminal callback may mutate only the exact scope+fingerprint+key lock acquired by its own `onMutate` context; a rejected duplicate submit **must not** release another live request's lock. If a scope-changing command can race this action in the opposite direction, both commands **must** acquire mutually exclusive exact-owned handles from one same-lifetime authority before any guard-recovery/cache/backend side effect: each begin rejects the other's active or invalidated handle, `mutationFn` proves its own handle, and every terminal path releases only its context handle. Before and after any awaited success-side cache sync, the callback **must** resolve that exact terminal handle state; an invalidated result skips or stops old-scope sync and only consumes its own tombstone. The final post-await verification and terminal state mutation **must** have no intervening await. A privacy-reset tombstone **must** make a stale callback no-op before any new-scope write. A same-scope no-op **must not** acquire this mutex or run redundant authority writes. A preflight boolean check without an acquired handle is insufficient because the opposite command may start while the first request is in flight. A logout/privacy/authority reset may unconditionally clear the live UI intent, but a later terminal callback **must** recognize only its exact invalidated handle and no-op without resurrecting state; that invalidated handle continues blocking conflicting commands until its exact terminal release. Only a handle with a future in-flight terminal callback becomes such a tombstone; a quiescent retry handle with no pending callback **must** be discarded on reset rather than creating a permanent lock. A generic empty-state no-op that hides unrelated completion mismatch is forbidden. While the request is in flight, every UI input that contributes to the fingerprint **must** be disabled and its handler/store invariant **must** reject changes, so visible state cannot diverge from the durable request intent. Paused, transport-uncertain, or sync-failure paths preserve the original selection and exact intent pair. |

Partial resource-retirement application (**MUT-M27**/**MUT-M28**): When an irreversible delete first records a durable closing decision and cleanup finishes later, a failed terminal response does not prove the resource is still active. Do not optimistically reverse a confirmed closing state or demote the current actor before confirmation. Read the server's authoritative closing list for the exact retry id across remounts and fresh sessions; a local modal or persisted selection is not that authority. On session bootstrap, validate persisted active-resource data against the server before using it to select scope; its cache age cannot prove the resource is still active after a closure elsewhere. An empty active list does not prove the actor's role changed: resolve the current profile/actor authority before changing role or mounting a role-specific recovery reader. A typed stale-session cancellation is not a current-session failure and **must not** be reported as one. A failed next page of the closing list **must** retain confirmed rows and expose retry for that page. These relationships span server and client modules; a single-file AST cannot establish them, so cross-boundary review remains required.
