# TanStack Query — UIP band 2: cold start, idempotent refresh, list persistence, sensitive families

```kit-cover
type: normative
part-of: README.md
binds: UIP-M18 to UIP-M23 - the second band of the UIP MUST family: the native-splash and cold-start gate, idempotent store refresh, guarded synchronous native calls, cache-first canonical list persistence, the function-based query persistence boundary and the last confirmed answer that survives a failed refetch
open-when: shape:frontend-heavy, signal:cache-lifecycle, signal:cache-persistence, signal:offline-ui, signal:retry-ux, signal:app-cold-start, signal:infinite-list, signal:pii-scrubbing
skip-when: signal:backend-only, signal:no-client-persistence
owns: UIP-M18, UIP-M19, UIP-M20, UIP-M21, UIP-M22, UIP-M23
```

Scope: The second band of the **UIP-M** family — the rows that govern the cold-start window, reference churn on refresh, throwing synchronous native calls, which list variant is persisted, which query families **must** never reach device storage, and which confirmed answer **must** survive a failed refetch. The band split keeps the complete normative set within the authoring limits while cutting only at whole-rule boundaries inside the same UI/persist domain. The complete band set is the **Domain part files** list in [ui-persist-offline.md](ui-persist-offline.md). Rows appear in their source order (**UIP-M19**, **UIP-M20**, **UIP-M18**, **UIP-M21**, **UIP-M22**, **UIP-M23**).

Rule prefix: **UIP-M**\* — this band owns **UIP-M18**–**UIP-M23**; the first band is [ui-loading-and-persist-options.md](ui-loading-and-persist-options.md) (**UIP-M1**–**UIP-M17**).

Compliance: Violations of UIP- rules are defects; stop dependent work until fixed and do not knowingly release them — see the cross-cutting [TanStack Query standard](tanstack-query.md) (**TSQ-C4**, **TSQ-C11**).

References: [ui-persist-offline.md](ui-persist-offline.md) (scope, **UIP-N1**–**UIP-N7**, failure path); [mmkv retention](../mmkv/mmkv-retention-limits-and-buster.md); [security](../security/README.md).

## **MUST**

| ID | Rule |
|----|------|
| **UIP-M19** | Idempotent store/state refresh (no reference churn): A function that refreshes or re-syncs state from a source (API response or derivation) and writes to a store or React state (`setState`, `store.setState`, `dispatch`), especially on focus, mount, or an interval, **must not** write a new object reference when the value is unchanged. Compare the new value with the current one (stable serialization or field compare) and write only on a real change. Replacing an unchanged object can trigger a render cascade; if a remount-sensitive consumer depends on it (such as a list slot or callback dependency; **UIP-N5**), this can form a remount/refetch loop. |
| **UIP-M20** | Guarded synchronous native calls (render / hooks / interceptors): A synchronous native-module call that can throw — e.g. Expo sync functions (`Localization.getLocales()`, `getCalendars()`) throw context-lost errors on Fast Refresh / background-resume — and is reachable from a render path, hook, or request/response interceptor **must** be wrapped (try/catch) behind a single safe accessor returning a documented fallback (empty list / `undefined` / `null` — fail-safe, no fabricated value). An unguarded throwing sync native call in render white-screens the subtree (error boundary); in a request interceptor it breaks every request. Centralize the safe accessor (one authority) — do not repeat raw sync native calls across call sites. |
| **UIP-M18** | Cold-start / native-splash gate = local readiness only (never a remote query): Dismissal of the native splash screen (and any blocking full-screen cold-start gate before first meaningful frame) **must** depend only on local readiness signals — store hydration, persisted-cache restore, local init completion. It **must not** be gated on a remote query's loading state (`isLoading` / `isPending` / `isFetching`): a network round-trip can hang or time out, holding the splash for the full request + retry duration even though all local data is already ready (the splash is meant to cover the local cold-start window, not a server round-trip). A startup-time remote check that genuinely **must** run (kill-switch / app-availability / maintenance / force-update) **must** be (a) persisted so cold start reads a cached value first (cache-first, stale-while-revalidate per **UIP-M6**; not in `persistable/shouldDehydrateQuery`-excluded set), and (b) surfaced via an in-app view (the app's own loading / blocking overlay) when it is still unanswered after the splash hides. Once local readiness holds, the splash **may** stay up while the first screen's session and blocking decision settle, so that with a persisted cache the user's first frame is the ready screen and no in-app loading view or skeleton ever appears; that hold **must** be bounded by one short named cap measured from local readiness (a few seconds, well below the OS launch watchdog and user patience), after which the splash hides and the screen draws its own loading footprint (**UIP-M2**). The hold decision belongs to the startup readiness owner, never to a second gate; a cache-backed start **must not** wait on the network for anything the cache already answers. A saved session (profile, tenant list, settings) **must** open the first screen at once as a display hint, never as session proof: the stored key is validated and the session re-read in the background through the same bootstrap pipeline, which re-publishes without dropping the same user's readiness — only while the server's role and tenant link equal the drawn ones, because a changed scope **must** pass that role's own readiness gate (a retained single-user screen would otherwise open a tenant-scoped screen without its tenant scope); an invalid key signs out through the existing session-integrity path; only a transport failure (no server answer) keeps the drawn screen and is reported once; any server answer that rejects the chain (other subject, contract violation, closed tenant) fails the start exactly as without the cache (every request is still authorized by the server). First-ever launch with no cache may briefly show the in-app loading view after the cap (same background as the splash for visual continuity) — not a frozen splash. Cold-start "time to first meaningful frame" telemetry **must** measure the same signal that requests splash dismissal: report in the same guarded request branch, without independently waiting for a stricter content/session gate or for the asynchronous native dismissal result. The native dismissal request is issued before the diagnostic report so telemetry cannot become a prerequisite for the transition. This interval is a readiness/request-time measurement, not proof of the first frame's drawing. A new check for this reporting rule is not required; the single-branch mechanism is stronger. The subordinate clauses below are part of this rule. |
| **UIP-M21** | Cache-first canonical list persistence (default variant) — including `useInfiniteQuery`: When TanStack persistence is enabled and architecture selects this family for persistence, a bounded, account- or tenant-scoped list query that backs a primary list surface should persist its default canonical variant (no search term, entity filter, or alternate-context flag) through `shouldDehydrateQuery = true`, subject to the selected persister's per-family and total persisted-size policy (for MMKV, **MMR-M1**/**M2**) and the retention upper bound (**UIP-M11**), so a cold start can render cached rows and refresh in the background (**UIP-M6**). Memory-only remains a valid architecture choice; the in-memory cache budget is separate (**UIP-M13**). Exclude search, filter, alternate-context, and scratch variants (**UIP-N2**). Do not exclude every infinite-query list as a class; classify the variant. Exclude the default variant only for a documented semantic staleness hazard, the credential boundary in **UIP-M22**(a), or while awaiting the persistence risk review in **UIP-M22**(b); cite the exact reason, never merely that the query is infinite. |
| **UIP-M22** | Query persistence boundary — classified by function, decided by an owner. `shouldDehydrateQuery` is the single authority for an entire query family's device persistence, and what it answers is settled by what the payload *does*, read from the fields of the type the query returns — never from the family's name, and not by how the persister storage is encrypted. The same persisted-client boundary **must** set `shouldDehydrateMutation` to exact `false`: a paused mutation serializes its complete variables and is not covered by a query-family allowlist. (a) A family whose key or payload carries a replayable credential — a value that grants access or authority when captured and replayed (session/refresh token, purchase or receipt token, OTP, reset token, single-use join or delegation code, signed URL) — **must** return exact `false` for the whole family and be absent from every persistable allowlist, whatever encryption that storage has. (b) Every other family, including one carrying names, financial rows or tenant identifiers, is persistable only after the project's designated security/privacy authority records its acceptance against a written threat model; absent that record it stays memory-only, and an agent **must not** grant it alone. A root whose families mix the two classes **must** be split so the credential families live under their own root, because the allowlist decides whole roots: persisting the fact families under a shared root would persist the credentials, and keeping the root memory-only would deny the facts for no reason. A single field of the credential class inside an accepted fact payload is projected out at the persistence boundary, and a restored payload that loses it **must** fail closed (not ready) until the server answers again. (c) Either way the allowlist stays closed so an unknown new root is never written; stable-hashing only query-key segments is insufficient because the dehydrated payload survives intact; and any classification change **must** invalidate already-written disallowed state in the same rollout. A cache-buster change is the default. A source-owned targeted persisted-client migration may replace that change only when it rejects malformed envelopes and inconsistent independently serialized key/hash identities, excludes every retired query-family version/descendant and every prohibited generic mutation before any hydration, applies the same exclusion before persistence and throttled snapshot capture, and preserves non-retired query state and required SDK metadata. Live dehydration denial remains mandatory. Complete entry/import/caller/SDK restore/save ordering **must** be proved under the adopting project's permitted verification policy and the actual owner decision recorded; coverage or ordering that cannot be established still requires the buster. Name-only filtering, key hashing alone, fake empty success, silent legacy restoration and claims of physical purge without absence proof are forbidden. This classification-retirement alternative grants no persistence permission to unrelated families, changes no optimistic/bridge shape or contract-version binding obligation, and cannot recall already delivered or old loaded-client data. The typed boundary is stronger than a new check; cross-file/SDK order and historical-family coverage remain review-held. Clause (a) overrides the default-list persistence preference in **UIP-M21**; once (b) is satisfied **UIP-M21** applies again unchanged, so a family is never left excluded merely because it was once called sensitive. Aligns **MMR-M10** / [**SEC-M-STORE-2**](../security/security-secrets-and-logging.md). |
| **UIP-M23** | A confirmed answer that opens the user's way into an area survives a failed refetch. When a persisted query family's last successful answer decides whether an entry is drawn — a “return to the other workspace” item, an access affordance — and the action behind that entry is re-authorized by the server when it is used: (a) a failed refetch **must** leave the last successful data both in memory and in the persisted snapshot, and the snapshot **must** carry that success state, never the error object (a serialized error restores as an empty object and crashes its readers); (b) the family's `gcTime` **must** outlive the time no observer reads it, set once as a family default on the key-factory prefix (**CLI-M3**) so a restored, observer-less entry receives it too — unnecessary only where a session-lifetime observer reads the key; (c) the commands that change the answer **must** invalidate the family (**MUT-M6**), and its `staleTime` is chosen from **CLI-M7**; (d) the opt-in **must** name only the keys that carry the decision, in one module-owned list — a key that is also the prefix of other families' keys is opted in as that exact key, never through a prefix-matched family default, because the client library matches defaults by prefix and would extend the retention to every family under it. Reason: the persister rewrites the whole snapshot on every cache event, so one failed refetch or one collection drops a proven answer and the next cold start hides the user's way back. A family whose action is not re-authorized at use **must not** opt in — a stale answer would then grant what the server has withdrawn. This row is the narrow exception to the refetch-error clause of [**CLI-M12**](query-client-and-keys.md): it covers the same exact key only and never admits previous-scope data. |

### **UIP-M18** — The gate is judged by what it waits on, not by what it is named

The gate is judged by what it waits on, not by what it is named. A flag computed in local code is still a remote gate when every path that sets it awaits a server round-trip; before a flag is used as the splash gate, trace each assignment to it and confirm none of them is written only after a request resolves. A single-file check may identify direct remote loading dependencies in the file that dismisses the splash, but it cannot prove that an imported flag is independent of network work; a flag imported from another module that transitively awaits the network is outside its reach.

### **UIP-M18** — Cache-first means through the cache seam, not through the query function

Cache-first means through the cache seam, not through the query function. Where (a) applies, the cold-start read **must** be issued through the query client (`ensureQueryData` / `fetchQuery` / a query hook). Calling the family's query function directly reads identically at the call site but bypasses the persisted read, the staleness contract, in-flight de-duplication, the write-back into the cache and the global failure net — so the family is listed as persistable while nothing ever reads what was persisted. Project checks may flag direct query-function calls outside a `queryFn` slot; indirect calls need review.

### **UIP-M18** — Elapsed time is not a failure

A cold-start gate **must not** turn elapsed time alone into a terminal error. Only a proven failure — a step that threw or rejected, a storage read that reported an error, an invalid runtime configuration — may open the failed-startup surface; when a wait passes its expected duration the gate stays waiting, says so calmly, offers an optional retry that does not tear down the steps still running, and opens by itself the moment readiness arrives. One owner derives the waiting / ready / failed state that the splash, the loading view and the failure surface read; no consumer keeps its own timer or failure path. Reason: a slow but healthy start (cold device, slow network, debug bundle) otherwise lands on a dead-end error that persists after readiness completes, and a clock-made failure carries no root cause. A slow start is recorded as a duration measurement, not a crash event; a wait that outlives every bounded step (request timeout, font cap) is a stall and is delivered once through the client failure channel with the pending steps, without changing the screen, because a breadcrumb alone is lost when the user quits while waiting. A boot step rejected by the server's version gate (**FFL-RN-M9**(e)) is not a failed start: the startup owner's single disposition decision hands the screen to the update gate, opens no failed-startup surface and raises no crash event; while a blocking gate draws its terminal screen in place of the app, the slow and stall clocks do not run, because nobody is waiting on the start.

### **UIP-M18** — A stall report carries its own clock

The stall event and the failed-startup event **must** carry foreground and background time since launch, the app-state transitions, and the last stage the pending step's owner entered — never wall-clock elapsed time alone. Reason: an OS-suspended process resumes with its overdue timers firing at once, so a wall-clock "stalled for 32 minutes" is indistinguishable from a frozen background launch, and the event cannot say which await never settled.

### **UIP-M18** — The slow and stall clocks count only time someone can be waiting

The slow-notice and stall clocks **must** advance only while the app is not in the background and **must** re-measure the counted time when their timer fires; the stall threshold **must** exceed the longest single bounded step, its transport retries included. Reason: a background launch is waited on by nobody and its overdue timers fire together on resume, so a wall-clock budget reports a suspended process as a user stuck on the splash, and a threshold inside a step's own retry bound reports a request that is still within its bound as one that never settles.

### **UIP-M18** — One chain, one read

One chain, one read. When two consecutive steps of the same bootstrap need the same resource, the first step publishes its response into the cache under that family's key and the second reads it through the cache seam declaring an explicit freshness tolerance; the tolerance is opt-in per call site, so every other consumer keeps the freshness it has today. Asking the same endpoint twice in one serial chain is not only latency — it is two readers of one fact that can disagree.

### **UIP-M22** — A pending write never reaches disk

While any mutation is pending, the persisted-client boundary **must not** write a query whose data changed after the earliest pending mutation started: it writes that query's last persisted version marked invalidated, or omits it when none exists, and the next snapshot after the mutation settles writes the real state. The hold lives once at the persister boundary, never in individual mutation hooks. "Started" is the mutation's first transition to pending, recorded before the hook's `onMutate` runs; the hold **must not** read the mutation's current submitted timestamp, because a mutation library may restamp it after `onMutate` returns a rollback context (TanStack Query v5 does), which moves the boundary past the optimistic write it exists to hold. Reason: a cache-optimistic write is rolled back only while the process lives and mutations are not persisted, so an app killed mid-request would otherwise restore the temporary row (or the row removed before an unconfirmed delete) as real on the next cold start; the invalidated mark makes the restored last confirmed state refetch on first use, because the request may have reached the server.
