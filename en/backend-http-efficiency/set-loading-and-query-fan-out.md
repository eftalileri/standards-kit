# Backend HTTP efficiency — set loading and per-item query fan-out (**BHE-M13**, **BHE-M14**, **BHE-M16**, **BHE-N5**, **BHE-N6**)

## **MUST**

**BHE-M13**: Round trips **MUST NOT** grow with the size of the set. When a synchronous HTTP request computes a result over N entities (N staff members, N catalogue rows, N ids), the loader **MUST** take the whole id set and return a keyed result the caller groups in memory; the per-entity computation stays in a pure core that runs once per entity with no I/O. Seven obligations follow. (a) One loading authority. The single-entity helper **MUST** delegate to the batch loader with a one-element set, never keep its own query — two loaders for the same data drift apart the moment one is edited ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)), and the single-entity path must keep the same filter it had, so delegation cannot widen a subject or tenant scope. The caller's keyed lookup **MUST** apply the same normalization the store's query cast applies to the filter values (for example a schema `trim` on a String `_id`), otherwise a row the single read finds is silently reported missing. (b) Reuse what the request already read. When the id set was itself derived from a read of the same rows, the loader **MUST** accept those rows instead of reading them again, and the parameter **MUST** document the scope the passed rows are required to have — a narrower set silently produces missing totals rather than an error. A metric needing only exact ids **MUST** consume them from an already-resolved scope; it **MUST NOT** invoke a broader identity/display resolver merely to recover the same ids. (c) Resolve shared documents once per write path. When several builders in one write path need the same documents, they are resolved once by the single scope-validating read authority and handed to each builder through an explicit, documented option; each builder keeps its own completeness check and re-asserts the tenant of every passed document, so an id missing from the set still fails loud and the deduplication cannot remove a validation ([**BHE-N2**](backend-http-efficiency.md)). A validation-only twin of a resolve function that issues the same query is a duplicate authority, not a second check: delete it in the same change ([**DCD-M2**](../dead-code/dead-code.md), [**SSG-M8**](../ssot/ssot-principles-and-precedence.md)). (d) Concurrency is bounded by the session. Two independent loads may share one round trip, but **MUST** run sequentially when they carry a database session, because one session admits one operation at a time. (e) A live read that guards a later provider read is loaded per chunk. When the per-entity computation reads an authority live so that its answer cannot be overtaken by a provider-side change before the entity's own provider read (identity cutover, lease), the batch loader **MUST** split the set into chunks no larger than the provider concurrency bound and issue that live `$in` per chunk, immediately before the chunk's concurrent computations; chunk reads after the first are declared to the runtime detector as page-derived. One live read at the head of the whole set would widen every later entity's read-to-provider window. (f) A set-loaded token consumed by a per-item compare-and-set (each use advances the version it was read against) **MUST NOT** be shared by two items of the same key: the loop loads one token per key per round, runs one item per key per round and declares later rounds `pageDerivedIn`, so round trips grow with the largest per-key item count, not the set size — a shared token fails every later item's compare-and-set as stale. (g) Post-commit effects of a per-item writer are applied once per set. When a unit processes a set by calling a per-item writer whose post-commit effect authority has a set form, the writer **MUST** accept a collector from the unit and record the item instead of applying its effects, and the unit **MUST** apply the collected set once through that set form when it settles, including when it aborts; the writer called alone keeps applying immediately. Reason: the effect authority's preparation reads would otherwise repeat once per item outside the item's transaction. [Consequence: latency grows linearly with tenant size and is invisible in a small-tenant test; a fan-out that widens scope leaks another subject's financial rows.] [Verify: static inspection — query count in the loader is constant with respect to the set size; the single-entity path contains no query of its own.]

List-enrichment application: when one page needs several derivations from the same authority-document set, load that set once and pass the live documents to named derivation entry points; a narrow populate, a projected batch and a full batch over the same ids are duplicate reads, not three authorities. If another derivation already loaded the full history rows, derive counts from those rows rather than opening an aggregate over the same set. Preserve tenant re-assertion and missing-row behavior. The same holds for a composed read-and-derive helper and for a loop: a helper that reads a set and returns one answer over it (the single value the rows agree on) serves only a consumer that holds no rows; a consumer that has loaded — or in the same operation also needs — that set reads it once, derives every answer through the pure owner over its own result, and passes the result to its sub-steps (a readiness probe, a branch executor) instead of letting each re-read. A shared engine that derives from the set on behalf of several callers takes the source as a two-form input — *read this scope* or *here is the result I hold* — with its one derivation running over either form, so accepting held rows never creates a second derivation; and where every caller of one engine mode already holds the set, the held form is required in that mode and its absence fails loud, because an optional hand-over silently reverts to the re-read the first time a caller omits it. A set read once per iteration of a loop over buckets is read once before the loop, every map the loop needs built from that one result. Outside a transaction this is also a consistency obligation, not only a cost one: two reads of the same set can return different snapshots, so two answers of one request (two derived values of one response) would describe different states.  This is review-only: the duplicate is visible only across the loader and its transitive consumers.

Job-loop application: a scheduled job that reads and writes per item **MUST** issue its per-item reads as set reads before the loop; where shared builders read through the scope memo, each item runs in its own bounded scope seeded with that item's rows from the set read, and the item's builds run before its first write, because a seeded bucket carries no proven read set and any write in the scope drops it. One scope **MUST NOT** span the items: it would carry values between units and hold every item's memoized rows until the last item ends. When a shared engine runs per item and per subject (every subject re-reads the same tenant inputs), the job **MUST** hand the engine a held source set-loaded for a bounded chunk of items through the engine's two-form input, so a build opens no read; seeding cannot reach reads keyed per subject. A page or chunk loop's set reads after the first are declared to the runtime detector as paging; the builders' own reads stay undeclared. A recurring scan's candidate query **MUST** carry every bound the decision implies — the largest horizon at which a row can become actionable (for example the maximum reminder lead) and the instant from which an already-settled subject is due again — and page on a key its index walks in order, projecting only the fields the loop reads: a row that cannot be acted on this tick is otherwise read on every tick.

Multi-tenant application: a batch loader whose set spans more than one tenant **MUST** return its keyed result partitioned by tenant (each document filed under its own stored tenant id, every requested tenant present), and a consumer **MUST** resolve each row's reference only in the row's own tenant partition; a corrupt cross-tenant reference then resolves to "not found" for that row and is reported as a data defect. Merging the partitions under the referenced id alone **MUST NOT** happen: a row of tenant A carrying tenant B's id would receive B's document whenever B's rows on the same page requested it.

Per-item scope application: a background unit that runs each item (recipient, tenant pair) in its own fresh read scope **MUST** still load the item inputs that no earlier item's side effect can change once per page of items, in one scope shared by that page's read-only stage, and **MUST** keep only the reads an earlier item's side effect can change in the per-item scope; the page is the liveness unit and page loads after the first are declared to the runtime detector as page-derived. Reason: a fresh scope per item discards every set load, so the per-item derivation reopens one round trip per item and the isolation it was meant to buy is spent on data no item writes.

Varying-subset application: when one unit derives several id sets that are subsets of one bounded population (date windows, filter combinations, cohorts of the same platform) and each would issue the same read shape with its own `$in`, the authority **MUST** read the population once per unit (request-scoped memo, **BHE-M2**) and cut every subset in memory. A scoped variant of a grouped or paired read (group by a pair key, then classify) may cut its scope after the grouping only when the writer guarantees every member of a group carries the same scope keys; otherwise it keeps the scoped query. Reason: one read per subset repeats the same shape once per window or filter — an N+1 over subsets that grows with the number of consumers in the request, not with the data.

Conditional-write application: a unit that writes one conditional (compare-and-set) update per item of a set **MUST** send them as one ordered bulk write in which every operation keeps its own condition, and **MUST** reject an item whose target repeats an earlier item's target before the write, because the repeat's condition would be checked against the first write's result and its miss could not be told apart from a real conflict; a per-operation miss **MUST** still fail the unit with the same conflict outcome the per-item write gave, and with the same registered code the per-item path gave for that cause. When the per-item outcome depends on whether *this* write changed the item, a set write's count **MUST NOT** be attributed by reading the items back afterwards: another writer can leave the same state this write would have, so read and write the set in one transaction snapshot and treat only items found unchanged there as this write's. Reason for both: the batch otherwise reports a different cause, or passes another writer's result as its own and silences the per-item failure. The runtime detector's repeated-write report is the check; the code and attribution clauses are review-held. Reason: one round trip per item grows with the selection, and a batch that silently tolerates a miss turns the all-or-nothing write into a partial one.

Fix-proof application: a change made to remove a repeated read under this rule or **BHE-M15** — batching, removing a read, reusing a write result, or declaring a loop — **MUST** carry a behaviour-preservation proof made without test artifacts (agent-planning **M12**): over the same inputs, the old and the new code produce the same response, the same persisted fields and derived values, and the same emitted events and side effects (shown by running both against the real path, or against an isolated copy of real data, from a throwaway extraction); every consumer of a removed or changed read still receives the same value; and every tenant, permission and idempotency guard on the path is unchanged. The proof is recorded in the change's handover. Reason: a read can also be a check or a freshness boundary, and an efficiency fix that silently drops one breaks working behaviour that no detector will report.

**BHE-M14**: When part of a list endpoint's filter or sort is NOT expressible in the store's query, the page AND its total **MUST** both be derived from the same fully-matched set — and the endpoint **MUST NOT** pay per-item cost for rows it will never return. A filter whose value is *computed per row* (a status resolved from another aggregate, an entitlement fetched from a provider, a derived ranking) cannot narrow the store query, so the store returns a superset. Three obligations follow, and they are one design, not three patches. (a) The total is read off the set the page is cut from — never off a window. The tempting shortcut is to over-fetch a window of `pageSize × k`, filter it in memory and report the survivors as `total`. That number is bounded by the window, so `total` silently caps at `pageSize × k` and every page past `k` becomes unreachable: the client's own next-page control is computed from the value the server just capped. It is also wrong in the other direction for pages after the first, because the window was cut by a raw-field `skip` before a derived filter was applied, so rows are dropped and repeated across page boundaries. When a derived filter is present the correct shape is: load the whole matched set, resolve the derived value for every row, filter, take the length as `total`, and only then slice the page. When it is absent there is no in-memory filter, so the store's own count over the same query is the total. (b) One counting derivation, read two ways — never two counting authorities. Both branches answer one question: *how many rows match the complete filter set?* Where the set is already in memory its length is the answer and no second query is opened; where it is not, one count over the identical query is issued. A branch that computes its own count by a different route is a parallel authority ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)) and will drift from the branch beside it. A count that is issued and then discarded is the same defect wearing the opposite mask: the cost is paid, the answer is thrown away, and a wrong value is reported in its place. (c) The per-item resolution runs over the rows that are actually needed. An over-fetch window multiplies every per-row lookup by its factor — with an outbound provider call per row that is the dominant cost of the request. Where no derived filter is present the window has no function at all and **MUST** be removed: resolve the derived value for the page only. Where a derived filter is present the full set genuinely must be resolved, and that cost is the honest price of the filter, not of the pagination. [Consequence: rows exist that no page can reach, page boundaries drop and repeat rows, and every page pays k× the provider fan-out for rows it discards.] [Verify: for a list endpoint whose filter or sort includes a derived value, the total's provenance is traced to the set the page is sliced from; the store count appears exactly once and its result is consumed; the per-item resolution input is the page, or the full set when a derived filter is present.]

**BHE-M16**: Every unit of work that issues datastore commands — an HTTP request on any router or host, work detached from a request, and each unit of scheduled or queued work — **MUST** run inside the runtime repeated-read detector's measured scope, and that scope's summary **MUST** be classified and reported by the same single reporter as request scopes; a datastore client that bypasses the observed driver is forbidden. Reason: **BHE-M13** has no static fence, so a path that is measured but never reported, or not measured at all, lets an N+1 ship invisibly. [Verify: for each new entry point, route, job and detached work item, its commands appear in a reported scope summary.] The measured scope added for **BHE-M16** **MUST** be observation-only: it **MUST NOT** turn on a read memo or change any read's result in the unit it measures. Reason: a memo introduced by detection changes what the unit reads (pre-write values, hidden repeats) and so alters both behaviour and the very counts it reports. Process startup is one more unit: commands issued before the process starts serving and outside any other unit **MUST** be measured in a boot unit that is closed and reported when serving starts. Reason: boot runs once per deploy, so a boot-time loop is otherwise never seen. Every command **MUST** fall into a unit: a command outside every live unit — no unit scope, or a unit whose summary was already written (work after the response or after the unit settled) — **MUST** be counted in a process-wide outside-unit window and reported per call site with its own registered `SYSTEM` code, never dropped, and the window's summary **MUST** be written when the window elapses even if no later command arrives, and at process shutdown before the crash reporter drains; the request unit **MUST** open before the first layer that issues commands; a request whose client left before the response **MUST** report the commands its handler issues afterwards as a second summary of the same request, a tail holding only unit starts included; a unit that starts another unit **MUST** count each start as a value-free `detach <class>` shape in its own summary, so a per-item spawn is a repeated shape like a per-item call; and a maintenance script **MUST** run as a measured unit reported at process exit, a maintenance entry's summary carrying its success or failure. Reason: each child unit or orphaned command looks small on its own, so an unmeasured command or a per-item spawn is exactly where an N+1 ships unseen. Outbound provider calls (HTTP clients observed at the runtime's diagnostics channels, never by wrapping each client) **MUST** be counted in the same unit summary as datastore commands, and a client-driven repeat — one actor calling the same route template on many distinct resource paths in a short window, each call its own unit — **MUST** be counted in a window shared across instances. Reason: a per-item provider call or per-item HTTP request grows round trips with the set exactly like a per-item read, but no single unit's datastore counters can see it. Each counted provider call **MUST** also carry its duration (request created → response headers or failure) into the unit's time totals and shape totals, and every non-HTTP unit **MUST** emit the same access summary as a request (duration plus per-store counts and times, slow tier as a WARN symptom). Reason: a count without milliseconds cannot say whether a slow unit waited on the store, the cache or the provider. A unit's deliberate wait (debounce, settle delay) **MUST** go through the lifecycle's declared-wait primitive and **MUST** be excluded from the reported duration. Reason: a scheduled delay counted as duration reports every run as slow, and when that WARN itself re-arms the unit (an observability flusher) the loop never stops.

## **MUST NOT**

**BHE-N5**: **MUST NOT** treat a per-item query as absent because the loop body calls a helper rather than a model — what counts is the round trip the helper performs, one or two files away. **MUST NOT** "batch" by dropping the per-item filter and post-filtering a tenant-wide read in memory when the request needs one subject; a batch loader keeps the filter it replaces. **MUST NOT** keep the single-item loader and the batch loader as two independent implementations.

**BHE-N6**: **MUST NOT** report a paginated `total` computed from an over-fetch window, and **MUST NOT** issue a count query whose result is discarded (**BHE-M14**). **MUST NOT** keep an over-fetch factor on the branch that has no in-memory filter to absorb it. **MUST NOT** let a page's slice be cut by a store-side `skip` when a derived filter is applied after it — the slice moves to after the filter, over the full matched set.

## Enforcement guidance

Where builders that consume the same resolved documents appear together in one function, a project may enforce **BHE-M13**(c) with a static check that each receives the shared result. Scope the check to builders that actually consume the shared entity and to calls within one function body; a syntax tree cannot infer that an arbitrary parameter carries the shared documents, nor can it prove that calls in separate functions belong to one request. Treat any name-based builder inventory as incomplete unless the project has a maintained authority for that inventory. The harm is duplicate-read performance cost, so the check is optional.

An under-bound `Promise.all` destructuring (**BHE-M14**(b)) is statically decidable when the array literal and binding pattern are in the same file. Require deliberate omissions to be written as elisions (for example, `const [, value] = await Promise.all([sideEffect(), readValue()])`) and permit a rest binding where it accounts for the remaining results. This expresses intent at the call site without requiring a checker to inspect callee return contracts. A check should cover both declaration and assignment forms and should state its limits for spreads, non-literal arrays, and callback-based destructuring; leave over-binding to the type system when tuple types already reject it. This syntax lock does not prove **BHE-M14**(a)/(c): page-total semantics and derived-filter presence remain consumer facts.

Do not infer N+1 from syntax alone (**BHE-M13**). A loop may intentionally page through a large set, drain a queue, or process a transaction sequentially, and paging/drain and independent job or transaction loops share the same syntax as per-item request reads. Deciding whether a call performs I/O through helpers and whether it runs on a synchronous request path requires call context that may span modules and entry points; a function shared by a scheduled job and an HTTP handler cannot be classified by its name. Unless the architecture exposes machine-readable request-path metadata and the full call chain, retain review and the runtime detector as the stated enforcement limit rather than adding a broad loop rule that flags valid work.

**BHE-M16** is review-held: scope coverage is a runtime wiring fact (which scopes the reporter receives) that a single-file check cannot prove.
