## **MUST**

| ID | Rule |
|----|------|
| **NCM-M1** | Single resolver module: A canonical display name (`firstName` / `lastName` or project-equivalent fields) for a given tenant or organizational context and canonical identifier must be produced by one documented domain entry point. Its module path and return shape are defined by the adopting system's architecture and remain stable for consumers. |
| **NCM-M2** | Priority tiers (company + identifier context): First establish which stored sources own or are explicitly eligible to seed the display-name datum for this consuming contract; sharing an identifier does not make two different name semantics interchangeable (**SSG-M8**). Then apply strict order among eligible sources: (1) company-scoped primary entity for that identifier if present — use its stored name fields; (2) other company-scoped entity tier as documented in architecture (second rank in domain); (3) global user record only where the documented authority contract explicitly permits that record as a source for this same display-name semantic; (4) explicit caller/form/device fallback permitted by the consuming contract. A global account/profile name is not automatically eligible merely because it exists. If the surface promises the name recorded by a company, an account/profile name must not fill an absent company name; return absence per **NCM-M13**. A write may explicitly use an allowed seed input when creating the first company record, but a read must not silently treat that seed as an already recorded company name. Lower eligible tiers must not override a non-empty resolved name from a higher tier on create (**NCM-N1**). |
| **NCM-M3** | Fallback only: Caller / form / device input is fallback tier only — user input is not authoritative over higher tiers when those tiers yield a non-empty name (same person must not appear under conflicting names by skipping the resolver). |
| **NCM-M4** | Canonical identifier definition: Project architecture must name the identifier key(s) per flow (E.164 phone, email, composite tuple, etc.). The resolver and callers must use only those keys for matching and lookup. If not documented for a new flow, **NCM-C5** applies. |
| **NCM-M5** | Normalization minimum before compare or persist as part of identity / name resolution: (1) trim whitespace; (2) case folding rule per identifier type (document in architecture — for example lowercase email, canonical phone per phone standard when migrated); (3) Unicode normalization (default NFC for display name strings unless architecture documents a different form with reason). Same logical identifier with different surface strings (for example `ahmet` / `Ahmet` / `AHMET` under the same email rule) must match per documented rules — no ad hoc string equality without those steps. |
| **NCM-M6** | Authority (no dual masters): For a given resolution call, the authoritative display name is exactly the output of **NCM-M1** after **NCM-M5** and the eligible-source tier walk **NCM-M2**. Stored tier-1 company entity fields are authoritative for that company datum. A global user record may supply a name only when its eligibility for the same semantic is documented under **NCM-M2** and no higher eligible tier supplies a non-empty name; it is not a second master of a separately owned company record. If eligible tier-1 and global-user names disagree, company-context resolution prefers tier-1 per **NCM-M2** unless architecture documents a screen-specific merge for that same datum (must still cite default **NCM-M2** as baseline). A documented create-time seed does not imply read-time authority, and two name semantics must not be merged merely because their identifier matches. |
| **NCM-M7** | Post-create edit, cascade, and conflict on mutation: For each entity type that exposes mutable name fields, architecture must document: (a) whether end users (or admins only) may change the name after create; (b) on permitted change, whether denormalized copies elsewhere cascade synchronously, lazy re-resolve on read, or stay until batch job — no implicit cross-entity behavior. Until (a) and (b) exist for that entity, STOP shipping APIs or UI that mutate those name fields (**NCM-N4**). Default if architecture is silent on cascade: only the edited row changes; consumers re-resolve per **NCM-M8** or use documented snapshots with invalidation. |
| **NCM-M8** | Read-time vs write-time: On create / invite, persisted name must come from the resolver (**NCM-M1**–**NCM-M3**). For lists and detail screens, displayed name must be sourced by either (a) a read path that invokes the same resolution rules (API or shared library) per row or batch equivalent, or (b) a denormalized field documented in architecture with explicit invalidation (event, mutation hook, or bounded TTL with documented staleness risk). Must not mix ad hoc form labels and resolver-backed data for the same logical person without documentation. A current canonical name copied into a durable record is resolved inside the same database transaction as that record, after taking a persistent conflict fence shared with every identity-rebinding writer. A pre-transaction cache/name candidate and a cache generation acceptance are not proof of the durable subject's current identity. Where the identity writer must continue for a closing aggregate while new records are forbidden, fence the still-open aggregate without turning the closing branch into a new product rejection. Enforcement limit: the shared database write and required session are the runtime/type mechanisms; the cross-file inventory of rebinding and materialization writers remains review-bound (**ENA-A1**(c)). |
| **NCM-M9** | Performance: The resolver must not introduce unbounded N+1 queries in list contexts at scale without a documented mitigation (batch lookup API, JOIN strategy, or cache with invalidation on name or identity-link mutation). Indexes required for lookup keys (**NCM-M4**) must be stated in architecture or data model docs. |
| **NCM-M10** | Event-time name snapshots are a separate semantic: An explicitly documented immutable event-time name snapshot is not the current canonical display name from **NCM-M1** and is intentionally not invalidated by later name edits. A consumer that requires that historical semantic must read the stored snapshot only and fail loud when it is absent; it must not silently call the current-name resolver as a runtime fallback. If rollout data predates the snapshot, a one-time migration may materialize a currently provable entity name only when its exact tenant + entity association and non-empty value are proven before any write. The migration and product documentation must label that value as current-state materialization, not reconstruction of the historical event-time name; strict snapshot-only runtime reading may activate only after dry-run, apply, and post-apply missing-count proof. That activation proof is stated against the unresolvable residue, never against the missing count reaching zero. A materialization whose only lawful source is a foreign row repairs nothing once those rows are gone, so a gate worded "missing → 0" can never open, and the migration's own post-apply assertion is `remaining == unresolvable`. Residue rows are permanently unfillable and are therefore routed to **NCM-M13** — the read keeps the row and its non-name data and omits the field — never held open as a blocker and never closed by writing a value (**NCM-N6**). This is what decides between M10's fail-loud and **NCM-M13**'s keep-the-row: the boundary, not the field. A write refusing to create a *new* record without a snapshot is M10/NCM-M11; a read refusing to serve *existing* rows because one of them predates the snapshot converts a display gap into total denial of the surface, and is **NCM-M13**'s case. *Stated enforcement limit:* no static check decides this — it needs, per snapshot field, whether a residue row's source still exists, which is production data present in no source tree; enforcement is the migration's own post-apply assertion plus review. |
| **NCM-M11** | Event-time snapshot write side — one derivation authority, written on every path, unconditionally: When a record carries an event-time name snapshot (**NCM-M10**), the snapshot text must be produced by exactly one documented derivation entry (the write-side twin of **NCM-M1**), and every path that creates the record or changes the referenced identity must call it — single create, bulk/batch insert, re-assignment, and any re-materialization path alike. The write must be unconditional for the resolved identity: a snapshot written only for one identity shape (for example only the secondary/unlinked identity, or only when an optional identity field is populated) leaves the remaining records permanently unlabelled, which is a defect, not an optimization. Derivation must fail loud when no source yields a non-empty value; writing an empty snapshot, a placeholder, or a fabricated label is forbidden (**NCM-N6**). Enumerate the paths with the type checker, not by reading: where the write paths share a record/document builder, the snapshot must be a required (non-optional) input of that builder — an optional field silently permits any path to skip it, and "which paths write this record?" then depends on manual search. Making it required turns every unwired path into a compile error, so the path list is produced by the compiler and cannot drift; when the value may legitimately be absent, express that as an explicitly-passed empty value, never as an optional parameter. Where a builder is untyped or bypassed, the same obligation must be enforced by a static rule instead. |
| **NCM-M12** | No parallel snapshot path: Once **NCM-M11** write-time snapshotting exists for a field, any second store of the same semantic — a legacy duplicate column, or a "freeze the name just before the source row is deleted" pre-step — must be removed in the same change that introduces the authority, with existing data migrated into the single field (**NCM-M10** materialization rules apply to that migration). Two stores of one display semantic drift and label the same subject differently on different screens. Rationale from field failure: a delete-time freeze step only matches the rows whose identity shape it was written for, so it silently covers 0 rows for the other shape, and it cannot run at all once the referenced account is erased through an unrelated flow. |
| **NCM-M13** | Absent snapshot is displayed, not hidden and not invented: When a required event-time snapshot cannot be produced for a legacy row, the read path must keep the row and its non-name data (amounts, counts, status) and surface the absence as an explicit, localized marker at the presentation boundary. The backend must not embed a hardcoded display string for this case; it omits the field, and each render surface (server-rendered document, server-composed notification body — resolved per RECIPIENT, in the recipient's language, before the body is assembled — API text field the client draws verbatim, resolved in the requesting user's language through the registered reader-language authority — client screen) resolves the marker from its own translation catalogue in the viewer's language; every server edge of one marker reads one label authority (**SSG-M8**). Dropping the row, returning a fabricated name, or emitting a single-language literal from the data layer are all forbidden (**NCM-N5**, **NCM-N6**). |

## **MUST NOT**

| ID | Rule |
|----|------|
| **NCM-N1** | On create / invite, must not prefer form / device / caller fallback name when a higher tier in **NCM-M2** yields a non-empty name — forbidden. |
| **NCM-N2** | Must not match or deduplicate identifiers without **NCM-M5** normalization steps documented for that type — forbidden. |
| **NCM-N3** | Must not scatter alternate precedence or duplicate resolver logic in handlers outside the **NCM-M1** module family — forbidden (single center — gray M1 intent). |
| **NCM-N4** | Must not ship mutations to name fields where **NCM-M7** (a) / (b) is undocumented for that entity — forbidden. |
| **NCM-N5** | Must not present a current-state migration materialization as a historical event-time name, or hide a missing required historical snapshot with a current-name/raw-identifier/placeholder runtime fallback — forbidden (**NCM-M10**). |
| **NCM-N6** | Must not write a deterministic placeholder ("Unknown", "N/A", an id, an empty string) where a name resolver or snapshot derivation failed, in any layer — resolver return value, persisted field, DTO, report row, or notification body. A batch resolver must express "not resolved" as an absent entry so every call site decides explicitly (fail loud / documented omission with observability / localized marker per **NCM-M13**); a shared placeholder makes a missing person indistinguishable from a real one and silently spreads into persisted data — forbidden. An empty name is not automatically a failure, and the discriminator is the CONSUMING CONTRACT, not the resolver. Where the product legitimately allows a record to carry no name, the resolver returning the empty value is correct and must not be turned into a raise — the same helper serves surfaces that tolerate the gap. Where a consumer's contract declares the name required (a schema field constrained non-empty, a document column that would otherwise print a nameless row), the empty value **MUST** be rejected at the resolution authority, with the record's identifiers in the raised context — not left to travel down to the boundary validator. Both endings fail, so this is not a choice between loud and silent; it is a choice between a diagnosable failure naming the record and an opaque schema error two layers away that says only that a string was too short, from which the offending record cannot be identified. When one resolver serves both kinds of consumer, the required-name gate is a thin surface wrapping the shared resolver, so the rule has exactly one writer ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)) and the tolerant consumers keep the tolerant path. *Stated enforcement limit:* no static check decides this — the predicate needs, per call site, whether that consumer's contract requires the name, which lives in a different file (the schema) from the call; a single-file syntax tree sees only a resolver call, and a whole-tree check would have to infer call-site → DTO → field constraint. Enforcement is this rule plus review at the point a report/document field is added. That limit covers the CHOICE, not the PLACEMENT — placement IS mechanical. The wrapping gate is a named export, so which files reach the raising ending is decidable from one import list: fence it to a declared set of write-path files and every other module — including new ones — fails on import. Scope by the ALLOWED write paths, never by naming today's readers, or the next reader inherits the hole ([**SEC-M-ZT-6**(b)](../security/security-actor-class-gates.md)). |
| **NCM-N7** | Must not constrain a human name input field (given name, family name, or equivalent) to a language-specific alphabet whitelist — forbidden. A character-class pattern enumerating one or two scripts (for example ASCII letters plus the writer's own diacritics) rejects the legitimate names of every other script the product serves — Arabic, Chinese, Japanese, Korean, Cyrillic, Greek, Devanagari — and additionally rejects punctuation that is ordinary inside Latin-script names (hyphen and apostrophe: `Anne-Marie`, `O'Brien`). The defect is silent in the authoring locale and only surfaces as a rejected write for other users, so "it passes our tests" is not evidence. Permitted constraints on a name field are the script-neutral, safety-motivated ones only: trimming, a maximum length, and an emptiness/required decision. Any narrowing beyond those is a product decision requiring the owner (**NCM-M7** (a) discipline), never a validator-authoring convenience. Where "valid name" is stated in more than one layer (request validator, schema, persistence constraint), the layers must resolve to one invariant per [SSOT **SSG-M8**](../ssot/ssot-principles-and-precedence.md) / [**SSG-M16**](../ssot/ssot-must-access-and-schema.md) — two layers disagreeing on the accepted character set is the same defect twice. A name SEARCH-term acceptance pattern is the same class: it **MUST** admit every character a stored name can carry — combining marks (Devanagari vowel signs, Arabic harakat), the typographic apostrophe phone keyboards substitute for `'`, and in-name periods — because a rejected term reads as "no match" for a name that exists. The search fold **MUST** map those optional variants (typographic vs ASCII apostrophe, Arabic harakat and tatweel, ZWNJ/ZWJ) to one key on both the query and the stored-key side, because a name saved with one variant and typed with the other otherwise never matches; a term that folds to empty **MUST** be rejected by the format, not reach the query; and a fold change **MUST** rebuild every stored folded key, because a key derived under the old fold silently misses the new query. [Verify: inspect name-field validators for character-class patterns; a per-script fixture review is not required to prove the rule.] |
