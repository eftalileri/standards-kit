## Definitions

| ID | Definition |
|----|------------|
| **I18N-RN-D1** | Selected localization stack means the single translation engine and locale source chosen for the application. Expo Localization and i18next/react-i18next are common Expo options, but the adopting project selects compatible maintained packages and records its locale authority. |
| **I18N-RN-D2** | App string means any user-visible UI text that is not sourced from [locale names](../locale-names/country-currency-ui-display.md) LCN-\* resolution of ISO codes. |
| **I18N-RN-D3** | Outbound string means an app string the product composes for the user to send onward (share sheets, messaging deep links, clipboard payloads, mail/SMS bodies). It is an app string: it is authored in the sender's app language and is subject to every rule below — except where the product holds a registered authority for the reader's language (a recipient the product messages, whose own language preference the server already resolves): then the string is authored in the reader's language, that language is read from the authority and never guessed (phone prefix, device locale) or re-derived at the call site, and the reader's language is a required input of the composer (**I18N-RN-M4**). A string whose reader the product does not know (share sheets, invitations) stays in the sender's language. |
| **I18N-RN-D4** | Fixed-language fallback means emitting a user-visible string in one hardcoded language (a literal in code) when the translator or the resolved locale is unavailable, instead of failing. It is a silent language downgrade: a user of language X receives language Y. |
| **I18N-RN-D5** | Placeholder substitution engine means the one code path that replaces variable placeholders inside a resolved translation string with runtime values. Its placeholder syntax is the exact textual shape it recognizes (for example single braces `{name}` versus double braces `{{name}}`). A catalog is the set of translation resources that engine reads. Unresolved-placeholder guard means any check that inspects produced text for placeholders left unfilled. |

## Agent execution contract

| ID | Rule |
|----|------|
| **I18N-RN-C1** | Keep one localization engine and locale authority. Replacing the selected stack (**I18N-RN-D1**) requires a documented compatibility and migration decision that preserves existing catalog, interpolation, pluralization, and RTL behavior. |
| **I18N-RN-C2** | When adding languages, **must** update translation resources and verify pluralization and RTL behavior for target locales per product requirements. |

## **MUST**

| ID | Rule |
|----|------|
| **I18N-RN-M1** | New React Native/Expo app strings **MUST** use the application's selected localization stack (**I18N-RN-D1**). |
| **I18N-RN-M2** | **MUST** derive device locale signals through the selected platform localization API (Expo projects may use `expo-localization`). **MUST** persist a user-selected language in one client preference authority; the device locale is only the initial default. |
| **I18N-RN-M3** | **MUST** keep translation keys stable across releases; renames **must** be treated as migration with explicit checklist (no silent key removal). |
| **I18N-RN-M4** | Every function that produces an app string or outbound string (**I18N-RN-D3**) **MUST** take the translator as a required, non-optional parameter. A missing translator is then a compile-time error instead of a runtime fixed-language fallback (**I18N-RN-D4**). A composer whose reader's language differs from the active app language (**I18N-RN-D3**) takes that required target-language code instead of a translator and resolves the translator from it through the single client translator authority (the language's catalog loaded, then a fixed-language translator) — one parameter that cannot disagree with a second one, and still compile-time required. |
| **I18N-RN-M5** | Static labels inside an outbound string (link captions, prefixes before a URL, section headers) **MUST** live in the same translation entry as the sentence they belong to, so the block is one translatable unit and no segment is left in the author's language. Multi-segment outbound text **must** be assembled in one authority; a second assembly site is a duplicate string SSOT. An outbound text that invites the reader to install the app should carry one install link whose platform is chosen when it is opened (a device-routing redirect the product owns), not one link per store: a per-store pair makes the reader pick the right one and adds store captions that every locale **must** translate. The client then holds that one URL as one constant. |
| **I18N-RN-M6** | A catalog **MUST** have exactly one placeholder substitution engine (**I18N-RN-D5**) and exactly one documented placeholder syntax, and every placeholder in that catalog **MUST** be written in that engine's syntax. Every runtime value **MUST** be supplied as input to that single call; translated output **MUST NOT** be post-processed with a second replacement mechanism. An unresolved-placeholder guard **MUST** speak the same syntax as its engine and run only after substitution: a guard whose pattern also matches an unsubstituted form of the engine's syntax fires before substitution and turns correct data into a hard failure. When a product runs two catalogs with different engines (for example a client i18n library using double braces and a server catalog using single braces), each catalog keeps its own syntax and any mechanical check **MUST** be scoped to the catalog it belongs to — never applied across both. A translator whose signature accepts no variables forces the substitution to the call site — the signature is the defect, not the call. A lookup typed `(key) => string` over a catalog that contains placeholders leaves the caller no legal way to fill them, so the second engine appears as a `.replace()` on the translated output and looks like a local shortcut rather than the architectural break it is. The fix is always the signature — accept the variables and interpolate inside the one engine, failing loud on a placeholder left unresolved — never a tidier `.replace()`. A check over this class **MUST** match the placeholder argument in every supported literal form and argument overload of the selected engine, not only the regex one: a `.replace('{n}', v)` string argument is the commoner spelling, and a regex-only predicate leaves the rule running, configured and blind — the "configured but not covering" failure **FP-M20**(c) names. |
| **I18N-RN-M7** | A bootstrap gate that **must** start the translation layer before the language authority has resolved **MUST** treat the language it uses as a display-only provisional value. It **must** prefer the authority and validate it before use (persistence layers commonly rehydrate stored state without re-validating it, so an unsupported code can reach the store typed as a valid one); it **must not** open a second resolver over the same persisted data (reading the raw persistence blob beside the store is a parallel reader — **SSG-M8**); and it **must not** write its provisional choice back into the authority. Rationale: the translator needs *some* language to render the loading and error surfaces at all — an uninitialized translator resolves every key to nothing, so a failed startup cannot even display its own message (readiness [**M17**](../ssot-readiness/readiness-writes-outcome-and-seed.md)). That display need is not a user preference: writing it to the authority silently converts an unusable stored preference into an accepted one and destroys the fail-loud contract of **I18N-RN-N7**. Resolving and validating the stored preference stays with the single language-write path, which fails loudly when it is unusable. |
| **I18N-RN-M8** | A runtime language-change operation **MUST** publish the persisted/client language authority and its derived locale/RTL settings only after the translation engine reports success. The awaited operation is the single write authority and **MUST** preserve a translation-engine rejection unchanged for readiness/session owners; a synchronous or detached UI facade **MUST** delegate to that operation and own rejection through the canonical no-throw client-observability boundary. A lower translation helper **must not** absorb the rejection, a detached facade **must not** leave it unhandled, and the two facades **must not** carry duplicate authority writes (**SSG-M8**; client observability [**COB-RN-M6**](../client-observability-rn/classification-authority-and-outbound-links.md) / [**COB-RN-M11**](../client-observability-rn/silent-failure-paths.md)). |
| **I18N-RN-M9** | A locale guard **MUST** derive its required keys and placeholders from the live translated consumer path it protects and the selected engine, not from dead catalog keys or historical surfaces. A catalog entry with no reachable translation lookup is not product authority and **MUST NOT** make a guard green or red. Every reachable consumer in the protected feature **must** be inventoried; each required key **must** exist in every supported language and carry the exact placeholder set expected by that catalog's substitution engine. Client and server placeholder syntaxes remain disjoint under **I18N-RN-M6**. Because key/placeholder parity is a cross-file property, review or project checks **must** cover the catalog registry, resource files, and live consumers without claiming single-file coverage; single-file checks may additionally lock consumer calls and server catalog values to their canonical runtime field. |
| **I18N-RN-M10** | A numeric limit that code enforces **MUST NOT** be written out inside catalog text; it **MUST** reach the sentence as an interpolation value read from the single constant that enforces it. A number typed into the sentence is a second authority for that limit (**SSG-M8**): raising the limit in code leaves every locale asserting the old figure, and the reader is refused for a reason the text denies. The conversion order is binding, and it is the half most often got wrong: the call site **must** supply the value BEFORE the catalog gains the placeholder. Under the common engine default of skipping unresolved variables (for example i18next `skipOnVariables: true`), a placeholder no caller fills does not render empty — the raw `{{max}}` is drawn on screen, in every declared language at once. The two halves are therefore one change set and **MUST NOT** be split across tasks or file-ownership boundaries. Where the call site is out of reach, the catalog **MUST** be left exactly as it stands and the debt recorded as an observation: converting the catalog alone trades a stale number for a broken sentence, which is a regression, not a partial fix. A registered error's message reaches its sentence through no call site of its own, so its constant **MUST** be bound to the code once, as a message variable in one code-keyed table, read by one function that both the server boundary and the client error catalog call — otherwise the two catalogs state the limit independently. |
| **I18N-RN-M11** | A translator bound to several namespaces **MUST** look a key up in every namespace it declares, in the declared order, and that mode **MUST** be set once in the translation engine's init configuration (for react-i18next, `react.nsMode: 'fallback'`). A translator that declares no namespace **MUST** bind the single default-namespace constant the init's `defaultNS` reads — never a list kept for another purpose. Reason: react-i18next's default mode binds only the FIRST declared namespace, so a key the author placed in a later declared namespace renders as its raw key, or as the caller's fallback text, while every catalog and every source check that assumes the declared set reports it resolvable. Because the engine tries each namespace across the whole language chain before the next, a key the first namespace holds renders identically in both modes. A check that models key resolution **MUST** read the mode, the default namespace and the no-argument binding from their sources, never assume them ([**I18N-CAT-M4**](user-text-catalogs-and-parity.md)(c)). |
| **I18N-RN-M12** | A sentence whose wording depends on a number **MUST** select its form by that number's CLDR cardinal plural category in the sentence's own language, read from the single plural-category authority, on the client and the server alike. The selector is the `count` variable as a finite number: a template whose number has another placeholder name keeps it and the caller also passes `count` = that number; a number passed as text selects nothing. Forms are sibling keys `<key>_<category>`; the bare key holds the `other` form and is the fallback; `_other` is never written. A key with any sibling carries every non-`other` category of its language, and no category outside that language's set (`_zero` excepted: the engine tries it at 0 in every language). Every form keeps the number, except a category that denotes exactly one integer (ar `_one`/`_two`). A sentence with two agreeing numbers names one as `count` and phrases the other so it needs no agreement; a natural label-value sentence needs no forms. On a JS engine without `Intl.PluralRules` (Hermes) the client **MUST** install, before the translation engine initialises and only when the constructor is absent, an `Intl.PluralRules`-compatible constructor backed by that authority — never a plural package, never count-independent wording as a workaround. Reason: without the constructor i18next selects only `one`/`other`, so ru/ar read wrong for most numbers while every desktop runtime looks correct. The key-set half is verified for each catalog by the adopting project's catalog check where one exists; whether a sentence agrees with its number is review-held. Locale-aware separators, weekday names and other `Intl` output follow the same test — use only constructors the engine ships, or a project-owned authority. |
| **I18N-RN-M13** | A horizontal position that crosses between a native measurement and a layout or index **MUST** be converted through the single inline-offset mirroring authority. React Native reports `onLayout` x, `measureInWindow` x, a scroll event's `contentOffset.x` and ScrollView `scrollTo({ x })` physically (from the left) also in right-to-left layout, while a `left`/`start` style binds to the start edge and page/tab/card indices count from the start. Reason: copying a measured x into `left`, or dividing a raw `contentOffset.x` by the page width, mirrors the result in RTL — the selected-tab indicator lands under the opposite tab, a pager reports the last page while showing the first. A transform (`translateX`) is never mirrored: a start-relative movement multiplies by −1 in RTL. A list that converts internally (FlatList/FlashList `scrollToOffset`) takes the start-relative value as is. |
| **I18N-RN-M14** | A glyph that points along the reading direction (back/forward chevron or arrow) **MUST** take its rendered name from the single directional-glyph authority; shared icon-drawing primitives resolve it, so a caller passes the left-to-right name. Reason: right-to-left layout mirrors the row but never the glyph — a "previous" button moves to the right edge while its arrow still points left. A glyph that depicts a physical direction (not "back"/"forward") stays outside the table. |
| **I18N-RN-M15** | Every user-visible date, time, number and currency format **MUST** take its BCP 47 locale from the single formatting-locale authority, built from the reader's language **and region** — on the client the device region, on the server the region of the tenant the text is about; field order, separators, digits and the 12/24-hour clock **MUST** come from that locale's `Intl` output through the single display-shape authority. A stored wall-clock `HH:mm` is shown through that authority too, never raw, and a time ENTRY follows the same 12/24-hour decision (12-hour locales type `hh:mm` and pick the day period) while the stored and wire value stays 24-hour `HH:mm`. Code **MUST NOT** force a clock (`hour12: false`, `hourCycle: 'h23'`) or assemble date parts by hand on a display path, and **MUST NOT** keep a per-language table of separators or symbol placement. Reason: a language-only locale reads `10.12.2026` as 10 December to a US reader and prints 15:00 as `03:00` once the day period is dropped; machine keys and comparisons keep their fixed formats and are outside this rule. A range of two dates or times **MUST** come from the locale's range pattern (`Intl.DateTimeFormat#formatRange`); on an engine without it (Hermes) the same authority **MUST** still print the fields both ends share once — read from `formatToParts`, kept on whichever end the locale's own field order puts them — and join the ends with the reader language's catalogue range pattern (its compact form where one end is a bare day number), never a code literal or hand-ordered parts. Reason: "12-18 Oct 2026" assembled by hand reads in the wrong order for en-US, ja, zh and ko, and two complete ends print the month and year twice ("19 Oct 2026 – 25 Oct 2026"). A language+region tag the runtime does not resolve to that same language and region **MUST NOT** be returned by that authority, nor one the engine does not list as supported; it **MUST** be replaced by the language's served variant whose date field order and 12/24-hour clock equal the region's own (read from a served locale of that region), and only when none matches by the language default. Reason: a best-fit matcher (Hermes on Android) resolves an unserved pair such as `en-TR` to the device locale, so every month and weekday name silently comes out in the device language, and a runtime that drops the region formats a day-first, 24-hour region month-first with a 12-hour clock. Review-held. |
| **I18N-RN-M16** | The first day of a calendar week **MUST** come from the single region week-start authority with the region of the calendar's owner (CLDR `weekData`), and every surface of that calendar (grid, date picker, "this week" ranges on client and server) **MUST** read the same value; a cycle that is not a calendar week (a fixed 28-day recurrence anchor, an analysis bucket) **MUST** name the ISO week explicitly. Reason: a Monday-fixed week shifts the visible week and every "this week" total by one day for Sunday-first regions, and two readers of different regions would otherwise disagree on the same week. Review-held. |
| **I18N-RN-M17** | User-visible names **MUST** be ordered with the single reader-language collator — the app language on the client, the output's language (report or tenant language) for an order fixed on the server; code **MUST NOT** hardcode a collation language or rely on the runtime default. Reason: one hardcoded alphabet sorts every other language wrong (Turkish `Ç` after `C`, Swedish `Å` after `Z`) and the runtime default is the process locale, not the reader's. Review-held. |
| **I18N-RN-M18** | A distance **MUST** be computed and carried in metres and shown in the unit system of the reader's region read from the single distance-unit authority; choice steps (search radius) **MUST** be whole units of that system. Reason: a kilometre-only display is unreadable at a glance where road distances are in miles. Review-held. |

**I18N-RN-M7** persistence clarification. An absent preference and a present-but-unusable preference are different outcomes. A persistence library's precisely identified empty-state envelope is a no-preference result only when it contains no preference at all; the single record-validation authority recognizes that exact library-owned shape and version, and every persistence and raw-initialization reader consumes the same result. For a released library envelope of `{state:{},version:1}`, the predicate is exact: a non-array object containing exactly the `state` and `version` keys, an empty non-array state object and version exactly `1`. It is historical middleware metadata/reset serialization of an unresolved preference, not a corrupted stored language. Other invalid JSON, invalid envelope/state shape, missing language outside that exact empty envelope, an explicit null/empty/unsupported language and native storage unavailability retain failure. They **must not** become a successful device preference. The no-preference result follows the existing startup device-language policy without deleting the record, skipping hydration, inventing an authority value or broadening a catch. One exception: when the storage package itself failed to load for the process (**MMI-M10** — permanent, already reported once by the load authority), reads **MUST** resolve as no-preference and preference writes as memory-only successes. Reason: the fail-loud contract protects a stored preference from being overwritten by a provisional value, but with no storage for the rest of the process nothing can be read or overwritten, and failing would leave that binary on a startup failure it can never leave. A store whose package loaded but whose construction failed keeps the failure, because its one bootstrap retry (**MMI-M8**) can open it later in the same process.

Persistence middleware's automatic readiness/reset writes are not preference operations: they cannot create an unresolved preference record or replace a corrupt record, even when memory retains an older supported code. The write boundary requires a supported resolved code and no unresolved read failure, except an explicitly declared supported user choice or fresh typed server-user preference recovery. The persistence rehydrate and raw initialization paths enter the SAME read-settlement authority. Overlapping included attempts are joined; the language operation waits for all of them to settle before its guarded write boundaries, rather than treating the latest completed attempt as proof that an earlier read ended. The raw reader publishes its original Error to the existing memory-only read failure before rethrowing. Pending/error middleware guards prevent that metadata publication from writing the blob. No second native reader, preference state, clock or epoch is introduced.

Recovery carries the SAME current operation assertion and a supported preference equal to the requested output. A guest's explicit device choice uses the existing auth-lifetime assertion together with mounted/latest-selection ownership; it **must not** fabricate an authenticated session handle. Tenant/device/cache fallback is never corruption-recovery evidence. A read boundary that intentionally degrades native errors to null retains that generic contract but exposes one typed PII-free value/absence/unavailability outcome to its readiness consumer. Only a successful native read proving no key establishes physical key absence; the exact library-empty record establishes no preference, not physical absence. Native unavailability establishes neither. The narrow preference adapter delegates to that same reader and carries failure to the existing initialization/retry owner. A generic native no-op writer retains its degraded contract but exposes one typed written/unavailable outcome; a no-op is not successful preference persistence. The narrow adapter consumes the same native writer and rejects unavailability without opening a second write path. Already-owned native errors are not reported twice.

A blocking preference-startup failure exposes an actual supported user choice through the existing single awaited language operation. The recovery surface observes the current read failure and latches recovery for its own mounted error-view lifetime, including a language failure arriving after another startup error displayed. Clearing memory error metadata before durable acknowledgement **must not** unmount or cancel its pending repair. The chosen language's catalog, translation-engine success, locale/RTL projection and actual preference persistence precede initialization retry. Choosing the same language is still a real repair and **must not** take a detached facade's equality shortcut. During the pending operation both selection and manual retry are unavailable through pointer and accessibility interaction. Native write failure retains failure and localized actionable feedback; it does not unlock startup through a false success.

Once preference write acknowledgement is known, that error surface locks selection and save; only the existing initializer callback may be retried. A callback failure is a separate contained continuation failure: it preserves the acknowledged preference and exposes manual retry without rewriting it. Auth/lifetime cancellation suppresses obsolete UI and initialization completion, but an unowned real engine error remains observable through the same observed-aware terminal authority even if the UI operation has become stale. The original Error remains the reporting input; a new error copy, classifier or second crash-reporting path is not introduced. Rehydrate failure is memory-only, retry reruns the failed read, and a legitimate successfully persisted language operation clears the failure. Enforcement limit: no static fence is admitted for this one-authority corruption path (**ENA-A1**(a)/**ENA-A2**); typed outcomes, the validated write adapter and narrowed merge are the stronger runtime boundary (**ENA-A4**). Language-literal checks do not prove JSON/state/outcome, complete overlapping-read settlement, middleware/native acknowledgement, mounted control ownership or callback ordering; use the enforcement mechanism the adopting project documents, and record its actual scope and limits — a reference to a check is not evidence that it exists or covers the full rule; source review traces those relationships. This is not physical-device success or fleet evidence.

**I18N-RN-M8** authority-precedence clarification. Bootstrap and background
settings refresh pass the same tenant-language and current user-preference
inputs through the registered resolver before invoking the single language
operation. A branch without an active tenant still delegates its documented
startup/default input to that operation and cannot bypass a valid preference.
A timezone-only settings refresh cannot override valid user preference with
company language. The settings snapshot used to detect freshness is an input
snapshot, not the resolved displayed language. An accepted server preference
command publishes its returned preference to the client account mirror before
applying it to the translation engine; pending refresh writers re-prove that
their preference input remains current. The awaited operation consumes
the persistence middleware's actual write result as well as the translation
engine result, so a rejected write is not detached or presented as success.
Enforcement limit: shared resolution holds the runtime choice; arbitrary
call-graph preference semantics and middleware return propagation stay
review-bound. No path-named check is admitted in place of that proof.

## Stated enforcement limit — a number embedded in user text

**I18N-RN-M10** has two halves with different enforcement status; state which half a check covers rather than assuming both.

The SUPPLY half — a declared placeholder no caller fills — can be checked by a guard that derives from the reference catalog every key declaring a placeholder and fails when a translator call on that key omits it — the ordering regression **M10** names. The binding is derivable — the same key is written literally at both ends — so no hand-kept table can go stale. Such a guard's baseline ceiling is 0 (**FP-M18**). Use the enforcement mechanism the adopting project documents; a reference to a check is not evidence that it exists or covers the full rule.

The NUMBER-IDENTITY half is not mechanically checkable by a value-only predicate. The obvious predicate — "the value of a named numeric constant appears bare in a catalog string" — is cross-file, so it would be an aggregate guard rather than a single-file rule, and it does not survive measurement on a real catalog set: values such as `0` and `1` match version and minimum-count constants against unrelated sentences, so the findings are dominated by false matches. A number carries no identity: the value is the one part of a constant that says nothing about which constant it is, so a value-only predicate is not a noisy rule to be tuned — it is the wrong predicate. Opening it would seed a rule born red, which [**FP-M18**](../false-positive/check-design-rules.md) forbids.

What a check would need in order to exist. A binding from the catalog key to the constant — not from the number to the number. That binding **must** be derivable, because a hand-written key-to-constant table is exactly the manually maintained list that goes stale in silence (**I18N-CAT-M4**(c); **SSG-M8**), and a stale table reads as coverage. Two shapes could supply it: a naming convention strict enough to be machine-checked in both directions, or a registry that the call site itself is locked to. Until one exists, this half of **M10** is carried by review.

## Stated enforcement limit — per-language terminology

There is no canonical per-language term authority in this kit. Every rule above binds the *mechanism* of translation: one stack, one placeholder engine, one language authority, no fixed-language fallback. None of them binds the *wording* — which noun a language uses for a domain concept, or its register / form of address.

A catalog may carry two words for the same concept in one language — regional variants are the usual case — while every gate stays green. That is a known, accepted limit, not an oversight.

What a check would need to exist. All three are missing until the adopting project decides them; a check built on fewer would be guessing:

1. A term table — per supported language, the canonical term for each domain concept, plus that language's register / form of address. This is a product decision, not a derivation: it cannot be inferred from the catalogs, because their disagreement is exactly the defect being measured.
2. A key-to-concept mapping — which translation keys express the same concept, so the checker knows which entries to compare across languages. Keys are normally grouped by screen, not by concept, so this mapping does not fall out of the catalog structure.
3. One registered authority owning both of the above, so the check reads a single source instead of re-deriving it (**SSG-M8**). Such a check compares two or more catalogs at once, so no single file's AST can decide it: it is a cross-file script guard, not a single-file rule.

Until that authority exists as a product decision, no canonical term is written here — inventing one would record an authority that does not exist and impose a rule the product never decided. The limit is written down instead, so its absence is visible rather than silent.

This limit is narrower than it looks, and two rows sit inside it. It governs a concept with no visible surface: where the product already draws the concept — a screen title, a tab, a menu row — that label is the authority and the choice is decided ([**I18N-CAT-M9**](product-term-visible-surface.md)). What happens after a wrong word is reported is a separate change-set obligation needing no term table ([**I18N-CAT-M5**](user-text-catalogs-and-parity.md)) — one change set across every declared language, keys unchanged. Reading this limit as "nothing is required here" is a misreading.
