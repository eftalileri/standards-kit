## **MUST NOT**

**N1**: Silent failure — no catch that drops errors on critical paths without rethrow or mapped API error.

**N2**: Default / fallback return values to hide missing or invalid data where **M6** requires a throw.

**N3**: Skip null/undefined checks after retrieval when the operation requires the entity.

**N4**: Omit root cause (and fix direction) from throws or API errors covered by this policy.

**N5**: Use console.log / console.error instead of the project logger for operational error reporting.

**N6**: Return API errors with only a user string and no semantic error code.

**N7**: Invent ad-hoc error-code strings outside the single registry that is the service contract; add codes through the consuming project’s documented change process.

**N8**: Emit extra keys on API error bodies not present in the shared contract (drift risk).

**N9**: Maintain a parallel status or error-response authority — no per-controller / per-domain copy of "code → HTTP status" (switch, if-chain, lookup map, or direct `res.status(...).json({ success:false, ... })` branch). Status and error envelope come only from the registry via the boundary (**M12**, **M16**), except a separately documented protocol/exact-idempotency replay boundary whose persisted response is not a new error decision.

An unreachable boundary is not a licence for the manual envelope **N9** forbids. The manual envelope is often defended in code by an observation that is entirely true: on this path the boundary handler *cannot* be called, because the response object in hand is a capture stub — a batching endpoint that runs sub-requests in parallel and collects each sub-response, an adapter, a double — carrying only the two methods its writer needed, while the boundary also reads a correlation id from the response's locals and the request from the response, and would throw on the stub. The observation is accurate and the conclusion is wrong: it describes a defect in the stub, not an exemption from **N9**. The stub is code the same team owns, and the fix is to give it the fields the boundary reads — passing the real request and the real locals *reference* through, which opens no second writer and, as a side effect, makes each sub-branch's log carry the parent request's correlation id. Two marks identify this case and both are why the debt looks immovable: the justification is duplicated into every file on the path, so one infrastructure gap presents itself as many independent decisions; and the envelopes it protects are exactly the ones a scanner reports as remaining debt, so a measured ratchet stalls against a blocker nobody re-reads. Distinguish it from the genuine constraint that usually sits beside it: where a sub-branch's failure must not abort its siblings it is right not to throw — but calling the boundary handler directly on that same stub response preserves the local flow exactly (it writes, the branch returns) while restoring the category, retryability, correlation id and single structured log the manual envelope drops.

**N10**: Embed the code or root cause inside the thrown message as a parse-prefix (`throw new Error('CODE - ...')`) and split it back out later. The code is structured identity, not a string to parse (**M13**).

**N11**: Store a `severity` field, or set log level / crash routing per call site. Level and routing derive from category only (**M15**, logging policy).

**N12**: Send expected errors (`OPERATIONAL` / `BUSINESS` — i.e. `WARN`) to crash reporting. Aggregate signal for expected errors goes to a separate metric channel (logging policy **M18**), never the crash-report channel.

**N13**: Collapse all third-party / upstream errors into a single `SYSTEM` code, or route retryable upstream / transient failures (overload / rate-limit / 5xx / timeout / connection) to crash reporting. That floods crash reporting with noise outside your control and buries the genuine (non-retryable / malformed) provider defects (**M19**, **N12**). The same collapse inside the server is equally wrong: a catch around a multi-step operation that re-wraps every failure, an already registered carrier included (for example a retryable transient conflict), into one generic code. Re-raise a carrier with its own code, adding context only; give the operation's registered code only to a value that is not a carrier. "Carrier" means every registered-code carrier of every tier — the application's and a shared tier's own carrier alike — recognised by one predicate; a wrapper that tests only the application class renames the shared tier's rejection (code, category, retryability: a SYSTEM rejection would be re-labelled as an expected read failure and leave the crash channel).

**N14**: Use optional chaining, unchecked casts, sibling-object guesses, `??` / `||` defaults, or partial-schema success to turn a malformed third-party response or a failed owner-object join into a valid inactive / success / default state (**M21**) — or return a FAILED read (non-`2xx`, transport error, truncated pagination) as an empty / `null` result a consumer then writes as complete state; it throws the **M19** carrier.

**N15**: Copy a client-supplied provider identifier or environment into a durable projection; grant server-side access from it; accept cached/ambiguous provider evidence where **M22** requires a fresh exact-match gate; persist a reusable provider reference before its environment gate; or use a stored reference for a later live provider operation without re-checking its provenance against the current runtime.

**N16**: Log authenticated push contract drift in an inner catch and then return success outside the single boundary; rewrite registry facts to manufacture an acknowledgement; acknowledge a retryable/unknown failure; or attach the raw provider payload, credential, or replayable token to the error context (**M23**).

**N17**: Infer ownership or authorization failure solely from an ambiguous provider not-found response when the same response may represent post-write propagation; discard the caller's retry path before successful provider-owned binding evidence exists (**M19**).

**N18**: Acknowledge a valid provider callback and only then create its audit/inbox record; rely on a detached promise or process memory to finish accepted work; or return `2xx` when durable acceptance failed (**M24**).

**N19**: Copy or spread typed-carrier context, operator diagnostics, request snapshots, raw identifiers, or arbitrary error properties into an API response; return endpoint-specific error data outside the single boundary; or attach data that is not backed by the shared API contract, runtime-validated, and explicitly client-safe (**M25**).

Check reach of **N19**'s client-safe clause. Three of **N19**'s arms are mechanically decidable. Two are fenced: a handler writing its own error body and a diagnostic/`rootCause` field appearing in a response body. For the third — the envelope type having a second declaration — a name-anchored rule is not admitted because a renamed copy passes it, and a local copy missing a field fails loudly at compile time where it is used. The remaining arm — *is this attached payload a shared-contract-backed, client-safe DTO?* — is not decidable from one file's syntax tree, and saying otherwise would present a partial fence as a complete one. The check would have to follow the argument's type across modules to the shared schema that defines it, which one file does not contain. The correct reduction is not a bigger checker but a narrower type: make the parameter accept only a type that nothing but the runtime validation can produce — a schema-parse output, or a branded type minted solely by the validator — so that attaching an unvalidated object stops compiling and the compiler, not a lint pass, becomes the proof. Where the project has not yet done that, this arm is review-bound, and the review question is the provenance of the value, never its shape at the call site. A cross-file checker is the wrong answer here even though it could work: it would re-derive, less reliably, a fact the type system can carry exactly.

**N20**: Let a throttling / transport middleware answer with its own hand-written error envelope, register an unregistered code for it, duplicate the same throttling meaning as several per-limiter user strings, or drop the wait-hint header — all of which turn an expected quota rejection into an unclassifiable client-side defect (**M28**).

**N21**: Ship a registered `messageKey` that resolves in only some supported languages; hand-write the key list, language list, or catalog paths inside the completeness gate instead of deriving them from their authorities; or cite the runtime fallback chain as evidence that a missing translation is acceptable (**M29**, **M18**).

**N22**: Write a diagnostic / `rootCause` / stack / internal-state field into a response body outside the single boundary; re-implement or environment-branch that presence condition inside a handler; place raw caught-error text (`message` / `stack` / `cause` / `String(...)`) in a response body under any status, environment, or flag; or delete a diagnostic string without relocating the same information to the observability channel in the same change (**M30**).

**N23**: Choose an error's category from the appearance of its surface (endpoint, code name, HTTP status) instead of the provenance of the data its check reads; downgrade a check over server-produced data from `SYSTEM` to an expected category because a sibling code was downgraded; or reclassify a family of codes in one sweep without deciding each member's provenance separately (**M33**).

**N24**: Answer from a **failure boundary with a success envelope** — a `catch` (or any error-containment scope) that writes a `2xx` response carrying a success flag, an empty collection, a zero total, or any other value that reads to the caller as a legitimate business answer. This is a strictly worse form of the silent failure **N1** already prohibits: **N1**'s bare drop is at least ambiguous, whereas a fabricated success envelope **asserts a false fact**. The caller cannot distinguish it from a real answer, the client renders it as truth (for example, as a legitimate empty result), and no channel records anything — so an incident that the registry classifies as `SYSTEM`/`500`, and that therefore belongs in crash reporting, becomes structurally invisible. **The remedy is never a substituted value.** The failure goes to the single boundary (**M16**), which reads status, category and user text from the registry; a genuinely best-effort step continues the product flow by reporting through the classification authority, not by authoring a response of its own.

A fabricated success envelope can be introduced as a convenience—for example, returning an empty result after a caught failure. It is dangerous because callers cannot distinguish it from a valid business answer, and the failure may become invisible to logs and crash reporting. A fallback branch may also become unreachable after an earlier authoritative check is added; then it hides only anomalies. Before removing or retaining such a branch, trace the upstream checks and determine whether it has any valid input state. A dead fallback that hides invariant failures should be removed, not replaced with another fabricated value.

Enforcement (mechanical, single-file): The predicate — a response call inside an error-containment scope whose status is `2xx` and whose literal body carries a success flag — is decidable from one file’s syntax tree and can be enforced by a static rule. State the rule’s exclusions alongside it: a non-literal body, an inner function body, and a computed status require separate analysis. Keep the rule narrow enough to avoid suppressions that hide genuine findings, and measure its baseline before enabling it.

**N25**: Give one rejected fact two registry identities — a second code meaning the same thing as an existing one and differing only in *which stage of the request noticed it* (`X_NOT_FOUND` for the lookup, `X_NOT_FOUND_FOR_SNAPSHOT` for the writer that reads the same row later). Two identities are two answers to "what happened", so their registry facts drift: one twin can sit at `404` / `OPERATIONAL` / its own translated message and the other at `500` / `SYSTEM` / generic, so which internal helper noticed a deleted catalogue row first decided whether the user was told what was wrong or shown a generic failure, and whether an expected business rejection was filed as a crash (**N12**). The twin is not a harmless alias: it is the *default* answer whenever the deeper stage runs first, which is the opposite of what a reviewer reading either entry alone would predict. Merging duplicate reads behind one loading authority ([**BHE-M13**(c)](../backend-http-efficiency/set-loading-and-query-fan-out.md)) reorders those stages, so the codes **MUST** be unified before the merge rather than discovered after it. Choose the survivor by measuring, not by seniority or by which call site is being edited: read both entries' `httpStatus`, `category`, `retryable`, `reasonPermanence` and `messageKey`, and keep the one whose category matches the provenance of the data the check reads (**N23**) — a caller-supplied selection that no longer exists is an expected rejection the caller can act on, not a server defect. Then delete the loser's entry together with every producer and every consumer of it in the same change ([**DCD-M2**](../dead-code/dead-code.md)), and before removing it from the wire confirm what a released client does with each of the two codes ([**DCD-M8**](../dead-code/dead-code.md)) — a code with no client text resolves to the generic message, so replacing it with a translated sibling is an improvement for already-shipped clients, while the reverse would silently degrade them.
