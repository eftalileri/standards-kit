## **MUST** — **M33** to **M34**, **M36**

**M33**: The error CATEGORY is chosen by the PROVENANCE of the data the check reads — not by how client-facing the surface looks. The same failing assertion is an expected business rejection or a system defect depending on one question: whose data did the check just find wrong? Five obligations bind.
- (a) Client-supplied input that fails a check is expected — the caller sent something the domain rejects — so it is `BUSINESS` (or `OPERATIONAL` where it is a resource-lifecycle outcome), `WARN`, metric channel, with its own `messageKey` so the user learns what to correct. A normal outcome of the user's own earlier action belongs here too (deleting a record later makes "no such record" a legitimate state, not a defect). A refusal text that names an exit **MUST** name one the actor can actually reach in that state. A refusal triggered by the user's own edit, or by the clock crossing a start time while the screen stayed open, is `BUSINESS`/4xx too; a 5xx class would also switch on the transport retry.
- (b) Server-produced data that fails a check is an invariant violation and stays `SYSTEM`, even when the endpoint, the error name, and the HTTP surface all look client-facing. If the values under test were produced by the server's own query, projection, or derivation, then "the check failed" means the server's own data is not what the server guarantees — a defect, and `httpStatus` is independent of category (see Error categories), so returning `4xx` for it is allowed while the category **MUST** remain `SYSTEM`. 
- (c) Input an UPSTREAM gate already validated is no longer client-provenance. Where a schema or guard enforcing the same condition runs before the check, reaching the check proves the two disagree — a server defect — so (b) governs and the category stays `SYSTEM`. Prove reachability past that gate before moving a raw throw to an expected code.
- (d) A check that compares STORED server data against a value the request is CHANGING belongs to the request. When the stored record satisfied the check before the request and the request's new value is what breaks it — a price lowered below a stored fixed amount that must not exceed it, a limit shrunk under stored usage — the caller's input is the fault and the user can correct it (change the value, or first edit the dependent record), so (a) governs. Stored data that already failed the check before any change is (b). Where one shared predicate serves both kinds of caller, it returns a closed violation name and each caller raises its own registered code, so the expected rejection never shares a code with the defect. 
- (e) One code raised at sites of DIFFERENT provenance is split by site. A registry row holds one category (**M12**), so a code shared by a check that reads server-produced data and checks that read the user's own earlier actions can be right for only one of them. The site reading server data gets its OWN registered `SYSTEM` code; the user-correctable sites keep the expected code. Where a caller translates the defect code into another code for a wire contract, the translated code is also `SYSTEM` — an expected category there would drop the defect to `WARN` at the translation and erase it from crash reporting, which is the (b) failure one hop later. Name a new defect code so a compile-time lock covers it where the registry offers one. Check reach: choosing the category per site needs the call graph; only the `_INCONSISTENT`-suffix `SYSTEM` lock is mechanical.

The trap this closes is a bulk reclassification driven by the surface rather than the provenance: a family of codes that all look like "the caller sent something wrong" is moved to `BUSINESS` together, and the one member whose check reads server-produced values is silenced with the rest — a real defect loses its crash-reporting signal forever, which is a quality-ratchet regression, not a cleanup. Reclassify one code at a time, and record the provenance finding next to the registry row (a comment at the entry, and the project's endpoint or error catalog where it has one) so the next reader does not repeat the sweep. Where provenance is genuinely mixed or unclear, the doubt → `SYSTEM` rule above decides. A helper whose callers differ in provenance keeps its request guard; each caller holding server data resolves and checks it at its own boundary first ((b)), so only request input reaches that guard (review-bound: provenance needs the call graph). [Consequence: Either a real data/query defect is downgraded to a silent expected outcome, or an ordinary user mistake is reported as a crash; both must not ship.]

**M34**: Where a CLIENT keeps its own code→text dictionary, the codes it owes a text to are decided by CATEGORY, and a code with no text is a KNOWN GAP — never a crash report. **M29** binds the completeness of the server catalog; a client that resolves the wire's error code against a dictionary of its own is a second consumer of the same registry, and the questions "which codes must it carry" and "what happens when one is missing" have their own answers. Three obligations bind.

- (a) The required set is DERIVED from the registry, filtered by category — never a hand list. The expected band (**M33**(a): `BUSINESS` / `OPERATIONAL`) names an outcome the reader can correct, so every one of its codes owes its own sentence. The defect band (**M33**(b): `SYSTEM`) names the server's own data being wrong, so the reader has nothing to correct and the single generic sentence is the designed text there; demanding one string per code in that band manufactures a family of near-identical sentences that carry no information the generic one lacks. A gate **MUST** measure the expected band at `error`, **MUST** read both the code set and the categories from the registry (**M29**(b)), and **MUST** fail loud on a category value it does not recognise. Texts already present for defect-band codes are a bonus, not a violation: the gate **MUST NOT** demand their removal.
- (b) A missing client text goes to the expected channel or to none — never to crash reporting. The build-time completeness gate is the failure signal for a missing translation. At runtime, the resolver renders generic text and reads the envelope category: expected (or absent, so unproven) → record at `WARN`; `SYSTEM` → emit no duplicate client-side crash event when the boundary already reported the failure under its correlation id.
- (c) A missing text is FILLED from the project's own words or left on the debt list — it is never invented. Where the same code already has a shipped, reviewed sentence under another catalog authority of the same product, filling the client dictionary is a faithful copy of it, per language. Where the project itself has no sentence for that code — its registry key resolves to the generic message, or the existing sentence contradicts the code's only producer — the code stays on the gate's shrinking exemption list (**FP-M18**) with the reason recorded. An invented translation in a language nobody on the team reads is worse than the generic text: it cannot be reviewed, and it reads as covered. Copying does create a second home for one sentence (**I18N-CAT-M1**); where the two catalogs serve different surfaces that is the accepted shape, and where it is not, the reconciliation is its own change, not a silent side effect of the fill.

[Consequence: Expected business errors flood the crash channel while users see a generic message; must not ship.]

**M36**: An HTTP status CLASS is a CONTRACT about whether the request's state-changing attempt happened — so one registered code **MUST NOT** be raised at two different moments of the write path. **M33** chooses a registry row's `category` from the provenance of the data the check reads; this row chooses the same row's `httpStatus` class from the *moment* at which the failure was settled, and **N23** already forbids the reverse inference — reading a category off a status. Three obligations bind.

- (a) The class states the MOMENT, not the guard that raised it. The pre-write refusal class — the authorization family, canonically `403` — asserts that the request was refused before the write was attempted: the decision read the actor and the target and nothing durable moved. The conflict class — canonically `409` — asserts the opposite: the write reached the store and the store refused it, because a uniqueness constraint, a compare-and-set, or a concurrent writer had already settled the outcome. A persistence failure mapped onto the pre-write refusal class breaks that contract for every reader downstream, and those readers are not only human: a caller that decides *may I retry* or *did anything happen* from the class is handed the wrong answer with no signal that it is wrong. Choose the class from the write path, never from which guard happened to be holding the failure.
- (b) One code, one moment — because a registry row holds exactly one status. A code reused at both moments binds one registry row to two answers, and the row cannot be right for both (**M12**; [**SSG-M8**](../ssot/ssot-principles-and-precedence.md) — one authority per datum). The repair is a second registered code for the second moment, each with its own `httpStatus`, `messageKey` and `category`. The repair is not a status decided at the raise site or passed into the carrier: that reopens the parallel status authority **N9** forbids and the second-writer defect the carrier rows already close. The same arithmetic that makes a two-status code unregisterable makes a two-moment code undiagnosable — one alert, two unrelated failures, and neither's real frequency is knowable.
- (c) `retryable` does NOT answer this question and **MUST NOT** be used to. `retryable` is a transport fact — *is re-sending this exact request now useful* — and it is deliberately `false` for a large family of rejections whose cause is external mutable state. Whether the state-changing attempt happened is a different fact about a different instant, and no value of `retryable` implies either answer. A design that needs "did anything durable happen" reads the status class under (a), or introduces its own registered fact; it never overloads the transport flag.


[Consequence: A caller cannot tell a refused request from a half-applied one, retry and reconciliation logic silently take the wrong branch, and one registry row is asked to answer for two different failures; must not ship.]

## **MUST** — **M40** to **M44** (observability completeness: will a defect be seen, and what happens once it is?)

**M40**: Every registered code **MUST** carry the category its REACHABILITY dictates, decided when the code is registered and re-decided whenever a raise site is added. A code a correct client with honest input can trigger — request input the domain rejects, a normal outcome of the user's earlier action, a provider's transient state — is expected (`BUSINESS` / `OPERATIONAL`). A code reachable only through a server or client defect, stored-data corruption, an invariant or contract break, input an upstream gate already accepted, a server-built value, or misconfiguration is `SYSTEM`. Validation follows the same split: a route schema rejecting request input is expected; a parse of server-produced data (stored document, internal re-parse, derivation or response schema) failing is `SYSTEM`. One code **MUST NOT** carry both meanings: split it at the raise sites (**M33**(e)); a mostly defensive code whose few expected sites can move to an existing expected code is reclassified `SYSTEM` instead. Reason: a defect raised under an expected code reaches only the metric channel, so an endpoint can fail every request with no crash report. Enforcement: a reclassified code joins the registry's compile-time `SYSTEM` category lock; the per-site choice is review-held (it needs the call graph).

**M41**: A caught failure that the catching code has not structurally classified **MUST NOT** leave as an expected code; unknown is `SYSTEM`. A catch may convert to an expected code only behind a structural classifier over the caught value — a specific error class, a driver or transport code, the project's transient classifier, or the lower layer's own registered expected carrier; everything else passes through unchanged or is wrapped in a registered `SYSTEM` code. A typed wrapper class with a fixed expected code obeys the same rule at its construction sites. Reason: catch-alls are where a bug, a datastore outage or a corrupt cache entry gets relabelled "provider unavailable" or "lease lost". Enforcement: where the consuming project uses static analysis, a focused rule over catch bodies, `.catch` handlers and the non-carrier branch of a typed-carrier `instanceof` test; wrapper classes with a fixed code and classifiers that test state other than the caught value are review-held (limits in the rule header).

**M42**: Every unexpected failure — HTTP or background (scheduled job, queue or outbox, webhook, push or email sender, a retry loop that gives up, fire-and-forget work, process-level handler) — **MUST** reach crash reporting exactly once through the single boundary ([logging policy](../logging-policy/failure-level-and-channel-routing.md) **M15**–**M17**, [background boundaries](../logging-policy/background-boundaries-and-sink-safety.md) **M21**). A catch whose only handling is a `warn` / `info` line, a neutral return value or nothing is a swallow unless the caught value was structurally classified expected under **M41**; a best-effort side path routes its failure through the background authority, which keeps expected classes on the metric channel. Reason: a swallowed defect is indistinguishable from success. Enforcement: review-held for log-only and neutral-return catches (the catch shape cannot tell an expected probe from a swallow); the rewrite form is locked by **M41**'s rule.

**M43**: Expected-failure volume **MUST** stay observable through a mechanism someone is alerted from, and the project **MUST** state what consumes its metric channel and where that consumer is blind. A code or route whose rejection rate shows a broken flow — one endpoint rejecting most requests — must surface even though each rejection is expected (the per-route reading is [logging policy](../logging-policy/failure-level-and-channel-routing.md) **M18**). Expected failures a client produces itself — no server response carried them — reach the server as raw occurrences and are counted there into the same window, so the one alarm consumer that judges server-side expected failures judges them too ([**COB-RN-M6**](../client-observability-rn/classification-authority-and-outbound-links.md)); a failure the server already counted **MUST NOT** be emitted again by the client, and a second consumer (a crash-tool monitor on a client metric, a separate evaluator) **MUST NOT** be added. Signals fed by an unauthenticated source **MUST** be judged as one family-level subject so a caller can open at most one episode from them; their per-identity counts stay as triage evidence, never as separate alarm subjects. The consumer statement names its blind spots: low volume below the general rule's floors, client occurrences that never reach the server, and a single client signal diluted in its family's baseline. Reason: a defect misclassified as expected is otherwise seen by nobody. Enforcement: review-held.

**M44**: The crash channel and the expected channel are two boxes with fixed meanings, and every new crash-channel issue **MUST** receive a verdict. Three obligations bind.
- (a) The level names the box. An expected outcome (`BUSINESS` / `OPERATIONAL` — a wrong password, a validation rejection, an offline device) is a *warning*, never an *error*: it is written at warning level and counted per code on the metric channel. The error level and the crash channel hold only what may be a defect: unknown failures, server-produced bad data, a fatal or generic error screen, and the episode alarm for a suspicious volume of expected rejections (sent at error level, because it needs a verdict). A crash-channel event that must stay visible for a proven environmental cause — a fatal screen on a device that is definitely offline — is sent at the tool's warning level. Reason: the reader must tell "warning" from "error" from the level alone.
- (b) The verdict is "defect" or "expected", decided for each new issue. A defect gets a root-cause fix in code. An expected outcome is reclassified at its single authority — the registry row (**M40**, **M33**) or the client classifier (**COB-RN-M6**) — and the same change decides what the user sees: a clear localized message from the product's own words (**S4**, **M34**), or nothing. After that change the outcome arrives as a warning, not as an error.
- (c) A verdict **MUST NOT** be carried out by ignoring, muting, archiving or resolving the issue in the crash tool, by an inbound filter, a client send-hook drop or a sample rate, or by demoting the level at a call site. Reason: each of these hides the next real defect of the same shape and leaves the category wrong for every other consumer of the registry.

[Consequence: The crash channel answers "is anything broken?" only for the defects that happened to be classified correctly; must not ship.]
