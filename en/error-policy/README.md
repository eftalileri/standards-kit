## Agent TL;DR

- One error registry maps each semantic code to its HTTP status, category, message key, and retryability (**M12**); a typed code type is derived from it where the language supports that relation (**M14**). Raise codes through the consuming project’s typed carrier or throw factory with structured context (**M13**, **N10**).
- The closed category set (`OPERATIONAL` / `BUSINESS` / `SYSTEM`) drives classification; severity is derived from category, not stored (**M15**). HTTP status and category are independent.
- One boundary handler resolves status, severity, and user message from the registry; unknown codes fail loudly as system errors (**M16**). The boundary attaches a correlation ID (**M17**) and does not throw if localization fails (**M18**).
- Third-party responses are runtime-validated at their documented owner paths (**M21**). Client-supplied provider identifiers are intent only: a projection write requires a fresh provider read, exact identifier match, provider-derived write value, and a production-environment fail-closed gate. Reusable provider references preserve environment provenance and are re-gated before every later live provider operation; authenticated unknown webhook kinds are audit-only (**M20**, **M22**, **N15**).
- Authenticated push contract drift remains a registered `SYSTEM` failure. A protocol-required success acknowledgement may override only the wire status, only for an explicit non-retryable contract code, and only after the single boundary emits its one error/crash event; retryable failures remain non-`2xx` (**M20**, **M23**, **N16**).
- A valid authenticated provider callback that continues asynchronously is persisted as a durable retryable inbox record under its immutable event/message id before `2xx`; detached promises are not acceptance, and persistence failure remains non-`2xx` (**M24**, **N18**, **IDEMP-M14**).
- An ambiguous provider not-found immediately after an external write remains retryable when it cannot distinguish propagation from permanent absence; ownership/authorization requires successful structural provider evidence and is never inferred from status alone (**M19**, **N17**).
- A registered `messageKey` must resolve in every supported language, proven by a fail-closed gate whose key set, language set, and catalog paths are all derived from their authorities; the runtime fallback chain is a recovery mechanism, never an excuse for a permanently missing translation (**M29**, **N21**).
- The diagnostic-field presence condition lives only inside the boundary, no bypassing handler writes one, and raw caught-error text never reaches a response body under any condition — a removed diagnostic is relocated to the observability channel, not deleted (**M30**, **N22**, **SEC-N-RESP-2**).
- Category comes from the PROVENANCE of the data the check reads, not from how client-facing the surface looks (**M33**, **N23**): client-supplied input that fails a check is expected (`WARN`, metric, own `messageKey`); a check over server-produced data is an invariant violation and stays `SYSTEM` even behind a client-facing endpoint — `httpStatus` and `category` are independent. Reclassify one code at a time; a family-wide sweep is how a real defect loses its crash-reporting signal.
- A status CLASS is a contract about whether the state-changing attempt happened (**M36**): the pre-write refusal class says nothing durable moved, the conflict class says the store itself refused the write. One registered code never spans both moments — a registry row holds one status — and `retryable` answers the transport question, never this one.
- "Can this rejection's CAUSE stop being true?" is a third fact and needs its own REQUIRED field (**M37**): retryability asks whether re-sending *now* helps, the status class asks whether the write had been attempted, and neither says whether the same request will still deserve the same answer later. Required, closed value set with no "undecided", bound to retryability in one direction by the type rather than by prose, and read directly by the consumer — an unresolvable code takes the reversible branch under its own event name, never an invented value.
- Expected (`WARN`) errors use a metric channel rather than crash reporting (**N12**). Operator diagnostics are exposed on the wire only under the API contract’s explicit non-production condition (**M4**). Coordinate with logging and client error-handling standards.

**Declared enforcement limit — a registered code with no producer is not mechanically classifiable as dead.** A registry-first workflow creates a legitimate interval before a new code has a raiser, while an older released client may still rely on a code the current server no longer emits. A source scan cannot distinguish those states from the registry row alone. Keep raise-site membership checks derived from the registry, verify the full producer scope (including build or migration code), and review code removal against released consumers. Translation completeness remains mechanically checkable because its inputs can be derived from the registry, supported-language authority, and catalog layout.
