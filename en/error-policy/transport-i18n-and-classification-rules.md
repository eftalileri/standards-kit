## **MUST** — **M27** to **M30**, **M35** and **M38**

**M28**: Transport-layer middleware rejections — including rate limiting — are registered errors and **MUST** pass through the single boundary. Middleware that responds directly **MUST NOT** write its own error status or envelope. It raises the registered code through the project’s typed carrier and lets the boundary derive status, category, message key, correlation id, and retryability from the registry (**M12**, **M16**, **M17**). Bypassing the boundary loses those fields and may make a client classify an expected rejection as a defect. (a) One limiter meaning uses one registry code; limiter-specific operational details stay in structured context, not in user-facing text (**M4**, S3, **M25**, **N19**). (b) An exhausted quota is an expected caller outcome → `BUSINESS` or `OPERATIONAL` → `WARN` → metric channel, `retryable: true`. (c) The response carries the protocol’s standard wait hint (`Retry-After` or documented equivalent), and the client resolves its message through the one display-text authority. Middleware infrastructure failures use the project’s operational logging authority; any fail-open choice is deliberate and observable.

**M27**: Before the first irreversible call in a multi-step provider write, validate the complete intended operation against every locally provable provider limit and invariant. If the whole operation cannot be proven executable, fail before any provider side effect. Splitting one logical grant/write into several non-reversible calls is forbidden unless a durable provider-aware saga explicitly models partial completion, idempotent resume, terminal eligibility/quota, and user/operator-visible reconciliation. [Consequence: Partial money/subscription side effect.]

**M29**: A registered `messageKey` is a promise in EVERY supported language, and that promise **MUST** be measured by a gate. Once the registry `messageKey` is the single authority for user-facing error text (**M4**, **M12**), registering the key is not the deliverable — a resolvable translation in every language the product declares it supports is. The runtime language chain (recipient language → English → default) is a recovery mechanism for a race or a partial deploy, never a licence to ship a permanently missing translation: rendering another language instead is an unmet requirement that produces no failure signal at all, and **M18** (the boundary never throws on i18n resolution) guarantees the miss stays silent forever. A silent miss is exactly the class that only a gate can catch. Three obligations bind.
- (a) Completeness is a gate, not a convention. A check **MUST** fail closed when any registered `messageKey` lacks an entry in any supported language. "Translators will catch up" is not a control.
- (b) Every input of that gate is DERIVED from its authority — no hand-written list. The required key set comes from the error registry, the language set from the supported-language authority, and each catalog's location from the language code. A key list, language list, or file-name list typed into the gate goes stale silently — the same defect one layer up ([SSoT](../ssot/ssot-principles-and-precedence.md) **SSG-M8**).
- (c) Declaring a language means shipping its catalog. A language present in the language authority whose catalog is missing or unreadable **MUST** fail loud; the gate **MUST NOT** quietly treat it as "not supported yet" and shrink its own scope.

Where the existing debt is too large to open the gate at `error` immediately, it is opened as a staged ratchet, never as a warning — see [false positive prevention](../false-positive/check-design-rules.md) **FP-M18**. [Consequence: Users in unsupported-by-accident languages receive foreign-language error text with no failure signal; must not ship.]

**M30**: A diagnostic field in a response body has exactly ONE gate, and any point that bypasses the boundary **MUST NOT** write one. **M4** already fixes the *condition* (operator diagnostics only under the API contract’s explicit non-production condition) and **M25** / **N19** already fix the *path* (endpoint-specific error data leaves only through the single boundary). A common failure is a handler answering the client **without passing through the boundary at all** and hand-rolling a diagnostic field, so the contract exists but is not consistently enforced. Three obligations close that gap.
- (a) One condition, one place. The condition under which any diagnostic (operator root cause, stack, internal state, upstream detail) may appear on the wire is expressed once, inside the boundary. A handler **MUST NOT** re-implement, relax, or environment-branch that condition locally; a local copy is a second authority (**SSG-M8**) and it drifts toward disclosure, not away from it. Beware the split this creates between environments: a bypass gated on "not production" behaves correctly in every test and leaks only where nobody is watching — or, inverted, is dead everywhere except development, so its removal looks riskier than it is. Measure which case you are in before deciding either way.
- (b) Raw caught-error text has no condition at all. The `message` / `stack` / `cause` / `String(...)` of a caught throwable **MUST NOT** reach a response body under any status, environment, or flag — the single authority for user-facing text is the registry `messageKey` → i18n (**M4**). A boundary-owned diagnostic derived from validated, project-authored material is a different thing and stays governed by (a). [What counts as project-authored: logging policy **M31**. What counts as a caught throwable: logging policy **M32**.]
- (c) The diagnosis is MOVED, not deleted. Removing a diagnostic string from the body is correct only when the same information reaches the observability channel as structured fields (registered code, category, correlation id, bounded scalars) in the same change. A redaction that drops the diagnosis without relocating it trades a disclosure bug for an observability bug — a quality regression, not a fix. "Moved" is only satisfied if the destination is readable and the pointer resolves. Two measured ways it is not: the destination sink applied its own name-based redaction and erased the same text on arrival (logging policy **M25** — the observability channel scans by value instead), and the client event named a correlation id the crash reporter had never published as a searchable tag, so the address was printed and led nowhere (logging policy **M27**). Verify the relocated diagnosis by looking it up the way the pointer instructs, not by confirming the write.

Enforcement: this class is decidable from a single file's syntax tree and **MUST** be locked by a static rule over the whole server tree at `error` severity; each exemption is an individually measured debt entry with a closure plan, never a standing allowlist. Security cross-reference: [security secrets and logging](../security/security-secrets-and-logging.md). [Consequence: Internal diagnostics disclosed to clients in production; must not ship.]

Published validation-detail fields stay in the shared envelope when a local responder moves to the single boundary. Forward the validated details explicitly without changing their shape; never use their free text as the user message or copy operator context into the body. Existing manual-response enforcement covers the bypass; payload provenance and released-client compatibility remain review obligations.

**M35**: A registered code's user-message key is resolved ONLY from the registry — a CALL-SITE OVERRIDE is forbidden, and once its last consumer is gone the override FIELD itself is deleted. **M4** and **M12** make the registry `messageKey` the single authority for user-facing error text and **M29** makes a gate measure that promise in every supported language. A parameter that lets a caller pass its own key — or a local `switch` mapping a code to one — quietly opens a **second authority** for the same datum ([SSG-M8](../ssot/ssot-principles-and-precedence.md)), and this duplicate is worse than an ordinary one because it is **invisible to the completeness gate**: that gate derives its required key set *from the registry* (**M29**(b)), so a key resolved outside the registry is never in the set, and its missing translations are never counted. A local code-to-key mapping can therefore remain invisible even when the registry-derived completeness gate passes. Three obligations bind.
- (a) One code, one key, resolved in one place. The boundary reads `messageKey` from the registry entry for the raised code. A caller-supplied default for the unknown/unmapped case is a different thing and stays allowed, because it answers a question the registry did not; a value that overrides a registered key is not.
- (b) Context-specific wording is a NEW REGISTERED CODE, never an override. If a call site genuinely needs different user text, the difference is a difference in *meaning* — and meaning is precisely what the registry indexes. Registering it brings the key inside the gate's horizon in the same move (**M29**(a)–(b)); overriding keeps it outside forever.
- (c) When the last consumer goes, the FIELD goes with it, in the same change. An unused override parameter left on the options type keeps the second authority one keystroke away and unfenced. Deleting it makes the type system the enforcement — a later attempt to pass one fails at compile time, repository-wide, with no governed file set to maintain and no exemption list to grow, which is a stronger fence than any check that could be written for it ([**DCD-M2**](../dead-code/dead-code-rules.md); [**FP-M18**](../false-positive/check-design-rules.md) for what a check-based fence would have had to carry instead).

[Consequence: users in most supported languages receive foreign-language or fallback text for a code the completeness gate reports as fully translated — a silent miss the gate is structurally unable to see; must not ship.]

**M38**: A validation schema SHARED across the client/server boundary that writes an error CODE as an issue message binds that code to the registry — an unregistered literal is a user-facing sentence that degrades to a generic field label. Shared schemas are imported by both tiers, so a failed parse on the client hands the UI an issue whose `message` is a machine identifier. The resolver turns it into text only for a registered code; an unregistered one falls through to the caller's generic label, so the schema knows exactly what it rejected and the user is never told. Three obligations bind.
- (a) The literal is a registration, not a string. Writing a code-shaped identifier as a schema rejection message is the same act as raising that code: it **MUST** exist in the registry first (**M12** ordering), and for any non-generic category it owes its sentence in every supported language, in both catalogues.
- (b) Registration here is behaviour-preserving, and that is the point. The server typically wraps a schema failure into one boundary code and carries the identifiers as detail, so registering opens no new raise path; only the client resolver's first step starts succeeding. Do not let the absence of a server raiser argue the code away — the consumer is the other tier.
- (c) The predicate is cross-file, so the fence is too — and it must be scoped to REJECTIONS. Whether a literal is registered cannot be decided from the file writing it, so a single-file syntax-tree rule structurally cannot see it and a whole-tree check is the only mechanism. Scope it to schemas validating inbound requests: one asserting an outbound response contract writes an identifier no user sees, and sweeping it in yields a finding whose only honest answer is a suppression. [Consequence: a rule states precisely why input was refused and the user reads an unrelated generic label; must not ship.]
