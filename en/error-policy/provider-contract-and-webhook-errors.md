## **MUST** — **M19** to **M26**

**M19**: Third-party and upstream failures **MUST** be split by retryability, not collapsed into one `SYSTEM` code. A provider’s documented retryable response or a transport failure that remains after the selected client’s own retries is an expected operational outcome: classify it as retryable `OPERATIONAL` or `BUSINESS`, return an honest temporary-failure status, and send it to the metric channel rather than crash reporting (**N12**). Non-retryable provider errors and malformed or unexpected responses are ordinarily `SYSTEM`. When a just-completed external write may be followed by a temporary not-found response, keep that case retryable until successful provider-owned evidence distinguishes propagation from permanent absence; status alone never proves an ownership mismatch. Use one provider-adapter resolver over runtime-validated structural facts (such as a bounded HTTP status or an exact documented code), and share one transient-failure classifier across retry and severity decisions. Treat SDK error classes as evidence only when the SDK documents them as stable public contract. Inspect structured cause information where the selected runtime exposes it; do not classify by free-text error messages or internal class names. A provider’s documented semantic codes **MUST** be represented by one closed set and matched exactly; preserve only the validated safe scalar in the carrier. For runtimes that expose fetch-style transport failures, normalize non-success responses at the credential-aware boundary and retain only the validated status—never response text, status text, or stringified errors.

**M19** account-level corollary: a provider failure that refuses the *account* rather than the request — expired or revoked credential, missing permission, suspended or restricted account, exhausted balance, billing — **MUST** carry its own registered `SYSTEM` code, separate from the per-message/per-request rejection code, chosen from one closed set of documented provider codes held by the provider adapter's single evidence authority; its `rootCause` **MUST** name the provider code and the exact credential variable or console screen that fixes it. A per-message rejection keeps its code with a `rootCause` derived from the documented provider code. An account-level failure of queued work **MUST NOT** end the queue row terminally on the first attempt: the code is `retryable` so the row stays under the queue's bounded attempt policy. Reason: one generic rejection code hides a fixable account fault behind a per-message story and turns every queued message during the outage into a silent terminal loss. Review-held: which provider codes are account-level lives in the external contract (**M26**).

**M20**: Inbound third-party webhook payload validation **MUST** mirror the provider's documented contract — including nullability — and **MUST** always answer. (a) The validation schema is a *mirror of the provider's published event contract*, not of the happy-path sample: identity fields the provider documents as always-present stay required — "always" holds **per documented field group**, not globally. A type whose subject lives in another group (transfer id lists) **MUST** get a per-type schema union branched by one type→subject-contract map every known type is compile-time forced to declare, plus its own processing branch outside the single-subject path. An ownership-move event grants nothing locally: it invalidates each resolvable party's derived views for provider re-derivation. Limit: map-vs-docs accuracy is review-only. Every field the provider documents as nullable, or demonstrably sends as `null` / absent for some event types (test / cancellation), accepts `null` **and** absence. A schema that rejects documented-real payloads silently drops provider events — that loss is the defect, and widening the schema to the documented contract is **not** a fallback (consumers still handle absent values explicitly). (b) When the raw payload is persisted for audit / replay, parse in a mode that **preserves unknown keys** (loose / passthrough) — a stripping parser silently corrupts the audit record and breaks forward compatibility when the provider adds fields. (c) Classify by trust boundary: schema failure **before** the webhook's auth check is caller noise → `BUSINESS`; schema failure **after** auth passed means contract drift or a schema defect → `SYSTEM` (fail-loud, crash reporting), even with a `4xx` wire status. (d) A validation or auth failure **MUST** still produce an HTTP response through the boundary (**M16**) — leaving the request unanswered makes the provider time out and re-deliver, multiplying the noise. (e) A loose/passthrough envelope may preserve an authenticated **unknown event kind** for forward-compatible audit, but unknown must remain no-op for every known-event projection, reusable credential/reference, access, entitlement, lifecycle, and other durable side effect. Only the canonical known-event classifier may open those paths.

**M21**: Outbound third-party response reads **MUST** use a runtime schema that mirrors the provider's documented field ownership, then read each field from its documented owner object/path. A sibling, summary, entitlement, transaction, or top-level object is not interchangeable with the record that actually owns the field. When the contract links objects by an identifier, validate that identifier and join to the documented owner record before deriving domain state. A present response whose required owner object, required field, or documented link is missing/incompatible is provider-contract drift or an integration defect → `SYSTEM` (fail-loud); it **MUST NOT** become inactive, not-found, free, cancelled, successful, or any other valid domain state. Only an explicitly provider-documented absence state, proven either by a schema-valid payload at the correct owner path (for example an optional record is absent) or by the transport boundary (for example a verified not-found response), and explicitly mapped by the domain contract, may become an honest inactive/not-found result.
**M21** absence corollary: A wire format that omits empty/default values (for example, Protocol Buffers JSON) defines that omission as an input shape to validate. The schema must accept documented absence and the reader must map it explicitly; absence must never silently imply success. Review conformance against the provider’s published contract.
**M21** corollary (both directions): a provider timestamp is normalized to canonical UTC ISO-8601 (`Z`) through one helper before any write; an offsetless value passes only with the zone the provider documents (read per account, resolved by the local-time authority), else it fails loud with a registered code, never guessed as UTC. A write API's row rejection becomes a registered carrier with bounded structural evidence (reason, column, counts; never provider message or row values) and the original as `cause`. Use one timestamp normalizer and one typed provider-rejection carrier; where a project supports static enforcement for the write API, keep the row fields constrained by a branded type or equivalent.

**M21** precision corollary: when the same provider instant reaches a monotonic comparison through evidence paths of different precision (for example a webhook's epoch milliseconds and a REST record's whole-second ISO time), every path **MUST** be reduced to the coarsest common precision through one helper before it is compared or stored, and a value stored before that reduction is read through the same helper. Reason: otherwise a replay of the same purchase reads as older than the projection it equals, the writer rejects it, and the follow-up command fails although the state is already correct.

**M21** sealed-envelope corollary: when a provider's authenticity proof is cryptographic and independent of the payload fields (an AEAD tag that verifies under our key), the proof alone owns the channel/source claim. A payload field outside the contract leaves only that field empty — never a default or a derived stand-in (**SSG-M17**) — and raises the registered `SYSTEM` provider-drift code with bounded structural evidence; it **MUST NOT** drop the proven channel (that is not the **N14** partial success: no state is derived from the malformed field). A provider id that can exceed 2^53 **MUST** be read as its exact digit string (string field, or a JSON integer's source text), never through `Number`. Reason: dropping the channel records attributable events as unknown. Review-only.

**M21** unauthenticated-link corollary: values any link author controls (a referrer parameter, an app-open URL query) **MUST** be validated field by field at the source against the shared contract. An out-of-contract field is omitted — never truncated or replaced (**SSG-M17**) — the in-contract fields are still sent, and each omitted field is reported once per read as `BUSINESS` (input validation, metric channel), not as `SYSTEM` provider drift, since no provider vouches for the value. An opaque provider id is bounded above the provider's documented or observed maximum, never below it. Reason: one over-bound parameter would otherwise drop the whole measurement. Review-only.

**M21** warehouse-write corollary: In a staged analytical write, table creation, non-row load failure, and atomic replacement failure **MUST** reach the outer boundary as a registered carrier with a closed stage label, a validated numeric status when present, and the original error as `cause`. Row rejection keeps its specific carrier. Structured context excludes provider text, query text, and row values. Retryability uses **M19**’s shared classifier; unknown evidence stays `SYSTEM`, and status alone proves neither billing nor authorization. Exact external-job cause remains review-bound because an AST cannot establish it.

**M21** wire-format corollary: when a provider read requests the wire itself (raw REST) and decodes it with an SDK converter, the requested value format (for example a warehouse TIMESTAMP as int64 microseconds) and the format the converter is told to assume **MUST** come from one constant on every request and continuation page. Reason: the server default and the converter default can differ, and then every row of that column type throws during decoding and the whole report reads as unavailable.

**M22**: A client assertion **MUST NOT** authorize a server-side projection write of third-party-owned state. If a mutation carries an expected provider identifier, product, environment, entitlement, or transaction, treat it only as intent: bypass any derived provider cache, fetch a fresh provider record, runtime-validate it under **M21**, and require an exact match against the corresponding provider-owned item before writing. The write value **MUST** be derived from that matched provider item, never copied from the client assertion or inferred from a different active item. In a production runtime, provider evidence explicitly marked non-production/sandbox — or evidence whose production status is absent or ambiguous when the provider contract exposes that distinction — **MUST** fail closed before granting access, persisting a reusable provider credential/reference, or applying the user-initiated projection write. A separately authenticated and runtime-validated provider webhook is not client intent and MAY use the provider event itself as evidence without a redundant subscriber fetch; it still **MUST** pass the production environment gate before access or any entitlement, lifecycle, or other durable side effect. Persisted provider environment provenance **MUST** remain attached to the reference, and every later live provider operation that consumes it **MUST** re-assert compatibility with the current runtime before the external call; the original ingest decision is not permanent authorization. An intent mismatch **MUST** use a typed conflict code; it MAY be `OPERATIONAL` + retryable when documented provider propagation can temporarily omit the newly purchased item, while an explicit sandbox policy rejection is `BUSINESS` + non-retryable. A malformed provider schema remains `SYSTEM`. None of these paths may partially write or fall through to a different side-effect method after an environment rejection.

**M23**: An authenticated third-party push may acknowledge non-retryable contract drift at the wire level only after the single error boundary has preserved the semantic failure. Some push protocols require a success-class response to stop permanent malformed events from redelivering forever. In that case, only the transport status MAY become `2xx`, and only for an explicit registered non-retryable provider-contract code after authentication. The registry-owned `code`, semantic `httpStatus`, `category`, and `retryable` facts **MUST** remain unchanged; the boundary **MUST** still emit the one structured `ERROR`, crash-report event, trace id, and error envelope required by **M16**–**M17**. Retryable provider, datastore, cache, network, timeout, and unknown failures **MUST** retain a non-`2xx` wire response so redelivery remains possible. Raw payloads, credentials, and replayable tokens **MUST NOT** enter the carrier, log, or crash-report context.

**M24**: Success acknowledgement of an asynchronously processed authenticated provider callback requires durable acceptance first. Authentication and runtime validation occur before acceptance; then the validated replay payload and immutable provider event/message id **MUST** be durably persisted in a retryable inbox state before the controller sends `2xx`. Persistence failure is retryable and **MUST** remain non-`2xx`; a detached in-process promise is not acceptance. Once accepted, worker failures are recorded and retried from the durable inbox under [idempotency **IDEMP-M14**](../idempotency/boundary-stores-and-provider-callbacks.md); they **MUST NOT** be converted into a second HTTP response or disappear after process restart. This rule is independent of **M23**: protocol-required `2xx` for a non-retryable malformed event still passes through the semantic error boundary, while a valid event receives `2xx` only after durable acceptance. [Consequence: Critical acknowledged-event loss.]

**M24** waiting-person corollary: when a provider redelivery (or a client retry) is the only retry of an effect a person confirmed and now waits on, a system failure of that effect **MUST** be recorded on the record the person's status read answers as a visible retrying state, and **MUST** end — after a bounded number of failed attempts or at that record's own deadline — in one registered terminal outcome the status read, the client and any in-window reply all state; the record and the keys that route a redelivery to it **MUST** outlive the deadline long enough to answer that end, and a completed effect always answers first. Reason: an unrecorded failure leaves the person on "waiting" until a timeout that names the wrong cause, and a terminal refusal written on the first failure would stop the redelivery that could still succeed. Review-held.

**M24** reconciliation corollary: an entitlement served from a billing provider's state **MUST** be compared periodically, outside any request, against the provider's fresh uncached answer for every subject that can hold it; the comparison writes nothing (repair stays with the existing sync/callback writers), re-reads a disagreement only after every cache the served path may answer from has expired, and reports a disagreement that survives as one registered `SYSTEM` event per subject and direction (paid but not served / served but not paid) inside the provider's published rate budget. Each paid transaction the provider reports **MUST** also be matched against the durable callback inbox after the provider's whole retry schedule: no matching callback is one `SYSTEM` event (lost delivery), while a late callback is a `warn` symptom. A rule of the form "no callback for X hours" **MUST NOT** stand in for that match where the measured gap between callbacks exceeds any useful X. Reason: callbacks are the only push path, so a lost or misapplied one is otherwise silent — the payer stays blocked, or access outlives payment, until someone complains. Review-held.

**M25**: Endpoint-specific error response data may leave the server only through the single error boundary and only by an explicit boundary option. The value **MUST** be backed by the shared API contract and a runtime schema (or an equivalently closed, validated constructor), and every field **MUST** be deliberately classified as client-safe. typed-carrier context, operator `rootCause`, request snapshots, log metadata, provider/internal identifiers, and arbitrary caught-error properties are observability inputs; the boundary **MUST NOT** copy or spread them into the response automatically. A controller that needs safe conflict/recovery data raises the registered typed error and passes only the validated response DTO to the boundary; it does not write an ad-hoc error envelope. [Consequence: Error-boundary bypass and sensitive context disclosure.]

**M26**: A provider HTTP status shared by authentication/configuration failures and documented eligibility/quota/domain failures **MUST NOT** be classified from status alone. Parse only the provider's bounded runtime-validated structural error code. A documented eligibility/quota result is a typed `BUSINESS` outcome; an authentication/configuration code is `SYSTEM`; an unknown or malformed body is provider-contract drift → `SYSTEM`. An exact structural code match is not, by itself, exact semantic evidence: when the provider uses the same code for a wrong/missing resource or service scope/configuration and for an expired/consumed lifecycle, the result remains `SYSTEM`; a `BUSINESS` lifecycle result requires a separate structural signal that the published contract makes exclusive to that result. Code exclusivity lives in the external provider contract and is not reliably decidable by a single-file AST rule; the provider-adapter SSoT record **MUST** preserve the evidence and closed-set decision. Raw provider bodies and free-text provider messages **MUST NOT** enter the error carrier, logs, or crash-report context. If a background/worker boundary wraps the typed provider error before the outer log, it MAY preserve only an explicit runtime-validated allowlist of non-secret scalar diagnostics needed to audit that classification; arbitrary context propagation or spreading remains forbidden. A partial evidence reader **MUST** report what it did not parse. A zero count of matched provider facts is a claim about the reader, not the provider, unless paired with a non-optional count of the entries skipped or rejected — an absent count and a zero count are indistinguishable downstream. Telemetry-vs-domain property intent is not decidable from one file's syntax tree, so this half is review-only.

**M45**: A public provider route of an integration that ships dark (none of its configuration values set) **MUST** answer as an unmounted route — the registered `OPERATIONAL` not-found code, `warn` and metric only — and **MUST NOT** raise a `SYSTEM` configuration code per request; only a partial configuration (some values set, some missing) is a `SYSTEM` misconfiguration. Reason: an anonymous internet hit on a switched-off feature is not a server defect, and per-request crash reports from scanners bury real incidents. Review-held.

**M46**: A failure of a provider message send — synchronous (error response) or asynchronous (a later `failed` delivery status) — **MUST** reach crash reporting with the provider's own reason (code, title, message, detail text, documentation link) in `rootCause`, taken from the one provider-error reader, and with the send's own context (send class, purpose, tenant id) from the one send ledger; every send, whatever its class, **MUST** name that context at the provider call. A warn-only metric **MUST NOT** be the whole signal for an undelivered message. Reason: an undelivered customer or owner message is otherwise invisible until the person complains, and a generic cause hides the fix the provider already stated. Review-held (no mechanical check is admitted; the required context argument makes an anonymous send fail typecheck).
