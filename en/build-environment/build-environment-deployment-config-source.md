# Build and environment — deployment configuration source

```kit-cover

part-of: README.md
```

**Scope:** A project’s checked-in deployment configuration and the live service state it claims to own. Applies to infrastructure-as-code and provider configuration sources when one replaces or updates another.

**References:** [build-environment.md](build-environment.md); [repository and scripts](build-environment-repository-and-scripts.md); [SSoT principles](../ssot/ssot-principles-and-precedence.md).

## MUST — BE-M

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **BE-M28** | A deployment-configuration source cutover **MUST** preserve the complete live resource and environment-key inventory. Before applying the new source, compare its exact project, environment, partial ownership, service settings and secret-free variable names with read-only provider state and review a redacted plan. Omitted resources are safe only when that named partial does not own them; omitted managed variables are deletions. Freeze automatic deployments while retiring the old file and the provider’s config-file binding and applying the new source, then verify the effective deployment before resuming. A preview with any unexpected create, destroy or runtime change **MUST NOT** be applied. | Service, secret or data loss; unsafe deployment — STOP. | Live evidence: key-set parity and a redacted plan with zero unexpected changes, followed by authorized post-cutover deployment and health evidence. Limit: provider state and deployment timing are external; a source-tree rule cannot prove this comparison. |
| **BE-M29** | A deployment configuration source **MUST** declare only values the provider stores; a field whose value equals the platform default, and which the provider therefore drops, **MUST NOT** be declared — its effective value is verified from each deployment’s resolved manifest. A declared value the provider refuses to store produces a plan difference (`null → value`) that no apply can clear. A plan that is never empty stops being a drift detector, and every “zero-change plan” gate built on it becomes unreachable — which is how gates get waived. The declaration is also a phantom authority ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)): it reads as pinning a value that the platform default actually decides, so a later change of that default would contradict the source silently. Where runtime code relies on such a default (for example, a restart after a non-zero exit), the code comment names the platform default and the manifest check, never the configuration source. Pinning a behaviour against a future default change means declaring a non-default value the provider stores — a reviewed behaviour change — never restating the default. | Permanent plan drift, an unreachable zero-change gate, and a configuration source that claims a value it does not own. | Operational: after each apply or deployment, a fresh plan shows no changes and the resolved deployment manifest shows the undeclared fields’ effective values. A narrow single-file lint rule over the configuration-source tree may reject provider-default fields by name, but which fields a provider drops, and whether its defaults change, is provider state no source tree carries: an unlisted dropped field surfaces only as a permanent plan difference that the operational check sees. |
| **BE-M30** | Applying a configuration source **MUST** be handled as a deployment, and a provider-settings commit meant to skip deployment **MUST** use the provider’s explicit skip-deploy path and read the committed patch back. An apply that claims ownership or changes service settings can start a deployment of the connected branch head even where the provider documents no such effect; so automatic deployment is frozen first, the connected head is the reviewed commit before apply, and deployment identity, source revision, status and health are read immediately after. Where the provider offers a “commit staged changes without deploying” action, stage the fields, then commit the staged patch with deployment skipped; staging merges into any pre-existing staged patch, so that patch is read before staging, and the committed patch is read after, because a provider may silently drop fields (**BE-M29**). What was sent is never assumed to equal what was stored. | An unreviewed head deployed, unrelated staged changes shipped, or a setting believed stored that is not. | Operational: deployment list and active deployment identity read before and after each apply or settings commit; staged and committed patch bodies read back. Limit: the provider’s deploy side effects and patch storage are external; no source-tree check can observe them. |
