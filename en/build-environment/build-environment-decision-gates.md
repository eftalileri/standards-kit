## Decision gates (normative) — GBE

Purpose: Route changes to the applicable environment file or injection layer. Gates cite existing **BE-M** / **BE-N** rows and add no independent obligations; secret-policy detail beyond GBE2 (detail: [security-secrets-and-logging](../security/security-secrets-and-logging.md)).

| GBE1 | Is the new variable documented in `.env.example` (name + placeholder or comment)? | **BE-M2**, **BE-M4** | STOP — add documentation before using the var in code. |

| GBE7 | Executable build configuration: Can the configuration be read with only production-installed dependencies — i.e. no development-only loader/transpiler, and every value it consumes stored in a form a plain host runtime can parse? | **BE-M15** | STOP — move the consumed SSoT value into a plain data file and drop the development-toolchain dependency; prove it empirically with the development-only packages unavailable. A build that only works where devDependencies are installed is a production build defect. |
| GBE8 | Splitting a tool-chain configuration file: Is the configuration's declaration order semantic (later entries override earlier ones — flat/array configs, middleware chains, plugin pipelines)? If YES, are you moving only contiguous slices in their original order, and can you prove losslessness from the tool's own resolved-config output (before/after diff), and have you re-pointed every text-scanning consumer (guard, script, doc) at the whole new surface? | **BE-M16** | STOP — do not reorder by topic, do not accept review-by-eye as proof, and do not leave a guard reading only the old file. An order change in an order-semantic config is a silent scope change, not a refactor. |
| GBE9 | Adding or editing a lint/compile/scan gate: Is its scope expressed as directories plus the project's single source-extension authority — with no hand-written file-name list and no restated extension set — and have you confirmed from the tool's own file inventory that every file in those directories is actually processed? | **BE-M17**, **BE-N8** | STOP — a hand-listed scope silently excludes new siblings and a restated extension set silently stops matching when the extension set grows. Derive the scope, then measure the inventory — the gate's exit code cannot tell you whether it looked. |
| GBE10 | Upgrading a runtime dependency: Does the deployable package's single `engines` authority satisfy the highest direct/transitive dependency runtime floor, do every CI/container/platform consumer use a supported runtime that satisfies that authority, and does any directly imported framework-exposed driver resolve to one compatible physical instance? | **BE-M18**, **BE-M13**, **BE-M14** | STOP — do not accept a manifest-only upgrade. Raise the single engine authority, align every runtime consumer and shared driver major, and regenerate lockfiles from the merged manifest. An EOL runtime or split nominal driver identity is not enterprise-compatible even if installation technically succeeds. |
| GBE11 | Migrating an extension literal in a scanner to the source-extension authority: have you CLASSIFIED the literal first, and is the fact it carries a scope declaration — "which files does this walk collect"? A source-extension literal is not one fact but four, and only the first belongs to the authority: (1) scope declaration (`entry.name.endsWith('.ts')` inside a directory walk) — migrate it; (2) parser-option discriminator (`jsx: file.endsWith('.tsx')`, or choosing a TSX vs TS script kind) — the literal decides *how* to parse one file, not *which* files exist; (3) module-specifier resolution (a candidate-extension list, or an ESM `.js` specifier remapped to its TypeScript source) — the literal carries a *resolution convention* and usually an *order*, which an unordered scope set cannot express; (4) domain selector (the extension is part of the artifact's identity — "a screen component is `.tsx`", a barrel's `index`, a `.d.ts`) — widening it changes *what the check is about*. Before migrating, have you also measured that the tree the walker visits contains no file of the extensions the authority would ADD, so the population is provably unchanged on the day it lands? | **BE-M17**, [**SSG-M8**](../ssot/ssot-principles-and-precedence.md), [**FP-M18**](../false-positive/check-design-rules.md) | STOP for classes 2–4 — converting them is a category error: it makes the extension authority answer a question it does not own, and for class 4 it silently changes the check's subject. Leave them literal and say so. For class 1, do not migrate blind: if the authority's set is wider than the literal and the tree holds such a file, the walker's population changes on landing and the gate is no longer born green — measure first, then land. Fence placement: the sub-surface that IS single-file decidable, and therefore **MUST** be fenced by a lint rule once its population is zero, is the authority call's argument position (an extension array literal passed where the authority's own exported set belongs); the anchor is derived from the import that resolves to the authority module, never a list of helper names. A literal in a hand-rolled walker body is NOT fenceable, because classes 1–4 share one syntax shape and no property of the file separates them — that absence is a declared limit, not coverage. |

Package-local compiler resolution (GBE9 application). In a repository with separately installed package roots, a root `tsc --project child/tsconfig.json` command executes the root compiler even if CI installed the child's dependencies. The verification gate **MUST** enter the owning package for each compile project and invoke that package's own installed compiler entry, including the root package's own compile scripts. A bare `tsc` inside an npm script can still fall through to an ancestor package when that package's installation is absent; an explicit package-local compiler path makes absence fail loudly. Each package's manifest and lockfile must agree on the compiler and its executable entry, and CI must install that package before invoking its gate, in the same job and in that order. The check is cross-file and cross-format (manifests, lockfiles, workflow), so a single-file ESLint rule cannot establish it; where a fence is admitted it is an aggregate guard whose population includes every package changed by the decision. Check declined ([**ENA-GV3**](../enforcement-architecture/enforcement-admission.md)): the compile scripts invoke the explicit package-local compiler path, so an absent installation already fails the gate loudly (the design rung of [**ENA-P1**](../enforcement-architecture/enforcement-admission.md)); the guard that re-checked the command text failed [**ENA-A1**](../enforcement-architecture/enforcement-admission.md)(b)–(c) and was retired, and a new compile script's command shape is held by review. This does not require independently installed packages to share one compiler version: **BE-N7**'s version-parity clause applies to one workspace/toolchain boundary and local-versus-CI parity, while each separate package uses its own declared compiler.

GBE10 for Expo native SDK upgrades: Resolve the target from the stable Expo release and its bundled native-module table; align React Native, animation/worklets, native packages and the lockfile as one graph. Align TypeScript and its lint parser/plugin peer ranges when the SDK's supported compiler line changes; migrate deprecated compiler options and fix newly reported source findings rather than silencing the compiler or weakening the gate. A changed native ABI requires a fresh native binary and a distinct OTA `runtimeVersion` before publishing JS updates; generated `ios/` and `android/` trees are regenerated from the tracked config when Continuous Native Generation owns them. Check the build host's Xcode/Android toolchain against that SDK's published requirements and any release-specific opt-in needed for app launch. If that toolchain rejects a transitive native SDK, advance its maintained official bridge within a compatible major and compare the app's public purchase/error/identity contracts before accepting the build; never patch generated pods as the authority. A local Node selector does not choose the remote build-service image's Node version: when the image default falls below the package's `engines` authority, declare an explicit compatible build-profile runtime version and verify the tracked template against any local profile copy. Re-run the dependency audit and retire exception records whose vulnerable package has left the resolved graph. This is a cross-file and external-release contract: no single-file AST rule can establish the SDK's live compatibility table, build-host version, lock closure and published OTA cohort together; verify those inputs explicitly at upgrade time.

GBE10 for a native package added inside an existing OTA `runtimeVersion` (no bump, so JS updates keep reaching the installed binaries): the package's JS entry **MUST NOT** be imported as a value anywhere; one module checks the native side's presence without throwing (optional native-module lookup) and loads the package lazily, and every surface draws an "update the app" state when it is absent — a static import throws during module evaluation on a binary built before the package. Bump `runtimeVersion` instead when the JS cannot work without the package. Check declined (**ENA-GV3**): the type-only import rule and the single loader module are held by review; the loader’s consumers are listed where the adopting project documents the loader.
