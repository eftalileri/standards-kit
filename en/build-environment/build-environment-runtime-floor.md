## MUST — BE-M

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **BE-M18** | A dependency upgrade **MUST NOT** leave the deployable runtime below the dependency graph’s supported floor. Before accepting an upgrade, inspect the selected direct package metadata and the resolved lock closure for runtime requirements. The deployable package’s `engines` field is the single minimum-runtime authority; CI setup, container base images, platform runtime selectors, local runtime files, and operational documentation are consumers and **MUST** all satisfy that authority. Runtime entry points and build/typecheck scripts **MUST** consume one canonical checker derived from that field; a checker that exists only in an aggregate root gate is bypassable. SemVer precedence is binding: a prerelease with the same numeric tuple as a stable minimum is lower than that minimum and **MUST** fail before application code starts. If the previous runtime line is end-of-life, merely raising to the lowest technically installable patch is insufficient: choose a currently supported production line under the project’s quality/security policy. When an ODM/framework exposes a transitive driver at runtime and the application also imports that driver directly, align the direct dependency with the framework’s supported driver line and require one physical lockfile instance; parallel majors split nominal classes (`instanceof`), sessions, serialized value types, and collection types even when method names look compatible. Production container base images are executable supply-chain dependencies and **MUST** use a readable compatible tag plus an immutable multi-architecture `sha256` digest; a mutable tag alone is not deployment authority. Narrow vendor-artifact exception: when the required official vendor image verifiably publishes no multi-architecture artifact, an architecture-bound immutable digest is allowed only if the deployment architecture is measured, target-platform builds are explicit, every build/runtime stage fails loudly before application work on any other architecture, the exception is recorded in the adopting project’s decision record, and no documentation claims multi-architecture support or provides an alternate-image fallback. Regenerate every affected lockfile from the merged current manifest (**BE-M13**/**BE-M14**); never copy an older upgrade branch’s whole lockfile over a newer graph. | Install/build/deploy incompatibility, bypassable runtime validation, duplicated runtime class identity, mutable supply-chain input, unsupported architecture, or unsupported-runtime security defect — **MUST NOT** merge or deploy. | Inspect package metadata plus direct lock entries; locate every runtime selector and prove each satisfies the declared floor; verify build/typecheck plus every executable entry point reaches the canonical checker and that no minimum literal is copied outside the engine authority; where app and framework share a driver, prove the lock has one compatible physical instance and imports do not cross parallel majors; verify every production `FROM` reference carries the intended immutable digest. For the single-architecture exception, retain vendor-manifest evidence, measured deployment architecture, explicit target-platform build proof, and per-stage fail-loud guards as one cross-file invariant. ## Source-mode entry points

A verification or operational CLI that executes shared TypeScript source **MUST** use a documented loader profile compatible with the complete source graph. Native type stripping of a leaf file is not proof that transitive emitted-extension ESM edges resolve in the unbuilt tree. Preserve the shared runtime schema/import contract (**MRP-M2**, [monorepo rules](../monorepo/monorepo-rules.md)); fix the source consumer’s loading mode, rather than rewriting correct production `.js` edges, duplicating schemas, generating stand-in compiled source, or adding a private loader. Reuse the installed trusted package’s public loader operation with its required parent context. Production-only executable configuration remains governed by [**BE-M15**](build-environment-config-and-runtime-floor.md); a CI source loader is not permission to add a development dependency to that production profile.

Stated limit: even an admitted single-file check could not prove source-graph compatibility — runtime versions/flags/preloads, conditional exports, transitive source graphs and physical `.js` remapping are not facts in one file’s syntax tree. Executing the real CLI remains the proof of its source-graph and output contract.

## Node types and runtime-bundled clients

In every Node package root, `@types/node` manifest and lock majors match the runtime major. Dependency-update automation defers only major upgrades; minor and patch remain enabled. Cover all roots with a cross-file check.

A userland dispatcher handed to the runtime’s built-in `fetch` (an `undici` `Agent` passed as `dispatcher`, directly or through an SDK) **MUST** stay on the major line of the client the runtime bundles; the dispatcher/handler contract changes across majors, so the built-in fetch’s handler is rejected on the first request while types and build stay green. Raise that dependency’s major together with the runtime line. Verify with one real request through the built-in fetch with that dispatcher; the bundled client version is a runtime fact absent from source, so review plus the real-request proof hold it.

## Operator entry points

A runnable maintenance/operator entry point — above all a privileged one that creates or rotates administrator credentials, grants roles, or repairs production records — **MUST NOT** live inside the source tree the deployable runtime is compiled from. An exclusion in the production build profile is defence in depth, not the placement: a general build of that tree still emits the scripts, and every rule scoped to the operator-script tree (single environment authority, explicit run mode, destructive-run gate) silently misses a script that sits in the runtime tree. The runtime tree opens its database connection through exactly one connection authority; any other runtime-tree file that opens its own connection is either a second connection path ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)) or a misplaced operator entry point, and is moved to the operator-script tree, where it reads the environment through the validated authority ([**BE-M24**](build-environment-env-key-declaration.md)) and takes an explicit mode before connecting ([**REP-M-15**](../repository/repository-index-migrations-and-validated-reads.md)).

Verify by inspecting the production and general build file lists for operator scripts, and by a boundary check owned by the adopting project that treats the connection authority as the single permitted opener (module connect members, named imports of the driver client, and its construction). Limit: an entry point that opens no connection of its own (delegating to a runtime module) is not distinguishable from a runtime module in one file’s syntax tree, and a binding passed through a function parameter or a computed module name is not tracked; those remain review-bound.

## Behavioural compatibility

**BE-M18**’s driver-line clause covers *identity* breaks that survive a green build (`instanceof`, sessions, serialized value types). This section binds the quieter half of the same hazard: an upgrade that keeps the signature and changes what the library is willing to infer. When a major version stops guessing the meaning of an argument shape and requires the caller to declare it, the omission is invisible to every gate that runs before deployment — the flag is optional in the published types, so the type checker is green; the shape is a legal overload, so the build is green; and the throw happens on the first runtime execution of that path. An upgrade of this kind **MUST NOT** be accepted until each argument shape its migration notes name carries a mechanical fence landed in the same change, and the opt-in is declared at the call site, never switched on globally for the process — a global default removes the declaration from the place the reviewer reads the argument, so the next call site inherits a guarantee nothing at that line states. The fence **MUST** be able to tell the framework’s surface from the underlying driver’s, and that distinction is a type fact, not a name: the two expose the same method names, and only one of them honours the option, so a predicate keyed on the call’s name or on the argument’s shape flags the driver’s correct calls as violations. Reach for the type checker before writing such a fence, and where a subtree carries no type information, exclude it explicitly and state what is undecidable there rather than letting the rule return a silent zero ([**KIT-INV-8**](../authoring/kit-structural-invariants.md)(b), [**FP-M35**](../false-positive/check-verification-rules.md)). This failure class is loud, not silent — it throws client-side with no server round trip, so no wrong write, lost atomicity or cross-tenant read follows from it; what it costs is every guarantee the unexecuted path was arming, and a boot-time arming path loses all of them at once ([**SJO-M7**](../logging-policy/scheduled-work-boot-arming.md)).

Limit: such a fence says nothing about a pipeline’s semantic correctness, and it requires the option to be visible as a literal in the call’s own options object — an option object passed by variable or spread is reported, deliberately, because the declaration must be readable where the argument is.

## Stated verification limits

The lockfile and published package metadata can establish declared runtime compatibility, not every provider’s live behavior or an external deployment’s actual architecture. Static checks also cannot prove that an operator script reaches only the intended database through every dynamic import path. Record which properties were verified from source, resolved configuration, and an actual artifact; do not imply broader coverage.
