## MUST

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **BE-M15** | Executable build configuration **MUST** be readable using dependencies guaranteed to be installed in its build environment. If production-only installation omits development dependencies, the config **MUST NOT** depend on a development-only loader, transpiler, or registration hook. A value shared between build configuration and application code **MUST** have one data authority that the host can read directly; typed accessors may read that same data but **MUST NOT** duplicate it. Type-only imports are acceptable because they do not execute at runtime. | Configuration works locally but fails on a clean production build, or required values are omitted from the generated artifact. | Evaluate the configuration with the project’s own config command in a production-like dependency environment and verify the resolved values. Inspect executable config with the project’s normal language checks. |
| **BE-M16** | A toolchain configuration MAY be split into modules, but its declaration order **MUST** be preserved when later entries override earlier ones. Extract contiguous blocks and compose them in the original order. Before and after the split, compare the tool’s resolved configuration for representative targets; require equivalent effective settings. Repoint any text-scanning consumer to the complete composed surface in the same change. | Silent change or loss of effective configuration. | Compare resolved configuration before and after; inspect ordering and identify every consumer of the old source. A successful command alone does not prove equivalence. |
| **BE-M17** | The scope of a lint, compile, or scan gate **MUST** be derived from a directory authority and a source-extension authority — never restated as a hand-written list of file names or extensions. Two failure modes share this one root cause, and both are silent. Clauses (a)–(e) and the derivation rules for surfaces a single-file rule does not reach [below](#be-m17--gate-scope-derivation) bind. | Silent enforcement loss or false scope failure — the gate is green because it never looked, or a generated/local artifact is mistaken for authored source and makes a later gate environment-dependent. **MUST NOT** ship a scope declared by hand, a root-only generated-output exclusion in a multi-package tree, or an aggregate scanner that bypasses the shared non-source predicate. | Empirical and static checks [below](#be-m17--gate-scope-derivation). |

### Gate scope derivation — BE-M17 clauses

(a) Named-file scope. A gate command that enumerates individual files (`lint a.ts b.ts config.ts`) governs exactly the files someone remembered to type; a newly added sibling is simply never checked, and the gate still exits 0. Point the command at the directory and let the tool’s own file-matching configuration decide membership.

(b) Restated extension globs. Every glob that spells out an extension set (`**/*.{ts,tsx}`) is a copy of a decision that belongs in one place. The moment the project adopts one more source extension, every un-updated copy silently stops matching those files — the tool reports no error, because a glob matching nothing is not an error. Define the governed source extensions in one module and generate every glob/pattern from it.

(c) “No matching configuration” is usually a warning, not an error. Most linters/compilers treat an input file that no configuration block matches as a non-fatal condition with exit code 0 — so scope loss produces the same output as clean code. Whether such files exist **MUST** therefore be measured separately from the gate’s own verdict.

(d) Generated and repository-declared local scratch output is not authored source. Compiler-declared output directories are derived artifacts (**BE-M13**) and **MUST** be excluded through each gate’s single scope-exclusion authority with a recursive pattern or predicate that covers the repository root and nested package roots. A root-only output ignore is insufficient in a multi-package tree: a build may create a nested `dist` after the source lint but before an aggregate inventory check, making generated declarations or JavaScript look like governed-but-unvisited source. A custom aggregate scanner **MUST** consume the project’s shared non-source directory/file predicate instead of writing a private recursive walk with a second skip list; otherwise the linter and scanner can give opposite answers for the same artifact. The exclusion **MUST** target only generated or explicitly local-scratch directories; every tracked authored source directory remains in the measured gate scope.

(e) A check body **MUST NOT** re-gate itself on a hand-written path list. An in-body membership test yielding an empty visitor for files absent from its own list is a second scope authority that removes protection while both gates [**FP-M20**](../false-positive/check-verification-rules.md)(c) measures still report the check enabled — severity resolves blocking, the runner reaches the file, the body inspects nothing. Twin hand-kept lists drift both ways: configured paths the body rejects, and body entries whose files were deleted. Membership **MUST** be derived.

**Verify — empirical (required):** ask the tool itself which files it would process for the gate’s arguments and diff that inventory against the directory authority’s own file list — a non-empty difference is scope loss; separately confirm no in-scope file falls outside every configuration block. An inventory diff **MUST NOT** filter both sides through the same membership predicate. A member that the shared filter drops disappears from both lists at once, the comparison balances, and the check reports OK on its own blind spot — it verifies its blindness rather than the tree. A directory-vs-composition module inventory that filtered each side with the same name-pattern regex can print “all modules complete” while an unimported module with a different extension sits in the directory. At least one side **MUST** be unfiltered ground truth, and the discriminating property (here the extension) **MUST** enter the comparison instead of the filter; where a naming convention is the real membership signal, filter on the convention and let the extension be compared. For generated/local output, run in the real production command order, prove a real nested artifact is excluded by every effective scanner configuration, and prove the corresponding tracked source file remains governed and reached.

**Verify — static:** gate commands name directories, not files; no scope declaration contains a hand-written extension set; a single module exports the extension authority and every pattern is generated from it; generated/local-output exclusions are recursive across package roots; every custom filesystem walk delegates to the shared non-source predicate.

A hand-written extension set in a scope declaration is decidable on the single-file lint rung; use the enforcement mechanism the adopting project documents, and record its actual scope and limits. The scope loss it would cause is measured by an aggregate check that diffs tracked source against the files the linter actually reaches, and cross-file source/config/output inventory remains an aggregate check.

Two surfaces a single-file lint rule does not reach:

- *(i) Declarative tool configs.* A linter parses source, not JSON/YAML, so an extension set restated in a tool’s declarative config is outside every single-file syntax-tree rule — detectable by asking the linter for that file’s effective config and getting no matching configuration at all. The repair is (b)’s: move to the tool’s executable config form so the set is derived, which also brings the file back inside the lint scope.
- *(ii) A check’s own internal file-walker.* Scope restated inside a scanner’s body — a default extension array on a shared walk helper, or a literal at its call site — is the same defect as a restated glob, but a rule over it cannot separate a genuine scope declaration from a legitimate per-file discriminator (choosing parser options by extension, or filtering for a format that really is single-extension). That separation needs the walker’s intent, which no property of the file carries; a rule over such literals would be born red and could not be landed at blocking severity ([**FP-M18**](../false-positive/check-design-rules.md) staged ratchet applies, and the baseline is recorded where the debt is tracked). The walker family is closed by derivation, not by the rule: the extension authority **MUST** also export the walker’s dotted form (`.ts`) beside the glob form (`{ts,…}`), because a walker comparing with `endsWith` cannot consume a glob and otherwise keeps its own copy. A shared walk helper **MUST NOT** carry a default extension set — a default nobody passes today becomes a silent second authority at the first call that omits it; make the argument required so such a call fails loudly. What survives derivation is a scope decision (which trees, which languages a check governs), not an extension slip: widening it needs the owning authority’s call and a per-subtree baseline before it lands ([**FP-M18**](../false-positive/check-design-rules.md)). A set’s membership is derived from the toolchain that actually loads the files (for example the bundler’s own resolved source-extension list, read by loading the real config), never from the configuration under audit — deriving it from the audited thing is the circularity that makes a check verify its own blind spot.

## Stated verification limits

A source-only check cannot prove that a provider accepted deployment settings, that an artifact contains the intended configuration, or that a runtime loader resolves every emitted import. Verify those properties using the selected toolchain’s resolved output and the built artifact. If an automated check covers only source files, state that limit rather than treating it as artifact coverage.
