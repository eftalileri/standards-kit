Scope: Package, script, environment, build, deployment, and verification surfaces for JavaScript/TypeScript applications. The owning package or workspace is project-defined.

**Document type:** Normative part — **BE-M1**–**BE-M14**, plus **BE-M20**–**BE-M21**, **BE-M26** (gates, commits), **BE-M31** (third-party package patches), **BE-M33**–**BE-M34** (one app shipped to several delivery channels), **BE-M35** (public host reachability in the target market), **BE-M36** (a browser app runs only on its canonical origin). **BE-M5** and **BE-M10** are not defined; the gaps are never back-filled.

**References:** [README.md](README.md); [build-environment.md](build-environment.md); [decision gates](build-environment-decision-gates.md); [prohibitions](build-environment-prohibitions.md); [monorepo architecture](../monorepo/monorepo-architecture.md).

## MUST

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **BE-M1** | If an application uses TypeScript, its effective compiler configuration **MUST** enable strict checking for the deployable package. An extended configuration must be verified through the compiler’s resolved configuration. | Type safety varies by package or inherited settings. | Inspect the effective compiler configuration for each deployable package. |
| **BE-M2** | If an application consumes environment variables, it **MUST** provide a discoverable declaration/template of supported variable names and any required setup. Do not expose secret values in that template. | Missing or mistyped configuration blocks operation. | Compare environment reads with the declared configuration authority. |
| **BE-M3** | A package that produces a deployable application **MUST** define a non-empty build command in its owning manifest or build system. | No reproducible build entry point. | Run the declared build command in the intended package context. |
| **BE-M4** | Every environment variable read by application code **MUST** be declared in the application’s discoverable environment authority or documented environment schema. | Undeclared configuration and spelling drift. | Compare environment reads with the schema/template using project tools or review. |
| **BE-M6** | Deployment configuration **MUST** identify the selected platform and build/start behavior through its machine-readable deployment source or maintained operational documentation. Validate machine-consumed scalar types against the platform’s current schema. If prose or example documentation conflicts with the provider’s live machine schema and the platform rejects the artifact, the machine schema plus the observed parser result is the authority until the provider resolves the conflict. A library-only package **MUST** state that it has no deployed runtime. | Deployment cannot be reproduced or the platform rejects configuration. | Parse or validate the deployment source with the selected platform tooling; confirm values preserve required types. |
| **BE-M7** | Contributor documentation **MUST** name the package manager, environment setup, and build command for the deployable application. Workspace projects **MUST** identify the owning package. | Contributor setup or build is ambiguous. | Follow the documented setup from a clean checkout or package environment. |
| **BE-M8** | Deployment-specific values **MUST** be loaded from environment configuration or an approved runtime authority, not embedded as literals in application code. New environment variable names SHOULD follow the language ecosystem’s standard naming convention. | Configuration drift or embedded secret/value leakage. | Inspect configuration sources and the application’s secret-handling policy. |
| **BE-M9** | When hosted CI is used, required build and verification gates **MUST** run on the changes and branches the project declares, and the CI workflows **MUST** invoke the build and the project’s own verification gate (**BE-M20**). When hosted CI is absent or retired, the project **MUST** identify the local or release process that enforces blocking checks, the **BE-M20** full gate is the sole enforcement point, and it **MUST** contain every blocking check. Retiring a workflow first maps each check it ran to a full-gate member; that membership floor is then fenced, since the workflow was the only independent copy of it, and no operator in the gate’s resolved scripts may mask a member’s exit status (**BE-M12**) — by the gate’s single orchestrator failing on any non-zero child ([**ENA-PL5**](../enforcement-architecture/enforcement-gates-and-lifecycle.md)), or, until one exists, by a cross-file check. This standard does not prescribe a CI vendor or require hosted CI. | Verification has no clear owner; a retired workflow silently removes a check. | Inspect the project’s declared gate policy and confirm each blocking check has an execution path. |
| **BE-M11** | A monorepo **MUST** identify each deployable package and the location of its environment template, scripts, and build configuration. | Commands or configuration target the wrong package. | Compare workspace metadata with the project’s package map. |
| **BE-M12** | A gate is green only when the gate command’s own exit status proves success. A pipeline observer (`tail`, `head`, `grep`), background-task notification, or outer wrapper status **MUST NOT** be treated as the gate result. When output is captured, preserve the gate status immediately and write a literal `EXIT=<status>` record beside the complete relevant output. A failed focused gate **MUST** be diagnosed and fixed at its root cause before the same gate is rerun; blind repetition or an unrelated broad rerun is not verification. | False-green process bug — **MUST NOT** merge or ship on indirect evidence. | Run the exact gate; inspect its direct status. For captured output, verify one terminal `EXIT=0` record and review the complete relevant failure/output section, not only a tail excerpt. |
| **BE-M13** | Generated artifacts are derived outputs, not authorities. After an authority change or merge, affected lockfiles, schemas/types, API snapshots, hashes, and migration artifacts **MUST** be regenerated from the merged authorities and inspected with artifact-appropriate verification. An executable artifact **MUST** be applied or executed only when its contract requires it and only in an authorized safe environment. “The tool generated it” is not correctness evidence. | Build or deployment drift bug — **MUST NOT** ship an uninspected or stale generated artifact. | Review the generated diff and provenance; run the documented generator/validator. When execution is contractually required, verify the result in an authorized non-production or otherwise approved safe environment. |
| **BE-M14** | Merge and rebase conflicts **MUST** be resolved from the authoritative intent on both sides. An agent **MUST NOT** choose an entire side with `--ours`, `--theirs`, or an equivalent wholesale checkout merely to clear conflicts. If evidence establishes that one side is the only correct authority, record that evidence; otherwise merge both valid changes deliberately and then apply **BE-M13** to every affected derived artifact. | Silent work-loss or stale-artifact bug — STOP until the merged intent is verified. | Inspect every conflict hunk and the resulting diff; document any evidence-backed one-side choice; regenerate and verify affected derived artifacts. |
| **BE-M20** | A project **MUST** define each gate’s owner, command, scope, and blocking membership in one discoverable policy. The fast commit gate runs whole-source lint, the formatter check and typecheck only — cached where safe ([**ENA-PL1**](../enforcement-architecture/enforcement-gates-and-lifecycle.md)); the formatter is its own step, never a lint rule ([**ENA-N8**](../enforcement-architecture/enforcement-anti-patterns.md)); a full gate runs every check the project treats as blocking plus the [**SEC-GC-9**](../security/security-governance.md) security review before code or operational configuration leaves the author’s machine. Neither gate runs per edit, and each gate name has exactly one owning script across the repository. Any exception, such as a documentation-only path exemption, is valid only when the project explicitly defines it and classifies the complete change set. Each gate and exception states both what runs and what is excluded. An unclassified mixed change cannot use a documentation-only exception, and an exception does not remove checks from CI workflows or repeal the kit’s Markdown content and structure obligations. This standard does not prescribe hosted CI or a universal test-runner policy. | A named gate omits a required check or an exception is applied to a mixed change. | Compare declared gate membership with the actual scripts/workflows and inspect the complete changed-path set for any exception. |
| **BE-M21** | Every finding the gate reports is fixed before the gate is called green — warnings included, and regardless of who wrote the code. Two excuses defeat a gate and both are refused. “It is only a warning”: a warning that is genuine is a defect the tool happened to rank lower; leaving it standing normalises a non-zero count, and once the count is non-zero nobody notices the next one. Target zero, for errors and warnings. “It is not mine”: where several agents or sessions share a branch, a finding in code the current author did not write is still theirs to fix — ownership is not a property the gate can see, and a finding routed to a person rather than to the code is a finding nobody fixes. Where the volume of pre-existing debt makes that impossible in one change, the answer is the staged ratchet of [**FP-M18**](../false-positive/check-design-rules.md), never a tolerated floor. A genuine finding is fixed at its source; only a confirmed false positive is suppressed, in the form [**FP-M24**](../false-positive/guard-runtime-rules.md) requires. | A gate whose green means nothing — the count is not zero, so a new finding is invisible among the tolerated ones. | The gate command’s own exit status is zero and its report shows zero errors and zero warnings (**BE-M12** — an observer’s output is not the proof). Review: no finding in the diff is dismissed by author or by severity. |
| **BE-M26** | A commit in a tree the author does not exclusively own **MUST** name its paths. Staging and committing are two operations and the gap between them is not atomic: whatever is staged inside it — a concurrent worker, a formatter, a watcher — is committed too, under the first author’s message and review. Pass an explicit pathspec to the commit, or re-read the staged set just before it and prove it equals the intended list; a blanket “commit everything tracked” flag fails the same way. | Review and history bug — one author’s commit carries another’s unreviewed work, its message describes the wrong change set, and reverting it silently reverts the stowaway; must not push. | Review: the commit carries a pathspec, or the run records a staged-set comparison taken just before it. Not tree-decidable. |
| **BE-M31** | A local patch to a third-party package **MUST** be applied by exactly one authority, and that authority **MUST** run in the project’s explicit install entry, in the configuration that native code generation or compilation evaluates before it reads patched sources (where such a step exists), and in the bundler’s configuration before any module is resolved. An install lifecycle hook is not such an entry: dependency lifecycle scripts are off ([**SEC-SUP-2**](../security/security-supply-chain-admission.md)), which skips the project’s own hooks too, and a tree installed before the patch landed bundles the unpatched code with no signal — an over-the-air update bundled from such a tree silently withdraws the fix from every installed app. Application **MUST** be idempotent and **MUST** fail loud both when a patch does not apply and when it was made for a different package version, so an upgrade cannot pass without deciding whether upstream has shipped the fix (then the patch is deleted). A patch **MUST** reproduce the upstream fix exactly when one exists, and its upstream reference is recorded in the project’s decision record for that patch. A patch to the native sources of a package that ships a prebuilt native artifact the build links by default **MUST** be paired with the build’s build-from-source declaration for that package, and the same authority **MUST** fail loud when the declaration is missing: the build links the prebuilt artifact and the patched source is never compiled, with no signal. | Silent regression — the fix ships through one build path and disappears through another; must not ship. | Static inspection: the explicit install entry, the code-generation configuration and the bundler configuration call the same authority, which passes the patch tool’s fail-on-error and fail-on-version-mismatch options and refuses a native patch on a prebuilt-linked package. Real-run observation: a drifted patch target makes the install entry, the code-generation configuration and the bundler configuration exit non-zero; a code-generation run on a tree whose patches were reversed re-applies them first; a bundle exported from a tree installed with lifecycle scripts disabled contains the patched code; removing a patched package from the build-from-source declaration makes the authority exit non-zero. The bundler-side call is the mechanism itself, not a check; whether a patch mirrors upstream exactly is review-held. |
| **BE-M33** | When one application ships to more than one delivery channel (e.g. store binaries with over-the-air updates and a static web export), every release **MUST** build each channel’s artifact from the release commit before anything ships, through one release script per channel that builds before it uploads or deploys and stops on the first failure. Reason: a change that compiles for one channel but not another otherwise breaks the next release of every channel. | A channel whose artifact is first built at deploy time, or deployed by hand; must not ship. | Static: each channel’s release script builds before it uploads or deploys and exits non-zero on any failed step ([**ENA-P1**](../enforcement-architecture/enforcement-admission.md) rung 1). A separate full-gate build step per channel is admitted only where a build break limited to one channel has a recorded defect history ([**ENA-A2**](../enforcement-architecture/enforcement-admission.md)). |
| **BE-M34** | The channels of one application **MUST** release from the same commit in a fixed order: the channel without per-client rollback (the static web deploy) first, the over-the-air update only after it succeeded, never one without the other for a change that both carry. Reason: two channels on different commits serve two behaviours of one backend contract. | Diverging clients; must not ship. | Review: the release report names one commit, the web deployment id and the update group id, in that order. The order is a procedure, so this rule is review-held ([**ENA-GV3**](../enforcement-architecture/enforcement-admission.md)). |
| **BE-M35** | A public host **MUST NOT** be served from a shared platform domain or its shared edge addresses that are blocked in a target market; its reachability **MUST** be checked from that market’s networks before launch and after any hosting or DNS change, and a blocked host is moved behind addresses that market can reach (e.g. the zone’s own proxied records). Reason: a host that resolves to blocked shared addresses is unreachable for the whole market while every check from outside it passes. | Unreachable product in a market; must not ship. | Review: the release or DNS-change report names the networks the host was opened from. Reachability is measured outside the repository, so this rule is review-held ([**ENA-GV3**](../enforcement-architecture/enforcement-admission.md)). |
| **BE-M36** | A browser app whose API admits one exact web origin **MUST** start only on that canonical origin: loaded on any other host (the hosting platform’s own default domain, a preview deployment), its release bundle **MUST** navigate to the same path on the canonical origin before the app starts, decided by one startup module reading the same origin constant the server’s allowlist uses; loopback hosts are exempt for local checks. The other hosts **MUST NOT** be added to the credentialed allowlist instead. Reason: every request from a non-canonical host is refused, so the app there can only show a broken screen, while a second allowed origin is a second cookie and CSRF boundary. | Broken app for users on a stale address; must not ship. | Review: the startup module is the single decision point; a mechanical check would not meet [**ENA-A1**](../enforcement-architecture/enforcement-admission.md) (one entry point, no recurring class), so this rule is review-held ([**ENA-GV3**](../enforcement-architecture/enforcement-admission.md)). |
