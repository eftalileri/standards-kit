# Build and environment — environment-key authority

```kit-cover

part-of: README.md
```

**Scope:** The environment-key surface and the process that consumes it. Applies when an application has a validated configuration authority, especially when operator, migration, or maintenance commands can write data.

**References:** [build-environment.md](build-environment.md); [executable config and gate scope](build-environment-config-and-runtime-floor.md); [SSoT principles](../ssot/ssot-principles-and-precedence.md); [security](../security/README.md).

## MUST — BE-M

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **BE-M23** | An environment key read through a validated configuration authority **MUST** be declared and validated by that authority. Where the environment is funnelled through one parsed, typed object, that object is the single answer to *which settings exist* ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)). An undeclared key read off it is not announced by its absence: a permissive schema — catch-all, passthrough, index signature — hands the raw value back, so the read works at runtime and reports nothing. Three guarantees go silently together: the key skips the authority’s validation, it is absent from the type it publishes, and — the sharpest — a misspelled key name becomes undetectable, since an unknown name and a mistyped known one are the same read. That makes this a safety rule, not a tidiness one: where the key is a destructive operation’s confirmation or mode token ([**REP-M-28**](../repository/repository-irreversible-operation-evidence.md)), an operator exporting exactly the token the command documents still runs a gate that never sees it. Declare it in the existing authority, in the shape its sibling keys use — never a second reader for one key. | A setting bypasses validation, typing and typo defence while every gate stays green. | Derive the declared key set from the authority’s own declaration (never copy it into the check) and resolve every accessor-then-property read in the tree against it; report an unresolved key at its line. Limit: only the direct shape is decidable — a read through an intermediate binding or computed key is an under-catch, not a false positive. A type checker decides the same class only for files inside a compiled project, so a cross-file check is the half independent of it. |
| **BE-M24** | Every process that reads environment configuration **MUST** consume it through the validated authority. Operator, migration, and maintenance commands are included; they **MUST NOT** independently load dotenv-style files or read raw process environment values when the application has a shared authority. The shared-helper and derived-field obligations [below](#be-m24--one-environment-read-path) bind. | A script may run with different, unvalidated configuration than the application — for example, a production-writing script configured by an unvalidated value. | Use the enforcement mechanism the adopting project documents; verification detail [below](#be-m24--one-environment-read-path). |
| **BE-M27** | A process that is not the released production deployment **MUST NOT** resolve the production datastore as a write target. Point local, pre-release, or harness work at an isolated scratch store, or establish read-only mode and declare it before connecting. The released deployment is the single writer of production data ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)); a build nobody released is by definition a second one. The damage is not the write the operator intended but the incidental one — a half-migrated tree writes whatever its half-changed code writes, and those rows then live inside the authority every later measurement reads. The prohibition is absolute rather than a preference for two reasons: it is silent (the run leaves no deployment record, so its artefacts are attributed to production code that never ran) and it is beyond review (the connection target came from the operator’s shell, so neither the repository, the deployment history nor the change record can say where the row came from). A production read-only measurement stays legitimate — some claims cannot be measured any other way — but it is a different run, declared read-only before the connection opens and never sharing a code path with one that writes. Reachability is not identity, and a gate that decides this **MUST** measure both: a tunnel or port-forward maps the production store onto loopback, so a socket address alone is a fact the operator’s shell can forge. The fact it cannot forge is what the server advertises about itself in the handshake (its own address, its peers, its replica-set name). A store counts as scratch only when both are loopback, and an advertised shape the predicate does not recognise resolves as shared; the predicate is written against measured handshakes, never guessed ones ([**FP-M18**](../false-positive/check-design-rules.md)). | Unreleased code creates untraceable production data or mutates authoritative state, and nothing in the repository can explain the rows. | Declare the connection target and execution mode before connecting; evidence that any run that reached the production store was read-only. Limit: the launching shell’s connection target and the production store’s identity are not in the source tree, so this needs a runtime mechanism — for example, persistence boot that resolves the authority from the store the connection actually reached and refuses an unreleased process on a shared store before the first write. A store advertising no address at all is indistinguishable from a local one through a tunnel; closing that needs an operator-declared expected identity. |
| **BE-M32** | A value that a release build embeds into the shipped binary from the environment — a provider client token, an SDK key — **MUST** be read from the release build’s own environment authority (the build service’s environment for that profile), never from a developer-local env file, and the release build **MUST** fail when it is absent or malformed; the configuration that injects it **MUST NOT** silently drop the key. Where the value is valid only as a pair with an identifier kept elsewhere (an application ID in the committed config), the release build **MUST** also ask the issuing provider whether the pair is accepted before it builds, and **MUST** prove that the provider actually validates the supplied value (a deliberately false value must be rejected), because the identifier may be readable without any credential. Reason: a store binary cannot be patched over the air; a dropped or mismatched value fails only on the device, against the provider, where no crash or error channel sees it, and the two environment stores (local file, build service) drift the moment one is updated alone. | Every binary until the next native release ships without working provider calls while local builds look healthy. | Inspect that the configuration injecting the value throws in the release profile when the value or identifier is missing or malformed, and that a pre-build hook checks the pair against the provider with a false-value control and stops the build on rejection or persistent unreachability. Limit: a release archive built outside the build service skips the hook. |

### One environment read path — BE-M24 clauses

Where one authority parses the environment once against a schema, a script that calls the dotenv-style loader itself and then reads the raw environment object is a second environment path ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)): it produces the same data by a route that carries none of the authority’s guarantees — no schema validation, no published type, no typo detection, and none of the precedence the authority fixes between its sources. Nothing announces this, because a raw read works; only the guarantee is missing. The exposure is not symmetric with the application’s: these scripts run outside the request path, usually against production data, often issuing bulk or irreversible writes, and the operator’s only evidence that the run is correctly configured is the value the script read.

Where the authority cannot serve a script’s launch conditions on its own — a working directory the authority does not resolve, a load order the process needs before its first read — the answer is one shared entry-point helper that performs the load and hands control back to the same authority, never a per-script loader.

Where the authority publishes a derived answer over several alias keys — one resolved value standing for two historic names — the script consumes that derived field, never its own re-derivation: a re-derivation is a second writer of the same derivation ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)), and one written in the opposite precedence order is worse than an unvalidated read — where those keys name a database, the script silently connects to a different target than the application it shares an environment with, and both runs look correct. The rule binds the read path, not the value: whether the key exists in the authority is the sibling question **BE-M23** answers.

**Verify — static (single file):** within the directory a script class lives in, a dotenv-style loader import and a raw process-environment read are both decidable from the file’s own syntax, so this is a lint rule, not a cross-file check. Membership is the directory, never a hand-written script list ([**FP-M32**](../false-positive/check-verification-rules.md)); a legitimate loader is kept outside that directory, so the exemption is expressed by placement rather than by an allowlist the next script will not be added to. Measure the baseline over the tracked tree, not the working tree: a directory of this class also holds ignored, untracked one-time analysis scripts that never reach CI, so a baseline that counts them makes the gate’s answer depend on the machine it ran on — red locally, green in CI; the ignore authority the linter already honours must be the one the baseline uses. Where the shared entry-point helper still lives inside the guarded directory, the loader arm cannot be opened yet without the check being born red, and the only way out would be the name exemption this row forbids: stage the two arms with a rule option whose default stays the full prohibition, and declare the closure order — move the helper out, convert the remaining consumers, then drop the option. A staged arm is a measured debt with a stated order, not an exemption: membership is still read from the directory alone.

Closing that staged arm has three parts, and each has a wrong obvious answer.

- (a) *The helper’s new home is chosen against the build-artifact boundary, not merely “outside the guarded directory.”* The obvious destination — the directory the validated authority itself occupies — is usually inside the deployable application’s compile set, so a helper that only ever runs from a command line would be emitted into the shipped artifact. The destination must be outside the guarded scope, outside that compile set, and already inside the same type-check and lint scopes as the scripts it serves; a repository that already keeps a shared-helper directory for that script class satisfies all three with no new gate plumbing, while a brand-new top-level directory silently starts outside every existing lock and must be re-attached to each one.
- (b) *Scope shape: one recursive directory minus one directory beats a list of directories.* Once the helper sits in that sibling directory, the guarded scope becomes the whole script tree with a single directory-level exclusion — still placement, still no name. Enumerating each script subdirectory instead reproduces the list this row forbids, and a list cannot name the subdirectory nobody has added yet.
- (c) *Drop the option from the rule’s own schema, not only from the configuration.* An option left declared can be re-passed silently; an empty schema turns any attempt to re-stage into a configuration error.

Limit: an environment read reached through an intermediate module the script imports is invisible to a single-file predicate — an under-catch, not a false positive.
