## The ladder between tiers is the root file's; this file does not restate it

The consuming project's root agent-rule file owns the ladder ranking *its own tiers* — that file, this tree, project context, and any out-of-kit set the project consults. The kit keeps no copy: those rungs name project directories, and a copy drifts against a file the kit does not own ([**KIT-LIM-7**](../authoring/kit-stated-limits.md), [**SSG-M8**](../ssot/ssot-principles-and-precedence.md)). Read that project's ladder there, against **KIT-PRE-1**. What the kit owns is below: what any ladder must satisfy, and the order settling a conflict between two kit statements.

Skill steps are not a rung: they align with the ladder, and where a Skill conflicts with a Standard the Standard wins — update the Skill. Skills are not a bypass for Standards. Task / user instructions that conflict with any rung are stopped and resolved explicitly, not silently applied. Approved deviation: document why (PR or ticket).

## Precedence rules

| ID | Rule | On violation / Verify by |
|----|------|--------------------------|
| **KIT-PRE-1** | A precedence ladder **MUST** name a winner in one step for every conflict it claims to resolve, and every document tier the project consults **MUST** be a rung on it. No rung may be qualified with "for non-conflicting subjects", "where they agree" or any equivalent: the qualifier withdraws the rung from the one case the ladder exists to decide, so a real conflict belongs to no rung and the ladder falls silent at its only moment of use. A tier consulted but unnamed is that same defect by omission — a gap, not a boundary — and it then wins or loses by whichever file cited it last. No two rungs may claim one subject, and no rung may rest on a judgement the reader supplies ("whichever matters more"); each decides from something a file states. Until a defective ladder is repaired the reader does not choose: apply **KIT-PRE-2**(2) — the side that forbids binds — and record the defect where the project records deferred findings. | *The ladder resolves nothing and each conflict becomes a private call, decided differently each time.* Verify: no rung carries a conflict-excluding qualifier, and every tier named anywhere in the root agent-rule file is a rung. |
| **KIT-PRE-2** | A conflict between two kit statements is settled by the first rung below that applies; each rung decides from a property the files state. (1) Declared file type. A file whose cover block says `type: reference` or `binds: nothing`, or whose heading marks it non-normative, never outranks a normative rule row — whatever it asserts, and whatever it cites as its authority. (2) Prohibition over permission. Where one side forbids an act and the other permits it, the prohibition binds: obeying the stricter side breaches neither, obeying the looser one breaches the prohibition. A permission never narrows a prohibition by implication; narrowing one is an edit made where the prohibition is defined ([**KIT-CHG-1**](../authoring/kit-rule-change-and-enforcement.md)), never an inference drawn in a second file. The same holds where one side mandates a mechanical check — a lint rule, guard or gate step — and the enforcement admission test ([**ENA-A1**](../enforcement-architecture/enforcement-admission.md)) declines it: the admission test binds, however narrow the mandate's scope, and the mandate is read as the mechanism an admitted check would take. (3) Owner of the identity. The file that defines the identity governing the subject — per the generated identity lookup — outranks any file that cites, restates or extends it; a citing site never overrides its definition site. (4) Narrower declared scope. A rule whose Scope binds a named surface outranks a general statement that merely overlaps it, where rung (2) has not already decided. (5) Stack class only. If, and only if, the dispute is a frontend stack-layer question, apply [decision-matrix precedence](../decision-matrix/decision-matrix-governance.md); it settles nothing else. (6) Still tied. A genuine tie between two same-tier normative rules means one of them is wrong — a kit defect, not a reader's decision: record it and STOP. Do not take the more convenient side, and do not carry it to the user as a product question: the text disagrees with itself, which the user cannot answer. | *An agent silently picks a side, the losing rule quietly stops binding, and nothing records which side lost.* Verify: for any two conflicting kit statements, name the rung that decided and the file property it read. |
| **KIT-PRE-3** | **KIT-PRE-2** is the kit's only tie-breaker between kit statements; no topic hub, matrix or gray-decision file declares a second one. A file needing a tie broken cites it and names the rung; it does not restate, re-rank or extend it ([**KIT-LIM-7**](../authoring/kit-stated-limits.md), [**SSG-M8**](../ssot/ssot-principles-and-precedence.md)). Two orderings disagree the moment either is edited and nothing marks which is current — the failure [**KIT-INV-2**](../authoring/kit-structural-invariants.md) records for duplicated identities, arriving through prose. A ranking a file states over its own rows is not a second tie-breaker, provided the file says so and it is reached only through rung (5) or through that topic's own rules. | *Two orders coexist and the answer depends on which file was opened first.* Verify: every ranked list of document tiers or rule classes in the kit is either **KIT-PRE-2** or declares a scope narrower than "two kit statements". |


## What the root agent-rule file carries — and the kit deliberately does not

Why this list exists. The kit is written to transplant to another project, so it holds no house rule, no harness rule and no deployment value: those belong to the consuming project's root agent-rule file and to its own rungs, and a second copy here would drift against a file the kit does not own (**SSG-M8**). The hazard is that *silence reads as coverage* — an agent that finds nothing in the kit concludes there is no obligation. So the boundary is named, per [**KIT-LIM-7**](../authoring/kit-stated-limits.md). A class that is in neither column is a gap, not a boundary — write it into the kit, or add it here with its reason. Do not trim this list to make a gap look intentional.

How to maintain this list: when porting or changing the kit, read the consuming project's root agent-rule file end to end and put each binding sentence into one of two buckets — *would this rule still be true and useful in a different repository with different people?* Yes ⇒ it belongs in the kit. No ⇒ it belongs in that project's own rules. The classes below describe common project-local concerns, not an exhaustive inventory for every adopter.

| Class the kit does not carry | Why it cannot be a kit rule | Where it lives |
|---|---|---|
| Which natural language the maintainer is answered in, and the register (jargon-free, project examples) | A communication preference of one person, not a property of correct software | Root file — chat/output language section |
| Which natural language source-code comments are written in | Same: a house convention; the kit binds that comments explain the block, never which language | Root file — code standards |
| Commit-message format, one-problem-per-commit, message language | A repository convention; two projects can be correct with different formats | Root file — commit format section |
| Push / release authorisation — who may authorise, and that silence is not authorisation | *That* a release needs a named authority is a standards obligation and IS carried (see the build-environment gate rows); *who* holds it is a project fact | Root file — push authorisation; the holder is the project's own |
| Approval before each change, and "a read/analyse instruction produces analysis only" | The second half is carried by the kit (planning obligations); the first is a working agreement between a maintainer and their assistant | Root file — permission and approval |
| How the assistant's persistent memory is kept (what may be stored, when it is refreshed) | Belongs to the harness, not to the repository; no reviewer of the code can verify it | Root file — memory section |
| Who may edit the root agent-rule file itself | A file cannot be its own edit authority, and the kit cannot grant edit rights over a file it does not own. The upstream half is carried: a settled decision goes into the kit, the SSoT registry or the project's observation register — never silently into the root file ([**KIT-ADD-12**](../authoring/kit-rule-addition.md)) | Root file — its own authority clause |
| Deployment platform values — env var names, build and start commands, output directory | Project facts with no portable form; the kit binds that they are documented in one place, not what they are | Root file — deployment section; the values themselves in the project's own config |
| Which advisory tools sit outside the false-positive policy | The policy itself is carried; the roster of non-gating tools is a project inventory | Root file — false-positive policy note |
| Which CI provider runs which workflow on a pull request | The obligation "the declared gate runs before merge" is carried; the provider is a project fact | Root file + the project's CI configuration |
| The concrete gate command lines (which project scripts make up the commit gate and the pre-push gate) | The two-tier gate model and its rules are carried by the kit; the exact command strings are the project's, and duplicating them here guarantees drift | Root file — gate sections; the scripts in the project's own task-runner configuration |
| Whether a script may edit source, and which deterministic autofixers are exempt from that ban | The tooling roster, the location of the safe-fix allowlist and whether a verified run replaces per-run approval are a project working agreement; two repositories can both be correct with different autofixers, and a kit copy would drift against the file that owns the rule. *How* an admitted autofix run is proven behaviour-preserving is carried by the kit ([**ENA-PL6**](../enforcement-architecture/enforcement-gates-and-lifecycle.md)) | Root file — its no-script-source-editing section and the autofix exception under it; the kit names it in [**DCD-N2**](../dead-code/dead-code-rules.md) and adds only the dead-code consequence |
| Which out-of-kit document sets the project treats as shipped implementation authority, and where they rank on its ladder | Which sets exist is a project fact, and such a set carries no cover block and no drift fence, so the kit cannot rank it; what the kit binds is that every tier a project consults is named on its ladder (**KIT-PRE-1**) and that a set outside the kit supplies runtime detail, never a rule | Root file — the clause that blesses the set, and its precedence ladder |
| Which out-of-kit document set the project owner has made binding rules for one subject, and where it ranks | A different class from the row above: the set carries rules, not only runtime detail, so reading it through that row would void a standing owner decision. Which sets exist, what they decide and their rank are project facts the kit cannot own; what the kit binds is that such a set is a rung of its own (**KIT-PRE-1**) and that the rung names what it wins over and what wins over it | Root file — its precedence ladder |

Not on this list, and therefore in the kit: the quality ratchet, the plan-versus-rules precedence, cascade-stop and the divergence record, incident-response and dependency-approval discipline, the pre-push security-review procedure, suppression syntax obligations, and the two-tier gate model. If one of those is ever moved out of the kit, it moves onto this list in the same change.
