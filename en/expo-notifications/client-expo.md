## **MUST** — NOTIF-CLI-M

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **NOTIF-CLI-M1** | Use one documented import or project-owned wrapper for `expo-notifications` APIs so client behavior has a clear integration boundary. | Inconsistent client integration. | Review notification API imports and the selected wrapper boundary. |
| **NOTIF-CLI-M2** | Register foreground notification behavior once, before interactive UI depends on it. Explicitly set the supported presentation options for the selected Expo SDK (for current SDKs, banner/list visibility, sound, and badge behavior). Do not depend on an older SDK’s default alert behavior after upgrading. | Undefined or inconsistent foreground behavior. | Review handler registration order and compare option names and behavior with the current Expo Notifications API. |
| **NOTIF-CLI-M3** | On Android, create every notification channel used by provider payloads before a push may arrive. Channel identifiers are stable and come from one shared client/server contract (NOTIF-CLI-M13). The channel name is user-visible text (the OS notification settings list it), so it **MUST** come from the catalog in the active app language, be created once that language is resolved and be re-applied when it changes; it **MUST NOT** be a literal or reuse the channel id. | Channel mismatch or silent delivery loss. | Compare created channel identifiers with the payload contract and verify on a built Android app. |
| **NOTIF-CLI-M4** | Route notification-response events through one handler that validates the payload and delegates navigation to the application’s navigation authority. | Duplicate navigation or dead end. | Review listener ownership and notification tap handling. |
| **NOTIF-CLI-M5** | Obtain an Expo push token using the project identity from the application’s Expo configuration authority. On a supported physical device, missing project identity or token acquisition failure **MUST** produce an actionable failure outcome. | Missing or unusable token without diagnosis. | Review the token request and its configuration/error paths against the selected Expo project. |
| **NOTIF-CLI-M6** | When the backend reports that a stored push credential is unregistered, clear the matching client cache so a later registration can obtain a fresh credential. | Repeated sends to an invalid credential. | Review the server invalidation response and client cache reset behavior. |
| **NOTIF-CLI-M7** | On notification open, resolve the validated navigation payload through one navigation authority. Missing or invalid destinations **MUST** fall back to a usable in-app notification surface. | Dead-end tap behavior. | Review the resolver, its validation, and its fallback route. |
| **NOTIF-CLI-M8** | Token registration **MUST** have one retry owner, a finite attempt cap, a total time budget, and cancellation support. Retry only when the application’s canonical transport classification authorizes it; do not infer retryability from status codes or message text at a second call site. Cancellation is a distinct outcome and **MUST NOT** be reported as a registration failure. Exhausted or non-retryable outcomes flow through the client error/observability authority. | Duplicate requests, unbounded retry, or silent registration failure. | Review retry ownership, total bounds, cancellation, and terminal error reporting across the registration flow. |
| **NOTIF-CLI-M9** | Push-credential acquisition **MUST** be a bounded, cancellable command. Retry only failures whose transience is established from a structural provider error, using one retry authority with a finite attempt cap and total time budget. The retry decision is read from the closed reason set's total fact map, in which every reason answers both "retry inside the command?" and "permanent for the session?" (encoded so the contradictory pair is unrepresentable); a second hand-kept list of retryable reasons **MUST NOT** exist. Permission refusal, unavailable configuration, unsupported execution environments, and cancellation **MUST NOT** be retried as transient failures. Accept a cancellation signal; cancellation is a distinct outcome, not a delivery error. A reason that is neither retryable inside the command nor permanent (a provider failure whose transience cannot be proven structurally) is not retried in the command but still receives the lifecycle re-attempt: when the command ends on a non-permanent reason while the session holds no confirmed registration, the caller re-attempts at the next canonical foreground or reconnect transition through the project's existing lifecycle and connectivity authorities (no second app-state or network listener; every such authority that is actually fed by an event source), under its own finite re-attempt cap, and stops as soon as the session holds a confirmed registration for that identity. Exactly one terminal report per reason is emitted per session episode, after the attempts are exhausted and never per attempt, carrying the measured attempt count. | Bug — a registration failure is either silently lost or retried without bounds. | Review retry ownership, cancellation, and terminal failure reporting. Confirm foreground/reconnect recovery uses lifecycle authorities that are actually connected to native events. |
| **NOTIF-CLI-M10** | A push received in the foreground, and a tapped push, **MUST** refresh client caches through one decision authority that maps the closed notification-type set to the existing invalidation authorities (notification list and badge on every push, entity screens by type and the payload's audience/tenant scope); the type map **MUST** be compiler-total over the type set. Listener callbacks **MUST NOT** write per-type invalidation themselves and **MUST NOT** let an exception escape — a failure goes to the no-throw classification authority ([client observability](../client-observability-rn/classification-authority-and-outbound-links.md)). | Bug — a push announces a server write the open screen has not read; per-type branches in the listener drift as types are added and leave screens and the badge stale, and an exception thrown from a native listener reaches the fatal handler. | Review that one listener file only parses and delegates, that the compiler rejects a type missing from the map, and that scope mapping is correct (review-held). |
| **NOTIF-CLI-M11** | A tapped tenant-scoped notification **MUST** open its target in the notification's own tenant. Which tenant a target needs is decided by one authority next to the target resolver (account-level and tenant-independent audience targets need none), and the resolver **MUST NOT** return a tenant-scoped target while another tenant is active — the gate stands once, not per type. When the tapped notification's tenant is not the active one (or the session's tenant scope is not established yet, for example on cold start), the client **MUST** wait for the scope, then switch through the single tenant-switch flow with all its stops — at most once per tap — and open the target only after the switch. The wait is read from the app's single scope-gate authority and **MUST** end at a terminal scope state (never an unbounded pending open that fires later); a tenant absent from a cached tenant list is re-read from the list authority once before it is called inaccessible. If the scope is terminal or the switch is refused or fails, the client says so truthfully and does not open the active tenant's screen. | Bug (cross-tenant) — a per-type gate is forgotten on new types, and a multi-tenant user sees another tenant's data under the tapped notification. | Review. |
| **NOTIF-CLI-M12** | When the client mounts a different navigator tree per mode (for example a consumer tree beside an operator tree), the target resolver **MUST** label each target with the tree that registers its route, decided in one place, and every tap surface **MUST** compare that label with the mounted tree derived by the same single authority the root navigator uses. A target whose route the mounted tree lacks **MUST NOT** be navigated in that tree, in either direction; every tap surface (push, in-app list, in-app modal) opens it by switching through the single mode-transition flow first — at most once per tap, then the tenant rule (NOTIF-CLI-M11) — and says so truthfully if the switch is refused or fails. | Bug — dead end: navigating a route the mounted tree lacks is silently dropped, so the tap does nothing. | Review. |
| **NOTIF-CLI-M13** | Android notification channels **MUST** come from one catalog shared by the server and the client: the closed channel set, each channel's importance class, and a compiler-total map from every notification type to its channel. The server writes the push channel id only from that map and the client creates exactly that set before a push can arrive. A channel id that released binaries already created keeps the class it was created for — the platform never lets an app lower a created channel's importance, so the most time-critical class stays on that id and only new classes get new ids. | Bug — every type shares one maximum-importance channel, so a person cannot silence low-priority types without silencing urgent ones; a re-purposed old id keeps its old importance on every installed device. | Review that the compiler rejects a notification type missing from the map and that the server payload builder and the client channel creation import the same catalog. |
| **NOTIF-CLI-M14** | The client **MUST** subscribe to the platform's push-token rotation signal and start a new registration when the observed token differs from the last token the registration acquired. Because reading the token itself emits that signal, a token equal to the last acquired one **MUST NOT** start a command, and a rotation observed during a registration in flight is picked up when that flight ends — single flight is kept. | Bug — after a rotation the server keeps sending to a dead token until the next cold start; comparing with the last *registered* token instead loops whenever a registration fails. | Review. |
| **NOTIF-CLI-M15** | Cache refreshes triggered by received or tapped pushes **MUST** go through one burst collector per session lifetime: pushes arriving within a short declared window after the first are merged and each screen family is refreshed once, with the union of the identifiers the burst named. The collector's pending burst is dropped when its session lifetime ends. | Bug — a fan-out of N pushes restarts the same refetch N times (each invalidation cancels the previous one), costing N requests and N re-renders for one change. | Review. |
| **NOTIF-CLI-M16** | The app icon badge **MUST** mirror the unread count the in-app bell shows, read from the same query and scope, and be written only from a count the server answered in the current app run inside a signed-in session — on Android a written zero also removes the app's notifications from the tray, so nothing is written before the count is known and a count restored from a persisted query cache is never written. When the signed-in identity retires, the presented notifications and the badge **MUST** be cleared by the single device-data retirement authority, with a re-read proving them empty. The tray removal call resolves when the request is dispatched, not when the OS has applied it, so that proof is a bounded loop that re-issues the removal and re-reads under a declared attempt cap and step — never one immediate read — and an exhausted budget stays an unverified result; the tray and the badge are proven and reported as separate surfaces. A runtime that cannot hold such a surface at all (a browser context without the Push and Notifications APIs) answers clean from the same capability read push acquisition uses — never by catching the missing API's rejection — while a rejection from an API that exists stays unverified. | Bug — the badge never moves, and the next person on a shared device reads the previous account's notifications from the lock screen; a single immediate re-read reports a removal the OS was still applying as a residue, and one shared surface label hides which of the two remained. | Review. |

## Stated limits

A provider may expose one structural error code for multiple outcomes. If the response status or another discriminating field is unavailable, do not infer retryability from message text or timing. Use the conservative failure classification and re-evaluate when the provider exposes stronger structured evidence.

A source-level check can inspect local cancellation and listener wiring, but cannot prove asynchronous ordering or that a lifecycle signal is fed by a native event source. Review those properties against the selected query, lifecycle, and connectivity integrations.


NOTIF-CLI-M7 clarification — a tapped target whose entity no longer exists. A notification outlives the record it points at, and the target resolver is a synchronous, pure function of the payload: it cannot know the record is gone and **MUST NOT** be made to fetch it. The "record no longer exists" answer is a property of the destination screen, decided once there from the server's registered not-found code (read through the project's single client error-code reader, never from message text): the screen renders a designed "this record was deleted" empty state — not a full-screen error, not a blank screen — with an action to a durable place (the entity's list), and no per-entry-point branch is opened in the resolver or in any second screen. A "go to the related record" action is offered only for identifiers the payload really carries. The registered not-found code is an expected outcome: it goes through the single client failure-classification authority as a warning and is never a crash event, and the query is not retried. Whether a destination screen reached by a notification handles its own registered not-found code is a per-screen property no single-file check decides; it stays a review obligation.

## **MUST NOT** — NOTIF-CLI-N

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **NOTIF-CLI-N1** | Do not swallow token registration or backend-registration failures on a supported physical device. Surface them through the application’s established client error and observability authorities. | Silent failure. | Review all caught registration failures and their user-visible/observability outcomes. |
| **NOTIF-CLI-N2** | A simulator or emulator may lack a provider token; keep that development-only outcome distinct from a physical-device registration failure. | Misclassified severity. | Review the runtime environment branch and confirm it does not hide physical-device failures. |
| **NOTIF-CLI-N3** | Do not log raw push credentials in production, including tokens returned by the provider. | Credential exposure. | Review logs, crash context, and payload diagnostics for token redaction. |

## Navigation contract (local minimum)

Shape (must match NOTIF-BE-M2 payload): `navigation: { screen: string; params?: Record<string, string> } | null`. If `null`, client uses notifications list fallback (NOTIF-CLI-M7).
