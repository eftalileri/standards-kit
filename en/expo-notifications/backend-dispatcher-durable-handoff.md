Scope: Domain events whose synchronous HTTP producer would otherwise wait for push provider delivery. This is a clarification of [NOTIF-BE-M4/M5](backend-dispatcher.md), not a separate provider delivery authority.

When a committed domain command would otherwise await provider delivery within the response, its immutable recipient/content/event identity is written in the same transaction as that command and drained by a durable leased worker. The domain queue's `completed`/`cancelled` state reports work processing only; the Notification ledger remains the single authority for provider acceptance and receipt. A queue row that ends `cancelled` **MUST** carry its reason from one closed set owned by the queue contract (for example: no push registration, event superseded, recipient no longer eligible, subject deleted, tenant closed), written by the cancel transition itself and decided by the validity predicate's own verdict — a bare `cancelled` merges facts that need opposite follow-ups (a missing token, an edited event, a recipient who left). Verify: the cancel writer takes the reason as a required parameter and the stored field's enum consumes the closed set.

The same requirement applies to an HTTP producer that detaches notification work after commit: detachment is an optimization, never a durability boundary. Snapshot reads join the command transaction and bypass request memo/cache; no eligible event is acknowledged without its recoverable job. Where one event has one job per frozen recipient, those rows are written together and retain separate terminal outcomes, so cancelled or failed work never becomes an all-sent event. Initial intent creation or retryable reclaim fences the exact active job and current validity predicate in the same transaction as `PENDING+NOT_STARTED`; the same kernel fences the exact lease and predicate again at `STARTED`. A stale worker cannot insert a new unstarted intent after cancellation. Cancellation writes the existing predicate records and exact outbox/ledger verdict together, preserving business timestamps.

An answer to the recipient's own just-processed message (for example a chat reply to the message that confirmed an action) that its command commits as an outbox row **MUST** be run right after that commit through the drainer's own claim, lease and failure path, by the committing unit; the periodic drain stays its fallback and the attempt never fails the committed write. Reason: waiting for the next drain tick adds up to a full interval to a conversational answer the sender is watching for. Review-held: which rows answer the sender is a producer fact no syntax shows.

Presentation bounds **MUST** fit valid domain input before freezing. Moving best-effort notification work into the business transaction **MUST NOT** make a valid business write fail because an interpolated list exceeds the established text limit. The rendering authority measures remaining budget with the same catalog template and limit authority, preserves essential date/time/tenant facts, and fits only the display summary using visible omission at Unicode grapheme boundaries. Canonical names and the saved domain snapshot remain intact in the authenticated-detail payload. Temporary budget-measurement text is never persisted or displayed; final rendering uses the same placeholder engine with real inputs. A malformed fixed catalog with no summary room stays fail-loud; limits are never increased silently. Stated limit: the single budgeted renderer and existing schema bounds are the stronger mechanism; preservation of essential translated facts and template variable multiplicity remains review-held.

Stated enforcement limit: dispatcher callback/API, unique natural-key ledger, closed phases and domain transaction authorities carry the handoff guarantee. Pairing caller callbacks and all snapshot/predicate reads with the same atomic view requires cross-file review; use the enforcement mechanism the adopting project documents and record its scope.

Before an irreversible send, the worker fences both its exact lease and the event's current authorization/validity predicate in the same transaction as the ledger's `NOT_STARTED→STARTED` CAS. A queued event invalidated before handoff is terminally cancelled with no provider call. A provider-started unknown outcome is never blindly retried, since the provider has no proven idempotency guarantee.

Cancellation cannot rely on an invalidity preflight from a previous transaction snapshot: the worker re-reads the predicate and writes its existing authority records as conflict fences in the same transaction as the outbox/ledger cancellation. A newly valid predicate aborts that cancellation; an absent event-time recipient or deleted record cannot be replaced by a later guessed audience.

Event-time payload, event-state concurrency, and provider outcome cross multiple records and a remote system; one file's AST cannot prove them, so runtime transaction and durable-ledger review remain required.

Durable positive evidence: Duplicate intent existence is not provider acceptance or successful completion. A domain obligation that outlives the ledger's retention may retain a separate positive acceptance witness, written only from the exact intent's actual provider ticket and validated acceptance timestamp. The business acknowledgement is a different fact and cannot supply that timestamp. The evidence read and domain write fence the original recipient, tenant, event snapshot and lease in the same transaction; failed, cancelled or pending duplicates cannot acknowledge success. A later retryable receipt preserves the dispatcher retry decision even when a prior acknowledgement exists. Expired historical evidence remains unknown; no timestamp or acceptance is backfilled from the current clock or acknowledgement. Enforcement limit: the existing type/API and durable transaction authorities carry these guarantees; cross-record evidence and timing remain review-held.

Technical fence writes preserve business timestamps under [TX-M-3](../transactions/transaction-policy.md). A status-validity predicate that treats a missing timestamp as a fallback **MUST** use the same nullish set (`null` as well as absent) at the database handoff fence; a preflight JavaScript `??` check and a narrower database predicate are not equivalent. That cross-layer predicate parity remains a review obligation because the two expressions live in separate modules.

A domain-specific notification type subset **MUST** derive from the existing closed notification type authority. Repeating its string literals in a queue contract opens a second runtime list that can drift from the Notification model's accepted enum. The shared named constants may be re-exported to preserve an import path, but that forwarding path defines no values. A syntax check may enforce a closed set for a specific project, but this standard does not prescribe a lint rule or guard name. Review that every subset derives from the declared type authority.

Prepared-command authenticity: A hidden symbol and a shallow `Object.freeze` alone do not establish runtime authenticity: spread copies enumerable symbols, reflection discovers them, and nested input objects remain mutable. Preparation **MUST** bind the exact original command object to a private receipt and capture its input values before the first awaited read. Dispatch consumes only that private receipt; a copied or fabricated command fails before persistence/provider effects. An object-lifetime identity association is transient capability metadata, never a cross-instance duplicate decision, lease, or retry authority. The existing durable dispatcher fences remain mandatory.

Single dispatch preparation (NOTIF-BE-M1/M4/M5): A helper that needs durable duplicate preflight **MUST** consume the dispatch authority's prepared-command seam: canonical intent fingerprint and durable decision are produced together, and that same opaque command passes to the single persistence/provider dispatcher. Domain-specific eligibility, lease fences, and outcome mapping stay with their authorities; they do not rebuild the fingerprint/read/write chain. A read-only scheduler preflight may consume preparation without dispatching. This transient command is neither a lease nor cross-instance dedupe state: the database unique constraint, exact-intent comparison, retry claim and provider phase remain authoritative. Distinct mutations of existing notifications (user action, exact credential-cleanup reconciliation, transactional recipient-identity transfer, receipt, deletion and display-name cascades) remain separately registered writers; registering them does not grant a new notification creation/provider path. Mechanical limit: the opaque type blocks unprepared commands and the existing model-writer boundary rejects unregistered writers; the exact fields each registered operation may change and cross-record ordering require review, since model ownership alone cannot prove those semantics.
