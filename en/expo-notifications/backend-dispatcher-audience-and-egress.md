Scope: The audience band of the NOTIF-BE-M family — how a notification that is not scoped to one tenant is modelled, which fields may leave the record, which authority decides tenant and role membership, where a personal salutation's name may come from, and what a flow owes before it narrows its audience by something other than structural membership. This band answers who is eligible; the delivery-derived inactivity projection that a suppression reads is [receipt-and-delivery.md](receipt-and-delivery.md) (NOTIF-RCP-M11–NOTIF-RCP-M13), and the two open together on the eligibility/suppression signals.

## **MUST** — NOTIF-BE-M (audience band)

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **NOTIF-BE-M8** | Cross-tenant broadcast (admin announcement) **must** be modelled as a tenant-independent broadcast audience, never as a borrowed tenant id. When one announcement targets recipients independently of their tenant (e.g. an operator announcement to all users), each record **must** (a) carry an explicit broadcast audience marker meaning "not tenant-scoped", (b) omit the tenant key entirely rather than fill it with any single/first/foreign tenant, and (c) be matched by a dedicated tenant-independent branch of the list filter. Choosing one tenant id for a cross-tenant broadcast tags every recipient with someone else's tenant: push arrives but the in-app list hides it whenever the recipient's active tenant differs. A notification about one recipient's own account is NOT a broadcast and follows NOTIF-BE-M12. | Bug — announcement invisible for multi-tenant users; or send endpoint permanently fails because the caller has no tenant id to supply. | Pass: Broadcast sender passes the broadcast audience marker and no tenant key (type-enforced per NOTIF-BE-M2); list filter contains a branch matching that marker alone; `rg` broadcast sender for a "pick first tenant" fallback exits 1 (zero matches). |
| **NOTIF-BE-M9** | Replay, deduplication, lease, and credential material **MUST** be excluded by explicit closed-allowlist projections before notification data reaches a provider or client. Do not use omission-based types, unchecked spreads, or duplicate ad-hoc denylists. If provider and authenticated-client audiences need different fields, define separate named projections from the same stored contract. A producer's extra-data input to the dispatcher **MUST** be typed to the allowlisted keys the intent builder copies, never an open string record: a key outside it would be accepted and silently dropped. The provider projection **SHOULD** be narrower and contain only fields the client actually needs from push data (tap navigation, foreground cache refresh, click telemetry); person names, contact data, monetary amounts and pre-composed message text stay on the authenticated response. Keys that name or contact the end recipient or carry an operator-to-recipient draft **MUST** be copied only for an operator-audience record, so a recipient-facing copy cannot carry them even when a writer adds them. A key joins the provider allowlist only when a push-data reader for it exists. Do not log raw push payload objects. | Security or replay bug — internal capability data or unnecessary personal data escapes. | Review that each audience uses a named allowlist projection, internal fields and credentials are excluded, and consumers read only their audience-specific projection. |
| **NOTIF-BE-M10** | Tenant-scoped notification visibility, recipient filtering, preview counts, and automation evaluation **MUST** derive role and tenant membership from the persistent owner/personnel/customer relationship authorities for the exact tenant. A global user-role label, the first element of a tenant array, a “primary” tenant helper, or a missing-context default **MUST NOT** select a tenant or role. A multi-tenant rule **MUST** evaluate each exact recipient–tenant pair; preview **MUST** consume the same company-scope and channel/capability authorities as runtime and **MUST** fail loud when an exact intent decision cannot be computed. A recipient set is derived from current membership alone: an identity that an event or its stored record merely carries (a seller reference, an assignee, a creator) is an anchor — a recipient candidate and a source of message content, never a recipient by carrying alone. It enters the set only when a stated product rule names its role as a recipient AND the resolver proves its current membership from the membership authority, because stored references are not rewritten when a person leaves the tenant and an unproven candidate would keep delivering tenant data to a non-member; a candidate that is not a current member is dropped, and the notice still reaches the tenant owner through the set. A member who enters only as an involved candidate keeps every other egress restriction that applies to them (NOTIF-BE-M15 (d)). The anchor's input contract **MUST** accept exactly the identity kinds the producer persists — including a person with no account or contact identifier — and **MUST NOT** bind the field to a contact-identifier format the message never used; existence is checked against the authority of the anchor's own kind, and only an account identity can ever be a recipient. An event with no initiating user (a scheduled reminder) carries no actor field, and an anchor **MUST NOT** be substituted as the actor. Whether the set the producer writes equals the set the consumer's schema accepts is a cross-file relation held by review. | Cross-tenant disclosure, hidden notification, wrong recipient count, or preview/runtime drift. | Pass: list access verifies the requested tenant is in the persistent membership union; staff branches open only for an exact owner/personnel membership; recipient filters and subscription filters intersect requested tenants with persistent memberships; automation preview and execution consume the same canonical company-scope resolver; static enforcement rejects global-role, first/primary-tenant, and catch-to-default paths. |
| **NOTIF-BE-M11** | Every text the end recipient reads about their own record — a push title/body or data field, a draft an operator opens to the recipient on a device channel (a messaging app, SMS, share sheet), an automated reply, an account screen showing what a tenant holds about them — **MUST NOT** carry the name the tenant entered on its own record about that person: a tenant labels the people it serves freely, so that label is a private note, not the person's name. A personal name in such text **MUST** be the person's self-entered name, admitted only after the exact tenant-scoped record proves its canonical account link and that linked account exists; the linked account's own name fields are the only source, whatever role that account holds elsewhere. A name the person typed for themselves in the same flow (a booking form) is self-entered too and is read from that input, never from the record. A tenant-local business/display name, phone match, placeholder, fabricated name, or fallback is forbidden. If the link, linked account, or usable account name is absent, the template **MUST** select an explicit localized no-name branch; it **MUST NOT** leak the named branch's placeholder. A notice the person reads about their own record is written in the second person and needs no name; it **MUST NOT** reuse an operator template that names them. One authority derives the self-name; producers call it and never re-derive it. The single exception is the data-subject access copy (a regulatory personal-data export): it **MUST** include the record name, because the access right covers the personal data the controller holds; a reader serving both surfaces selects by a declared purpose, never by caller role. Operator-facing labels remain separate semantics and **MUST NOT** be rewritten by this policy. Recipient resolution **MUST** complete before the first irreversible dispatch side effect. | The tenant's private label shown to the recipient, cross-tenant disclosure, wrong-person salutation, fabricated identity, unresolved placeholder, or partial dispatch before recipient proof. | Pass: review the complete tenant entity -> canonical account link -> account name -> named/no-name template branch -> dispatch flow; every recipient-facing builder and device-channel draft receives only the self-name authority's output or no name; prove the no-name branch has no name placeholder in every supported catalog and runs before the first dispatch. This provenance spans query, resolver, template catalogs, and dispatch order, so runtime and cross-file review is required rather than a single-file source-shape check. |
| **NOTIF-BE-M12** | A notification about one recipient's own account, independent of every tenant they may own or join, **MUST** use an explicit person-account audience. It **MUST** omit the tenant key, **MUST NOT** reuse staff/customer/global semantics, and **MUST** be matched by a dedicated account branch in the canonical list filter. Tenant membership, active/first tenant, or a global broadcast marker **MUST NOT** be fabricated to make it visible. The typed dispatcher union and persistence validation **MUST** both reject a tenant key on this audience. | Hidden or cross-context notification, false broadcast semantics, or fake tenant attribution. | Pass: account sender carries the account audience and no tenant key; dispatcher type + runtime/model validation enforce that shape; the list filter matches account audience independently of active tenant; no ownership-array/active-tenant helper participates in account scope. |
| **NOTIF-BE-M13** | When a mutable recipient identity is part of a durable Notification natural key or canonical dispatch fingerprint, an identity migration **MUST** rebind one atomic evidence cluster: recipient projection + canonical key + versioned canonical intent snapshot + digest. The Notification/provider/event id, ticket/receipt correlation, delivery stage, immutable event/entity id, tenant scope and attempt evidence remain unchanged. Every new keyed Notification writer **MUST** persist its recipient-bound row and a real write on the recipient's durable identity-fence authority in one transaction before provider effects; the identity migration **MUST** touch the same fence before reading/rebinding rows. A same-store outbox/campaign whose recipient or opaque recipient digest feeds that Notification **MUST** either migrate its durable recipient/key projection in the same migration transaction or block under an exact active lease/claim. Opaque/external identities **MUST** come from a durable mapping authority and **MUST NOT** be parsed or guessed. Partial key/hash/snapshot state, an unverifiable legacy digest, snapshot mismatch, target natural-key collision, exact-CAS no-op, or active processing claim **MUST** fail loud and abort the whole migration. No snapshot/key/raw recipient may enter provider/client egress or general logs. A recipient's opt-in to messages on one contact address names that address and **MUST NOT** be carried by an identity migration that changes it; the new address starts undecided (review-held). | Duplicate or lost notification, false replay conflict, resend after outcome-unknown, stale-recipient provider effect, or leaked replay/PII material. | Pass: the enforcement mechanism the adopting project documents locks the canonical snapshot/hash authority, dispatcher identity-fence transaction and migration rebind call graph; cross-file review proves every producer/outbox writer touches the same durable fence, all migration writes share one session, lease/CAS predicates are exact, and public/log projections remain closed allowlists. |
| **NOTIF-BE-M14** | When a notification flow narrows its recipients by something other than structural eligibility — engagement history, event history, a frequency cap, a quiet-hours window — that narrowing is a named, scoped suppression and owes all four of the following. (a) One eligibility authority. The criterion is read from a single named authority that every dispatch path of that flow consumes; a second "is this recipient still eligible" derivation at another call site is a parallel authority ([SSG-M8](../ssot/ssot-principles-and-precedence.md)). What that authority owes once it exists — one durable store, transaction/CAS ordering, reset epoch, separation from the user's explicit preference — is NOTIF-RCP-M12, cited here and not restated. (b) The chosen signal's coverage **MUST** be measured before the criterion is adopted, and the measurement recorded beside the decision. A suppression resting on a signal that is only sometimes written punishes missing instrumentation instead of genuine disinterest, and it fails silently: a recipient suppressed by an unrecorded signal is indistinguishable from one who ignored the notification. The record **MUST** carry, for the criterion chosen and for each criterion rejected, the share of the population it would suppress and the population it was measured over. A criterion based on missing interaction data can suppress legitimate recipients when the signal is not consistently collected; establish that the chosen signal is complete before using it as an eligibility rule. A criterion whose coverage cannot be measured **MUST NOT** be adopted on the assumption that it could. (c) The scope is a named purpose and does not spread. The suppression names the exact notification purpose it governs; every other purpose — transactional, appointment, payment, automation-rule, security — stays outside it until a separate decision brings it in. A suppression written against "notifications" rather than one named purpose mutes flows nobody decided to mute. (d) Its window and threshold quantities are named constants of this topic's deterministic-constant family, defined once and cited by every consumer, never literals at a call site. Two adjacent states are not this rule and **MUST NOT** be folded into its gate: an expected suppressed run is a typed no-send outcome on the scheduler's own contract (IDEMP-M19) and never a failure or a crash-channel event, and a permanent credential-invalidation/uninstall marker is a separate durable state (NOTIF-RCP-M13). Stated limit ([KIT-INV-8](../authoring/kit-structural-invariants.md)(b)): no check can decide whether the criterion is the *right* one — which event counts as engagement, and how long the window should be, are product decisions, and the correct engagement meaning remains a product decision that **must** be recorded by the adopting application. Only (a) is mechanically decidable, and as a call-graph question: verify that all dispatch paths consume the named authority. | Bug — an entire class of recipient is silenced by an instrumentation gap that looks like disinterest, or one flow's decision quietly mutes every other flow. | Pass: one named eligibility authority, imported by every dispatch path of that flow and by no second derivation; the coverage measurement written down beside the decision together with the rejected alternatives; the suppression's scope stated as a purpose and every other purpose provably outside its predicate; window/threshold values resolved from the named constant family; the suppressed outcome typed as a no-send rather than an error. |
| **NOTIF-BE-M15** | A server-composed lifecycle notification states only facts that are true for the case it is sent for, and one recipient receives exactly ONE message for one lifecycle event. The required truth, deduplication, localization and disclosure contract is below. | Bug — a user is told something happened that did not, or receives the same event twice; a staff member reads another person's language. | Review the recipient payload, catalog and coordinator against the contract below. |

## Lifecycle notice contract

(a) The variant follows the fact the sentence asserts, not the event's name. When one event type covers cases with different truth — a completion with and without a successor, a warning that promises a follow-up only some records have — the composer takes the deciding fact as an explicit, REQUIRED input from the layer that decided it (a typed flag, never a default), and the catalog carries one variant per truth in every supported language; one sentence that is true for only one of the cases **MUST NOT** serve both, and an event-type-keyed text that a different event type can reach is the same defect.

(b) A combined message and its component message are one recipient-side notice. Where one lifecycle event has both a combined message and a component message for the same recipient, the coordinating module dispatches exactly one of them to that recipient and suppresses the other through an explicit, required flag on the component event's input, decided once at the coordinator; it **MUST NOT** thin the recipient list after the fact, and other audiences of the component event (staff) are untouched. A caller that had already withdrawn the combined message from the recipient leaves the component message reaching them: the recipient receives one, never zero by accident.

(c) Display values a body embeds are composed per recipient, from the single authority for each. A calendar day passes through the project's one calendar-day display authority in the recipient's language ([timezone](../timezone/README.md)), never the raw machine string; a missing name is carried as absence and written as a catalog marker in the recipient's language ([name consistency](../name-consistency/README.md)), never a literal from the call site; a body composed for several recipients is composed inside the per-recipient payload step so the recipient's own language ([user-text catalogs](../internationalization-rn/user-text-catalogs-and-parity.md)) and a formatting failure are per recipient — not one recipient's language lent to all, and not a throw that cuts the coordinator's remaining sends. A draft that a staff recipient sends onward to the end recipient (a ready-made message body carried in the notification data, opened in a messaging app) is written for its READER, not for the staff recipient: it is composed in the end recipient's language (their own language preference, else the tenant default language per the registered language chain), never guessed from a phone number, chosen once per event and independent of the staff recipient, while the staff-facing title and body stay in the staff recipient's language; its composition stays inside the per-recipient payload step (same failure isolation), and a draft that embeds a permission-gated value is carried only to a recipient (d) allows to see that value. A client that composes such a draft itself takes the reader's language from the server and never re-derives it.

(d) A value a recipient's permission does not allow is absent from that recipient's notice, decided per recipient by the single permission authority. A body or payload field that carries money, a balance or another permission-gated value is composed only for a recipient the permission authority allows to see it; the audience resolver asks that authority once per member and hands the composer the decision as a REQUIRED typed input (a visible/hidden value, never a boolean default), so the text variant follows the fact the recipient may read (the value-free variant is a catalog key in every supported language, not a blanked placeholder) and every payload field that repeats the value (a raw amount, a prepared outbound message that embeds it) is omitted with it. A member restricted by the permission may still be a recipient (for example as involved staff) — restriction removes the value, not the notice. Stated limits: whether a sentence is true for the case, which reader a body is written for, recipient-side duplicates and which event writers carry a permission-gated value are cross-record or cross-file facts held by review, while the type system carries the required flag, the per-variant catalog keys and per-language parity.

(e) A notice sent on a sender identity that every tenant shares carries only platform-owned catalog text. A tenant-entered value **MUST** travel only as a typed, length-bounded parameter drawn from that tenant's declared published fields (its display name), never as free text or a link. Reason: the shared sender's reputation and transactional category belong to the platform — one tenant's free text reclassifies or bans the sender for every tenant and turns it into a phishing channel. Verify: review that the send path accepts a catalog key plus typed parameters only.

(f) A lifecycle notice **MUST NOT** be sent to the account that initiated the event through a self-service surface; the producer passes the initiating account as a REQUIRED typed input and the resolver drops that recipient only, keeping every other audience. Reason: the initiator already holds the server-confirmed result on screen, so a notice of their own action is a duplicate (one message per event, above) that trains users to ignore real notices. A command's response delivered on the surface the initiator acted from (the reply in the conversation their own message opened) is that command's result, not a lifecycle notice, and is allowed once; repeating it on any other channel is the forbidden duplicate. Verify: review that the self-service producers pass the initiator and the resolver's skip removes no other audience.

(g) Where a shared sender's provider bills per delivered message past a free tier, one quota authority **MUST** count from the provider's own delivery and billing signals (deduplicated per message) and be read before the provider call; past the cap it **MUST** skip only notices the recipient can read on another surface, by a closed per-kind class map, and **MUST NOT** gate the answer to the recipient's own message; every threshold crossing and every provider refusal for billing is loud once per episode. Reason: an uncounted shared quota bills every tenant's notices to the platform or silently stops delivery for all of them, while a cap that also silences answers strands the user mid-request. Verify: review.

Optional deleted recipients (NOTIF-BE-M15): When a committed lifecycle operation outlives an optional recipient record, absence discovered by any subsequent recipient read **MUST** explicitly skip only that optional recipient branch and preserve the other eligible audiences and later lifecycle events. A prior existence read is not proof that a later resolver can still read the record. The single recipient resolver may expose an explicit missing-record policy for this lifecycle consumer; its default missing-record failure, exact tenant/account binding, input validation and infrastructure error propagation **MUST** remain unchanged. A deleted recipient is an honest no-recipient state, never a fabricated identity or a broad caught failure. Scheduled reminders whose durable source outlives an optional recipient consume the same explicit scoped-null policy. A preparation, input, repository, account, permission, calendar-day or required-currency rejection is not recipient absence: it keeps its original error to the scheduler/outbox or committed-payment notification owner, never becomes a clean zero/empty event summary or a guessed display value, and uses the existing strict backend currency read authority and recipient-language calendar formatter, preserving other audiences, genuine no-send counts, durable outcome and financial commit. Stated limit: whether an operation survives recipient deletion spans the committed write, coordinator and resolver; the explicit resolver API owns the absence result, and cross-file review holds opt-in consumers, error identity and audience continuity.
