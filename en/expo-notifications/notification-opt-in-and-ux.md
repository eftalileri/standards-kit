## **MUST** -- NOTIF-UX-M

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **NOTIF-UX-M1** | Request push permission only after a user action that implies opt-in or after the product has explained the value. Do not prompt on first launch before the user understands the request. Record the chosen prompt gate in the application’s product or architecture documentation. An in-app explanation card whose button opens the prompt is itself that user action: its candidacy **MUST NOT** wait for a further in-app event some roles never reach, and in the NOTIF-UX-M9 priority list it ranks above optional non-permission requests — otherwise a new install, losing each session's single turn to those requests, is never asked. | Permission denial and poor user experience. | Review that permission requests follow the documented user action and are not triggered automatically at startup. |
| **NOTIF-UX-M2** | Foreground alert / banner behavior **must** match `setNotificationHandler` flags (NOTIF-CLI-M2); product **must** document whether foreground notifications show banner or silent update only (per channel). | Inconsistent UX / user trust. | Same file as NOTIF-CLI-M2 review. |
| **NOTIF-UX-M3** | Notification tap / response **must** delegate to one handler (NOTIF-CLI-M4) with documented fallback route (NOTIF-CLI-M7). | Dead ends / double navigation. | Pass: NOTIF-CLI-M4 Verify. |
| **NOTIF-UX-M4** | An in-app notification action **MUST** use a stable command identifier separate from localized display text. The backend **MUST** validate that the identifier is an allowed action for the exact persisted notification and recipient; reject free-form client commands. | Client-controlled or cross-notification action confusion. | Review the validated notification action list and the backend’s recipient/action checks. |
| **NOTIF-UX-M5** | The first accepted in-app notification action **MUST** become a durable terminal state through one atomic write. Retrying the same action **MUST** return the committed result without repeating its side effect; a conflicting action after terminalization **MUST** return an explicit conflict. | Duplicate effects or contradictory results under retry/concurrency. | Review same-action replay, conflicting-action behavior, and event reconciliation after a mid-flight failure. |
| **NOTIF-UX-M6** | The client’s action label and destination **MUST** derive from one navigation authority. Render an action only when both its validated command and destination are available; perform navigation only after the command’s terminal write succeeds. | Misleading buttons, divergent routes, or navigation after rejected work. | Review the shared resolver and verify missing destinations render no action and rejected commands do not navigate. |
| **NOTIF-UX-M7** | When multiple notification channels request completion of the same user task, use one completion definition across channels. Optional publication, visibility, or preference choices **MUST NOT** be treated as required completion fields. | Contradictory completion state or coercive UX. | Review completion derivation and confirm optional preferences do not change the required-task result. |
| **NOTIF-UX-M8** | When a notification opens a multi-step task, route to the next actionable step using the same completion authority as the task surface. Keep controls needed to withdraw an existing permission or publication choice reachable while the task is incomplete. | Dead-end action or inaccessible withdrawal. | Review the notification entry flow, next-step derivation, and visibility of relevant opt-out controls. |
| **NOTIF-UX-M9** | Prompts that open on their own at app start or on return to the foreground (not from the user's own tap) **MUST** go through one turn authority: at most one such prompt per foreground session, chosen from one declared priority list in which a mandatory gate outranks optional requests. A foreground session starts only when the app returns from `background` after a declared minimum absence; a short switch away (reading a login code in SMS or mail) and a transient OS interruption (iOS `inactive`) are not a new session — otherwise every short return opens one more prompt and the prompts arrive back to back. A prompt waits while a higher one is open or about to open — an unresolved input of a mandatory gate counts as "about to open" — and answering any prompt (a decision, "not now", completion) uses up the session's turn, recorded in the answer's event handler, never by an effect. A time-of-day condition is evaluated at the instant the session started, not at render, so a prompt never opens in the middle of a task when the clock passes its threshold. | Back-to-back prompts read as nagging; on iOS a second native modal cannot be presented, so an optional prompt can hide a mandatory gate. | Review that the visibility of every auto-opening root prompt includes the turn authority's answer and that the priority list is declared once. |
| **NOTIF-UX-M10** | The permission authority's "granted" signal that restarts push token registration **MUST** fire on every observed not-granted → granted change, including the foreground re-read after the person enabled notifications in the OS settings, not only after the in-app prompt. | A device whose owner granted in the OS settings keeps no token until a cold start and silently misses every push. | Review that the foreground status read and the in-app request reach the same transition check that emits the signal. |
| **NOTIF-UX-M11** | A permission card re-offered at a value moment (past its snooze) **MUST** be triggered only by a server-confirmed fact, never a client-side count, observed on that fact's own read rather than after one client write path (another actor, device or channel may cause it); it is offered at most once per device, its "used" record kept by the same authority as the snooze and set by any answer or observed grant; it takes its turn through NOTIF-UX-M9, and while it is a candidate no other offer of the same permission (inline card) is drawn beside it; and when the OS can no longer show its dialog the card's button opens the system settings instead of requesting. | A re-offer that repeats or fires on a guessed event becomes nagging (NOTIF-UX-N1); one bound to a single write path never fires for users whose fact changed elsewhere; a request the OS silently ignores is a dead button. | Review that the trigger reads the server answer wherever it is refreshed, that one storage record has an absent → pending → used path, and that the action follows the platform's "can ask again" answer. |
| **NOTIF-UX-M12** | A permission offer's candidacy **MUST** follow the platform's "can ask again" answer, not "never asked": Android reports `denied` after one refusal while it can still show its dialog once more, and a candidacy tied to `undetermined` never uses that chance. A refusal in the OS dialog is recorded as the offer's dismissal (the same snooze as "not now"), so the second chance comes after the snooze, never the next session. Every surface that offers the permission (root card, inline card, onboarding step, settings row) takes its button's action — OS dialog or app settings — from the one permission authority, and an offer whose only action is the app settings does not render where the platform cannot open them (a browser page). Offer, answer and OS result are measured per surface inside the authority's user-action entry points, the surface a mandatory argument, never re-derived by each surface. | Users who refused once are never asked again, or are asked every session (NOTIF-UX-N1); two surfaces disagree on whether a tap asks or opens Settings; a dead button; a funnel that cannot tell which surface converts. | Review that candidacy reads the "can ask again" answer, that the request entry point writes the snooze on a non-granted result, that no surface derives request-vs-settings from the status, and that the type of every entry point requires the surface. |

## **MUST NOT** -- NOTIF-UX-N

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **NOTIF-UX-N1** | Must not re-prompt permission on every app open after denial — respect OS settings link only (per platform guidelines). | Harassment class UX / store risk. | Manual test: deny → restart → no automatic system dialog. |
| **NOTIF-UX-N2** | Must not persist route names, deep links, or localized labels inside a notification's action list, and **must not** build a second route map inside the in-app notification surface (no route-name literals there) — routes stay in the client route registry and the single navigation authority (NOTIF-UX-M6). | Bug — duplicated routing and permission checks on the server; drift between tap and action. | Pass: grep of the action-list writer shows no route / URL / label field, and grep of the in-app notification components for route-name literals returns zero. |
