# Scheduled work — boot arming and tick exclusivity (**SJO-M7**)


Scope: Durable declarations are seeded completely before scheduler arming; partial seed leaves all schedulers unarmed. Defines **SJO-M7** and applies **SJO-M1**/**SJO-M2** to boot.

---

## **MUST** (normative) — **SJO-M7**

**SJO-M7**: A recurring run's exclusion window is the scheduled OCCURRENCE, not the run. A lock released on completion is a mutex: it stops two runs from overlapping, and nothing else. It does not stop the *same* occurrence from running twice — a second instance whose own tick fires after the first instance's run has already completed finds the lock free and repeats the occurrence. This is not a multi-replica-only concern: a rolling deploy runs the old and the new process together for the length of the overlap, so every single-replica deployment is briefly a two-instance one and "safe by topology" is not a guarantee. Four obligations. (a) The job declares it. Whether repeating an occurrence is harmless is a product statement about that job's effects — an inflated counter, a doubled alert, a second report to an external system — and nothing in the source derives it; a job whose repeat is not harmless declares once-per-occurrence in its own declaration, beside its cadence, so the claim and the cadence cannot drift apart. A job that does not declare it keeps the mutex unchanged. (b) The hold is written with the trace, in one compare-and-set. The completion write that records the run's durable trace also releases the lease, and for such a job it releases it to the end of the occurrence it just completed instead of to "free" — the same single owner-token write **SJO-M2** already requires, carrying a different value. Splitting the two writes lets a lease be released without a trace. (c) The occurrence is DERIVED from the declared cadence, never from a second constant, and the derivation refuses what it cannot align. The reference instant is the moment the run acquired, never the moment it finished: a run that crosses a boundary would otherwise suppress the next occurrence as well. A cadence whose real firings are not the aligned windows the derivation would compute — an irregular step, a month approximated by its longest length — **MUST** be refused where the declaration is written, loudly and at start-up, because an approximate window suppresses a legitimate occurrence, which is **SJO-N3**'s defect arriving by arithmetic instead of by edit. Deriving the window from each process's own clock is what makes it skew-proof: two instances label the same occurrence identically however far apart their clocks are, which a fixed cool-down period after completion cannot do, and a cool-down long enough to cover real skew also swallows the next legitimate tick after a slow run. (d) A FAILED run releases immediately. The occurrence was never completed, so it is still owed; holding it would convert one failure into a silent skip. (e) The hold lives only where the lease is DURABLE, and a declaration the runner cannot honour is REFUSED, not ignored. Duplicate suppression rests on the database authority, so a coordination store that may evict — a cache lease — cannot carry an occurrence hold: the eviction reopens the occurrence precisely when nobody is watching. A cache lease does not, however, disqualify the *runner*, only the *store*. A runner whose mutual exclusion is a cache lease still honours the declaration when the hold itself is written to and read from the durable trace the runner already maintains: the cache lease keeps two runs from overlapping, the durable row keeps one occurrence from running twice, and the two are separate facts in separate stores. Reading that hold after the mutex is taken is not a race, because at that moment there is one runner. Conflating the two can silently leave repeat-sensitive jobs without any way to declare their requirement, which is the same silent gap by the opposite route. So: a runner that genuinely cannot reach a durable hold **MUST** reject the declaration at the earliest boundary that can see it — the type system where the runner's options are typed, otherwise start-up — and a runner that can reach one **MUST NOT** be refused on the strength of its mutex. Accepting a declaration the runner silently drops is the worst of the three outcomes: the job now *claims* once-per-occurrence, the claim is read as coverage, and nothing enforces it (**SJO-N2**). Where one durable field carries both facts — "held by a running worker" and "this occurrence is finished" — its write paths are a closed set and a mechanical fence belongs on them: a third writer removes both guarantees without failing, because releasing it early reopens a completed occurrence and advancing it skips a legitimate one, and a skipped run reaches no channel at all. [Consequence: A repeated occurrence corrupts every count, window and alert derived from "how many times has this run", and the corruption is indistinguishable from real activity — it is the supervising job's own episode counter that inflates first.] [Verify: Drive two workers into one occurrence against a disposable local datastore — the second is refused and the work happens once — beside a control job without the declaration showing the mutex still admits both; then the next occurrence running normally, a failed run retried inside the same occurrence, an expired lease taken over by another worker, and a stolen lease unable to write a trace. Which jobs need the declaration is not derivable; see the check reach below.]

Check reach. A check can prove that a named job's registration carries the declaration: the declaration object and the registration call sit in one file, so a single-file AST decides it, and the job is identified by the canonical work its handler reaches rather than by its name. The check cannot decide the general question — *which* recurring jobs are unsafe when an occurrence repeats — because that needs each job body's effect on every store it touches, which neither a single-file parse nor a repository-wide scan has. A project therefore fences the jobs whose repeat cost it has established and records the remainder as unclassified; reading the absence of findings as coverage is the inversion **SJO-N2** names.

Classifying a repeat — the question is what the job's own code promises, not whether it "looks idempotent". A mutex guarantees only that the repeat runs strictly *after* the first run finished, so every read-then-write guard the first run completed is already visible to the second. That is why a drain whose rows carry an atomic claim, and a reconciler that recomputes a value from its authority and writes it conditionally, are genuinely safe under a repeat and **MUST** stay on the mutex — declaring them would cost liveness for nothing. What survives that filter is narrow and concrete: a counter advanced by read-modify-write, a record appended with a freshly generated identity, a report to an external system, and — the case a survey misses most often — a step whose own predicate is a *per-occurrence* predicate ("write this once, in the round where the window closes"), which the repeat satisfies a second time. Two effects are NOT closed by the declaration and are recorded separately rather than counted as covered: an effect reachable from a second entry point (a manual or HTTP trigger of the same job), which the hold would additionally *refuse* — so a job with a legitimate in-tick re-entry **MUST NOT** declare it — and a non-idempotent write that sits *before* the job's own idempotency gate, whose root cause is that write's placement and which stays open for every other job reaching it.

Clock frame of the durable lease and the occurrence hold. A durable lease row is written and compared with the process clock (the adopting project's one "now" authority), not with the database server's clock, and this is a settled choice with a stated premise — not an oversight to be "fixed" by moving the comparison into the database. (a) Why the hold must stay in the process frame. The hold is a cadence-aligned boundary, so "hold ≤ my now" in the acquiring process is equivalent to "my occurrence's label is past the completed one" — a frame-free label comparison, which is what makes (c) above skew-proof. Compared against the database clock instead, a replica whose clock runs even a few milliseconds ahead of the database fires at its own boundary, finds the hold not yet passed and loses the occurrence — a silent skipped run (**SJO-N3** by clock). (b) What the process-frame lease relies on. The mutex half compares one process's expiry with another process's "now", so it is correct only while inter-process drift stays far below the lease margin — the lease TTL minus the renewal interval, i.e. the least time a live owner's expiry is ahead of real time. That premise is to be measured, not assumed: compare, per write, the database's own apply wall clock (replication log) with the application-written update timestamp carried in the same write, and replay the log to count acquisitions that succeeded while the previous stored lease was still valid by the database clock. (c) When to redesign, and how. Re-measure when the hosting platform, the replica topology or a lease TTL changes; drift reaching a tenth of the smallest margin, or any acquisition over a still-valid lease, is the trigger. The redesign is then to separate the two facts — a lease expiry written and compared with the database clock, and the occurrence hold kept in the process frame — never to move the shared field to the database clock, which trades a theoretical steal for the measured lost occurrences of (a). The same premise covers every other database-backed worker lease compared with the process clock ([**REP-M-13**](../repository/repository-atomic-claims.md)): drift is a property of the hosts, not of the collection, so the one measurement serves them all, but "the smallest margin" in the trigger is the smallest across every such lease, not only the scheduler's — and a new lease with a smaller margin lowers the trigger with it. Record the measured drift and margin where the adopting project documents its lease settings. No runtime check measures drift; the re-measure triggers hold the premise, because a clock is a property of the host and no source check can see it.

Boot consequence. Every current declaration is durably seeded before any scheduler is armed. Seeding may retry an idempotent declaration write, but partial persistence is not called success: final failures are collected, reported once with bounded non-secret job identities through the registered SYSTEM error path, and thrown. The process **MUST NOT** arm any scheduler after such a failure. Only a complete seed permits arming, and the affirmative armed record follows both operations. This is fail-stop ordering, not a claim that all declaration rows are written in one database transaction; an interrupted boot may leave an idempotently repairable subset, while running zero scheduled jobs.

Seed or arming failure is terminal. A failed seed, or a post-arm mismatch, **MUST** end the process with one fatal record carrying a registered SYSTEM code whose meaning is "declared scheduled work was not completely seeded/armed", with the underlying settlement error as its standard `cause`. It **MUST NOT** enter the datastore connect-retry loop — re-running the post-connect bootstrap re-registers listeners and repeats every boot write — and **MUST NOT** fall through to serving the API with zero schedulers: that process looks alive, fails its health check forever and silently runs no scheduled work (**SJO-N2**). The platform's restart-on-failure policy re-runs the whole boot; at deploy time the previous deployment keeps serving until the new one passes its health check, so the exit costs no availability there. A lifecycle gate that refuses arming because shutdown has begun uses the registered intake-closed code, not a trace/seed code.

An exhausted datastore connect window is the same terminal class. The paragraph above settles a *seed* failure; the sibling arm is a boot that never reaches the datastore at all, and it **MUST NOT** be allowed to end in a third way. Three outcomes exist and only two are permitted: connect and arm, or end the process with one fatal record carrying a registered SYSTEM code meaning "the datastore was unreachable for the whole boot window", with the last attempt's error as its standard `cause`. The forbidden third is returning normally from the connect authority and serving anyway — a valueless `return` after the retries run out — because the end state is the one **SJO-N2** already names: alive, health red forever, zero schedulers, and no further attempt. Four obligations. (a) The window is bounded by TIME, not by attempt count. An attempt budget is the wrong unit: it silently lengthens or shortens whenever a driver's connection-selection timeout changes, so the operator's mental model and the real window drift apart. (b) Its bound is the platform's own patience for a new deployment to become healthy, and that number is recorded as a chosen value, not a judgement. Waiting longer buys nothing at deploy time — the deployment has already failed by then and the previous one keeps serving — while exiting sooner spends one unit of a restart budget whose reset rule the platform may not document, so an unrecoverable unit must be assumed. (c) Backoff is capped and the process must exit rather than spin. A restart budget is the outer loop; the in-process window is the inner one, and the inner window must be long enough that an exit means *sustained outage* rather than *blip*, which is what keeps the design out of a restart loop. (d) An attempt that will be retried inside the window is an EXPECTED failure and takes the WARN/metric channel; only the exhaustion is an ERROR. Writing a crash-sink event per attempt turns one outage into attempts × restarts events, and the diagnosis is not lost because the last attempt's error travels as the terminal carrier's `cause`. [Consequence: the forbidden third outcome is invisible from outside the process, because a platform health check is typically evaluated only while a deployment is going live — after that a red endpoint triggers nothing, so a non-zero exit is the only mechanical recovery path the deployment has.] [Verify: point the boot at an unreachable datastore and watch the window elapse, the single terminal record appear with the registered code, and the process exit non-zero; then restore the datastore mid-window and see the same boot arm without restarting.]

Mechanical boundary of the terminal arm. The composition root's half is single-file decidable and **MUST** be fenced: in the file that opens the listener, a top-level `catch` that precedes the listen **MUST** terminate control flow, so no allowlist of "survivable" boot failures can be reopened there — such a list is also a second authority for a question already answered where the error is raised. The connect authority's own half is NOT single-file decidable, because "the retries are exhausted" is an arithmetic property of a loop rather than a syntactic shape; it is closed by the TYPE SYSTEM instead — the connect function returns a closed outcome union with no "gave up" member, which makes the valueless `return` a compile error. Either half alone leaves the class open.

Armed record carries independent numbers. The seed returns the seeded job names. After arming, the composition root re-reads the current declarations and compares the two name sets; any declared-but-unseeded or seeded-but-undeclared name is the terminal failure above. Only then is the armed record written, carrying the post-arm declaration count, the seeded count and the scheduler-handle count read from the scheduler runtime's own inventory. Deriving "declared" from "seeded" makes the record tautological — it can never show the mismatch it exists to reveal. The handle count is logged evidence, never compared to a hand-kept constant (**SJO-M1**).

Mechanical boundary. A single-file AST rule can prove the reachable lexical chain `resolve authority → assert authority → awaited seed → arm → post-arm name-set assertion` inside one function of the composition root. It cannot prove that a repository write succeeded, that the process really exits, or that the runtime contained a particular declaration or handle count; those remain runtime evidence (boot log after every deploy, and a forced-failure boot against a disposable local datastore).

First-tick gap. A recurring read whose stored result is the only input of a send or serve gate **MUST** also run once when its scheduler is armed — same declaration, same lease, same outcome trace — and a writer that records only partial facts (an event without the read's content) **MUST NOT** turn the gate's "not read yet" into an alert. Reason: a fresh datastore or a deploy otherwise keeps the gate closed until the first tick, silently, for a whole cadence. A declaration with tick exclusivity takes the boot run only through its own catch-up. Review-held: whether a job's output gates a user action is not decidable from its registration.
