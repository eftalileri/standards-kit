## **MUST** — **M39**

**M39**: A durable workflow may call a crash-report emission accepted only after the SDK reports the matching stable event id through its post-send hook with an explicit 2xx transport response. The pending correlation **MUST** exist before capture, **MUST** be bounded by a timeout, and **MUST** be removed on every terminal result. The event id is the provider-compatible stable identifier (for example 32 lowercase hexadecimal characters); event timestamp and fingerprint are frozen workflow inputs, not regenerated on retry. Concurrent events correlate by event id, never by callback order. An in-flight duplicate id fails loudly.

The logging transport callback proves only that the local transport invocation completed. The SDK's flush proves only that local SDK processing/buffering drained. Neither proves provider acceptance, so callback or flush truth/completion **MUST NOT** write `accepted` or `acceptedAt`. Timeout, missing response, network failure, rate limiting and every non-2xx response are not accepted. The delivery directive is internal control data: it **MUST NOT** be enumerable log metadata, a crash-report `extra` field, a tag, or a user/tenant/credential carrier. Existing credential scrubbing and ordinary log behavior remain in force.

An explicit 2xx response is the strongest receipt exposed by the installed SDK, but it is not proof of durable storage and does not provide physical exactly-once delivery. A crash after remote acceptance and before durable local finalization can retry the same event id; the provider may still ingest more than one physical event. Code and operational claims **MUST** therefore say at-least-once delivery with a stable logical event identity, never external exactly-once. A higher-level episode authority may enforce one logical SYSTEM episode, but this receipt row neither defines nor widens that authority.

Where a source-level check is used, it can reject acceptance writes that rely only on local transport completion or buffer flush. Such a check does not prove provider response handling or cross-function data flow. Use the enforcement mechanism the adopting project documents; a reference to a check is not evidence that it exists or covers the full rule. Record its actual scope and limits, and verify the provider's explicit-success, timeout, failure, correlation and cleanup paths through review and runtime evidence.

### Durable episode alarm — two phases and one removal predicate

An episode whose alarm must survive a crash carries its delivery intent in the same conditional write that opens the episode, so "episode opened, alarm consumed, nothing sent" is unexpressible. The intent freezes the alarm identity at open time — stable provider-compatible event id, event timestamp, fingerprint and a bounded error snapshot — and every later attempt resends that same identity.

Exactly two phases are needed, because exactly two questions exist: has the alarm been accepted, and if not, is it still owed. A third "being attempted" phase is a second exclusion authority and **MUST NOT** be added where the drainer already runs under one (see the **REP-M-13** application below). The predicate "not yet accepted" is written once and used by both the candidate query and the acceptance write; `not accepted` is the correct form, never `equals pending`, because a row whose phase is unreadable — hand-edited, or left by a previous version during a rolling deploy — is still owed its alarm, and excluding it would leave the episode open and silent forever.

The single removal predicate is acceptance. An episode is removed only by a write that requires its intent to be `accepted`; a recovery, an orphan cleanup and a healthy verdict are none of them sufficient on their own. This is what makes loss impossible: a job that recovers while the provider is unreachable keeps its episode open until the alarm is finally accepted, and only then is it closed and its recovery recorded. The recovery record is the log line the removal emits; no separate durable "recovered" stamp is kept, because its only reader would be the removal that deletes it.

A stored intent that cannot become an event is itself an alarm. The read that turns a persisted intent into the sink's `(error, directive)` pair is the sink's own precondition — event-id shape, finite timestamp, non-empty fingerprint, registered SYSTEM code — never a second copy of the storage schema, which is the write-side authority and would drift from it. When that read refuses, the row raises one registered per-episode defect alarm whose identity is derived from job plus episode-open time, marked only after its own accepted receipt, and the episode is still not removed.

Every row outcome is a per-row result and never a round terminal: not-accepted and undeliverable rows are candidates again next round, so the supervising run still returns its summary, writes its trace and checks in, with one fixed-label warn per round. Honest guarantee: at-least-once delivery with one logical event identity — a crash between provider acceptance and the local write resends the same id.

"Per-row" includes the drain's own durable writes, and the isolating seam is shared with the supervising stage. The acceptance stamp and the defect stamp are as capable of failing as the send is, and a round that ends at the first such failure leaves every later candidate untried — the permanent-candidate defect [**M21**](shutdown-watchdog-clarifications.md) names, arriving through the write instead of through the read. Each candidate's whole step is therefore isolated, and the isolation is one seam serving both stages of the round, not a second copy beside the supervising one: the same obligation written twice is the shape where a fix lands on one stage and never reaches the other ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)). Three properties make the isolation safe rather than silencing. It re-reads the lease fence before containing, so lease loss and a lifecycle abort — the latter carrying no registered code — both keep rising as the round's failure and a shutdown cannot be reported as a completed run. It never marks the row, so the contained row stays a candidate under the same "not yet accepted" predicate and is retried next round with the same frozen identity; the guarantee that an alarm is never consumed without delivery is therefore preserved by construction, not by care. And the contained row is named in the round's summary and counted in the attempt metric, so the per-outcome counts still sum to the number of rows scanned; an outcome with no label is the silent absence **SJO-N2** names.

A source-level fence over the supervisor, where one is used, would lock the supervisor's own internal shape; the runtime proof is the driven episode (open intent, delivery receipt, removal). The direct crash-SDK capture half is owned by the single backend-wide capture rule (next paragraph).

The direct crash-SDK capture surface is not this fence's question and **MUST NOT** be given a second predicate here: one rule already owns it across the whole backend package, and two predicates for one question is the parallel authority [**SSG-M8**](../ssot/ssot-principles-and-precedence.md) forbids. Cross-store transitions and provider receipts require real runtime evidence.

### The frozen fingerprint must survive the event boundary

A frozen grouping identity is a guarantee only if it reaches the provider. The event sanitizer running in the SDK's pre-send hook is the last writer of the payload, so a sanitizer that deletes `fingerprint` unconditionally makes this row's frozen-fingerprint clause inert: retries still carry one logical event id, but the provider groups by its own default rules and one logical episode can fan out into several issues. This is verified by decoding the real outgoing envelope, never by reading the producer — reading the producer alone shows a guarantee that is never delivered.

The grouping field is not covered by the free-text relaxation, because it is not diagnosis: it is an indexed grouping key, the same egress class as crash-report tags, and the [**SEC-M-LOG-4**](../security/security-logging-core.md) tag corollary governs it unchanged. The boundary therefore keeps a fingerprint on that corollary's own terms and no looser: a marker written by exactly one application-owned producer must be the first part; every part must match a closed identifier shape under a bounded length, a bounded part count and a bounded digit run, so an email, a JWT, an authorization scheme, a connection string, a free-text sentence, a phone-shaped tenant id and an event-varying counter are all structurally inexpressible; and the sanitizer rebuilds the array from the validated parts instead of forwarding the producer's bag. Everything else is deleted exactly as before, including a grouping key set by a third-party integration. The marker is one shared constant the producer imports, never a second copy of the string on each side ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)). The digit bound does two jobs and both are intended: it keeps phone/card/epoch-shaped values off an indexed surface, and it keeps per-event values out of the grouping key, which is what bounds issue cardinality.

Fingerprints are produced only in the log/crash boundary; a source-level check, where one exists, may require a fingerprint to originate from that single application-owned authority and match the bounded, closed format, but it cannot verify the provider's final event envelope — verify that with runtime evidence.

A non-durable crash event (no durable intent; a fresh event id per attempt, its receipt read only to open the defect channel's noise window — [**M17** corollary](failure-level-and-channel-routing.md)) **MAY** carry a grouping fingerprint only through the single logger seam's own parameter, and that parameter **MUST** accept only a branded fingerprint type that exactly one builder produces; the builder **MUST** ask the event sanitizer's own predicate (never a copy) before branding, so a fingerprint the sanitizer would drop is unrepresentable at the seam and the seam itself never throws. The builder composes every part as the marker, the registered code, and identity parts made of a sanitised readable prefix plus a letters-only digest of the raw identity (route template, query shape), the readable prefix truncated to the length budget left after the part's fixed prefix, separator and digest — never a fixed length — so no raw path, shape, value or 5-digit run reaches a part. When the builder cannot prove a fingerprint it raises a registered `SYSTEM` carrier; a caller running inside a response or event listener catches it at its own boundary and reports it once through the non-HTTP classification authority, never letting it escape the listener and never substituting a made-up fingerprint. Verified only by decoding the outgoing envelope. Reason: the sanitizer silently deletes an invalid fingerprint, and a throwing log seam inside a listener takes the process down — observability must fail loud, not fatal. A durable intent's frozen fingerprint **MUST** be minted by that same builder when the intent is created; an already closed-shape part (a declared job name) passes verbatim through the same predicate, and a free-form subject (a signal name with `:`, spaces or `/`) goes through the readable-plus-digest part. Reason: a raw subject part is deleted at the boundary, so every subject falls back to stack grouping and distinct alarms collapse into one issue that looks like a repeat.

### Lost events are counted, never swallowed

Every error event meant for the provider that does not arrive **MUST** be counted by one writer into a metric and the authorized runtime-health view, from both the backend SDK and the app SDK (the app reports it through its expected-failure ingest, the server counts it). Only the backend's own losses enter the dedicated warn-signal window field; the app's losses **MUST** stay inside the client expected-failure family and its one-episode cap. Reason: that ingest is unauthenticated, so an absolute subject fed by it would let one forged request open the alarm and hold it open over real backend losses. The count reads the SDK's own client report for delivery-loss reasons (network error, queue/buffer overflow, rate-limit backoff, send error, internal SDK error), the post-send hook only for a non-2xx response the SDK does not record (so nothing is counted twice), and the log sink's own failure; one shared classifier serves both runtimes. Filter verdicts (pre-send filters, event processors, sampling) are deliberate decisions, not losses. The log sink **MUST NOT** swallow its own failure: it counts it and writes the process's first loss as one `warn` line, which never re-enters the crash sink. The field is judged by the existing warn-signal verdict as one subject — no second alarm path; its episode alarm is durable, so it reaches the provider once delivery recovers. Reason: a crash channel that fails silently is indistinguishable from a healthy one with no errors. Review-held: one writer and one classifier, no second authoring surface.

**REP-M-13** application — the drainer's claim is the job-level lease. [**REP-M-13**](../repository/repository-atomic-claims.md) is met here, not waived. The drain runs only inside the scheduled job's own atomic claim — a single-owner token, an expiring lease, a renewing compare-and-set — and that lease is re-asserted immediately before every durable write, which is the fence **REP-M-13** asks for. A second, per-row lease nested inside it and shorter than it excludes no writer the outer lease admits, so it is not a claim but a copy: adding one would put two authorities on one exclusion question ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)). The obligation therefore reads: where a durable outbox has exactly one drainer and that drainer holds a REP-M-13-shaped claim asserted before each write, the claim requirement is satisfied at the drainer; a per-row lease is added only when a second drainer can exist. Nothing is relaxed — a drainer without such an outer claim still owes a per-row one.
