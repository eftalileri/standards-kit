**M21** boot-watchdog clarification: Creating the event-loop-independent watchdog inside the parent JavaScript signal callback is forbidden. Event-loop/native-callback starvation can prevent that callback itself from running, so the watchdog **MUST** start during process bootstrap and complete its READY handshake before long HTTP/datastore/scheduler bootstrap begins. When the hosting init forwards termination to a process group, the watchdog stays in that group, installs its own termination-signal handlers before READY, and arms the first observed signal epoch in its separate event loop. A later parent IPC BEGIN message may preserve or shorten that absolute deadline but **MUST NOT** reset or extend it. The watchdog's hard-kill target **MUST** also be the hosting init's direct child (and therefore the container terminal authority); an `init → package-manager → shell → application` supervisor chain is forbidden because the package manager/shell may terminate on the forwarded signal, make init exit and tear down the watchdog before its hard timer fires, while killing only the application grandchild also does not prove init/container termination. Production starts the application executable directly beneath init while local package-manager UX may keep the same canonical executable arguments; cross-file enforcement **MUST** prove their argument parity. If the service supports both source-mode and compiled-mode startup, watchdog child selection **MUST** be a closed, module-relative derivation: source mode selects the source child with a package-resolved source loader, compiled mode selects the emitted child without a development loader, and every unsupported runtime extension fails closed; cwd, environment labels, guessed artefacts, and existence fallbacks are forbidden authorities. After final logger flush, a disarm-prepare acknowledgement **MUST NOT** remove the hard timer before the parent has actually exited: the child retains the deadline and original-parent PPID fence until parent exit/reparenting, then exits without becoming an orphan. This closes the pre-callback starvation, supervisor-teardown/non-terminal-kill-target and acknowledgement-to-exit watchdog-free gaps. A hosting control-plane teardown record emitted at the configured drain boundary is not application-exit evidence: the provider may retain/remove deployment metadata on its own clock after the process has invoked exit. After the canonical logger is closed, one fixed-schema, bounded, secret/PII-free direct-FD record MAY commit only that `process.exit` is the immediately next synchronous statement; it **MUST NOT** claim the process has already exited or open a reusable logging surface. The watchdog MAY emit a second fixed-schema direct-FD record only after exact original-parent PPID loss is observed. Static enforcement **MUST** bind logger flush → disarm prepare ACK → timer disposal → exit-intent record → adjacent `process.exit`, and bind the child record to PPID-loss dominance. Hard-deadline evidence belongs only to the forced path; its absence on a graceful path is expected.

**M21** READY-deadline clarification: The READY handshake's timeout **MUST** measure only the child's response while the parent is actually waiting for it. Arming it when the child is spawned — typically a module-evaluation side effect — makes it measure the parent's own synchronous work that follows (the rest of the import graph), and because an event loop runs expired timers before it polls I/O, the expired timer fires ahead of a READY message that is already queued: a healthy watchdog is declared dead and the fail-stop boot gate crashes the replica. The timer is therefore armed at the first readiness wait (only if READY has not arrived), and its expiry verdict is deferred past one I/O poll (a check-phase callback) so a READY delivered while the loop was blocked wins; a child that truly never answers still fails the boot. Pick the budget from measured spawn-to-READY latency under CPU contention, not from boot-graph duration. The failure shows up only under contention — for example while an old and a new replica share CPU during a deploy overlap, import-graph evaluation can take many times longer than a timeout armed at spawn, while spawn-to-READY latency stays small. The same race exists for every acknowledgement the parent waits on, not only READY: the shutdown-BEGIN and disarm-prepare acknowledgements are received while shutdown work may starve the loop, and a direct timer there turns a queued acknowledgement into a false watchdog failure and a non-zero exit during a routine deploy. Every such timeout is therefore armed where the acknowledgement is actually awaited (BEGIN after READY is confirmed, never at signal time) and created through one deferred-timeout authority — expiry → check-phase deferral → settled check → failure (**SSG-M8**); a direct timer on any handshake budget is forbidden. Verify by blocking the parent after arming: direct timers reject BEGIN and DISARM, the deferred authority passes, removing only the deferral rejects again, and a frozen child still fails at its budget. Where the adopting project uses a single-file watchdog contract check, it should carry this shape for all three budgets.

**M21** terminal-evidence exception: **M21**'s general “sole permitted direct-FD lifecycle record” restriction means the hard-watchdog record is the sole direct-FD record before final logger closure or on the forced path. The two post-logger records in the boot-watchdog clarification are the only narrow normal-path exceptions: one parent exit-intent immediately adjacent to `process.exit`, and one child observation after exact PPID loss. Neither is a feature logger, fallback sink, reusable API, or permission for arbitrary raw writes.

**M21** settlement corollary: A bounded parallel batch inside lifecycle-tracked work **MUST** retain every already-started sibling until all have settled; fail-fast aggregation that lets the outer tracked promise settle and release its lease while siblings continue is forbidden. After settlement, a non-cancellation failure takes precedence over lifecycle cancellation, and the outer boundary raises that failure before releasing ownership. An inner catch that observes lifecycle abort **MUST** preserve the caught error's identity instead of replacing every simultaneous provider/lease/domain failure with the abort reason; only the terminal lifecycle boundary may classify the exact abort reason as a shutdown skip. Lease release is part of terminal settlement: exact-owner release result **MUST** be awaited and verified before `ok`, `completed`, or equivalent success evidence is emitted; zero-match, indeterminate, or rejected release is failure evidence. The lifecycle signal **MUST** be re-checked after the release await and before terminal success evidence, because cancellation may arrive while release is settling; that race is cancellation/failure evidence, never success. This does not authorize unbounded fan-out: concurrency remains explicitly bounded and the loop still yields/rechecks the lifecycle signal between batches.

**M21** contained-failure settlement: A loop that catches per-item failures, continues, and raises "incomplete batch" at its end **MUST** keep each caught error unwrapped and hand the set to one settlement authority beside the boundary classifier. Wrapping every item failure in one fixed `SYSTEM` code, or raising a raw aggregate of them (`AggregateError` or equivalent), is forbidden: the boundary resolves neither, so the event becomes an unknown-category `SYSTEM` event, an expected retryable member (provider rate limit, transient outage) floods crash reporting, and — when the sink does not render aggregate members — the real cause reaches no channel. The authority reads each member's category from the registry through the same classifier the background boundary uses; if any member is `SYSTEM`/unresolved it raises the registered system code carrying a per-code failure histogram, the first system member's structural identity and that member as the standard `cause`; if every member is expected it raises the first member's own registered code (category preserved, so the boundary writes `warn` + metric) with the batch counts as secondary context. The one logger seam **MUST** render the `cause` chain and aggregate members (bounded depth/count, cycle-guarded, value-scanned per **M25**) and rebuild them for crash reporting's linked-exception view. A readiness failure found in the same loop (missing or invalid stored data, no thrown error) joins the same set as a registered `SYSTEM` carrier built at that reading seam, so one terminal carries every member; the run's non-failure counters travel as secondary batch context, never as a second post-loop gate. *Enforcement:* throwing a raw aggregate is decidable from a single file's syntax tree, so where the adopting project uses source checks it belongs to the raw-error-code throw rule; a rule against reducing a caught item error to a counter or class name and raising a fixed-code carrier after the loop stays a review obligation, because the harm is a mis-categorised event that still reaches the crash channel. A fixed-code re-wrap inside a catch is not locked because a registered `SYSTEM` translation at an owning schema/parser seam is legitimate (**M21**) and one file cannot tell the two apart.

**M21** permanent-candidate corollary: The settlement above applies to a loop that *chooses* to raise at its end; a scheduled loop whose failing item stays in its own candidate set on the next run (no time window, no attempt cap, no terminal state written on failure) **MUST NOT** raise its contained failures as a run failure. One bad row would then fail every run, keep the success trace from advancing — the liveness supervisor reports a working job as `late` — and stop later pages. It logs each item at the background boundary (**M21** severity) and completes; the item's own `SYSTEM` event is the loud signal, and the run's outcome counts only what it actually committed. A loop whose items leave the candidate set on their own (a reminder whose window closes) may raise once at its end. Both kinds **MUST** still contain each item. Whatever a loop does at its end, it **MUST** attempt every candidate of that run: a per-item failure that escapes to the loop boundary ends the run where it stands, and every later candidate goes unattempted with no record naming it. "May raise once at its end" never licenses ending the loop early. For a window-bounded candidate set that is lost work rather than a delay — the unattempted items age out of the window and their effect is never produced, and an unordered candidate query makes which items are lost arbitrary. Making a failure loud and containing it per item are independent obligations, and a change that satisfies only the first is a regression: contain each item, rethrow only the ownership/lease loss, and settle the contained set after the loop through the single authority above. A consumer/delegate loop is inspected together with its candidate query and terminal boundary; the signal/lease and contained-failure authorities carry the outcome. When such a loop runs more often than its item's data can be fixed (every minute), the item's `SYSTEM` record **MUST** be written once per item and defect per bounded window (for example one day) through a cross-instance claim, not on every run — otherwise one bad row floods the crisis channel at the job's cadence; a claim store outage writes the record again rather than dropping it.

**M21** delegate containment: Delegating an execution-item loop into another module does not move containment to the caller: the delegate receives the owner's existing lifecycle signal, contains its own items and settles them through the same authority. A caller catch cannot resume an escaped delegate loop. An interrupted item or recipient loop stops all new effects and reads immediately, but **MUST** settle its previously contained genuine failures before propagating the interruption. A current caught error joins that set unwrapped only when it is a genuine independent non-cancellation/non-lease failure; the abort reason is not an invented member. With no prior genuine failure, preserve the exact abort/lease object and current domain error identity. With one genuine failure, preserve that original object; with multiple independent failures, deduplicate identical objects and use the existing contained-failure settlement authority, retaining the registry-derived maximum severity, histogram and first system cause. This applies to checkpoints outside the former item try as well as a secondary classification read's rejection. A known non-failure skip remains a skip. The outer lease runner **MUST** retain task, renewal and release failures independently rather than replacing a task failure by a later lease failure. Ownership loss still forbids further work; it does not authorize erasing an already observed system failure. The existing signal and settlement APIs hold this cross-file contract; do not add a parallel guard beside them.

**M21** supervisor corollary: A liveness/health supervisor that re-reads every subject each run is itself a permanent-candidate loop, and its blast radius is wider than one subject's: a per-subject failure that escapes its loop leaves every later subject unsupervised, skips the run's own later phases (its alarm drain), and — because the supervisor is usually the one signal the outside world watches — reports the whole watchdog as broken while every other subject is fine. It **MUST** contain each subject, rethrow only ownership/lease loss, and name the contained subjects in the run's own outcome record. The identity it writes conditional updates against **MUST** be proven at the read seam, not asserted by the projection type. A raw (schema-bypassing) read returns what the store holds, not what the schema declares; declaring such a field with the narrow runtime type (a date, a number) is a second shape authority the compiler cannot tell apart from a proven value, and the unproven value then lands directly in the conditional-write filter, where the driver raises an unregistered cast error, outside the registry taxonomy. Declare those projection fields with the language's opaque/unknown type so the compiler forces exactly one reading seam to prove the shape and raise a registered carrier. A non-conforming stored value is never coerced: the shape is a fact the operator must see, and a silent coercion erases how it got there. *Enforcement:* the shape half is enforced by the type system — against the opaque projection type the pre-fix reader is a compile error, which is stronger than a lint rule and has no false-positive surface.
