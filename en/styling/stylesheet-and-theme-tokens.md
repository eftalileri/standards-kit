Scope: Styling obligations for React Native screens and components: the RN version gate, `StyleSheet.create`, the canonical theme module and its token exports, the design-token rules (color roles, type scale, radius roles, elevation, motion), the **STY-LAYOUT-OK** allow list, banned styling stacks, inline `style` literal bans, and the style-file split threshold. The adopting project declares its React Native version, theme authority, token names, layout exceptions, and source locations. This standard does not prescribe a repository path.

Document type: Normative part file under [README](README.md) — **STY-M1**–**STY-M17**, **STY-LAYOUT-OK**, **STY-N1**–**STY-N6**.

Compliance: Violations of **STY-M** / **STY-N** are bugs; **must not** ship — [styling.md](styling.md) **STY-C4**, **STY-C8**. The only exception path is **STY-EX-1** in [styling.md](styling.md).

References: [README.md](README.md); [styling.md](styling.md) (scope, **STY-C1**–**STY-C8**, GSTY1–GSTY6, **STY-EX-1**); [theming-and-appearance.md](theming-and-appearance.md) (**STY-THM**-\*); [ui-primitives.md](ui-primitives.md) (**STY-CMP**-\*).

## **MUST**

| ID | Rule |
|----|------|
| **STY-M1** | The React Native version **MUST** be supported by the project's platform toolchain and compatible with its Expo SDK, if used. Verify upgrades against the published compatibility guidance for the selected release. |
| **STY-M2** | Static component styles **MUST** use `StyleSheet.create` or the styling API established by the application. Do not pass an unstructured static object as the sole source of component styling. |
| **STY-M3** | A project **MUST** define one documented theme authority — a single canonical theme module — that exports the shared color, typography, spacing, shape (border radius) and elevation (shadow) tokens, each as a single object; further token exports (for example opacity, motion, gradients, per **STY-M12**) are allowed. Token names and module location are project decisions. |
| **STY-M4** | Shared visual values for colors, typography (font size, weight, line height, letter spacing), spacing, borders, radii, and shadows **MUST** come from the theme authority. Numeric literals **MAY** be used for structural layout when their meaning is intrinsic, as listed in **STY-LAYOUT-OK**; repeated or design-sensitive values belong in tokens. A property **STY-M4** names that has no entry in the theme is fixed by adding the token first — a theme-design decision, not a literal left in place. Held by review plus whatever source check the project documents. |
| **STY-M5** | Stylesheets **MUST** remain readable and cohesive. When a component's style block becomes difficult to review, move it to a nearby module using the project's established naming convention. |
| **STY-M6** | Compose React Native styles with the supported array form (`[styles.a, condition && styles.b]`), keeping dynamic values limited to properties that genuinely depend on props, state, measurement, or animation. |
| **STY-M7** | Native launch (splash) artwork **MUST** be the plateless brand mark, and the same asset the in-app branded loading surface draws. A launcher / app-icon asset deliberately carries an opaque plate because the OS composites it on an unknown wallpaper; a native launch screen composites the mark on a ground the app itself declares. Reusing icon art there paints the plate onto its own ground: where plate colour and declared ground coincide, the plate is invisible by construction (contrast 1.00:1) and the user sees only a small mark scaled down by the plate's padding. So the launch image **MUST** be a tightly cropped, transparent-background mark, and the plate is supplied by the declared background alone. The launch surface and the app's own branded loading view **MUST** reference one asset, not two copies — one authority per brand mark, so the cold-start hand-off from native screen to first frame is continuous (cold-start continuity itself is [**UIP-M18**](../tanstack-query/ui-startup-and-persistence-boundaries.md)). Where the launch screen is generated from build-time configuration (Expo prebuild and equivalents), that configuration is the only authority: generated native files are rewritten on every prebuild, so editing them is a no-op, and the image's on-screen size is a configuration option, not a property of the generated file. Enlarging that box while the art still carries a plate magnifies the invisible plate, not the mark — fix the asset first. The launch ground colour is a binary value while the in-app continuation can ship over the air to older binaries too: the continuation **MUST** take the colour of the binary it runs in — one theme token read from the launch configuration embedded in that binary at build time — never the newest configuration value an over-the-air update carries, and never a version string; otherwise one binary generation shows a colour jump at every cold start. The continuation **MUST** draw the mark in the launch screen's own box, at the same window-centre position and with no entrance animation, and **MUST** place everything else it shows (wordmark, localized tagline, progress) below the mark without re-centring it; any difference in size, position or opacity reads as the logo jumping. Text that depends on the device language belongs only in that continuation: a native launch image cannot follow the language. Verify (inspect): the declared launch image is not byte-identical to any other image role the app config declares (icon, adaptive icon, favicon); most of what the launch image draws has visible contrast against the declared background; the in-app branded loading view references the same asset path. Limit: what the user sees on device is not measurable from the source tree — a launch-screen change ships only in a new store binary, never over the air. |
| **STY-M8** | Theme colors **MUST** be organised as roles, not hues. (a) Neutrals (backgrounds, surfaces, borders, text greys) **MUST** come from one neutral ramp; a second grey family beside it is forbidden. (b) Every status or accent hue used as text or as a state-carrying icon **MUST** have a paired text tone that reaches 4.5:1 on white and on that hue's own light background, and text/icons **MUST** use the text tone, never the fill tone (bright fills typically reach only about 2–2.5:1 as text). (c) Content text **MUST** be at least 4.5:1 on its surface; a tone below that is reserved for disabled controls and placeholders. (d) A translucent tint of one color is produced from one source (one generator or one named step per percentage) — the same percentage under two names, or a literal fallback after an always-defined token, is a parallel value. (e) The exported color object names roles only: a raw ramp step or a second name for the same value in the same role is not exported, and a token name that states a number states the value's real alpha percentage. (f) Each status hue **MUST** carry exactly one meaning across the product (for example positive/done, incomplete/pending, mild negative such as an amount still owed, error/danger); one element's icon, tint and amount use one hue family, a neutral attribute (a permission or role badge) carries no status hue, and an informational surface (strip, badge, toast, info icon, selected card) uses the brand tint and brand text tone, not a status hue. (g) Text colour **MUST** come only from one closed set of text emphasis tiers declared once in the theme: primary, secondary and tertiary/meta (each at least 4.5:1 on every light surface the app draws, so a tier never changes with its surface), disabled (disabled controls and placeholders only), brand text, the status text tones (on white, the page and their own light ground only), on-fill text and the dark-scene tiers (dark scene only). A fill, border or pressed tone, a raw grey and a per-screen pick are not text colours, and text **MUST NOT** be dimmed with `opacity` — on the text or on a view that only wraps text; a quieter text takes a lower tier, and opacity dims only a whole disabled control or a text-free surface. A component prop or map that carries a text colour is typed to the tier values, so a fill tone does not compile. Reason: a tier carries a measured contrast; a fill tone used as text or a dimmed tier silently drops below it and the text stops being readable. Verify (inspect): review; recompute contrast with the WCAG relative-luminance formula for each text/fill pair when a color token changes; use the lint rule or check the adopting project documents for the tier set and opacity-on-text, and record its actual scope — a colour from another identifier and opacity on a view wrapping text stay review-held. |
| **STY-M9** | Typography **MUST** come from the theme scale. (a) No text smaller than the scale's floor token — sizes below it fail legibility at default font scale. (b) Weight emphasis uses the theme's weight tokens (a small closed set: regular, medium, semibold, bold) as numeric strings, never `'bold'` or a bare literal — numeric strings map predictably on Android. (c) Large titles carry the scale's negative letter-spacing; letter-spacing is otherwise not set ad hoc. (d) Numbers that change or align in columns (money, times, counts, KPIs) use the theme's tabular-numerals token so digits do not jitter. (e) `textTransform: 'uppercase'` **MUST NOT** be applied to localised copy — automatic casing breaks locale rules (for example dotted/dotless i); casing belongs in the catalogue string. (f) With custom typefaces, a style names a family ROLE (display / text / wordmark) through the theme's typography tokens, never a font file name, and states weight only through the weight tokens; exactly one resolver, applied to every `Text`/`TextInput` at render, maps (role, weight) to the concrete face file, and a family it does not know (icon fonts, emoji) is left untouched. Reason: a runtime-registered face is one family per file, and Android cannot pick a different file through `fontWeight` (it ignores intermediate weights and synthesises bold), so weight only works when the file itself is chosen — by one authority, not by every call site. A role token changes a whole class of text at once; a call site whose content differs from its token's class overrides only the family role. A third-party component that names its own default family (for example `'System'`) **MUST** receive the role through its theme/style keys for every text it draws — the resolver leaves a named family untouched, so an omitted key keeps that text in the system face. (g) A card or row title that names an item (a catalogue entry, a plan, a place, a stock item) **MUST** use the theme's single item-title role token — one step for an item with its own card, one denser step (never below the display face's text floor) for an item nested in another card, a grid tile or a list row — never a body/label token with a weight bump or a per-site family override; a person name stays in the text face. Any highlighted amount, standalone date or KPI figure spreads the theme's number-face token over its carrier size token (never below the project's documented minimum); digits that update in place or align in columns and phone numbers keep the text face. Reason: one role per class keeps every item name and every highlighted figure in the same face on every screen. (h) The product wordmark **MUST** render only through the single wordmark component, in its own family role; item titles and highlighted figures stay in the display face. Its text is Latin in every locale, so its role is flagged "content always Latin" and keeps its face in non-Latin display languages. Reason: one drawing keeps the brand identical on every screen and language. (i) A text class the product owner names separately (a header title, a date title, a screen title) **MUST** own its own typography role token even when it shares another role's face and size today; a class **MUST NOT** reuse or spread a sibling's role token because the two look alike. Reason: every role stays adjustable on its own. (j) Readability floors: running text (body, supporting, caption, helper, timestamp) is at least the project's documented running-text floor; text below that floor (badge, counter) is at least medium weight; a title that heads a card, a row or a list item is at least medium (500) in every state — a read, inactive or secondary card title takes a title or label role, never a regular body role. Verify (inspect): review; a literal font-size or font-weight lint is optional and its scope must be recorded. |
| **STY-M10** | Corner radius **MUST** be chosen by the element's role from the theme's role tokens — control (button, input), card, sheet, dialog, full (capsule/circle) — not by picking a raw step per screen. One radius per component class is the most visible consistency cue; a raw step stays available only for parts inside a component. A full capsule/circle uses the full-radius token, never a value that only rounds elements below a certain size. Held by review. |
| **STY-M11** | Elevation **MUST** come from the theme's elevation levels (none plus a small fixed number of levels), resolved once in the theme for all platforms: the theme renders the same soft shadow on iOS and Android through the cross-platform `boxShadow` style and supplies a light `elevation` fallback only where the platform cannot draw `boxShadow`. A component **MUST NOT** assemble shadows from `shadowColor`/`shadowOpacity`/`elevation` parts or branch on platform for depth — split per-platform shadows look like two different apps. The edge follows the surface: a resting white card on a near-white screen background pairs a hairline border with the lowest level (white on white needs both an edge and a lift); floating surfaces (menus, sheets, dialogs, elevated cards) carry the shadow without a border; inputs carry the border alone; tinted surfaces (status banners, icon tiles, tonal buttons, tinted blocks inside a card) never carry a shadow. Selection **MUST NOT** be signalled by a colored glow — use the selected background, border and mark (**STY-CMP-M11**). Verify (inspect): a search for shadow/elevation property literals outside the theme module finds nothing; level choice, platform branching and surface edges by review. |
| **STY-M12** | Animation durations and springs **MUST** come from the theme's motion tokens (a short duration ladder, one snappy press spring, one calm layout spring). Shared motion primitives (press feedback, entrance, skeleton shimmer) **MUST** honour the operating system's reduce-motion setting inside the primitive — movement and looping shimmer are dropped, opacity changes may remain — so no consumer re-implements the check. Held by review. |
| **STY-M13** | Icon glyph sizes **MUST** come from the theme's icon scale (a ladder for inline and control icons, and a separate display set for empty-state and info-screen hero icons), never a numeric literal in a `size` prop; a size outside the scale is added to the scale, not inlined — near sizes (±2 dp) snap to the nearest step so the app keeps one icon rhythm. Verify (inspect): a search for numeric `size` literals on icon components finds nothing; the rest by review. |
| **STY-M14** | System font scaling **MUST** stay on and **MUST** be capped by the theme's scale-cap tokens (a default cap and a lower dense cap). The default cap is applied once, globally, to every `Text` and `TextInput` by one installer at app start — not per screen; `Text.defaultProps` is not a mechanism (React 19's JSX runtime ignores `defaultProps` on function components). Dense surfaces whose width or height is fixed by layout (tabs, badges, chips, a label beside its value, calendar cells and session cards) take the dense cap through the one dense scope inside the primitive or card, never a per-`Text` literal multiplier. `allowFontScaling={false}` is allowed only on text drawn inside a fixed-size graphic, with a one-line reason comment. `Text`/`TextInput` **MUST** come from the `react-native` root export (animated text from Reanimated), never a deep `react-native/Libraries/...` import or React Native's own `Animated.Text`, which bypass the installer. Reason: unlimited scaling breaks dense rows (clipped labels, overflowing cells), while disabling it locks out low-vision users. Verify (inspect): a search for `allowFontScaling={false}` and `maxFontSizeMultiplier` literals finds nothing outside the cap authority. |
| **STY-M15** | Bundled brand typefaces **MUST** be shipped as static per-weight files whose file name equals the face's PostScript name, embedded natively for new binaries and loaded at runtime from the JS bundle for binaries that predate the embedding, so every binary reachable by an over-the-air update resolves the same family names. The first frame **MUST NOT** render before the load settles: loading is a local startup step inside the native-splash readiness gate, bounded by a timeout so it can never hold the splash. The decision is per face: a face the binary already registers is not loaded and adds no wait, and only unregistered faces load at runtime, started in parallel with the other local startup steps. The icon font the first system screen draws is part of the same gate. A failed or timed-out load **MUST** be reported through the client crash-report channel and the session continues in the system font, never with a half-registered face. In the browser build the files arrive over the network, so the timeout only releases the splash gate: it **MUST NOT** mark the load failed or be reported by itself, the fetch continues and the faces apply when they arrive, and only a rejection is reported, because elapsed time on a network fetch is no proof of a defect. Brand faces apply only while the display language is written in a script the font files cover (a role whose text is Latin in every locale excepted, **STY-M9**(h)); other languages use the system font, classified by one exhaustive language → script table, so one line never mixes a brand Latin face with per-glyph system fallback. A display (heading) face is not used below the project's documented minimum size for text or for a highlighted number, and a face without tabular figures is not used for digits that update in place or align in columns. Verify (inspect): the native embed list is derived from the font folder and the runtime asset map is keyed by the theme's face-name table, so a face without its file fails the bundle; the rest by review. |
| **STY-M16** | App icons, the launch mark, the notification icon and the in-app brand logo **MUST** be rendered from one artwork source by one generator into one file per role, never hand-edited or copied between roles. Per platform: iOS appearance icons are full-bleed 1024 squares with no pre-rounded corners (the OS masks); the light ("any") and tinted variants **MUST** be opaque because Expo prebuild flattens their transparency onto white — the tinted variant is grayscale artwork on black, since the system tints by luminance; the App Store icon carries no alpha channel. The Android adaptive foreground and monochrome layers **MUST** keep the mark inside the 66 dp safe circle of the 108 dp canvas (artwork square = the central 72 dp); the monochrome layer and the Android notification small icon are single-colour shapes on transparency, because the system reads only their alpha. An in-app logo **MUST** be a JS-bundled asset, never a native icon resource, so an over-the-air update to an older binary can draw it. Verify (inspect): open the prebuild output (iOS app-icon set, Android mipmap and notification-icon drawables) and look at it. |
| **STY-M17** | Server-rendered user-facing documents (PDF reports, e-mail HTML, any image or page the server draws) **MUST** read colours, type families and the logo from one server document brand module, and that module **MUST** derive every value from the cross-tier raw palette the app theme also reads; a template, chart or layout **MUST NOT** write a colour literal, a font family name or a logo path of its own. Brand text faces apply only in languages the face files cover, by the same language-script table **STY-M15** uses; the wordmark stays on its face in every language. An e-mail names the brand faces as intent with safe fallbacks and loads no web font; its logo is an absolute HTTPS image, never an inline data URI. Copy **MUST NOT** name a chart or status colour ("purple segment"): it names the series or legend, so a palette change cannot make the text lie. Reason: two hand-written palettes drift by construction. Held by review. |

### **STY-LAYOUT-OK**

Structural numeric values may remain inline or in a stylesheet when they express layout mechanics rather than visual design. These property names may use numeric literals without theme tokens when the value is only structural layout:

- `flex`, `flexGrow`, `flexShrink` — small integer flex ratios.
- `flexBasis` — numeric literal `0` only, or the strings `'auto'` or a percentage (`'%'` suffix) without raw dp integers (a fixed dp basis uses a spacing token or **STY-EX-1**).
- `zIndex` — small integers within the project's documented band unless **STY-EX-1** documents a deeper stack contract.
- A measured animation value.

Projects may document a short, stable set of further such exceptions. Any other numeric dimension (width, height, padding, margin, gap, radius) remains **STY-M4** — theme tokens required. Do not use this allowance for repeated spacing, typography, palette, or brand values.

## **MUST NOT**

| ID | Rule |
|----|------|
| **STY-N1** | Do not add or retain a styling framework or runtime styling dependency (utility-class RN styling, CSS-in-JS packages and the like) without **STY-EX-1** and a check of compatibility, bundle and runtime cost, and consistency with the application's established styling model. |
| **STY-N2** | Do not put fixed spacing, size, typography, radius, or shadow literals (padding, margin, gap, font size, width, height, min/max sizes, border radius) in inline style props where a shared style or token should own the value. Values that are solely a single identifier or member expression bound to runtime layout (GSTY1) are allowed. |
| **STY-N3** | Do not use raw color literals (`#hex`, `rgb`, `hsl`, or named web colors other than `transparent`) in inline style props or product components where the theme authority provides the palette; reference theme tokens instead. |
| **STY-N4** | Do not create a second theme or palette authority — a module exporting the color object (or the full token set) in parallel to the canonical theme module — for the same application surface. In a monorepo, check per mobile app package. |
| **STY-N5** | Do not ship new RN UI that omits `StyleSheet.create` (or the project's structured static-style mechanism) for component-owned static styles, and do not replace it with ad hoc style objects. |
| **STY-N6** | Do not choose or introduce visual tokens arbitrarily ("agent discretion", for example picking a new hex without a theme update); extend the theme authority when a design value is genuinely missing (GSTY4). |

## Verification limits

Source checks can find literal values and duplicate exports within their configured file scope. They cannot determine whether a visual choice matches the design system, whether an asset looks correct at device scale, or whether every screen remains readable with text scaling. State the actual check scope and review rendered screens on supported platforms.
