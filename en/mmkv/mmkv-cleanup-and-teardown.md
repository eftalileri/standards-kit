# MMKV — cleanup, removal and session teardown

```kit-cover
type: normative
part-of: README.md
binds: MMR obligations - what is removed when a session ends, a sensitive store is retired or an app update changes the persisted schema, and how that removal is proven
open-when: shape:frontend-heavy, signal:key-value-storage-only, signal:cache-persistence, signal:persistence-invariant
skip-when: signal:backend-only, signal:no-client-persistence
owns: MMR-M8, MMR-M11, MMR-M13, MMR-M14, MMR-N4, MMR-N6, MMR-N7, MMR-N8
```

Scope

- Included: Session teardown coverage and its single authority, the identity-change and sign-in retirement verdicts, dedicated legacy-sensitive instance removal with proof of absence, and what an app update keeps or resets (truth-owner classes, schema epoch, per-decision contract versions).
- Excluded: Budgets, `maxAge` and buster rules ([capacity and retention](mmkv-retention-limits-and-buster.md) **MMR-M1**–**MMR-M7**, **MMR-M9**, **MMR-M10** ); encrypted-instance design and its migration lifecycle ([encrypted-instance design](mmkv-encrypted-instance-design.md) **MMR-M12**, **MMR-N5** ); adapter failure shape (MMA-\* ); instance creation (MMI-\* ).

Document type: Normative — part of MMKV SSOT.

Binding principle: A store that nobody clears and a removal that nobody proved are the same defect: data that outlives the session that created it.

Rule locality: This topic's MMR rows are divided by question across three files. [mmkv-retention-limits-and-buster.md](mmkv-retention-limits-and-buster.md) covers persist budgets, age, buster, classification, and orchestration; this file covers teardown coverage, proof of removal and update-time resets; [mmkv-encrypted-instance-design.md](mmkv-encrypted-instance-design.md) covers key, identity, and migration requirements for encrypted stores.

## **MUST**

| ID | Rule |
|----|------|
| **MMR-M8** | On sign-out, clear server-state caches, reset or clear persisted client stores, and retire other device-resident data according to one teardown authority. Decide the purge-or-keep verdict for every persistent store in one place; keep only device- or preference-scoped facts that identify nobody. Data that identifies or locates the departing user must be purged. Record user-visible costs of purging, such as a required resynchronization. Prove sensitive-store removal with an exact post-delete absence read, and report any unproven removal through one fail-loud signal. A missing cleanup call is a whole-tree coverage problem: use the coverage check the adopting project documents (its store set discovered from the source tree, never from its own verdict table — deriving discovery from the table makes an unlisted store both "absent" and "undecided", and the check can then never fail), and record its actual scope and limits; review covers the remaining semantic scope. |
| **MMR-M11** | Dedicated legacy-sensitive instance removal: when a released version wrote sensitive data to a dedicated MMKV instance that cannot be invalidated by the current canonical buster, cleanup addresses that exact retired identity and the provider's complete known removal surface. Retire its writers and live handles before terminal instance removal. The single provider removes the retired contents and supplies an exact, read-only post-removal absence result for the same scope; that check **must not** open or create the removed target. A live-instance read needed for value import or key deletion is a different phase, completed before retirement, not a reason to reopen a removed instance. Logical key emptiness alone is not physical instance-removal proof: applicable data, integrity/CRC and legacy namespace entries **must** be accounted for, and the result **must** name any unproven scope. Unknown historical/custom roots, partial removal and native initialization, inspection or deletion failure are not success. Retain an explicit retry-required result, run a finite bounded retry cycle, and start a fresh bounded cycle when the app next becomes active. Exhaustion **must** fail loud through established client observability using code-owned surface labels, without logging keys, values or private paths. The retired adapter **must** expose no new read/write cache path. The proof covers only the provider's established removal scope; it is not future absence, backup removal or forensic-erasure evidence. |

| **MMR-M13** | A data scope is retired in more than one way, and the verdict table **must** answer each way. Sign-out is the obvious retirement, but it is not the only one: an account can also change the identifier it is keyed by (a phone number, an e-mail, a tenant handle) while the *same human being* stays signed in on the same device. Treating that as "not a logout" leaves the retired identity's data in place; treating it as a logout destroys the session that was just established. So every store whose sign-out verdict is `purge` carries a second, explicit verdict for identity change, and only two answers are admissible: purge (nothing overwrites it, so residue survives untouched) or survives with a written reason that passes one of exactly two tests — (a) the identity-installation path is the store's single writer and overwrites it with the new identity's value, or (b) the data identifies nobody and the same person remains. The sign-out verdict is the wrong trigger, and two answers are not enough. A `keep` store looks exempt — sign-out is the stronger event, so what survives it survives the weaker one — and that reasoning fails for a store whose key is derived from the identifier. There `keep` is not protection: the key changes with the identifier, the old record is addressed by nobody, and where the engine offers no key enumeration (secret stores typically do not) it can never be found again — kept in name, destroyed in function, so the weaker event produces the heavier loss. Trigger the second verdict from the code instead: every store writing an account identifier into its key *or* its payload carries one, whatever its sign-out verdict. Such a store often admits neither answer, because deleting it discards something the user paid for or is owed; the third verdict is migrate — rewrite the record under the new identifier's key. A `migrate` names the module that moves it and meets the same reachability proof as `purge` (**MMR-M8**): an unreachable move leaves the record as lost as no decision at all. Ordering follows what a partial failure costs — write the new key first, delete the old second; the reverse loses the record outright if the write is rejected, while this order leaves at worst an already-unreachable remnant. Reason (a) also fixes an ordering contract: a teardown that runs *after* the new identity is installed **must not** touch an (a)-class store, because at that moment the value it would delete is the new session, not the old one. Both retirements are served by the one teardown authority (**MMR-M8**) in two modes — a second module is a second verdict table and will drift. The modes differ in what they *may* touch, not in who decides: an identity-change mode **must not** reset the session/auth state, because the flag it would clear is what keeps the in-flight screen mounted. When judging a `survives` reason, do not assume the device state belongs to the person completing the change: a session dropped outside the teardown authority (an expired- or superseded-token interceptor, for instance) reaches a signed-out screen with the previous identity's data fully intact. A third retirement: signing in. Installing a session retires whatever identity the device last held — a session can be dropped *outside* the authority, leaving that data intact — so every session-installing path carries an explicit verdict, decided from evidence inside the authority, never at the call site: name the field recording the last identity, prove its writer and that the out-of-band drop does not clear it, then compare. Same identity ⇒ skip; unprovable ⇒ purge — "probably the same person" is forbidden, the cost of guessing wrong is someone else's personal data. Ordering is the inverse of identity change: *before* installation, which builds the very cache a later teardown would destroy. [On violation: Bug — privacy-class defect; the retired identity's data survives, or the freshly installed session is destroyed by its own cleanup] [Verify by: for each store, read the sign-out verdict and the identity-change verdict side by side, and confirm every `survives` reason names the single writer that overwrites it or the property that makes it identify nobody] Enforceable half: that a second verdict *exists* and that a `survives` verdict carries a reason is a cross-file coverage check (the same one that owns **MMR-M8**). Review checks that each reason is true. The bypass — a call site that retires the client cache itself (`queryClient.clear()` and its equivalents) instead of calling the authority — is enforced only to the extent the adopting project documents a running check for it; record that check's actual scope and limits. |
| **MMR-M14** | An app update **MUST NOT** re-ask a permission or decision the user already gave, and **MUST NOT** let current code read device data that an incompatible schema wrote. Each persistent store **MUST** declare who owns its truth in the same single declaration table that holds its teardown verdicts (**MMR-M8**, **MMR-M13**) — one row per store, read by every behaviour; a behaviour keeping its own store list is a second authority. Update behaviour is derived from that class alone. (a) OS-owned facts (permission and authorization status) **MUST NOT** be stored as truth: every decision reads the OS live; a stored copy is at most a non-authoritative hint that never opens, suppresses or re-opens a prompt, and re-asking happens only when the OS reports undetermined (or denied and the user acts). (b) A user decision recorded by the app (consent answer, "don't ask again", snooze, dismissal, preference, acknowledgement) survives every update and resets only when that decision's own contract version advances — the asked text or purpose changed. The version is per decision and never the app, build or bundle version; where the stored payload already carries the version it answered, that version is the contract and no second one is declared; a device with no recorded version adopts the current one; a stored version above the current one (a rollback) is kept. (c) A derived or server cache resets when one persisted-state schema epoch differs from the stored one, in either direction (a rollback reads a newer schema), and that epoch **MUST** be the query cache's only hand-set invalidation token (its buster suffix, which **MMR-M5** advances) so the cache and the cache-class stores invalidate together; a second hand-set marker for the same question is a duplicate authority. Introducing the epoch keeps the existing token's value, so no device loses its cache. (d) Identity and session data are governed by teardown (**MMR-M8**, **MMR-M13**) and survive updates. (e) Installation facts (installation id, at-rest key, credential, language, undelivered telemetry) are never reset by an update. The decision runs once per process before any persisted cache restores or any store hydrates; where the storage engine is not ready yet, nothing can hydrate either, and the decision repeats at the engine's readiness milestone. A device without a marker adopts the current epoch — the data it holds was written under it. The marker (epoch, running bundle id, decision versions) records a reset only after it proved absence (**MMR-M11** proof granularity); an unproven reset fails loud once with closed store labels, stays unrecorded and is retried on the next launch, while a proven decision reset is recorded so the user is not asked twice. Decision resets run in the same synchronous pass as cache resets, before any reader loads the old answer; a decision kept in asynchronous storage moves to synchronous storage before its contract may advance. Reset handlers are total per class by construction: a cache-class row or an advanced decision without its reset does not compile. Reason: an update that re-asks erodes the consent it asks for, one that reads old-shaped data misleads or crashes, and one store list per behaviour drifts. [On violation: Bug — user-visible re-ask of a granted permission or answered decision, or stale-schema data restored into current code] [Verify by: every row carries a class; no store caches an OS status; every cache-class row and every decision whose contract advanced has a reset reachable from the single lifecycle authority; the marker write follows the verified resets] Enforcement: use the mechanisms the adopting project documents (a type-level requirement that every row carries a class and that reset handlers are total per class, plus the coverage check of **MMR-M8** that every discovered persistent writer has a row); record their actual scope and limits. Review checks that each class is true. |

## **MUST NOT**

| ID | Rule |
|----|------|
| **MMR-N7** | **Must not** treat identity change as either identical to sign-out or as no retirement at all, give a `purge`-at-sign-out store no identity-change verdict, accept a `survives` verdict without a reason naming the overwriting writer or the non-identifying property, delete an overwritten-by-the-new-identity store *after* the new identity was installed, reset session/auth state during an identity change, open a second teardown module for the second retirement form, retire the client cache at a call site instead of through the teardown authority, install a session without an evidence-decided retirement verdict, or skip the purge on an unprovable previous identity (**MMR-M13**). |
| **MMR-N8** | **Must not** store an OS permission status as truth or gate a prompt on a stored copy, reset or re-ask a user decision because the app or bundle version changed, key a decision's validity on the app version, keep a per-behaviour store list beside the declaration table, record a reset in the update marker before it proved absence, run a decision reset after its readers or stores loaded the old answer, or restore a persisted cache or hydrate a store before the update decision ran (**MMR-M14**). |
| **MMR-N4** | **Must not** count a one-shot best-effort `remove`/`clearAll` call as legacy-sensitive cleanup, report success without an exact post-delete absence read, or abandon cleanup permanently because the native instance was unavailable during one mount (**MMR-M11**). |
| **MMR-N6** | **Must not** let a persistent store reach production without a written session-teardown verdict, spread session cleanup across call sites instead of one teardown authority, justify a `keep` verdict for data that identifies the departing user, treat a `purge` verdict as satisfied by a function that exists but nothing calls, or report session cleanup complete while a sensitive store's absence read failed (**MMR-M8**). |

## Failure paths (normative)

| Situation | Required behavior |
|-----------|-------------------|
| Dedicated legacy-sensitive instance cannot be inspected, fully retired or proved absent in its established scope | Return retry-required, use the bounded mount/foreground cleanup lifecycle, and emit a fail-loud observability signal after exhaustion; a creating reopen, unknown scope or logical-empty result is not physical removal proof (**MMR-M11** / **MMR-N4**). |
| A new persistent store is added | Give it a `purge`/`keep` session-teardown verdict in the same change; a store with no verdict is not "not yet decided", it is a store that silently keeps user data (**MMR-M8** / **MMR-N6**). A `purge` verdict — or any store keyed by an account identifier — needs the identity-change verdict too (**MMR-M13**). |
| An account changes the identifier it is keyed by | Route it to the teardown authority's identity-change mode: purge what nothing overwrites, leave the stores the identity-installation path rewrites, and do not reset session/auth state (**MMR-M13** / **MMR-N7**). |
| A session-teardown purge cannot prove the store is empty | Name the unproven surfaces in one fail-loud report using closed, code-owned labels and finish the teardown; the user is logged out either way, but the residue **must** be visible (**MMR-M8**, **COB-RN-M11**). Session teardown is a one-shot event, so it does not inherit **MMR-M11**'s foreground retry cycle — where a project wants the residue retried, that is a separate bounded lifecycle and **must** be stated, not assumed. |
