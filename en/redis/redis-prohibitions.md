## **MUST** (normative) — **RDS-M21** to **RDS-M23**

**RDS-M21**: A cache generation is never the correctness authority for a durable authorization/materialization side effect. When a durable write must be rejected if the relevant authorization or scope authority changes between an external read and its terminal durable write, the durable aggregate **MUST** own a persistent, monotonically increasing epoch/version. Every writer that can change the effective authority **MUST** advance that epoch in the same atomic database write/transaction as its projection; idempotent/stale no-op paths do not advance it. The candidate authority and any bounded provider/outbound read are obtained before the transaction under one fixed deadline. Inside one transaction, the materializer **MUST** compare the candidate epoch, touch/advance the same durable authority document so concurrent authority writers create a write conflict, and pass one opaque scope- and request-bound authority through every terminal write; current external-credential or evidence expiry is rechecked immediately before each terminal write. Cache/Redis calls and outbound work **MUST NOT** occur inside that transaction callback. Redis remains cross-instance cache coordination only: its TTL, eviction, restart, generation reset or outage cannot make an old durable candidate current again. Cache invalidation is still required by **RDS-M17**/**RDS-M20** after commit, but its success/failure does not replace the durable fence. [Consequence: Critical integrity bug — stale authorization or entitlement evidence materializes durable state, Redis ABA revives an old proof, or a cache outage becomes an untracked correctness hole.] [Verify: writer inventory proving same-write epoch advancement; transaction call graph proving one candidate/one fence per batch, scope/request-bound terminal dominance and no cache/outbound call in the callback; race review `candidate(epoch n) → authority writer commits epoch n+1 → materializer CAS/touch rejects`, plus expiry-before-terminal rejection.]

**RDS-M22**: A server-side derived read cache is admitted only on a measured need, never skips authorization, and is invalidated structurally by the data-write layer, never per handler. A derived read cache is a Tier B (**RDS-D2**) cache that serves a computed value without re-running its authority read — for example an expensive aggregate summary. A server response cache that answers without running the handler is not such a cache; it is prohibited for tenant-scoped and permissioned reads (**RDS-N14**). Scope of the write-coverage duty: a derived read that promises no actor post-write visibility — a cross-tenant operator aggregate whose product-accepted staleness is at least its entry TTL — uses the TTL-only strategy of **RDS-M6** (a), with that TTL declared as its stale bound in the key registry; the write-coverage sentences of (0) and (a)–(b) do not apply to it, while admission measurement, authorization order and key discrimination still do. Its input is every tenant's writes, so a write-layer bump would expire it on nearly every request and the cache would never hit. (0) Admission. Before the cache is added, the authority reads and latency a hit saves **MUST** be measured on production-shaped traffic and set against the invalidation surface — every write path that can change a value the cache serves; the cache is added only when the saving is material for that read, and the measurement is recorded in the project's decision record for that cache. The request's authentication, tenant resolution and permission checks **MUST** run before the cache is consulted, and the key **MUST** carry every input the served value varies by, including the actor's authorized scope where the value differs by permission. The cache is correct only when every write that changes a value it can serve has bumped it before that write's own response completes: a hit skips the authority read, so nothing on the read side can notice a write that did not bump. Coverage is therefore owned by the write layer, not remembered by callers. (a) Record at the write. The single data-write layer (repository / model write path) **MUST** record the affected tenant scope in a request- or job-scoped recorder for every write it performs, unconditionally. The recorder holds a set of scopes for the current unit of work only, never process-global state (**RDS-N1**). A write that runs outside any unit of work opens its own and flushes at its own completion; it never skips recording. Recording touches no Redis key, so it is safe inside a transaction (**RDS-M20**(b)); a scope recorded by a write that later aborts costs one unneeded bump, never a stale read. (b) Flush once, before completion. One awaited flush **MUST** bump every recorded scope immediately before the response is completed — for every status and on every response path, error responses included, because a failure response can follow a committed write. A job, queue consumer, cascade or background continuation **MUST** flush at its own completion point before it marks the work complete (**RDS-M17**(c)). The flush is the cache's single invalidation owner (**RDS-M20**(a)) and consumes the cache's own generation primitive (**RDS-M19**); no write site repeats the cache's key list. (c) Per-handler invalidation calls, route or path-prefix lists, request-method guesses and sweeps that run after the response was sent **MUST NOT** be the coverage mechanism. Each covers only the writes its author listed, so an omitted sibling write ships stale by construction, and a sweep after the response races the client's next read and loses it. (d) Failure semantics. The flush runs after the writes are durable, so it is the post-commit Tier B surface of **RDS-M17**'s caller classification: awaited and never detached (**RDS-N9**), never turning the committed write's response into a failure, degraded observably per **RDS-D3**. The cache entry TTL (**RDS-M4**) is then the whole stale bound after a failed bump, so it **MUST** be no longer than the staleness the product accepts for that read, and it **MUST** run from that entry's own fill: a hit, or the fill of a sibling entry stored under the same Redis key, never extends it, because a container-level TTL refreshed on every fill keeps a stale entry alive without bound. [Consequence: Bug — a write path missing from a hand list, or a sweep after the response, lets the next read receive the pre-write value; client invalidation and refetch then prove nothing ([**MUT-M28**](../tanstack-query/mutations-optimistic-strategy.md)); a cache consulted before authorization serves a revoked actor.] [Verify: recorded admission measurement; authorization middleware ordered before the cache read; writer inventory showing every write reaches the recording layer; the flush is the cache's only bump caller and sits on the response-completion path for every status; forced Redis failure leaves the write response unchanged and emits one degraded signal.]

**RDS-M23**: A database write that an accepted request would otherwise make every time (a "last used" / "last seen" stamp) **MUST** pass a cross-instance TTL gate first (`SET NX EX`, one per subject per window) and **MUST** be skipped, never written ungated, when the gate store is unavailable; the request neither waits on that write nor fails with it. [Consequence: request-proportional writes load the database, and a Redis outage that falls back to writing turns the stamp into a write storm.] [Verify: review-held — N requests inside one window produce one write; with Redis down they produce none and still succeed.]

## **MUST NOT** (normative) — **RDS-N**

**RDS-N11** same-record variant qualifier. For the explicitly defined **RDS-M19** same-record non-repeating variant, **MUST NOT** extend descriptor/value expiry on valid capture, hit, verify or publication; recreate an old captured identity after record loss; return a candidate without its final identity/current-epoch fence; treat a sent command's timeout as rollback; or claim older plain SET/DEL readers satisfy that protocol. This qualifier does not remove the numeric reusable-generation TTL margin, canonical paired-key Cluster co-location or staged future-namespace activation prohibitions in the original **RDS-N11** row below.

**RDS-M20**: Event-driven invalidation belongs to the write authority, and for a transactional write it happens after commit. (a) Placement. When several call sites reach the same durable mutation, the invalidation **MUST** live at the single write authority for that cached aggregate — the one function that performs the mutation — not be copied into each caller. An obligation duplicated per call site is a parallel obligation: it is satisfied on the paths the author happened to be looking at and silently omitted on the sibling paths (one mutation path invalidates while sibling paths that use the same write authority fail to do so), and the omission is invisible because the durable store is correct and only the cached read is stale. Where a caller must still invalidate — because the authority cannot know the cache scope, or because of (b) — that caller is the orchestrator, and the authority **MUST NOT** invalidate as well; exactly one of them owns it (this is [**SSG-M8**](../ssot/ssot-principles-and-precedence.md) applied to an obligation rather than to a value). (b) Ordering under a transaction. A write executing inside a transaction **MUST NOT** invalidate from within it: the key is deleted before the mutation is durable, so any concurrent reader repopulates it from the pre-commit snapshot and restores exactly the staleness the delete was meant to remove — and an aborted transaction has already destroyed a valid entry. The invalidation therefore moves to the post-commit boundary of the orchestrator that owns the transaction lifecycle ([transaction policy](../transactions/transaction-policy.md) TX-M-2), still awaited before success is reported (**RDS-M17**). A mid-transaction writer that consequently does not invalidate **MUST** record that fact and name its post-commit owner at the write site. (c) Ordering AMONG the effects at that single point. Once (a) has collapsed several obligations onto one named effect point, the order between them stops being a stylistic choice: where a later effect reads the state an earlier one invalidates, that later effect observes the pre-change value unless the invalidation completed first. The sequence is therefore part of the contract — fixed, `await`ed, and justified in the effect point's own header, naming which effect reads what. Two failures share one signature: reordering the pair, and leaving either one floating (`void`, un-awaited) so the second cannot have waited for the first. Neither raises an error; a dependent operation decides from a stale snapshot and persists the wrong result — state that the authority has already changed may remain visible to readers as current. Stated limit ([KIT-INV-8](../authoring/kit-structural-invariants.md)(b)): the ordering and the `await`s at the effect point are decidable from one file's syntax tree and are mechanically enforced; the inventory half — that every write path which changes the guarded state calls this effect point at all — is not. Whether a given function *is* such a writer is not a syntactic property: no marker type, decorator or naming convention declares it, so the enumeration lives in prose and is review-bound (**SSG-R4** governs how that list is written; a count is forbidden and an open-ended tail reproduces the defect deliberately). A single-file check can pin the ordering and the `await` on each effect and the single caller, but it does not prove reconciliation await, second functions inside the owner, or complete writer reach; the adopting project records the actual scope of any such check, and **SSG-R4** retains the closed writer inventory. (d) Two staleness KINDS in one key class. A cached entry can go stale two ways and they are not one class: the value drifts while the key still denotes the same subject, or the key comes to denote a different subject because the identifying attribute it is keyed by was reassigned to someone else. TTL-only ([**RDS-M6**](redis-connection-keys-and-authority.md)) is a real choice for the first — the entry is merely old and self-heals — and never for the second, because a wrong subject is not an old value: waiting does not make it right, and inside the window the cached answer can be copied into a new durable record and outlive the cache entirely. Where both kinds exist for one key, **RDS-M6**'s demand for exactly one documented strategy is met by naming each kind with its own strategy in the key's own header, so the mixture is declared rather than ad hoc. Choosing event-driven deletion for the rebinding kind does not oblige the drift kind to follow, and the writer enumeration of (a) is then made per kind — a contract that covers only some writers of the kind it claims is the same defect in a new place. [Consequence: Bug — a sibling write path ships stale-by-construction, a transactional invalidation is undone by a concurrent pre-commit fill, a dependent effect decides on the snapshot the invalidation was meant to retire, or a cached answer keeps naming the previous subject and is copied into a durable record.] [Verify: Cross-file check that every write path for a cached aggregate reaches exactly one invalidation owner — a single-file AST cannot see the authority and the invalidator in different modules; plus review that no invalidation call sits inside a transaction/session scope; plus a single-file AST rule pinning the effect point's internal order and the `await` on each effect, and forbidding the pair from being re-spelled together in any other function body.]

**RDS-N1**: Must not silently fall back to in-process state (in-memory `Map`, per-instance counter, local cache) for a cross-instance concern, and must not serve stale data on a Redis error. Observable degradation (database authority + loud log + degraded health per **RDS-D3**) is REQUIRED — it is the opposite of a silent fallback. Taking the whole process down for an infrastructure outage (rather than degrading) is also forbidden (**RDS-M2**). [Consequence: Critical bug — must not ship.]

**RDS-N2**: Must not write a key without a TTL unless it is registered as a durable exception with a reason and eviction-safety note (**RDS-M4**, **RDS-M13**). [Consequence: Bug.]

**RDS-N3**: Must not keep a second parallel store (a second cache, a shadow in-memory copy) for the same datum that already has an authority (**RDS-M5**). [Consequence: Bug — two sources of truth.]

**RDS-N4**: Must not return stale cached data when a Redis command errors; degrade to the database authority (fresh, not stale) and log per **RDS-D3** / **RDS-M14**. [Consequence: Bug — hidden incorrectness.]

**RDS-N5**: Must not use keys outside the **RDS-M3** namespace or keys absent from the key registry. [Consequence: Bug — unowned keys.]

**RDS-N6**: Must not release a distributed lock with an unconditional delete or reuse a lease beyond its TTL without re-acquiring (**RDS-M7**). [Consequence: Critical bug.]

**RDS-N7**: Must not commit a Redis connection string or credential to the repository or bake it into a build image (**RDS-M11**). [Consequence: Security bug.]

**RDS-N8**: Must not guard outbound work triggered by unauthenticated or untrusted input with process memory, a per-instance cache, or a Redis key containing attacker-controlled input; must not perform that work when the **RDS-M16** shared claim is unavailable, denied, or indeterminate. [Consequence: Security bug — distributed cooldown bypass / outbound amplification.]

**RDS-N9**: Must not discard, `void`, or otherwise detach an asynchronous event-driven invalidation whose completion is required by **RDS-M17**; must not call an error-swallowing/best-effort invalidation surface and treat its resolved promise as confirmed success; and must not finalize a durable event after an unavailable/indeterminate invalidation. A TTL safety net does not make a same-flow stale read, premature success response, or premature event completion correct. [Consequence: Bug — nondeterministic post-write visibility or lost retry.]

**RDS-N10**: Must not strip external-authority environment/event provenance from a derived cache, treat a cache hit or cache namespace as proof of production compatibility, or load a pre-provenance cache version into a policy decision (**RDS-M18**). [Consequence: Security bug — runtime policy bypass.]

**RDS-N12**: Must not duplicate the invalidation obligation across the call sites of a write authority, and must not place the invalidation of a transactional write inside that transaction (**RDS-M20**). [Consequence: Bug — a sibling write path ships without invalidation, or a concurrent read repopulates the key from the pre-commit snapshot.]

**RDS-N13**: A versioned key is private to its owner module, and an operational-metric module must not throw from its degraded path. (a) Must not spell a versioned key (**RDS-M3**) in any file other than the single module that owns it. A second file holding the same key text is a second writer that bypasses the owner's contract — field schema, atomic increment form, TTL decision, degraded behavior (**SSG-M8**); the write succeeds and only the owner's guarantees are lost, so the defect is silent. Enforcement limit (stated, [KIT-INV-8](../authoring/kit-structural-invariants.md)(b)): the mechanical anchor is the full key, never the namespace prefix — one prefix legitimately hosts several keys with different owners, so a prefix predicate accuses a legitimate sibling owner on its first run. A key assembled from fragments at runtime is not decidable from one file's syntax tree and stays review-bound. (b) Must not `throw` from a `catch` block of a module whose contract is fire-and-forget operational measurement (a counter, a status record). Such a module runs alongside the main flow; throwing on store unavailability carries a measurement failure into that flow, so the observability layer takes down the path it observes. The degraded path logs and returns the degraded value (**RDS-D3**). [Consequence: Bug — a parallel writer silently violates the owner's key contract, or an infrastructure outage in a metric path escalates into a main-flow failure.] [Verify: single-file AST rule anchoring each owned full key to its owner file across plain string and template-part forms, plus `ThrowStatement` inside a `CatchClause` in the owner files; a helper called *from* the catch is not visible to it.]

**RDS-N11**: Must not implement an event-invalidated cache as `DEL` plus an unconditional later `SET`, split generation increment/expiry/delete into independently interleavable commands, let the generation expire within the maximum in-flight fill window, substitute process-local generation for the shared protocol, return a fetch whose generation compare-set was rejected, let a post-invalidation request join and trust a pre-invalidation singleflight, issue a multi-key Lua/transaction without one shared canonical Redis Cluster hash-tag, or interpolate user-controlled raw braces as that tag. During a numeric-to-opaque migration, must not map a missing/malformed token to a reusable fixed sentinel, activate future readers before every live mutator dual-invalidates, let Phase A change the legacy reader/writer contract, reuse the process's exact pre-reconnect observed epoch when no peer rotated it, count scope invalidation as successful without an exact post-operation global-epoch fence, accept a future scope token whose Redis-run epoch differs from the current registered global epoch, retry missing global-epoch bootstrap without a strict bound, or put that differently-slotted global epoch key into a scope-specific Lua/transaction (**RDS-M19**). [Consequence: Critical bug — stale cache resurrection, stale response, cross-instance divergence, rollout split-brain, reconnect/restart ABA, or production-only Redis Cluster failure.]

**RDS-N14**: Must not answer a tenant-scoped or permissioned read from a server-side response cache that runs before or instead of the handler — a stored ETag or fingerprint, a per-tenant generation, a cached response body, or any key from which the server returns `304 Not Modified` or a stored response without running the handler and its authorization. Conditional GET for such a read **MUST** come only from the framework's body-derived ETag, computed from the response body after the handler ran, so the handler and its authorization run on every request; client freshness comes from the client query cache — its stale time and post-write invalidation ([**MUT-M28**](../tanstack-query/mutations-optimistic-strategy.md)). A computed value cached inside the handler, after authorization, is a derived read cache and is governed by **RDS-M22**. Reason: a handler-skipping cache answers before authorization, so an actor whose membership or permission was revoked still receives `304` for data it may no longer read; its freshness depends on every write remembering to bump it, so each missed write path serves a stale `304`; and a fingerprint derived from a cheap query (for example the maximum update timestamp of one collection) misses changes in the collections a response joins or populates. [Consequence: Security bug — a revoked actor's read is confirmed without authorization; Bug — stale `304` after a write the cache did not see.] [Verify: no middleware or handler prelude returns `304` or a stored body for a tenant route before the route's handler and authorization ran; the framework's body-derived ETag is the only conditional-GET source.]
