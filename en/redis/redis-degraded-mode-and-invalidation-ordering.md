## **MUST** (normative) — **RDS-M14** to **RDS-M19**

**RDS-M19** variant — same-record non-repeating generation. In addition to the numeric and staged paired-key contracts below, a cache MAY hold its generation and optional derived value in one physical record when that record is one indivisible loss boundary and the generation is a fresh CSPRNG identity, never a reusable missing/expired/malformed sentinel. Capture **MUST** atomically validate the current registered Redis-run epoch and retain a valid descriptor or install a fresh identity with an empty value. Publication **MUST** atomically compare that exact identity and epoch and preserve the descriptor's original remaining expiry; capture of a valid descriptor, cache hit, verification and publication **MUST NOT** extend it. Invalidation **MUST** atomically replace the identity with a fresh one and empty the value. Expiry, eviction, deletion and incompatible replacement **MUST** retire every previously captured proof; no delayed flight may recreate its old identity. A response-producing reader **MUST** reprove the identity and current global epoch after a hit or accepted publication, discard a rejected candidate, and use bounded retry followed by a NEW uncached authority read or the established fail-loud result. That final proof is the read's stated linearization point, not a guarantee against an invalidation after it.


Variant boundaries. The numeric reusable-generation TTL margin greater than the maximum whole flight remains mandatory for that numeric variant; the same-record non-repeating descriptor instead makes record loss expire the proof itself. Every record operation still owes the existing current-global-epoch pre/post fence. A single-key script needs no paired-key co-location, but **MUST NOT** add the differently-slotted global epoch key to it. The whole compound operation, including epoch awaits, reply completion, retries and authority reads, shares one fixed completion deadline; a queue timeout alone does not prove a sent-reply bound, and a timed-out sent command is not rolled back. Late continuations **MUST** recheck the same remaining budget before any next phase. Declare the read/fallback linearization and retain **RDS-M17**'s distinction between confirmed invalidation and irreversible-write Tier B degradation. Old plain writers/readers outside the protocol remain outside its guarantee: same-key coexistence is not fleet adoption, does not protect arbitrary restoration of all relevant bytes under an unchanged run/epoch, and does not activate or waive the staged future-namespace Phase A/B gates below. Runtime identity/CAS/epoch APIs are the stronger mechanism; cross-file caller coverage, expiry preservation, driver completion and rollout remain review/evidence obligations, with no additional fence admitted under **ENA-A1**(c).

**RDS-M14**: Observable degraded mode for derived caches. When a Tier B (**RDS-D2**) cache is unavailable after startup, the call site **MUST** read from the durable authority, emit a bounded signal under the consuming project’s [logging policy](../logging-policy/logging-policy.md), and provide degraded health or metric evidence. It **MUST NOT** serve prohibited stale data or substitute process-local cross-instance state. Expected operational degradation and system defects follow the consuming project’s canonical error classification; the cache layer **MUST NOT** duplicate its category-to-severity or reporting-channel map. Degradation **MUST** be observable and alertable, never silent (**RDS-D3**, **RDS-M17**). [Consequence: Bug — silent cache degradation hides Redis failure, or expected outages pollute the error-reporting channel.]

**RDS-M15**: Durable messaging for work. Job queue, event propagation, and retry **MUST** use a durable mechanism — a durable queue, stream with consumer groups, or database-backed mechanism supported by the selected stack — not fire-and-forget pub/sub, because a consumer that is down must not lose work. Raw pub/sub is permitted only for best-effort fan-out that also has an independent safety net (for example cache invalidation that also carries a TTL per **RDS-M4**). [Consequence: Bug — lost jobs / events treated as delivered.]

**RDS-M16**: Shared amplification gate for untrusted-input-triggered outbound work. When an unauthenticated or otherwise untrusted cache key, identifier, or token field misses a shared metadata cache and could trigger outbound work, the operation **MUST** first acquire one cross-instance Redis claim using an atomic conditional write such as `SET NX` with an explicit TTL. The key derives only from trusted service/issuer/endpoint identity; attacker-controlled input **MUST NOT** create unbounded key cardinality. Only the claim winner may perform the bounded refresh; losers may re-read shared metadata but **MUST NOT** issue another outbound request. If Redis is unavailable or claim status cannot be established, the guarded path **MUST** fail closed without outbound work; already validated cached evidence may remain usable only under the consuming policy. This security-sensitive behavior takes precedence over any ordinary rate-limiter fail-open policy. Register the key and TTL where the project maintains such an authority, and emit bounded denial/degraded signals without logging untrusted tokens or attacker-controlled identifiers. [Consequence: Security bug — cross-instance outbound amplification, unbounded key growth, or fail-open behavior when coordination is unavailable.] [Verify: cover every untrusted input that can trigger outbound work; where static analysis is available, constrain the path to a trusted-key shared claim and fail-closed handling. Review whether the claim dominates every outbound call and identify any modules outside the check’s scope.]

**RDS-M17**: Event-driven cache invalidation is an ordered part of the mutation contract, not fire-and-forget cleanup. An asynchronous delete / generation bump **MUST** be awaited before (a) a same-flow read that promises fresh post-write state, (b) returning mutation success when the documented coherence strategy says the write is visible after success, or (c) marking a durable event/inbox item complete. The invalidation boundary **MUST** expose an awaitable/outcome-bearing operation and distinguish confirmed completion from Redis unavailability. A correctness-required writer **MUST** use the required/outcome-bearing surface: when invalidation is unconfirmed it **MUST** return/record a retryable failure, retain the durable event for retry, or explicitly bypass the affected cache and re-read the authority; it **MUST NOT** report success/completion while an old cache key can become observable again when Redis recovers. A separate documented Tier B best-effort helper may complete after loud degradation only for callers whose correctness does not depend on post-write cache visibility. Both failure contracts **MUST** consume one key-derivation/delete primitive; duplicating the key or promoting every caller to required semantics without classifying its user-visible availability contract is forbidden. When one mutation invalidates several independent-slot keys through a best-effort contract, the boundary **MUST** deduplicate non-empty keys and run one bounded, slot-safe orchestration: each Redis command targets one key (unless a shared canonical hash tag proves co-location), concurrency/cardinality and command time are capped, overflow sends no command, and partial command failure is reported as aggregate unavailability rather than silent success. Its degraded signal is one aggregate expected-failure event with bounded cardinality and **MUST NOT** expose raw keys, tenant identifiers, or provider error text. Classifying a caller: a cache refresh that runs AFTER the durable write has already committed **MUST NOT** be promoted to the required surface. The required surface exists to withhold success while the write's visibility is still in doubt; once the write is committed and irreversible, the only thing still in doubt is a stale read, and raising there converts a succeeded operation into a reported failure. That is not fail-loud, it is false information, and it is worse than a bounded stale-read window in this case: a caller may retry a mutation that already committed, causing a duplicate attempt or an unrecoverable response even though the first operation succeeded. Where the stale window is bounded by a TTL and the read model repairs itself when the key expires, degraded mode plus self-healing is the correct contract, not a concession; the required surface belongs to the writers whose caller can still act on the failure (retry the whole mutation, retain a durable event, bypass the cache and re-read). Record the classification and its bound where the authority is defined, so the next reader does not mistake the best-effort call for an oversight. [Consequence: Bug — read-after-write or a completed durable event can expose the pre-mutation snapshot even though the mutation/event reported success.] [Verify: typed required/outcome surface + static promise-use enforcement appropriate to the consuming language and toolchain; call-order review for write → confirmed invalidation → fresh read/response/event completion; forced Redis-failure proof that success/completion is withheld.]

**RDS-M18**: A derived cache of external-provider evidence **MUST** preserve every security-relevant provenance field needed by current policy, including environment (such as test versus production) and validated event-kind evidence when the external authority exposes them. A cache hit proves only that the snapshot was previously derived; it **MUST NOT** bypass a current-runtime environment or known-event gate at the consumer. Cache schema/version changes **MUST** separate older snapshots that lack newly required provenance so absence cannot be interpreted as production or known-safe. Preservation covers the value's runtime TYPE, not only its fields. A serialization boundary silently downgrades types the authority read returns — a timestamp becomes a string, a decimal a number — and a consumer that validates the type then rejects the snapshot as unusable. Where that consumer is a security-sensitive consumer whose documented unresolvable-input branch permits work to continue, a cache-only defect is converted into an open gate and the cache layer reports nothing. A derived cache **MUST** therefore restore types through the same schema authority the authority read uses, never a hand-written second validator — that becomes a parallel shape authority which drifts silently as the schema grows ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)) — and **MUST** verify the restoration succeeded before returning the snapshot, treating any failure as a miss and re-reading the authority. [Consequence: Security/SSoT bug — cached test-environment or provenance-free evidence is treated as production-authoritative, or a type-downgraded snapshot opens the gate that consumes it.] [Verify: Cache DTO/schema + versioned key review + consumer runtime gate; round-trip a serialized snapshot and assert the consumer's own type predicate on the revived value.]

**RDS-M19**: Invalidation **MUST** win over an already in-flight cache fill and over the response produced by that fill. For a derived cache where an authority-changing event can race a fetch that began before the event, delete-only invalidation is insufficient: the stale fetch can complete afterward and repopulate the deleted key or be returned directly even when its cache write was rejected. The shared Redis protocol **MUST** take a generation/version snapshot before the authority fetch, write the result only through one atomic compare-generation-and-`SETEX` operation, and invalidate through one atomic generation-increment + generation-TTL-refresh + cache-delete operation. A compare-generation rejection invalidates the fetched snapshot itself: a response-producing reader **MUST** perform a bounded current-generation retry and, after coordination uncertainty/exhaustion, read the authority again without caching (or fail loud when the authority cannot produce a proven current result); it **MUST NOT** return the rejected snapshot. Any process-local singleflight is only a latency optimization and **MUST** be keyed by the shared generation (or revalidate the generation after join), so a post-invalidation caller cannot trust a pre-invalidation flight. The generation key TTL **MUST** exceed the documented maximum fetch + retry + parse + cache-write flight by a deliberate safety margin, and both keys **MUST** be co-located when Redis Cluster/Lua requires one hash slot. Co-location **MUST** use one canonical hash-tag derivation shared by every key in the atomic operation; user-controlled raw `{...}` text **MUST NOT** select the slot, the exact derivation belongs in the key registry, and the multi-key boundary **MUST** reject missing/different tags before issuing the Redis command. On Redis uncertainty a Tier B conditional write **MUST** skip caching and degrade observably; it **MUST NOT** install an in-process generation or unconditionally write the possibly stale result. Generation acceptance may govern whether that cache snapshot is stored or returned, but it **MUST NOT** authorize a durable/irreversible database side effect: TTL expiry, eviction, restart or outage can reset/erase Redis state and create ABA. A durable side effect that must remain ordered against authority changes uses the database transaction fence in **RDS-M21** / TX-M-12. This cache protocol also does not replace the external authority’s monotonic durable writer required by SSoT **SSG-M12** for separately accepted out-of-order events. [Consequence: Critical coherence bug — an invalidated pre-event snapshot is resurrected/returned, or ephemeral coordination is promoted into durable correctness authority.] [Verify: Atomic script/transaction review + key registry TTL/hash-tag proof + runtime same-tag rejection + race review sequence `snapshot(n) → fetch starts → invalidate(n+1)+delete → stale compare-set and response rejected → authority re-read`; separately verify durable effects under **RDS-M21**.]

**RDS-M19** (staged ABA-safe protocol migration): Where a system migrates a numeric generation protocol that maps a missing key to a reusable fixed value to a non-repeating opaque-token protocol, the bridge is itself part of the invalidation contract and **MUST** be staged across compatible releases. Phase A **MUST** leave legacy reader/writer keys, signatures and result semantics unchanged; every invalidator **MUST** update the legacy generation/delete pair and install a fresh CSPRNG future generation token plus delete the future entries key in one single-scope atomic boundary. The future generation value **MUST** bind the current Redis-run epoch, where one registered no-TTL global key stores an exact `{redisRunId, epochToken}` value: `redisRunId` comes from a validated server fact and `epochToken` is CSPRNG. A first process boot or rolling deploy MAY reuse an existing exact epoch for the same Redis run. After a process observed an epoch and then received reconnect/end, the next ready initialization **MUST** atomically rotate exactly when the global value still equals that prior observation; if another replica already rotated it, the process reuses the newer exact same-run epoch. Reconnect/end removes local readiness and retains the prior observation only as rotation intent, never as current authority. Each dual invalidation **MUST** read the current global epoch before its tenant Lua and re-read it afterward; only an exact unchanged `redisRunId+epochToken` proves success. A process-local promise may gate ready ordering but is never the epoch authority. The global key **MUST NOT** be added to a multi-key Lua/transaction across distinct cluster slots when it does not share that tenant's Cluster slot; the tenant token carries the epoch binding instead, so a later reader can reject a token from a rolled-back/replaced Redis run. A missing global key after readiness **MUST** receive one bounded, revision-safe fresh-epoch bootstrap because its disappearance makes old epoch-bound generations unreachable; malformed state or repeated missing/uncertain reads remain fail-safe unavailable. On bridge unavailability, legacy invalidation is still attempted so the shipped protocol does not regress, a correctness-required invalidator reports unavailability under its existing contract, and a best-effort invalidator emits observable degradation. Phase B readers/writers **MUST** remain inactive until every live mutator runs Phase A; activation then **MUST** treat missing, malformed or current-global-epoch-mismatched future generation as untrusted and atomically install a fresh token while deleting the paired future entries before any cache value can be accepted. Phase A documentation **MUST** say that future readers/writers are inactive; creating future keys is not evidence that Phase B is active. [Consequence: Critical coherence/rollout bug — an old mutator misses the future namespace, a reconnect window is not fenced, the epoch rotates between pre-read and tenant invalidation, a Redis restart restores an acceptable old token, or a mixed fleet activates readers before all writers dual-invalidate.] [Verify: Call-graph inventory of every invalidator; unchanged legacy read/write API and key proof; reconnect exact-prior CAS rotation; bounded missing-key bootstrap; pre-Lua/post-Lua exact epoch fence; global-key registry no-TTL reason; shared key-slot proof; release gate proving no pre-Phase-A mutator remains before Phase B activation.]
