## **MUST** (normative) — **RDS-M1** to **RDS-M13**

**RDS-M1**: The Redis client **MUST** be created exactly once per process (a singleton module) and reused; per-request or per-call client creation is forbidden. The client **MUST** register an error handler that logs per [logging policy](../logging-policy/logging-policy.md) and **MUST** be initialized during startup so readiness is known before traffic is served. That initialization **MUST** happen at a declared point in the boot sequence, after the process's signal and error handlers are installed, and **MUST NOT** be triggered by a module-level `await` in a module the entrypoint imports: an imported module is evaluated before the importing module's body, so a connection opened there precedes every handler the boot sequence installs — if it blocks, the process can neither log nor terminate gracefully, and the entrypoint's own ordering comments become false. Import-time module evaluation **MUST NOT** depend on an external service being reachable. Where a readiness wait before serving traffic is what keeps a security control present (for example a shared rate-limit store), the fix for a hanging boot is to bound that wait (**RDS-M2**(c)), never to delete it: removing it opens a window on every boot in which the control is absent, which is a regression even when the control's own outage behavior is a compliant fail-open (**RDS-M8**). Stated limit: import-time connection is single-file decidable but unfenced until a second site recurs (**ENA-A1**(a)); it is review-held. [Consequence: Bug — connection storms / unhandled errors / a boot that cannot log or shut down.]

**RDS-M2**: Startup configuration fail-fast; runtime infrastructure resilience. (a) If required connection configuration is missing or invalid, the process **MUST** fail startup and **MUST NOT** serve traffic through a path that assumes Redis is available; surface the configuration defect through the deployment's normal health and diagnostics. (b) If configuration is valid but Redis is temporarily unreachable, the service **MUST** follow its declared outage policy, report degraded health, and avoid taking down unrelated database-backed paths. No code path may silently substitute process-local state (**RDS-N1**); each use degrades per **RDS-D3** and its applicable rule. (c) The startup bound **MUST** be explicit and owned by the caller. A client whose reconnect policy retries internally may not settle its connect promise while retries continue, so awaiting it can block indefinitely and no `try`/`catch` will ever see it. A per-attempt socket/connect timeout does not supply this bound: it may end one attempt and feed the result back into the retry loop, so its presence is not evidence that startup is bounded. The caller **MUST** bound startup using the project-selected deadline (**RDS-T-CONNECT-TIMEOUT-MS**) and on expiry follow the configured outage branch (b), keeping any background retry running with its rejection consumed. Do not turn an infrastructure outage into an unbounded boot hang, which a platform may report as a failed deployment with no logs and no restarts. Since startup is shared, a caller arriving during initialization **MUST NOT** create a second client (**RDS-M1**): publish the singleton or one shared in-flight startup promise before awaiting it. That promise **MUST** resolve to the client object it created, never re-read a mutable slot after the await: a controlled close inside the window clears the slot, and every consumer would then dereference null instead of receiving the closed client whose commands reject through the degraded contract. Stated limit: whether an awaited connect is bounded depends on the client library's internal retry policy, which no syntax tree shows; review holds (c). [Consequence: Critical bug — configuration errors are hidden, or an infrastructure outage escalates into an avoidable service outage or failed deploy.]

**RDS-M3**: Every key **MUST** use a documented service namespace and stable semantic components (for example `<service>:<domain>:<version>:<purpose>:<scope>`). The key list is derived from code by searching the namespace prefix; where a system has enough keys or multiple producers, the project's key registry (or equivalent authority) keeps one row per key family (TTL, owner, authority / derived class, invalidation), never a hand-kept per-key inventory. A cached response's key **MUST** discriminate every input that changes that response — including principal and authorization scope where relevant — and any tenant/scope segment **MUST** come from the request's single scope-resolution authority. Two failures follow from breaking this and both are silent. (a) Where a response is narrowed by the caller's role or scope, a key built from the resource path alone can let different callers share an entry, so even a conditional request may reveal information about a body the asker was not entitled to receive — the fact travels even when the payload does not. (b) A second, ad-hoc normalization of the scope input can produce a different key from the invalidation path: the entry is written under one key and expired under another, so the cache is stale for its whole life while every read still looks correct. Because those segments exist only after the identity gate, a response-producing cache layer **MUST** be mounted behind that gate; in front of it the layer cannot see a proven actor, its own "no actor → skip" branch runs on every request, and the layer is dead while every reader of the mount believes a cache exists. That placement is decidable from one file's syntax tree; enforce it with the project's documented mechanism. Where the response varies by caller input but the authority record behind it does not, cache BELOW the shaping layer rather than the response. Keying a shaped response forces the key to enumerate every shaping input — client version, principal, locale — and the day one more input is added the key silently under-discriminates and one caller's answer serves another's request. Caching the raw authority record and re-shaping per request removes that failure class instead of guarding it: no caller-controlled value reaches the key at all, and that property is readable off the key builder in one file. One authority record gets ONE derived entry, with per-consumer PROJECTIONS over it. When a second consumer needs a wider field set, widen the single entry and let the narrower consumer read a projection of it; a second entry for the same record carries its own generation, TTL and invalidation, and when the two disagree nothing records which is right (**SSG-M8**). Widening an entry's payload, or changing the rule that derives its value, **MUST** bump the envelope's semantic version — so an old-format entry is a miss, never a misread — and **MUST NOT** rename the key: a renamed key splits old and new replicas onto separate generation fences for the length of a rolling deploy, and one replica's invalidation then stops fencing the other's writes. A cached field that GATES access (kill switch, maintenance flag, entitlement boolean) **MUST** have its type proven on read and **MUST NOT** fall back to a schema default — a defaulted `false` from a corrupt entry reads as *not blocked* and opens what the authority closed. A multi-key script **MUST** receive every key it touches through `KEYS`, all under one hash tag; a key whose name is held in another key's value (a pointer) **MUST** be read before the script, passed in, and the script **MUST** compare the pointer with the value it was read with and write nothing when it moved (the caller re-reads, bounded), because a key built inside the script is invisible to cluster slot routing and to the shared-tag check. Keys one operation uses together (a script, a `MULTI`, a multi-key read) **MUST** carry the same hash tag, produced by the project's one tag producer from the owner whose keys they are (a tenant, a sender, one global window); a tag written by hand is a second producer whose format the shared-tag check cannot recognise. A tag **MUST NOT** be shared by keys no operation uses together: a constant tag on a growing family pins all of it to one slot and buys nothing. Stated limit: the version segment, registry completeness and whether a field shapes the response are review-held unless the adopting project has a recurring violation that admits a check ([**ENA-A1**](../enforcement-architecture/enforcement-admission.md)(a)); a key composed from variables is invisible to a prefix search, which is why **RDS-N13**(a) requires literal key text; a payload or derivation change without a version bump is invisible to any key-text check. A registry row whose producer the search no longer finds is removed only after [**DCD-M6**](../dead-code/dead-code-rules.md) verification. [Consequence: Bug — collisions, unowned keys, or a permanently stale cache no read reveals; Critical security bug — cross-scope conditional-response disclosure.]

**RDS-M4**: Every key **MUST** be written with an explicit TTL (`EX` / `PX` / `EXPIRE`), using the call-site value or **RDS-T-DEFAULT-CACHE-TTL-SEC** when none is documented. Long-lived caches (for example feature flags or tenant configuration) MAY use a long TTL, or a no-TTL durable entry only when listed in the key registry with a stated reason, an event-driven refresh, and an eviction-safety note (**RDS-M13**). The write and its TTL **MUST** be issued at ONE atomic boundary. A write followed by a *separate* `EXPIRE` is two commands: if the process dies between them the key survives with no TTL, and nothing in the system is obliged to notice. Use the single-command form (`SET … EX`), a `MULTI`, or a script — the atomicity is the guarantee, not the presence of an `EXPIRE` call somewhere in the function. Conditioning that separate `EXPIRE` on "first write only" (`if (count === 1) expire(...)`) does not narrow the window — it makes it permanent, because the one call that would ever have set the TTL is exactly the one that failed; every later write skips the branch and the key is now unbounded for its whole life. An unconditional `EXPIRE` after every write is therefore strictly safer than a first-write-only one (a later observation repairs the omission) while still not being atomic, so it is a mitigation, never the compliant form. [Consequence: Bug — unbounded growth / stale reads; the conditional variant is an unbounded key that no later write can repair.]

**RDS-M5**: SSoT authority. The durable database write path is the authority for domain data; Redis holds a derived cache of it. For data the database owns, Redis **MUST NOT** be the source of truth; on any disagreement the database value wins and the stale cache entry **MUST** be corrected or deleted. Where Redis itself is the authority for a coordination datum (rate-limit counter, lock token, idempotency lease), that datum **MUST** have exactly one Redis authority and no parallel store. A decision on a Redis-authority datum (a limit, budget, cap, quota or unique-count window) **MUST** be one server-side atomic step that reads, decides and records together — a script over keys sharing one hash tag, or one conditional command — and **MUST NOT** read the datum in one command and record the decision in a later one, for example after the guarded side effect succeeds: Redis serializes commands, not the application's read-decide-write, so concurrent instances all pass the same limit. Where the counted fact arrives later (a delivery report), the admission reserves an in-flight slot in the same step, a certain non-send releases it, and the report moves it into the count in one transaction; a slot that may never be reported carries an expiry, and the authority states the bound that expiry leaves on the cap. Stated limit: the decision spans functions and modules, so no check is admitted ([**ENA-GV3**](../enforcement-architecture/enforcement-admission.md)); review holds it. This rule implements [SSOT principles](../ssot/ssot-principles-and-precedence.md). [Consequence: Critical bug — two sources of truth, or a cap that concurrency multiplies.]

**RDS-M6**: Cache invalidation **MUST** use exactly one documented strategy per key class: (a) TTL-only expiry, or (b) event-driven deletion / generation bump tied to a named write or webhook event that reaches every instance (direct delete plus, for cross-instance correctness, a pub/sub invalidation message per **RDS-M10**). Mixing ad-hoc deletes with TTL without a documented coherence rule is forbidden. [Consequence: Bug — stale data after write.]

**RDS-M7**: A distributed lock **MUST** use a named algorithm and a named library version documented at the call site (for example `SET key token NX PX <leaseMs>` with a unique acquisition-specific owner token), **MUST** carry a lease TTL (**RDS-T-LEASE-TTL**), and **MUST** release only when the stored token matches the owner (compare-and-delete), never an unconditional `DEL`. A long-running owner **MUST** renew by exact key + owner-token comparison before expiry and expose a sticky lease-lost fence to the task; the task **MUST** fail closed and consume that fence immediately before every authoritative or external side effect and once more before reporting success. Consuming the fence **MAY** be a local comparison against the latest expiry a store write confirmed for this owner token, when at least one renewal interval of it remains (acquisition requires an expired lease, so no other owner can hold it before then); only below that margin does the fence write the store — a store write per item turns the lock row into the job's hottest write path, and an in-transaction fence stays a store write. A process-global or job-name token is not an owner identity, and an expired worker **MUST NOT** continue effects after another worker acquires the key. Because a lease cannot undo an already-started external effect, that effect also needs its own durable natural-key idempotency. Stated limit: the owner-token and fence half spans functions and has one historical defect, so it is declined as a check ([**ENA-GV3**](../enforcement-architecture/enforcement-admission.md)); the project's single lease authority plus review hold it, and a second independent defect re-opens the admission test. [Consequence: Critical bug — lock stolen / stale worker side effect / false success.]

**RDS-M8**: A multi-instance rate limiter **MUST** use one shared store; process-local state is insufficient. Redis is appropriate where selected by the consuming architecture. On store failure, follow the documented risk policy: fail open with an observable alert only where the limited action may safely proceed; a control whose purpose is security-critical **MUST** fail closed or use another explicitly approved shared authority. Never silently switch to per-instance state. Every store call **MUST** carry an owned completion deadline raced against the reply, sized far above the store's measured round trip and far below the request budget; a client command timeout that stops counting once the command is written **MUST NOT** stand in for it, because a store that accepted the command and does not answer then holds every request open behind every limiter it crosses. After repeated availability failures the limiter **MUST** stop calling the store for a cool-down and admit one trial call before resuming (an open circuit follows the fail-open or fail-closed policy above, while a guess budget or spend ceiling keeps refusing, [**SEC-M-RL-3**](../security/security-rate-limiting.md)); the circuit's state lives in the instance, never in the store it guards (as [**RPDF-M27**](../report-pdf/report-pdf-charts-layout-and-limits.md)(d)), and an episode reports once — a counted `warn` when it opens, one `error` when it outlives its trial while the client still reports ready — never once per request. A store setup step whose result the store caches (a script load) **MUST NOT** keep a failed result: it is retried on use, or one outage at boot disables the limiter for the life of the process. Review-held unless the adopting project has a recurring violation that admits a check ([**ENA-A1**](../enforcement-architecture/enforcement-admission.md)(a)). [Consequence: Bug — limits not enforced across instances, a failure mode that contradicts the security policy, or every request stalled by a connected store that does not answer.]

**RDS-M9**: Idempotency duplicate-suppression durability **MUST** rest on the database authority (a unique-constraint claim per [idempotency **IDEMP-M5**(b)](../idempotency/key-scope-and-replay-contract.md)), so it survives a Redis outage and a multi-instance deployment. Redis MAY be used only as a non-authoritative accelerator (lease / replay cache), never as the sole guarantee. On Redis unavailability the operation **MUST** continue via the database claim — not double-execute, not fail the user. [Consequence: Critical bug — double execution on Redis outage.]

**RDS-M10**: Pub/sub, when used, **MUST** document channel names under the **RDS-M3** namespace and **MUST NOT** assume message durability (a subscriber that is down misses messages); when delivery must survive downtime, use a durable mechanism (Redis Streams with consumer groups, or the database) and document it. [Consequence: Bug — lost fan-out treated as reliable.]

**RDS-M11**: Network and secrets. In production, use a private network for the Redis connection where the hosting environment provides one; avoid public proxy paths for application traffic where a private endpoint is available. If a public endpoint is unavoidable, require TLS. Authentication credentials **MUST** come from the hosting environment's approved secret mechanism and **MUST NOT** be committed to source control. Follow the consuming project's [security](../security/README.md) standard for secret handling. [Consequence: Bug — unnecessary exposure or leaked secret.]

**RDS-M12**: Observability. Connection establishment/loss and command errors **MUST** be logged per [logging policy](../logging-policy/logging-policy.md) with action / rootCause / solution; caches SHOULD expose hit/miss and latency counters. ONE lifecycle classifier owns `error` / `ready` / `end` and monotonic shutdown intent set before close. Transient transport error → `warn` + counter; other → `error`; a not-ready episode emits one `error` (first non-transient or **RDS-T-SUSTAINED-DISCONNECT-ALERT-MS**), repeats `warn` + counter; `ready` resets it. `end` after shutdown intent → `info` lifecycle; otherwise → `warn` degradation. Every other consequence of that close — the in-flight startup `connect()` it rejects, the transport error it raises, a store command refused on the closed client — **MUST** also be classified against the same intent (`info` lifecycle), because a shutdown inside the startup window is not an outage and reporting it as one sends a deploy's routine stop to crash reporting. A second classifier/intent flag is forbidden; consumers read the classifier's intent. Stated limit: use the enforcement mechanism the adopting project documents for listener routing and record its actual scope — a reference to a check is not evidence that it exists or covers the full rule; the episode timing across events and modules is review-held. A credential-bearing connection, AUTH, construction, URL-parse or startup/close failure follows [**SEC-M-LOG-2**](../security/security-logging-core.md). [Consequence: Ops bug — false incident or silent degradation.]

**RDS-M13**: Eviction and persistence. The expected `maxmemory-policy` **MUST** be documented for the deployment; any datum that cannot tolerate eviction (a lock, an idempotency lease, an authoritative coordination value) **MUST** either be backed by the database authority or use a deployment whose policy guarantees its survival for the lease window. A lock that protects work spanning more than one lease period additionally follows **RDS-M7**'s exact-owner renewal and side-effect fencing; merely extending TTL without proving ownership does not make the worker current. Derived caches **MUST** tolerate eviction (a miss reloads from the authority). A leased batch job does not swallow lease loss — liveness is consumed outside the item `try` or re-thrown from its `catch` — and a partial item failure never yields a success heartbeat. Stated limit: neither half is mechanically fenced unless the adopting project documents a check and its scope ([**ENA-A1**](../enforcement-architecture/enforcement-admission.md)), and the heartbeat half is not decidable from syntax (a durable retry / dead-letter write in `catch` looks like swallowing); review holds both. [Consequence: Bug — lost lock / lease under memory pressure, or a fake success heartbeat.]
