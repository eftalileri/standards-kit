# Client observability -- silent failure paths (a caught failure's handling)

```kit-cover
type: normative
part-of: README.md
binds: the obligation that a client failure the code CATCHES reaches the classification authority instead of staying invisible - log-only handling, a rewrap that destroys the carrier, and a second record written beside the report
open-when: shape:frontend-heavy, shape:bug-fix, signal:client-failure-path, signal:silent-failure, signal:global-error-net
skip-when: signal:backend-only, signal:no-client-failure-path
owns: COB-RN-M11
```

Scope: Decide whether a caught client failure reaches an observable channel. A local log alone is insufficient unless the shipped client has a usable transport, retention, and retrieval path. A containment scope may rethrow to its owning boundary or report through the single authority; it must preserve the original carrier, specific diagnosis, and single-record ownership.

Document type: Normative part -- **COB-RN-M11**.

Related rule placement: Failures absorbed into defaults and framework-level nets are covered in [absorbed-defaults-and-global-nets.md](absorbed-defaults-and-global-nets.md). This document covers failures a call site catches; both rule bands share routing signals and the single classification authority.

References: [README.md](README.md); [classification-authority-and-outbound-links.md](classification-authority-and-outbound-links.md) (**COB-RN-M6**, the authority this rule routes through); [absorbed-defaults-and-global-nets.md](absorbed-defaults-and-global-nets.md) (**COB-RN-M12**, **COB-RN-M13** -- the sibling band, cited by ID below); [client-observability-rn-appendix.md](client-observability-rn-appendix.md) (non-normative origins).

## **MUST**

| ID | Rule |
|----|------|
| **COB-RN-M11** | **In a shipped client application, a local log is not observability unless it has a usable transport, retention, and retrieval path.** A level filter determines whether a line is produced, not whether it is delivered. Therefore a failure path’s sole handling MUST NOT be a local log: rethrow it to an owning boundary or report it through the single classification authority (**COB-RN-M6**). When a lower request adapter has no recovery or translation responsibility and a transport/framework boundary owns the failure, do not add an inner `catch -> local log -> rethrow`; let the original rejection reach its owner unchanged. Unchanged includes original `Error` identity and structural transport/envelope fields. Do not replace a caught failure with `new Error(caught.message)` or another display string, which discards the carrier’s code, category, retryability, trace identity, and transport kind. For binary responses, preserve successful payloads and decode non-success payloads at the shared response-error boundary before classification; avoid call-site status bypasses, parsers, or rewraps. An unreadable or non-JSON error remains a structural failure; do not invent a message. A local log may accompany a report when useful, but never substitute for one. A helper’s name does not prove it has a delivery channel. Server logging may have transports; verify client behavior independently. Because a containment scope whose only statement is a log call is decidable from one file’s AST, enforce this rule mechanically where feasible rather than by review alone. |
**COB-RN-M11** mixed-caller ownership clarification. When one asynchronous operation serves both awaited readiness callers and a detached UI facade, the lower operation must stay throwing and preserve the original rejection identity; it must not log-and-absorb or report locally. The awaited caller lets that rejection reach its existing error/retry/readiness boundary. The detached facade attaches a terminal catch and owns the same rejection through the canonical no-throw classification wrapper. Both facades must delegate to one success/write operation: duplicating the state commit creates a second writer, while committing before the asynchronous dependency succeeds publishes false success and can leave derived runtime state out of sync with the persisted authority.

**COB-RN-M11** layered-owner deduplication clarification. When a terminal owner absorbs failures from several lower operations and some lower boundaries may already have reported the original throwable while other branches remain unowned, the terminal owner must use the classification authority's observed-aware no-throw entry. It passes the original throwable unchanged and only code-owned structural metadata; it does not attach raw payloads or free error text. A lower report's identity mark suppresses the duplicate, while an unowned failure still reaches the channel. The terminal owner's existing return, timing, throw, readiness, and user-error state remain unchanged.

**COB-RN-M11** layered terminal file/share owner. A terminal UI facade receiving both already-owned API failures and unowned native filesystem/share failures passes the original throwable unchanged to the classification authority's observed-aware no-throw entry, with code-owned structural action metadata. The upstream identity mark suppresses its duplicate; a genuine local failure still reaches the channel once. Inner log-and-rewrap paths are removed rather than treated as observability. Code-authored user warnings carry the existing translation-key carrier and are resolved at display time; raw driver text stays out of user copy. A picker result that structurally declares `granted:false` is a known declined result owned at that branch, not a fabricated abort name or category. Granted permission with absent required destination is not that result and remains a fail-loud invalid outcome. A terminal feedback sink failure cannot turn an already-completed native write into a failed save. Obsolete command feedback is withheld through the existing typed scope assertion. Stated limit: branch provenance, original-identity preservation and layered owner reachability are cross-file review obligations; no new classifier, sink or fence is added.

**COB-RN-M11** centralized-display clarification. `Error.message` can contain transport diagnostics, upstream text, or application-authored user-facing copy. When a display authority stops exposing raw messages, first classify every thrown message as transport-produced (omit from user display) or application-produced (convert to a translation key or registered code and resolve at render time). Land both sides together: removing the raw-message branch alone can erase valid application guidance, while a generic retry string can misdirect users when retry cannot help. This cross-file relationship is not decidable from one file’s AST; review the throw sites together with the display authority.

**COB-RN-M11** enforcement-scope guidance (state the predicate, limits, and status). Define the containment scope precisely (for example, a `catch` or `.catch(fn)` body whose caught value reaches only a logger, with no rethrow, rejection, classification-authority call, or never-returning raiser). Treat framework error callbacks according to their actual rejection semantics; they are not automatically containment scopes. A handoff to another call proves ownership only when the callee can be inspected and shown to rethrow or report. Resolve local aliases of caught values. Keep client containment rules distinct from server-specific typed-raise rules, and state which arms are mechanically enforced versus review-only. Do not infer coverage from a rule inventory alone; validate its predicate against the governed source shapes. A reference to a check is not evidence that it exists or covers the full rule; record its actual scope and limits.

**COB-RN-M11** second-record clarification (a report and a log are not defence in depth). Once a failure has been handed to the single classification authority (**COB-RN-M6**), writing a **second, direct logger record for the same failure in the same containment scope** is not extra safety — it is a defect with two independent harms. **(a) One incident becomes two records.** The authority already decides category → severity → channel and emits exactly one record on the channel that decision selects; an inline call beside it emits another, so any count keyed on that failure is wrong and a reader cannot tell one occurrence from two. **(b) It inverts the severity decision the authority just made.** The inline call names its own level, so a failure the authority classified as expected (`warn`) is simultaneously recorded at `error` — the routing that **COB-RN-M6** exists to own is bypassed by the line standing next to it. The shape is persuasive precisely because it looks careful, and it is usually introduced by an author who does not realise the authority already logs. **The remedy is deletion, not de-duplication:** remove the inline record and, before deleting it, confirm every structural field it carried already appears in the report — if one does not, move it into the report first (the same meta-preservation obligation [logging policy](../logging-policy/logger-surface-and-levels.md) M15 states for its own class). A **client** inline record has a third cost the server tier does not: it has no transport at all (**COB-RN-M11**), so it is not even a worse copy of the report — it is nothing, while still carrying whatever fields were put in it.

That last point is why this clarification also governs **what those fields may be**. An inline record is written outside the authority and therefore outside whatever projection the authority applies, so a third party's identifier placed in it travels on a surface the report deliberately excluded. Where a containment scope's own comment already states that an identifier is withheld from the report, an inline call beside it carrying that identifier is a **self-contradiction in one scope** and is read as a defect, not as a permissive local exception — the narrower of the two decisions in the same scope governs, and widening it is a change to the shared masking criterion (**COB-RN-M8**), never a local override.

**COB-RN-M11** rewrap-arm clarification — the text's SOURCE does not soften the rewrap, and the guard around it is usually dead. M11's rewrap sentence is commonly read as covering only `new Error(caught.message)`. It covers equally the shape that reads the sentence out of the **transport response body** — `new Error(err.response.data.message)`, including through a local binding (`const body = err.response.data; … body.message`). The two are one defect: a new `Error` carries none of the canonical carrier's structural fields, so the code the consumer needs in order to resolve the right text is destroyed by the very line that tried to supply text. It is also a **second text authority** beside the code→translation authority, and it stays a defect while every present consumer re-resolves the text — the next consumer to print `message` puts the server's internal diagnostic sentence on screen. **The remedy is never a better message; it is to let the rejection through untouched.** Where a call site must attach its own contract (a conflict list, a retry hint), it **MUST** mark those fields **on the caught carrier**, never on a replacement object.

Two general lessons apply. (a) Re-measure any guard around a rewrap against where the carrier is actually built. A guard behind a transport-library type predicate, below a boundary that normalizes transport errors into a plain carrier, can never be true and the branch never runs. A branch is not evidence of behaviour; the constructor of the object it inspects is. The same class applies to a decision keyed on message text such as `text.includes('<CODE>')` ([logging policy](../logging-policy/logging-policy.md) **M25** (c)): a predicate written against an assumed carrier shape is dead from the day the shape changed. (b) A rewrap that preserves one field is still a rewrap. A site that copied the code onto its new object still dropped trace identity, category and retryability. Preservation is judged field by field against the carrier, not by the presence of the field the author happened to remember. Enforcement: the rewrap arm is single-file decidable (the argument of `new Error(...)` resolves, through branches and local bindings, to a `.message` read off a response/body chain) and should be locked by a lint rule where the project can; the containment and second-record arms remain review obligations unless the project records an actual check for them.

Stated enforcement guidance ([**KIT-INV-8**](../authoring/kit-structural-invariants.md)) — second-record class. A same-scope classification-authority call followed by a direct logger call is mechanically decidable and is a good lint candidate. If the predicate finds existing findings, do not ship a warning floor as if it were enforcement (FP-M18). Review each site to determine whether the record duplicates the report or represents a separate failure; declare residual scope and close it with a blocking ratchet. Until then, this is a stated review obligation, not a locked check, and a coverage inventory must not imply otherwise.

**COB-RN-M11** scoped feedback application. A raw local ERROR record beside a lower classified report is a second severity decision even when the logger is console-only; it need not be a second crash event to violate canonical WARN routing. Remove only the redundant reconstruction/reporting path after proving the lower owner and retained context. Localized feedback and current-scope UI containment stay intact. A legitimate independent developer diagnostic is not deleted merely as style; the proof must identify duplicated incident ownership or conflicting severity. Original carriers and their causes reach the owning reporter unchanged. The shared observed-aware no-throw authority preserves already-reported lower failures and reports unowned failures once; complete cross-file ownership remains review-held, not a new fence.

**COB-RN-M11** degraded-experience application. A client condition that hurts the user without being a defect -- a cold start past its slow threshold, the app going to the background while holding paused (offline, unpersisted) writes -- MUST NOT live only in a breadcrumb or a local log: it is reported through the classification authority as a typed carrier whose category is expected (**COB-RN-M6**), so it takes the warning branch and reaches the server's expected-failure window as one closed occurrence. The background check reads the exact OS `background` transition as a documented lifecycle-set member ([ALS-RN-D1](../app-lifecycle-rn/app-lifecycle-rn.md)), never the focus signal, which collapses `inactive` and `background` and fires only on change, so on iOS it never reaches `background`; it reports each paused write once, grouped per write family per transition; the family travels in the warning record and breadcrumb, not as a wire reason, because a wire reason needs a server allow-list and a second copy of the family catalog would drift. Reason: neither condition produces an event on its own, so their frequency is invisible until a user complains about lost work or a slow app.

**COB-RN-M11** user-tap application. A tap handler on a prompt, consent or permission surface MUST NOT return without effect for a reason the screen does not show: it acts, or the refusal is already drawn (a disabled or loading control, a hidden control), or the refusal is reported through the classification authority as a defect with a closed reason, once per reason per process. Lifetime, selection and scope checks, a missing value the visible surface was drawn from, and a tap's deferred continuation (an OS prompt queued until a window closes) losing its lifetime are all reported refusals; a second tap of the same control while the first tap's own work runs is not a refusal. A value the handler needs that has an authority with a defined fallback (the display language) is read from that authority at tap time instead of gating the tap. Reason: a silently dropped tap looks exactly like a frozen app, the user's only recovery is to restart it, and nothing reaches the channel. Review-held: a typed tap entry that reports its own refusal is the mechanism; whether a remaining refusal is already drawn depends on the rendering component, not on the handler's file, so a single-file predicate would misfire.

**COB-RN-M11** render-deadline application. A deadline that reports a missing render signal (an animation's end callback, a list's first paint or layout, a window's show event) MUST be started through the one render-deadline authority and MUST NOT be a wall-clock timer with a visibility check: in the browser the budget counts only time in which the page draws frames, on the phone it counts wall time and a budget that passes outside the foreground restarts when the app returns to it. A recovery fallback that must act on wall time (a missing dismiss event that unlocks a queue) is outside this clause. Reason: a browser page can report itself visible while receiving no frames (an occluded window, an embedded view that is not shown), so the signal cannot arrive and every such load would file a false defect, while a genuine failure on a page that draws frames still reports at the same budget. Review-held: whether a timer waits on a render signal depends on what its callback inspects, not on a call shape.

**COB-RN-M11** closed-rejection application. A caught throwable MUST be narrowed to the one class or closed code the code expects (an engine's closed rejection set, a decoding error, a JSON syntax error) and everything else rethrown; a shared value transform that both tiers use exposes that narrowing once (a "try" variant returning null only on the closed rejection) instead of each caller writing a bare catch. Reason: a bare catch around a library call turns a code defect into "invalid input" with no trace.
