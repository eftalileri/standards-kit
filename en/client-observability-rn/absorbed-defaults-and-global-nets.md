# Client observability -- absorbed defaults and framework failure nets

```kit-cover
type: normative
part-of: README.md
binds: the obligation covering a client failure NO call site owns - a path that degrades to a default and returns as if it worked, and a framework-level net that catches what nothing else did, and a promise whose rejection has no owner
open-when: shape:frontend-heavy, shape:bug-fix, signal:client-failure-path, signal:silent-failure, signal:global-error-net
skip-when: signal:backend-only, signal:no-client-failure-path
owns: COB-RN-M12, COB-RN-M13, COB-RN-M20
```

Scope: The obligations for a failure that reaches no owner: a path that absorbs it by degrading to a default must still report it without changing its return value, timing or throw behavior, a framework-level net is a safety net only while its reports name the operation that failed, and every promise has an owner of its rejection.

Document type: Normative part -- **COB-RN-M12**, **COB-RN-M13**, **COB-RN-M20**.

Why these rules are grouped: Absorbed-default failures and framework-level failure nets share the same reporting and attribution concerns, while caught failures have a separate owner in [silent-failure-paths.md](silent-failure-paths.md). Keep the rule identities and full obligations intact when organizing topic files.

References: [README.md](README.md); [classification-authority-and-outbound-links.md](classification-authority-and-outbound-links.md) (**COB-RN-M6**, the authority these rules route through); [silent-failure-paths.md](silent-failure-paths.md) (**COB-RN-M11**); [credential-masking-and-build-secrets.md](credential-masking-and-build-secrets.md) (**COB-RN-M8**, the masking criterion); [client-observability-rn-appendix.md](client-observability-rn-appendix.md) (non-normative origins).

## **MUST**

| ID | Rule |
|----|------|
| **COB-RN-M12** | A client-local failure that code absorbs by degrading to a default — for example a storage read/write, cache rehydrate, preference or feature lookup, or any `return null` / `return 0` / no-op-on-error path — MUST be routed to the single classification authority (COB-RN-M6) through one boundary helper, without changing the operation’s return value, timing, or throw behavior. The degradation remains as designed; only the silence ends. The report carries fixed, code-owned identifiers (module, instance/namespace id, operation name) plus structural error identity; it MUST NOT carry raw `message`/`stack`, stored values, or key contents (COB-RN-M8, COB-RN-N6). Deduplicate the same `(module, instance, operation)` at most once per process start, mark the record as deduplicated, and preserve a suppressed-repeat count so frequency remains recoverable. Call sites consume the boundary helper and MUST NOT create their own catch-and-report path (SSG-M8). Reporting MUST NOT create a retry loop; any supported reinitialization is separately bounded and documented by the selected storage or framework. |
| **COB-RN-M13** | **A global failure net is a safety net only while its reports are ATTRIBUTABLE; an identity-less report silently leaves the points it is believed to cover uncovered.** Where a framework-level seam (server-state cache, router, event bus, job/queue runner) is wired to report every failure no call site owned, the net's entire value rests on the report naming **which** operation failed. The identity is normally read from a field the framework treats as **optional** -- so a net can be correctly wired, fire on every failure, and still emit reports that say only "something failed". That is worse than a visible gap, because the net's existence then becomes the stated justification for **deliberately leaving other silent failure points unclosed** ("the global net already covers it") -- and that justification is false for exactly as long as the identity is missing. Three constraints are binding. **(a) The identity is mandatory, not optional.** Every operation the net observes **MUST** carry the field the net reads to name it; the framework's optionality is not permission to omit it. For HTTP request seams, this identity is a **static, code-owned route template**: dynamic path segments are named placeholders, the same template is carried by request observability and response-validation context, and a missing or unsafe candidate fails closed to an explicit unlabeled sentinel; the raw URL, query string, or interpolated identifier is never an identity fallback. **(b) The identity **MUST** come from one naming authority as a static, code-owned literal.** A free literal repeated at each call site makes collisions invisible -- two distinct operations silently share one name and their reports merge -- while a dynamic or derived value leaks user data into the observability surface (**COB-RN-M8**). The authority **SHOULD** be shaped so duplicate names are rejected by the compiler or type system rather than by review (for example a single map/enum whose duplicate keys cannot compile); if the authority is later split across files, that structural guarantee disappears and **MUST** be replaced by an explicit cross-file uniqueness check in the same change. **(c) Both halves **MUST** be enforced by lint rather than review** -- the presence of the identity at each call site and its provenance from the single authority are decidable from a **single file's AST**. Verification **MUST** be empirical: exercise a real failure through the net and read the emitted report. A wired net is **not** evidence of an attributable one, and "the net covers it" **MUST NOT** be accepted as a reason to leave a failure point silent until the report has been shown to name the operation. |
| **COB-RN-M20** | Every client promise MUST have an owner of its rejection: it is awaited, ends in `.catch` / `.then(_, onRejected)`, or is detached with `void` only when the voided call provably owns its own rejection -- the canonical no-throw terminal wrapper of the classification authority (**COB-RN-M6**), a server-state method that resolves on failure (refetch, invalidate, prefetch, next-page fetch, without throw-on-error), or a function whose every await sits inside a non-rethrowing catch that reports through that authority. A function that callers start detached MUST NOT throw an invariant failure; it reports through the authority and returns a failure outcome. `void` MUST NOT be used only to silence the check. Reason: an unowned rejection reaches only the runtime's anonymous unhandled-rejection net, which names neither the operation nor the root cause (**COB-RN-M13**). Enforcement: the upstream `@typescript-eslint/no-floating-promises` rule on the client lint profile (`ignoreVoid: true`) fails a bare floating promise; the ownership claim behind each `void` is review-held. A project rule demanding a visible owner at each `void` would flag many calls that already own their rejection inside the callee (the canonical wrapper, server-state methods and visible `.catch` chains), so it fails admission ([ENA-A1](../enforcement-architecture/enforcement-admission.md)(d)). Promise-returning callbacks in void-typed positions are a separate class, not fenced by this rule. A reference to a check is not evidence that it exists or covers the full rule; record its actual scope and limits. |

**COB-RN-M12** readiness clarification. Preserving a boundary's fallback value does not turn that value into proof of success. If a fallback feeds an initialization/readiness decision, the boundary adapter must also expose a typed, PII-free failure outcome; the consumer may recover through another authoritative read, but otherwise it must retain explicit error/not-ready state and the existing retry surface. The already-reported failure is not reported a second time by that consumer.

**COB-RN-M12** preference-validation clarification. A persisted preference getter may intentionally reject a corrupt value and continue a documented authority-precedence chain by returning its existing empty result. That validation failure is still an absorbed client failure: report the original throwable through the single classification authority at most once per process, without including the rejected value or raw error text. Do not change the getter's return/throw/timing merely to make it observable; the next authoritative source or the existing terminal error/readiness surface remains the owner of product behavior.

**COB-RN-M12** frequency-summary clarification. A suppressed-repeat summary consumes only a closed, code-owned failure identifier and a positive safe-integer count. It is a structured, non-event diagnostic path owned by the existing classification module; callers do not choose category or invoke a provider capture API. A synchronous acceptance result means only that the local reporting pipeline accepted the record, not that an asynchronous transport delivered it; an unaccepted snapshot remains unacknowledged.

**COB-RN-M12** parsing clarification. A parser that absorbs a decoding, URL construction, parameter-enumeration or output-building failure and returns accumulated values or its existing absent result reports at the parser's existing catch boundary; the outer capture boundary cannot observe an exception already swallowed there. Preserve its input order, loop scope, partial/empty result, cache and synchronous/throw contract. Where the original throwable could contain untrusted source text, report through a code-owned diagnostic carrier plus a closed structural error-kind fact; do not pass the original payload, URL, key/value map, raw message, stack or cause into the report. Sibling parser catches in one resolver delegate to the same private privacy boundary while retaining distinct code-owned operation identities. A naturally single-read operation needs no second suppression authority or suppressed-repeat marker: distinguish a workload that executes once from one whose repeated reports were deduplicated. Stated limit: no parser-specific check is admitted ([ENA-A1](../enforcement-architecture/enforcement-admission.md)(a), [ENA-A2](../enforcement-architecture/enforcement-admission.md)). Whether a catch returns accumulated values or an absent result, whether the read can repeat, and whether every report argument is free of raw source data require control-flow/call-graph review. Existing no-throw classification and source review hold the boundary; a source-level report call is not proof of telemetry delivery.

**COB-RN-M12** gate-consumption clarification. Where an absorbing boundary can receive a failure that an upstream owner (a framework net or a lower boundary) already reported, it MUST ask the authority's observed predicate before consuming its once-per-process gate. Consuming the gate on an already-owned failure spends the only slot and silences the next unowned defect for the rest of the process. A boundary that fires only on render or derivation MUST also use the no-throw entry and pass the original throwable, never a rebuilt `Error`. Review-held.

**COB-RN-M13** opt-out clarification (a call that silences the net is a DECLARATION and MUST carry its reason in writing). A net that skips already-owned failures needs a mark the owning site sets. Inside the classification authority the mark is part of reporting and needs no defence. **Outside it, the same call reports nothing and only silences** — it says "this failure will pass unreported", and nothing in the code can show whether that was deliberate. The mark is legitimate exactly when a *better-placed* owner exists — a hook that can read the provider's structural code, or a carrier that owns its own signal at construction so no call site can be first — and that fact is not derivable from the call: it names the owning context, where the signal's own record lives, and why a second, context-free record would be misclassified noise. **So every use outside the authority MUST carry a written justification at the call site, and this MUST be checked mechanically** — presence is decidable from a single file's AST, and the authority is recognized as the file that *defines* the mark, so no path list is needed and none may be introduced. Where a reason cannot be written, the mark is the wrong tool: report the failure.

**COB-RN-M12** caller-visible outcome clarification (an error-absorbing handler must report its outcome to its caller). A handler that catches failures and presents an error must return a typed outcome, and its caller must gate success-only side effects on that outcome. Apply this to every exit, including guards, validation failures, and terminal catches, so an error cannot be followed by navigation or state changes that imply success.

Two consequences follow. **(a) A guard must leave the user somewhere they can act.** A branch that records a failure into state the user cannot currently see (field-level errors written while a different step is displayed) is still silent from the user's side; the guard must also bring the relevant surface into view, using the destination the flow already defines rather than inventing a new message for the occasion. **(b) Do not author new user copy to fix this.** The failure branches already resolve their text from the message authority; the fix is the return value and the caller's gate, so a correct repair of this class adds **no** new translatable string — and if it seems to need one, the missing piece is usually a branch that was never showing the user anything at all.

**COB-RN-M13** terminal-callback position clarification (a net’s coverage depends on where the framework invokes the callback). Verify callback semantics against the source for the installed framework version; names and documentation alone do not establish whether a callback failure reaches the net, changes the operation result, or is discarded. Treat positions with different semantics as separate cases. Report callback failures through the classification authority without changing an already-confirmed operation result, except where an explicitly documented client-state teardown requires a distinct outcome. Use mechanically checkable rules where feasible and document remaining review limits.

**COB-RN-M13** scoped mutation application. The accepted server result and the later cache effect are separate outcomes. Scope assertion, synchronization and diagnostic logging after acceptance execute inside the existing terminal no-throw wrapper, so a stale scope or broken cache does not turn the write into failure or restore optimistic data over the committed server state. Definition error hooks retain the original operation/family/target context and use the existing observed-aware reporter: upstream ownership suppresses duplicates, while an unowned local validation or rollback failure still reaches the channel. A call-site catch only renders localized feedback. Stated limit ([**ENA-GV3**](../enforcement-architecture/enforcement-admission.md)): the existing typed command, classification marker and lifecycle lint are stronger mechanisms; complete callback placement, context and cache effect coverage require SDK/call-graph review, so no additional fence is admitted under [ENA-A1](../enforcement-architecture/enforcement-admission.md)(c).

**COB-RN-M13** confirmed-write diagnostic placement clarification. A diagnostic after a valid accepted response is a terminal side effect even when written in the request function before the framework resolves it. Each independent diagnostic uses the existing synchronous no-throw authority, so one broken sink neither reverses the accepted operation nor suppresses another post-acceptance diagnostic. A warning and a following success diagnostic have independent boundaries. Do not absorb the request, its acceptance checks, its required result data or any pre-acceptance rejection. The original Error identity and operation/family/target-or-count context still reach the single classifier. This synchronous containment does not settle a detached rejected promise or prove required active-query synchronization; MUT-M27 and terminal-callback constraint (d), including mandatory client teardown, remain unchanged. Stated limit (**ENA-GV3**): placement and complete independent-call coverage require source/SDK call-graph review. The existing typed no-throw API is the stronger mechanism (ENA-A1(c)); this clarification adds no rule identity, guard or exemption.

**COB-RN-M13** application -- asynchronous accepted-result terminal effects. A framework may await definition success and settlement callbacks inside the primary command's try, so a rejected secondary callback can re-enter the primary error/rollback path after an accepted server result. A terminal boundary must contain both a synchronous throw and the rejection of a returned promise, preserving the original throwable and required static operation/stage/root-cause context. It consumes the existing observed-error identity: an already-owned failure is not reported again, and an unowned failure is offered to the same category/channel owner without recursively reporting that owner's own sink failure. Read callback metadata and execute fallible cache reads inside that boundary too. Attempt independent terminal effects independently so one failed read, diagnostic or cache publisher does not suppress another required effect. Where the post-write method permits a detached invocation ([MUT-M28](../tanstack-query/mutations-optimistic-strategy.md)), it keeps that scheduling only when its returned promise is rejection-contained; `void` by itself is not containment, and no extra remote-refetch await is added merely to obtain containment. Keep pre-acknowledgement rejection, the original error identity, rollback ownership and the existing mandatory unfinished-client-state teardown exception (d). A contained promise is not business-completion or correctness-required synchronization proof: MUT-M27 and that teardown exception remain unchanged. Stated limit (**ENA-GV3**): local lifecycle lint cannot prove imported-helper rejection behavior, response provenance, locked SDK ordering, orchestrator substep isolation or downstream feedback/callback/navigation behavior. Typed original-context readers and the canonical no-throw API are stronger mechanisms, so ENA-A1(c) admits no additional fence. Provider-layer containment alone is not whole user-outcome closure.

**COB-RN-M13** web-surface coverage clarification (every web surface and every server boundary reaches crash reporting; a build without the provider key is refused). On a web client, every surface MUST open the tier's one browser crash-reporting client and have a route-level failure net that reports once, every server boundary that answers an unexpected failure with a generic response MUST report it first and return the event id in the error body, and a production build without the crash-reporting provider key MUST be rejected. Reason: a surface with no client and a boundary that converts a failure into a generic answer both fail silently, so zero events would read as zero failures. The build refusal is the build configuration's own check; the rest is held by review.
