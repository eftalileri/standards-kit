# Client observability -- outbound link ownership and capability-probe visibility

```kit-cover
type: normative
part-of: README.md
binds: the outbound-link and runtime-capability obligations whose failures must reach the client classification authority - owning every platform link-open promise through one schema-validated authority helper, declaring the platform package visibility that any query-first capability probe depends on, and answering a runtime capability in the layer that owns it so an impossible operation is never reported as a failure
open-when: shape:frontend-heavy, shape:bug-fix, signal:client-failure-path, signal:error-classification, signal:deep-link-open
skip-when: signal:backend-only, signal:no-client-failure-path
owns: COB-RN-M5, COB-RN-M7, COB-RN-M15
```

Scope: The obligations a call site owes when it asks the platform for something it may not be able to do: never letting the link-open promise become an unhandled rejection and never rebuilding the URL outside its one schema-validated authority helper, declaring the package/scheme visibility whenever a capability probe -- not the launch -- decides a branch, and reading a runtime capability from the layer that owns it so that an operation the runtime cannot perform is not filed as a failure. **Excluded:** the classification authority itself and what it must preserve on the way to the channel ([classification-authority-and-outbound-links.md](classification-authority-and-outbound-links.md), **COB-RN-M6**); a failure the code catches ([silent-failure-paths.md](silent-failure-paths.md), **COB-RN-M11**); a failure nobody owns ([absorbed-defaults-and-global-nets.md](absorbed-defaults-and-global-nets.md), **COB-RN-M12**-**COB-RN-M13**).

Document type: Normative part -- **COB-RN-M5**, **COB-RN-M7**, **COB-RN-M15**.

Related rule placement: The classification authority is defined in [classification-authority-and-outbound-links.md](classification-authority-and-outbound-links.md). These outbound-link and capability-probe rules remain separate so each call site can verify promise ownership, URL validation, platform declarations, and runtime capability handling.

References: [README.md](README.md); [classification-authority-and-outbound-links.md](classification-authority-and-outbound-links.md) (**COB-RN-M6** -- the authority an open failure is routed through); [client-observability-rn.md](client-observability-rn.md) (**COB-RN-N3**-**COB-RN-N5** are the matching prohibitions); [credential-masking-and-build-secrets.md](credential-masking-and-build-secrets.md) (**COB-RN-M8** -- the credential material a rejection message must not echo); [maps-location-rn.md](../maps-location-rn/maps-location-rn.md) (**MAP-RN-N1** -- the raw coordinates the same rejection text must not carry).

## **MUST**

| ID | Rule |
|----|------|
| **COB-RN-M5** | **MUST** own every **`Linking.openURL`** promise: use **`await`** in an async handler or attach **`.catch`/`.finally`**. **`void Linking.openURL(...)`** and expression-bodied handlers that return the promise are forbidden because open failures become **unhandled promise rejections**. Project-owned legal/support/social/content URLs **MUST** go through one schema-validated authority helper; a content identity, start offset, derived URL and brand-icon mapping live together in one feature authority and are not rebuilt by screens or menus. Do **not** add alternate URL fallbacks without an explicit decision record. |
| **COB-RN-M7** | **MUST** declare the target's **platform package visibility** whenever a **query-first gate** (a `canOpenURL`-style capability probe) decides a branch. A probe is subject to the OS **visibility filter**; the **launch** is **not** (**Android 11+ / API 30+**: the probe resolves an activity and is filtered unless a matching **`<queries>`** entry -- scheme `<intent>` and/or `<package>` -- is declared, while `openURL` -> `startActivity` is never filtered; **iOS**: the scheme must be listed in **`LSApplicationQueriesSchemes`**). Without the declaration the probe returns **`false` on a device where the launch would have succeeded** -- a **false negative** that blocks the user with a wrong "app not installed" message, on **some devices only**, and therefore looks device-specific rather than like a config defect. The declaration **MUST** cover **every** scheme and package the code actually probes and **MUST** be extended in the **same change** that introduces a new probe. |

| **COB-RN-M15** | **A runtime capability MUST be answered by the layer that owns it, and an operation the runtime cannot perform MUST NOT be reported as a failure.** A platform-identity test, build flag, or native-module object answers which platform is present, not whether this runtime can perform an operation; simulators, desktop-class runtimes, and compatibility modes may lack the underlying system framework. Ask the native or vendor layer that can answer. An impossible operation resolves with the same empty-result shape as the established impossible branch, rather than rejecting. **(a)** Separate real failures by closed structural code and route them through the classification authority (**COB-RN-M6**); an untyped rejection can report an impossible operation as a crash while hiding genuine failures. **(b)** Keep provider/transport failures distinct from an empty capability result (**COB-RN-M12**): “could not ask” must not become indistinguishable from “nothing was available.” **(c)** Do not attach a hand-written once-per-process suppression marker unless a canonical noise gate backs it. Where execution is structurally limited to once per process, remove the dead marker (SSG-M8). |

**COB-RN-M15** enforcement limit ([KIT-INV-8](../authoring/kit-structural-invariants.md)(b)). Only clause **(c)** is decidable from one file's syntax tree, and it is lint-locked: the marker's presence and the canonical gate's call site are in the same tree. The other two clauses are **not** reachable by a single-file rule and the absence of a check is stated rather than left silent. **(a)** would need the **runtime type** of a caught binding produced in another module -- whether it was converted through a typed carrier is not visible where it is caught, and narrowing the check to one catch syntax (`try`/`catch` but not a promise `.catch`) would be an arbitrary cut that leaves the identical shape uncovered. The capability half is harder still: *"can this runtime perform this operation?"* is a **runtime fact about the device**, and the file that asks shows only a call. The information a check would need is the vendor framework's own answer on a real device of each class, which no source-tree scan performs.

**COB-RN-M15** web-counterpart clarification (one codebase, a second runtime). A phone-only capability MUST ship its web counterpart behind the same interface in the same change that introduces the capability. The web answer MUST live in a platform file beside the owning module (`<module>.web.ts`, type-checked against the phone module's exports), in the dependency's own web module, or -- for a React Native core API the browser lacks -- in the single web core-API adapter; it MUST NOT be a platform-constant branch at a call site or in a screen. The web target MUST NOT fall through into a phone branch (a binary `ios ? a : b` sends it to the Android side): every platform-conditional read names its web outcome, and a capability the browser cannot perform answers the resolved "cannot" shape above. Reason: a call-site branch lets each caller decide the web answer differently, and an implicit Android fall-through runs phone-only code (app schemes, intents, native modules) in a browser that cannot perform it. Review-held ([**ENA-GV3**](../enforcement-architecture/enforcement-admission.md)): whether an operation is phone-only is a product fact, and the platform-file placement is a structural choice no single-file syntax check separates from a legitimate phone-only guard.

**COB-RN-M15** device-data clarification (a valid value the device's engine data does not know). When the device's bundled engine data (time-zone, locale or calendar tables) rejects a value that the project's shared allowlist accepts, the device's data is older than the value's upstream release: that is a device capability condition, not a defect. A surface that can degrade (a label drawn without its offset) MUST report it through a typed carrier of the expected class ([**COB-RN-M6**](classification-authority-and-outbound-links.md)), and the producer MUST decide allowlist membership before choosing the carrier, because a rejected value outside the allowlist is stored-data drift and stays a crash-channel defect. The two classes MUST use separate once-per-process gates so the expected one cannot silence the defect ([**COB-RN-M12**](absorbed-defaults-and-global-nets.md)). Reason: an emulator with old engine data otherwise files a valid, allowlisted value as a crash on every run. [Verify by: review -- whether a value is allowlisted and whether the engine knows it are runtime facts about the device; no single-file check sees both]

**COB-RN-M5** allowlist-scope clarification (an allowlist admits what the builders emit, and its rejection text is an egress surface). The schema-validated outbound helper this rule mandates is a **security** boundary, so two properties of the schema are binding rather than stylistic. **(a) Scope.** The allowlist **MUST** admit exactly the scheme/host set the project's own URL builders actually produce. Adding a scheme "for completeness", or because a platform *also* supports it, is not neutral: it widens the set of addresses the helper will hand to the OS while nothing in the codebase produces it, so the widening buys nothing and the next reader cannot tell an intended target from a leftover. Where a design document names a scheme the implementation then does not build, the allowlist follows the **implementation**, and the omission is written down. **(b) The rejection message travels.** A schema's issue text is returned to the caller and is routinely folded into a failure report or a log line. A URL that carries **location, identity or contact** data in its query, path or fragment therefore **MUST NOT** be echoed into that text: name only the offending **scheme or host** component. Otherwise the very identifier the observability rules exclude (raw coordinates -- [maps and location](../maps-location-rn/maps-location-rn.md) **MAP-RN-N1**; phone/credential material -- **COB-RN-M8**) reaches the crash channel through the validator instead of through the call site, which is the one path a reviewer checking the call site will not look at.

**COB-RN-M7** probing-platform clarification (declare where you probe, and no further). The declaration obligation is scoped to the platforms whose code **actually executes a probe**. Where the branch is platform-conditional -- one platform probes for an alternative application while the other opens a universal address unconditionally -- the manifest/plist entry belongs to the **probing** platform only. Adding it on the non-probing platform is not a harmless surplus: a capability-query declaration is a public statement about what the application inspects on the user's device, and store review and privacy documentation read it as such, so declaring a query the code never makes is a false statement about the app's behaviour. The rule's requirement is exhaustive coverage of what is probed, not maximal coverage of what could be.

**COB-RN-M5** caller-outcome clarification (an opener that owns the failure message still owes its caller the outcome). An outbound-open authority that shows the user-facing failure message and files the single report itself MUST still return a named outcome (opened / not opened) to its caller. A caller that dismisses its surface, navigates away or marks a step done after the open MUST do so only on the opened outcome; on every other outcome the surface stays, so the message appears inside it and the user keeps the retry and the context (the drafted text, any alternative channel). "The helper handles the failure" settles who tells the user and who reports, never whether the flow may advance: closing the surface regardless turns a recoverable refusal into a dead end.

**COB-RN-M5** prepared-message channel clarification (one text, every on-device channel). A ready-made message the app opens for a person outside it (a reminder, a notice, a draft for another person) MUST be offered through one channel authority that presents every on-device channel the platform gives -- a messaging app, the SMS composer and the system share sheet -- for the same text, and a surface MUST NOT hardwire a single third-party messaging app. Reason: which messaging app people use is regional, so a single-app path silently strands every user in a market where that app is not the norm, while the share sheet reaches whatever is installed without a dependency or a server-side sender. Review-held ([**ENA-GV3**](../enforcement-architecture/enforcement-admission.md)): whether a string is a prepared message for someone outside the app is a product fact no single file's syntax tree decides.
