# Client observability -- the classification authority

```kit-cover
type: normative
part-of: README.md
```

Scope: The one authority that resolves error category to severity to channel, identifies which lifecycle seam may own a mutation failure, and preserves diagnostic context through reporting. **Excluded:** outbound-link obligations whose failures reach this authority — owning every `Linking.openURL` promise and declaring platform package visibility required by a capability probe ([outbound-link-ownership-and-visibility.md](outbound-link-ownership-and-visibility.md), **COB-RN-M5**, **COB-RN-M7**).

Document type: Normative part -- **COB-RN-M6**.

Related rule placement: Outbound-link ownership and package visibility are separate obligations in [outbound-link-ownership-and-visibility.md](outbound-link-ownership-and-visibility.md). Keep the shared classification authority here and route failures from adjacent client-observability rules through it; use the reading order in [README.md](README.md) to locate each owner.

References: [README.md](README.md); [client-observability-rn.md](client-observability-rn.md) (**COB-RN-N3**-**COB-RN-N5** are the matching prohibitions); [silent-failure-paths.md](silent-failure-paths.md) (**COB-RN-M11**) and [absorbed-defaults-and-global-nets.md](absorbed-defaults-and-global-nets.md) (**COB-RN-M12**-**COB-RN-M13**) consume this authority; [outbound-link-ownership-and-visibility.md](outbound-link-ownership-and-visibility.md) (**COB-RN-M5**, **COB-RN-M7**) is the sibling band whose failures route through it.

## **MUST**

| ID | Rule |
|----|------|
| **COB-RN-M6** | **MUST** route every write to the client crash channel through one classification authority that resolves error category → severity → channel. Expected operational or business outcomes use WARN and a non-event diagnostic record (such as a breadcrumb or counter), never a crash event; system or unmapped failures use ERROR and the crash channel. Derive categories from existing structured data: an API error envelope when available, otherwise structural transport markers such as `error.name` or a transport code. Unknown failures remain visible as defects; never demote them to silence noise. Classify provider error codes only in explicit provider context and against that provider’s exported constants. Where a provider defines a closed error-code set, map it exhaustively in this authority and attach the structural code to report metadata; do not maintain a second expected-code list. Expected domain outcomes (for example declined, pending, unavailable, or already-completed operations) must not be misclassified as crashes. Enforce exhaustive mappings with the type system where possible. Structural codes are diagnostic data, not credentials, and must be written by this authority rather than re-derived at call sites. The unconditional capture sink is called only behind this authority; feature code must not call provider capture APIs directly. Detached terminal recovery and irreversible-operation follow-up that cannot safely re-reject when a reporting sink fails use one canonical no-throw wrapper around the same authority; they must not add local classifiers, hide unknown failures, recursively report a broken sink, or leave a rejecting catch handler. Mechanically checkable sink calls, direct provider capture calls, and terminal promise ownership should be enforced by lint. Without one gate, expected request failures and offline transport can be filed as crashes; without no-throw terminal handling, reporting can create an unhandled rejection and overwrite a completed business result. |

**COB-RN-M6** typed command cancellation clarification. A stale operation that proves loss of its current command/session authority through the existing typed cancellation carrier is an expected OPERATIONAL result, not an unknown SYSTEM failure. The single classifier consumes the carrier's typed predicate; message text, a second name-string list or a feature-local category decision is not proof. If the authority's module imports persistence or other side effects, the carrier and predicate live in one pure module and the existing authority re-exports the SAME binding. Classification cannot import that side-effect authority back into its failure boundary and introduce an initialization cycle. Unknown carriers remain SYSTEM. Enforcement limit: the shared typed carrier/classifier provides the stronger runtime construction boundary ([ENA-A1](../enforcement-architecture/enforcement-admission.md)(c)/ENA-A4); no additional static fence is admitted for cross-module import ordering or arbitrary cancellation semantics.

**COB-RN-M6** lifecycle-ordering clarification (which seam may own a mutation failure). Where a server-state library runs a **cache-level** failure hook beside the **per-operation** hooks a caller may pass, the two are not interchangeable and only one of them can still own the failure. The ordering is a property of the library, so it is read from the library and written down once — never guessed per call site, and never inferred from the hook's *name*:

- A hook supplied in the **operation's own definition** (the `useMutation`-style options object) typically runs **inside** the cache's dispatch, i.e. **before** the cache-level hook. Reporting there **enriches** the single incident with context the cache cannot see (the variables, the rollback state, the screen), and the cache-level net stays silent for an already-owned failure. This is legitimate.
- A hook supplied at the **call site** (the second argument of a `mutate`/`mutateAsync`-style trigger) typically runs **after** the cache-level hook has already settled the failure. Taking ownership there is **too late**: the net has already emitted its report, so the call-site report is a **duplicate** (SSG-M8 — one writer per incident), and any "suppress the net" marker set there arrives after the decision it was meant to change.

Therefore a failure **MUST NOT** be owned, marked observed, or reported from a call-site-supplied lifecycle hook. Because "is this hook in the operation's definition or in the trigger's second argument?" is decidable from a **single file's AST**, this **MUST** be enforced by lint rather than review. Two consequences bind the writing, not only the code: a per-call-site justification comment is **not** evidence that the ordering was checked, and a hook that merely renders user-facing text (a toast, an alert) is **not** ownership and is out of this rule's scope.

**COB-RN-M6** scoped mutation lifecycle application. Definition hooks retain original throwable identity, real validator cause, operation/family and target/count context through the existing observed-aware no-throw authority. An already-owned upstream failure is not reported again; the later global net remains silent, while a call-site catch renders localized feedback without reconstructing or classifying the error. Unexpected rollback failures are contained and reported through the same authority, never a detached rejected promise. An accepted server write's later scope assertion/cache/reporting effect cannot reverse the outcome: execute that effect through the existing terminal wrapper (**COB-RN-M13**). Known scope refusals keep canonical WARN; unknown failures remain SYSTEM. Stated limit (**ENA-GV3**): the existing classifier, ownership marker and lifecycle no-throw lint hold the seam. Data-dependent context and complete consumer/SDK ordering require review; the stronger existing API declines another fence ([ENA-A1](../enforcement-architecture/enforcement-admission.md)(c)).

**COB-RN-M11** migration-attribution clarification (moving a call site onto a shared authority must not cost its identity). When a bypassing call site is migrated onto a shared helper that **already owns and reports** the failure, the caller's own report is removed so the incident is reported once -- but the context that report carried (which screen, which surface, which user action) is diagnostic information the shared helper does not have. Dropping it is a **regression** disguised as consolidation, and keeping both reports is a duplicate. The correct resolution is neither: the shared authority **MUST** take the caller's structural identity as a **required** parameter -- required, not defaulted, so a new caller cannot silently inherit another surface's name -- and fold it into the single report. The same reasoning applies in reverse: a helper that already reports **MUST NOT** be wrapped in a second call-site report merely to add context that the parameter could carry.

**COB-RN-M6** root-cause-visibility clarification (a report whose diagnosis is destroyed on the way out is not a report). The authority’s report is only useful when a reader can still see its diagnosis. Common silent losses between the call site and the event view include:

- **(a) A key-name redaction list destroys code-owned constants that share a name with a free-text class.** A masking authority that decides by **field name** must treat `message` / `stack` / `cause` / raw address fields as unconditionally unsafe, because no key list can prove what a driver or library embedded **inside** free text. That decision is correct and **MUST NOT** be relaxed. The consequence is a naming obligation on the producers: an observability meta object **MUST NOT** carry a **code-owned** value under one of those names, because it will be replaced by the redaction marker without the value ever being inspected. Rename the field (a fixed failure label is not a `message`); if the value is instead a caught throwable's raw text, it does not belong in the meta at all. Widening the deny-list to rescue one constant re-opens the leak the list exists for and is forbidden. Because "this literal object passed to the masking authority declares a deny-listed key" is decidable from a **single file's AST**, this **MUST** be enforced by lint rather than review.
- **(b) On an API failure the carrier's `message` is the server's rendered user sentence, not a diagnosis.** Where a transport boundary constructs its error from the server's translated copy, a root-cause describer that reads only `name` + `message` reports the same generic sentence for every failure in the product. The client describer **MUST** mirror the server's own root-cause contract in a fixed order: **(1)** a structural diagnostic field the carrier already holds; **(2)** failing that, the **address** of the diagnosis -- the registered error code and the correlation id -- stated as such; **(3)** only then the error's own identity and cause chain, which is what keeps genuinely local failures (validation, framework misuse) readable. Where the server **deliberately** withholds the operator diagnostic outside development, that is not information loss to be worked around by re-enabling it: the diagnosis is **moved, not deleted** ([error policy](../error-policy/transport-i18n-and-classification-rules.md) **M30** (a)/(c)), and naming the correlation id is how the client hands the reader the key to it. Only closed-set material crosses: a code is emitted when it is **registered**, and an unregistered candidate contributes the *fact* that it was unregistered, never its text. The same address, without the correlation id, MUST be the `message` of a code-owned `cause` carrier the boundary links; a constant there is forbidden. Reason: a crash SDK that appends linked causes after the thrown error makes the innermost cause the event title, so a constant titles every failure of the boundary alike, and a correlation id would put every event in its own group. Review-held: which object ends up linked as `cause` is not decidable from one file's syntax tree.
- **(c) A structural diagnosis attached under a bespoke field name is invisible to every generic reader.** When a boundary builds a safe structural object about a failure, it **MUST** link it through the language's standard cause chain, not only through a private field, or each consumer needs bespoke knowledge to find it and the shared describer walks past it. Where an existing bespoke field already has consumers, keep it as the **same object reference** -- one producer, two names, no second read path (SSG-M8) -- and say in the code which one is the authority.

The client-tier corollary of (b) is a **sink** obligation as well: where a client log sink deliberately refuses to write a caught throwable's raw text, it **MUST** still write the closed-set structural facts it can prove (validated class identity, registered code, bounded numeric status). A sink that substitutes a fixed redaction constant and nothing else converts a safety rule into a diagnosis blackout -- the redaction is right and the blackout is a separate defect, so both halves land together. The authority itself MUST attach the describer's output and a transport carrier's bounded status/kind/route/content type (never its raw body) to every report: a call site's fixed context sentence then cannot hide the diagnosis. A fact that was measured absent (a response without a content-type header) MUST be written as an explicit null, never omitted: an omitted field cannot be told apart from a field lost on the way, and the next incident's classification depends on telling them apart. That is held by construction, not by a lint row.

**COB-RN-M6** provider-text diagnostic clarification. Where a provider SDK carries a failure sub-reason (for example, why a store declined a payment) only inside its own composed description text and never as a structural field, that sub-reason may be attached to the report and to an analytics outcome as a diagnostic field, but only through one reader in the provider's taxonomy authority that finds the SDK's own fixed label, takes the segment it terminates, and matches it by exact equality against a closed set copied from the shipped SDK's exported constant names. The value MUST NOT feed category, severity, user-facing text or any branch; the surrounding text MUST NOT be stored; an unmatched segment yields no field; the closed set is re-measured when the SDK is upgraded. Reason: classification by message text stays forbidden because opaque text misclassifies, while a bounded exact-token diagnostic cannot change a decision and recovers a root cause the structured channel drops.

**COB-RN-M6** gateway-response clarification. Where the server answers every error status with its envelope, a 502/503/504 response whose body is not that envelope (non-JSON, binary, or JSON without the envelope's error-code field -- an edge's own JSON error body is still not the server's) was produced by the edge/gateway in front of the server, not by the server: the transport classifier MUST give it its own structural kind and the classification authority MUST map that kind to `OPERATIONAL` (expected, transient), with its own catalogued user text. A 502/503/504 that carries the envelope keeps the envelope's own category. The set is defined once, in the transport classifier. A non-envelope body on a 2xx or on a 500 stays a contract defect (`SYSTEM`): the server owns those responses. Reason: a gateway timeout during a deploy or an upstream stall otherwise files a crash event per affected request and shows the user a "response is not JSON" sentence.

**COB-RN-M6** refusal-condition clarification. A client guard that refuses work under one shared code MUST name the exact failed condition from a closed set (one name per condition; conditions are never OR-ed into one throw) and attach the facts that decided it -- request route template and method, captured versus current generation, the closed kind of the command that advanced it, and the elapsed milliseconds -- as numbers and closed values on the error, read by the one classification authority into every event, fatal ones included. Reason: a shared code with a generic sentence cannot tell which guard refused or why, so the next occurrence still has no root cause. No tokens, ids or free text enter these fields.

**COB-RN-M6** expected-volume clarification (the client's warning box needs a count, not only a breadcrumb). A breadcrumb is read only beside a later crash event, and a shipped client's local log reaches no one (**COB-RN-M11**), so a client-produced expected failure that is only breadcrumbed is invisible in aggregate: a client gate or provider outcome that starts refusing every user raises no alarm. The classification authority MUST therefore emit each expected failure the client produced itself -- no server response carried it (transport loss, edge gateway response, client-side refusal, provider SDK outcome, platform result) -- as one raw occurrence: category plus the closed structural identity it already resolved (wire kind and code, carrier class, closed reason code), never a timestamp, never free text and never personal data -- the server clock is the only time authority and counts each occurrence at arrival, so a client cannot backdate occurrences into the baseline. A failure whose code came from the server's envelope MUST NOT be emitted, because the server boundary already counted it ([error policy](../error-policy/error-category-provenance-and-client-text-set.md) M43). The client MUST NOT count, aggregate, threshold or judge these occurrences (the device computes nothing; derivation and decision live in one server authority, [SSG-M1](../ssot/ssot-must-authority-and-derivation.md)); its only job is transport: a bounded on-device queue that survives offline periods and process death, flushed in capped batches with a minimum interval, random delay after reconnect and exponential backoff on throttling, gateway or transport failure, never on the startup path. On overflow it drops the oldest occurrences and sends the dropped count so the server can count the loss. The server MUST validate every identity against a closed allow-list shared with the client (the client's typed closed sets bound to it at compile time; a carrier-specific reason accepted only with its own carrier), count accepted occurrences into the same multi-instance window its own expected failures use, count rejected and lost occurrences into closed loss fields of that window, and let the one existing alarm consumer judge them with its general rule -- a second evaluator or a crash-tool monitor on a client metric is a parallel consumer. Because the endpoint is unauthenticated, the per-identity fields are data, not alarm subjects: the consumer judges the client family's total as ONE subject against its own baseline, so an anonymous caller can open at most one episode from this family, and the episode carries the top contributing fields for triage. The ingestion endpoint is unauthenticated and shed-safe: a body-size limit and per-address plus global budgets run before body parsing, the write is one pipelined store transaction per batch with no database write and no per-occurrence log or crash event, and an unavailable store answers "defer" so the occurrences stay on the device instead of queueing in server memory. Remaining blind spots, stated where the consumer is: an occurrence from a device that never reconnects never reaches the window; offline occurrences arrive as a reconnect burst at delivery time, not at occurrence time; one signal's surge can dilute in the family's wider baseline; per-process persistence debounce can lose the last few seconds before a kill. Reason: per-occurrence crash events for expected failures would bury real defects, and no count at all hides a broken client flow.


**COB-RN-M6** enforcement-status clarification (a decidable lock whose population is not yet zero is staged and stated, never silently skipped). A decidable obligation may still have existing findings when introduced. Measure the population with the check’s own predicate, reproduce that predicate in the baseline, and state its blind spots (such as helper delegation or dynamic imports). Ship a blocking ratchet rather than a warning floor (FP-M18); list residual debt at file granularity, record its closure order beside the scope declaration, and remove each entry in the same change that closes it. Give framework callback positions with different semantics distinct rule identities. Report the remaining count and closure order so an unlocked class is not mistaken for covered.
