Scope: Raising a blocking minimum cuts the whole installed base below it in one step. This part holds the evidence that **must** exist before that happens, which surface is allowed to *discover* a release versus merely *confirm* it, and the signals the promotion (or its absence) **must** leave behind.

Document type: Normative part -- FFL-RN-M12-FFL-RN-M15, FFL-RN-N3-FFL-RN-N4.

References: [README.md](README.md); [app-control-policy.md](app-control-policy.md) (FFL-RN-M3-FFL-RN-M11, the policy these rules promote); [feature-flags-rn.md](feature-flags-rn.md) (definitions and agent contract).

## **MUST**

| ID | Rule |
|----|------|
| **FFL-RN-M12** | Store console evidence proves a release's configuration, not that users can obtain it. Promotion of a blocking minimum therefore **MUST** require, in addition to provider evidence, an independent public-availability proof that the exact release identity is really reachable through the public distribution channel. Where the provider exposes no review/publication state at all (some publisher APIs report a release as fully rolled out the moment the operator submits it, while the store is still reviewing), provider evidence alone is forbidden as a promotion trigger. Where the provider does publish a user-facing storefront surface that names the currently served version, that surface is the preferred proof — but it may be consulted only as a confirmation of an already-discovered identity (FFL-RN-M13): the confirming component **MUST** take the expected identity as input and return a boolean, so that no value from a cached/public surface can re-enter the discovery path. A stale confirmation can then only *delay* promotion, never redirect it. Cache-defeating is **MUST** where the surface is CDN-cached and ignores client revalidation. The provider-independent fallback proof, and the only proof where no such public surface exists, is first-party adoption: the backend has observed that exact release ordering token in live traffic from at least a named minimum number of distinct authenticated actors, counted in shared cross-instance storage that stores no reversible actor value, with the minimum defined exactly once. Adoption observation is evidence collection, not a second decision path — it **must** reuse the same canonical ordering authority. Because the client supplies its own release headers, a witness is format-validated but not authentic; the observation window **MUST** therefore be bound to the identity the provider is independently reporting right now (the persisted candidate), never to "any identity newer than active" — an open threshold lets future release tokens be pre-seeded so that promotion fires the instant the provider first reports the release, and it leaves the evidence key space client-defined. The residual limit (test-channel installs of the same release also count; headers are not cryptographically attested) **MUST** be written down as a scope boundary, with device attestation named as the strengthening path. Promotion **MUST** be fail-closed: if the availability evidence cannot be read, the policy does not advance. Bootstrap (where baseline equals active and therefore cuts nobody) is exempt. Check declined: a lint check can only pin that the promote decision is built in the decision authority and sits under a condition naming the evidence ([ENA-N4](../enforcement-architecture/enforcement-anti-patterns.md)); it cannot tell whether the evidence comes from the right source, so that predicate is review-held. A reference to a check is not evidence that it exists or covers the full rule; record its actual scope and limits. |
| **FFL-RN-M13** | The discovery authority for "which release is currently live" **MUST** be the provider's authenticated console API. A public, CDN-cached storefront/listing endpoint **MUST NOT** decide which release the authoritative API is asked about, and **MUST NOT** be a release-evidence source: such endpoints are cached per edge for hours-to-days and may ignore client revalidation headers, so a stale edge copy silently pins the policy to a previous release while every check still reports success. Where the authoritative API offers no ordering/sort guarantee, the newest release **MUST** be selected with the canonical version-comparison authority over a provably complete result page (page-completeness asserted, never assumed) — array position is not evidence. Where the authoritative API's "released" state is also true for superseded historical releases, that state alone is not "live"; liveness is the canonical maximum of the released set. |
| **FFL-RN-M14** | The moment a blocking minimum is raised is the moment the entire installed base below it is cut off, so it **MUST** leave an observability trace: promotion and initial bootstrap are recorded on the informational channel with platform and release identity. Symmetrically, a release the provider reports as newer but which stays unpromotable past a named threshold **MUST** leave one dedicated record per candidate episode, emitted once on threshold crossing rather than every cycle, carrying the candidate identity and the observed public-availability evidence against its required minimum; a generic per-cycle provider warning does not satisfy this, because without the dedicated record both "cut everyone off" and "stuck, never cutting over" are invisible. That record **MUST** go to the expected channel (`warn` plus its metric aggregate — [logging-policy **M17**/**M18**](../logging-policy/failure-level-and-channel-routing.md)), never to the crash/system channel: waiting for public availability is an expected external lifecycle decided by store review, propagation and the installed base's own update pace, which on a small base keeps a release below the adoption minimum for days, so a crash event would fire on most releases with nothing to act on. Elapsed time cannot tell a defect from that wait and **MUST NOT** classify it: evidence that cannot be read or written and a malformed provider response are classified at their own raise, while an evidence recorder that silently stops counting has no independent signal and is told apart from slow adoption only by that record's observed-versus-required count. |
| **FFL-RN-M15** | A staleness fence (FFL-RN-M8) measures whether the refresher is alive, not whether the store still matches the active policy. Therefore every successful provider verification **MUST** advance the last-verified timestamp — including a cycle that observes a *newer* candidate, and a cycle where the provider answered correctly but the release is not yet fully available. Advancing it only when the store exactly equals the active policy conflates "we could not reach the store" with "the store has moved on", so any pending release or paused rollout walks the platform into the fence and converts a mild delay into a total outage for all clients, current versions included. |

## **MUST NOT**

| ID | Rule |
|----|------|
| **FFL-RN-N3** | **Must not** expose a tenant/user role as the writer of a global app-control policy. Store credentials belong only to the server-side synchronizer; clients and ordinary product-admin roles are read-only consumers. |
| **FFL-RN-N4** | **Must not** promote review, draft, staged, partial, halted, unavailable-territory, or otherwise ambiguous store releases into a blocking minimum. Environment variables and hardcoded constants **must not** act as a parallel minimum-version policy or missing-data fallback. |
