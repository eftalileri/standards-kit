# Blocking app-control policy (force update / kill switch)

```kit-cover

part-of: README.md
binds: the blocking app-control and force-update policy - its single server authority, the client decision lease and envelope, release identity, the staleness fence, the server-side API gate and the release-order precondition
open-when: shape:full-stack, shape:backend-heavy, signal:force-update-policy, signal:app-control-gate, signal:release-identity
skip-when: signal:no-remote-config, signal:no-app-control-policy

```

Scope: A blocking app-control policy is the one remote decision that can stop an installed client from working at all. This part holds what the policy is, who may write it, how a client requests and persists it, how a release identity is proven, and where the decision is enforced.

Document type: Normative part -- FFL-RN-M3-FFL-RN-M11.

References: [README.md](README.md); [feature-flags-rn.md](feature-flags-rn.md) (definitions, agent contract, ordinary flag rows); [app-control-release-evidence.md](app-control-release-evidence.md) (FFL-RN-M12-FFL-RN-M15, FFL-RN-N3-FFL-RN-N4 -- what **must** be proven before a minimum is raised).

---

## **MUST**

| ID | Rule |
|----|------|
| **FFL-RN-M3** | A blocking app-control / force-update policy **MUST** have one durable server authority, a shared runtime-validated response contract, and an explicit client readiness state. Missing policy, malformed identity, an unvalidated response, or a first-load query in `pending` / `paused` state is unavailable, never an implicit allow decision. When the response varies by native platform/version/build request identity, its HTTP boundary **MUST** prevent intermediary reuse across identities (`Cache-Control: no-store` plus the exact `Vary` fields); application-owned bounded persistence remains governed by FFL-RN-M5. |
| **FFL-RN-M4** | Automatic force-update promotion **MUST** advance each store platform independently and monotonically, only from provider evidence that the exact release is publicly obtainable on the target production track. The distribution territory set **MUST** be read from the provider's own availability response on every evaluation and **MUST NOT** be a single configured territory — a release is pushed to every open territory at once, so one territory either excludes users of newly opened stores or stalls promotion when that one store closes; provider readers **must not** carry territory literals or deployment-variable mirrors, and any provider-to-provider code mapping (for example a territory code to a storefront code) has one owner. Candidate evidence and the stability window **MUST** be durable across processes; in-process counters are forbidden. In multi-instance deployments, a provider read performed under a distributed owner-token lease **MUST** renew and re-prove that ownership immediately before the durable policy write; lease loss or coordination uncertainty forbids the write, and a platform-scoped exact CAS remains the durable race barrier. A provider error or ambiguous release set leaves the active policy unchanged and is reported through the canonical observability boundary. On the first rollout, when no durable policy exists yet, deployment readiness **MUST** remain unhealthy until both currently supported native platforms can produce a validated public decision from their bootstrapped policies through the same runtime-validated response builder used by the public endpoint; checking only policy presence or a partial release derivation is insufficient because availability/kill-switch state can still make the public envelope invalid. Readiness may return an ordinary unavailable verdict only for a proven absent/incomplete policy; a persistence read failure, malformed stored policy, or response-validation/invariant defect **MUST** propagate to the canonical error/log/crash boundary and **MUST NOT** be collapsed into the same boolean verdict. This one-time traffic gate does not couple later candidate observations or promotions, which remain platform-independent. |
| **FFL-RN-M5** | A persisted allow decision for a blocking app-control query **MUST** carry a bounded freshness lease. A cached block decision remains blocking. The lease decides when the decision is re-read, not whether the app may be used: a persisted allow past its lease **MUST** keep the app open and usable (no loader, no touch lock) while the authority is re-read in the background; a fresh block, maintenance or force-update answer **MUST** replace the app with its blocking surface at once, and a failed or offline re-read keeps the last allow. Only a client with no persisted decision at all waits for the first answer (FFL-RN-M3). Reason: the answer arrives within moments and nobody can act on stale access inside that window, while a lock costs every cold start and the server re-authorizes each request anyway. Foreground and reconnect checks **must** be query-owned and explicit. The persisted decision namespace and request envelope **MUST** consume one canonical, exact native `platform + marketing version + build` derivation; missing native identity disables persistence and **must not** create a version/build fallback. |
| **FFL-RN-M6** | Store release display names / operator labels **MUST NOT** be treated as artifact marketing-version authority. Ordering uses the store's immutable platform build token; an equal ordering token with different artifact digest, signing/targeting digest, minimum-OS, or listing provenance is a fail-loud identity conflict, never silent equality. Provider query targets and the final native build configuration **MUST** derive from one canonical bundle/package application identity; a second deployment variable that **must** equal it is forbidden. Valid credentials with access to a different store application therefore cannot redirect promotion. A blocking listing address **MUST** match the platform's exact canonical HTTPS listing shape; credentials, a custom port, fragment, or unrelated/duplicate query parameters are invalid. A legacy marketing baseline needed only for pre-build-header clients may be bootstrapped once from an immutable, exact artifact-and-targeting-digest-attested release manifest or authorized migration; it is historical provenance, not an active minimum and is not updated for later releases. |
| **FFL-RN-M7** | When the client's release identity cannot be fully proven, the blocking decision **MUST** be resolved by strictness, not by an error that leaves no exit. If the platform is known but the version/build evidence is missing or malformed, the authority **MUST** return *update required* together with the validated store address for that platform; returning a non-actionable client error (no store link, no retry) creates a permanently dead screen and is forbidden. A hard client error is allowed only when even the platform is unknown, i.e. no platform-specific exit can be produced. Correspondingly, the client request envelope **MUST NOT** be all-or-nothing: when the platform is resolvable it is always sent, and only the unproven version/build fields are omitted. Every envelope completeness class (full identity, platform-only) **MUST** be named explicitly in the shared contract — a weaker class is an accepted input class, never a silent acceptance — and consumers that require the strong class (e.g. persisted-decision namespaces) **MUST NOT** accept the weak one. A client surface without a store binary (e.g. a browser that loads the deployed bundle) **MUST** declare itself as its own named envelope class and get an explicit branch in the same decision authority — no update required, availability/kill-switch still applied — and **MUST NOT** be added to the native platform set that force-update and the server-side gate read; an unknown or malformed platform never reaches that branch, because a fallback there would let a broken native client skip a forced update. A published pre-envelope client still in the field is a wire consumer, not an invalid caller: when its shipped source proves it calls the public recovery endpoint without the canonical envelope and production evidence supplies an exact transport signature that unambiguously proves the native platform, that endpoint **MUST** retain one narrow compatibility adapter. The adapter yields only the named platform-only class, never invents version/build, and delegates the decision to the same authority. Presence of any canonical release header wins even when its value is malformed; the adapter cannot repair or override it. A generic HTTP-library / OS User-Agent that does not identify the application is insufficient evidence and **MUST NOT** be accepted. The inference stays endpoint-local: general request-envelope middleware and server-side API gates **must not** treat headerless traffic as native. Stated enforcement limit: the still-in-field release set, its shipped source and the observed transport signature are external/version-history evidence; no single-tree static check can decide whether an admitted signature is legitimate or complete. Review records those three facts and re-measures them before adding or retiring an adapter; a syntax-only wiring check would create false coverage. The envelope half (named completeness classes, platform header always sent, strong-class-only consumers, native metadata read only in the derivation authority) is also review-held: a lint check could only pin the internal shape of the contract, derivation and interceptor files ([ENA-N4](../enforcement-architecture/enforcement-anti-patterns.md)). A reference to a check is not evidence that it exists or covers the full rule; record its actual scope and limits. |
| **FFL-RN-M8** | A durable policy that is refreshed on a schedule **MUST** carry a staleness fence in the decision authority itself. The authority reads the policy's own last-verified evidence timestamp and fails loud once a single threshold constant is exceeded; the threshold is defined exactly once (no magic numbers at call sites) and is chosen so that transient provider outages cannot trip it while a genuinely frozen refresher is caught. Without this fence a broken refresher silently freezes the policy and keeps outdated clients alive with no signal. *Stated enforcement limit (ENA-GV3):* review-held — a lint check could only pin the decision authority's own shape ([ENA-N4](../enforcement-architecture/enforcement-anti-patterns.md)), and without a recorded defect of the class it fails admission ([ENA-A2](../enforcement-architecture/enforcement-admission.md)). A reference to a check is not evidence that it exists or covers the full rule; record its actual scope and limits. |
| **FFL-RN-M9** | A blocking release policy **MUST** be enforced on the API surface, not only on the client screen; otherwise a tampered or downgraded client keeps full backend access. The server-side gate: (a) derives its verdict from the same single decision authority as the public policy endpoint — a second comparison or verdict path is forbidden; (b) applies only to requests carrying a recognized native platform envelope, so web/admin/server-to-server traffic is untouched; (c) is independent of authentication, so an expired or absent session cannot bypass it; (d) keeps an explicit, reasoned exemption list for surfaces that would deadlock or break if blocked — at minimum the policy endpoint itself, deployment health/readiness, the operator/admin surface, provider webhooks, and unauthenticated public entry points; (e) rejects with a registered error code whose class is an expected product outcome (warning/metric channel), never a crash-reported system error; and (f) is mounted after the request-envelope and rate-limiting layers and before the routed surfaces. The gate is not an availability authority: when the policy cannot be resolved it records the failure through the canonical background-failure boundary and lets the request proceed, because availability is already decided fail-loud by the policy endpoint and the client gate. That scope boundary **MUST** be written down; it is a documented responsibility limit, not a silent fallback. *Stated enforcement limit (ENA-GV3):* (a), (d), (e) and (f) are review-held — each is the internal shape of the gate, its bootstrap file or the error registry ([ENA-N4](../enforcement-architecture/enforcement-anti-patterns.md)), and a lint check for them fails admission without a recorded defect of the class ([ENA-A2](../enforcement-architecture/enforcement-admission.md)). A reference to a check is not evidence that it exists or covers the full rule; record its actual scope and limits. Retirement horizon — an enforced gate is what bounds "the oldest consumer release still in the field" ([DCD-M8](../dead-code/dead-code-rules.md) (a)) — but only for what the gate actually covers. For a non-exempt surface, a binary below the persisted active minimum can no longer reach it, so that minimum, read from the durable policy for every native platform (never from a store listing or an operator's recollection), is the field horizon. It does not bound: exempt paths (d), requests without a recognized platform envelope (b), or an older over-the-air bundle still running inside a binary at or above the minimum — those keep their own horizon and need their own measurement. A temporary oldest-supported-version gate on a compiled response contract ([MRP-M15](../monorepo/monorepo-rules.md)) is therefore removed when, re-measured at removal time, (1) the active minimum is above the last gated version on every platform, (2) the gated route is not exempt, and (3) request telemetry shows zero traffic from gated versions; the removal deletes the version branch and its constant, not the audience projection it shared. *Stated enforcement limit:* not mechanically checkable — the check needs the production policy document and live request telemetry, and no source-repository artefact carries either. |
| **FFL-RN-M10** | Promotion of a blocking policy cuts every older client at once; there is no gradual ramp. Therefore the release order — the server that recognizes a new build **must** be live and **must** have bootstrapped that platform's policy before the build reaches users — is a numbered operational precondition, not a risk note. Where a policy bootstrap is pinned to an immutable artifact manifest, moving the shipped build past that pin without the bootstrap having completed leaves the policy uncreatable and the deployment permanently unready. This precondition **MUST** be mechanically enforced: the shipped build identity is cross-checked against the pinned manifest and against a recorded acknowledgement, and a stale acknowledgement fails the pipeline. |
| **FFL-RN-M11** | While a blocking decision is active (update required / disabled / unavailable), the client **MUST NOT** keep emitting background traffic the server is already rejecting. The gate decision is placed above the hooks/effects that produce that traffic — in component-model runtimes this means the blocked subtree is not mounted at all, not merely hidden — while local readiness that dismisses the launch/splash surface stays outside the gate so the blocking screen is always visible. |

[FFL-RN-M9](app-control-policy.md) application — release order of a server rule that installed clients also derive (a card grid, an availability, an eligibility). Raising the minimum is the compatibility tool only when the client part needs native code or a binary below it could still reach a write the server does not decide. Otherwise: (a) the invariant the rule protects **MUST** be decided in the server write path for every client version, so a stale bundle may render wrongly but cannot write past it; a client-bundle version gate on writes **MUST NOT** be added there, because it would be a second authority that an absent header or a stale cache bypasses; (b) the client part, compatible with the pre-change server, ships first as an over-the-air update to the runtime version that every binary at or above the minimum carries; (c) the server change follows, and the remaining window — an older bundle inside an admitted binary — is display-only, bounded by the update library's launch wait and check cadence ([ALS-RN-M5](../app-lifecycle-rn/app-lifecycle-rn.md)); a foreground restart to close it stays forbidden. Wire-compatibility keys kept for that bundle retire only when measured traffic is zero **and** the minimum has passed every binary whose embedded bundle reads them: a fresh install whose first launch misses the update still runs that embedded bundle. Stated enforcement limit: review-held — the decision needs the live minimum per platform, that build's runtime version against the published update's, the client part's native diff and the server write path's location; no source artefact carries the first two.

[FFL-RN-M4](app-control-policy.md) application — verification-only writes still require ownership. A provider outcome that proves the service is reachable but not yet fully available may advance a durable verification timestamp without changing the active release. That timestamp is still an authoritative write, including when it participates in another worker's compare-and-set snapshot. The shared outcome handler requires and consumes the same exact-owner write barrier as normal transitions, after its snapshot read and immediately before persistence. Ownership loss, cancellation or renewal uncertainty exits before the mutation; only a successfully fenced persistence may retain the expected provider outcome. Stated enforcement limit: no additional lint/guard is admitted ([ENA-A2](../enforcement-architecture/enforcement-admission.md)): the exposure is one shared handler inside the single orchestration authority, reached by two platform callers, rather than independent authoring surfaces. The required barrier parameter prevents omission at either caller; whether the handler consumes it immediately before persistence remains review-held.
