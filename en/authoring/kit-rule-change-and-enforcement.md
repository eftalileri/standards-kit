Scope

- Included: The mechanism choice and proof obligation when a new or changed kit rule is mechanically enforceable, and what the kit's own addresses and rule text must keep true now that no kit check gates ([**KIT-LIM-12**](kit-stated-limits.md)).
- Excluded: What survives when an existing rule is edited, relocated or deleted ([kit-rule-identity-and-relocation.md](kit-rule-identity-and-relocation.md), KIT-CHG); retirement eligibility ([kit-rule-retirement.md](kit-rule-retirement.md), KIT-RET); the steps this procedure leaves unfenced, each with what a check would need ([kit-stated-limits.md](kit-stated-limits.md), KIT-LIM); adding a rule ([kit-rule-addition.md](kit-rule-addition.md), KIT-ADD); the structural invariants ([kit-structural-invariants.md](kit-structural-invariants.md), KIT-INV); check design in general, owned by the false-positive topic and cited here rather than restated.
- Document type: Normative — the KIT-ENF family.

Binding principle: A rule's identity is a promise to everyone who cited it. Changing the text under an identity is ordinary maintenance; changing which obligation an identity names, or reusing a retired one, silently rewrites every citation that already exists — including citations in code comments and in released documents no scan of this tree can see.

## When the rule is mechanically enforceable

The general obligations are not restated here — they are cited, because a restated rule can diverge from its source and a link cannot. What this section adds is the part that is specific to a rule about the kit itself.

| ID | Rule |
|----|------|
| **KIT-ENF-1** | Ask, for every new or changed rule, whether a check could catch the whole class — and build one only if it passes the admission test ([**ENA-A1**](../enforcement-architecture/enforcement-admission.md)); the default is no. An admitted check takes the highest rung of [**ENA-P1**](../enforcement-architecture/enforcement-admission.md); lint rule versus script check is [**FP-MS1**](../false-positive/mechanism-selection.md)–[**FP-MS5**](../false-positive/mechanism-selection.md). A check on the kit's own Markdown protects bookkeeping, so it runs on demand, not as a gate ([**ENA-N10**](../enforcement-architecture/enforcement-anti-patterns.md)); [**KIT-LIM-12**](kit-stated-limits.md) governs the kit-document checks. |
| **KIT-ENF-2** | A rule about the kit's own Markdown is the residue case, and the reason is measured, not assumed. Point the adopting project's linter at a real kit file and record what happens before claiming it cannot: a linter commonly reports the file as ignored and exits 0 when no Markdown processor is registered, no `files` glob covers `.md`, or the documentation tree is globally ignored. A finding that cannot even be produced, or that would be produced as a warning with a zero exit code, is not a fence. A kit check is therefore an on-demand script; whether one gates at all is **KIT-ENF-1**. |
| **KIT-ENF-3** | A kit check is unverified until the three proofs of [**FP-M20**](../false-positive/check-verification-rules.md) exist, and the strongest positive specimen for a kit-structure defect is the adopting project's own history of its kit copy. The defect the check exists to stop has usually already happened once: recover that revision, extract it outside the repository working tree, and run the check against it — that is a real specimen rather than a hand-typed approximation. Where the defect has never occurred, say so and use an induced violation, which is weaker evidence and is labelled as such. Every derived required set inside the check fails loud when it reads empty ([**FP-M19**](../false-positive/check-design-rules.md)); a check opened over pre-existing debt uses the staged ratchet ([**FP-M18**](../false-positive/check-design-rules.md)) with its exemption list in the check's source, shrinking only, and failing when a listed entry stops violating. No test artefact is created for any of this. |
| **KIT-ENF-4** | A list the kit keeps by hand must say, in its own text, why it cannot be derived. Prefer generation: a list that can be produced from the files is produced from them, on demand, and the generator is the whole mechanism — a generated list is never committed where it would change on almost every commit ([**ENA-N11**](../enforcement-architecture/enforcement-anti-patterns.md)). Some lists genuinely cannot be generated — their rows carry a judgement no file property holds (which historical document a topic replaced, which problem class routes where, what reading order helps). Such a list is legitimate, and three things become obligatory in the file itself: it declares it is not an authority for what exists, it states the specific fact that is not derivable, and it says that every destination it names must resolve — the one mechanical part, kept by review since no gate runs it ([**KIT-LIM-12**](kit-stated-limits.md)). Whatever the list cannot guarantee — normally its completeness — is written as a stated limit beside it, never left implied ([**KIT-LIM-6**](kit-stated-limits.md)). A number the kit writes about itself is the same class in miniature — a count of its own files, folders, gates, tokens or identities drifts the day after it is typed, and it drifts invisibly because it still reads as a measurement. The honest move is to delete the figure and name the command that re-derives it; where a figure has to stay, it carries the date it was measured, so it reads as a measurement of that day rather than of today. |
| **KIT-ENF-5** | An address the repository gives into the kit, and the kit's own rule text, must both stay true — and a check that decides them declares what it does not cover. Three conditions become checkable once a kit publishes a generated identity index and cover blocks, and all three are cross-file, so any check for them is a script check by **KIT-ENF-2**. None is gated ([**KIT-LIM-12**](kit-stated-limits.md)): the author resolves them with the generated lookups whenever an identity or a path changes ([**KIT-CHG-4**](kit-rule-identity-and-relocation.md)), and a check may be run on demand. (a) Inbound citation. Every kit path and every prefixed rule identity named from outside the kit resolves — the path on disk, relative to the declaring file, and the identity in the generated index. Range spellings are read as ranges, and a token whose family the kit does not own is not a kit citation. (b) Anchor. A `file#section` link resolves its fragment against the target's heading set, not only the file half; an unfenced zero is a coincidence, not a guarantee, and a fragment that silently stops resolving sends the reader to the top of the file with no error anywhere. (c) Restatement. No above-threshold run of the same rule words lives in two files unless the second names the first's identity ([**KIT-INV-3**](kit-structural-invariants.md), **KIT-LIM-7**); the threshold is derived from the measured distribution of legitimate cross-file repetition, never chosen, and the corpus is the rule rows — opening it to navigation prose raises the legitimate maximum several-fold and forces the threshold into blindness. Where a copy exists because the authority is unreachable from the copy's own readers, the answer is to move the rule to a home both sides open, never to replace it with a citation the reader cannot follow ([**KIT-RCH-1**](kit-rule-reachability.md)). Stated limit: a restatement in genuinely different words, and an identity-shaped label in free prose that is not a kit citation, cannot be told apart from text alone; review holds both. |
| **KIT-ENF-6** | Whether each rule is mechanically fenced is published in the rule itself — never in a committed generated inventory. A reader must be able to tell a fenced rule from a review-held one. The answer lives where the reader already is: a fenced rule names its fence (a lint rule identity, a guard), and a rule without a named check is review-held; a declined check may name its failed admission condition in one sentence ([**ENA-GV3**](../enforcement-architecture/enforcement-admission.md), [**IV-M13**](../implementation-verification/change-acceptance-bar.md)). Three properties are obligatory. (a) No committed inventory. A kit-wide identity-to-enforcer inventory is derived on demand and never committed ([**ENA-N11**](../enforcement-architecture/enforcement-anti-patterns.md)). (b) A citation is not a fence — an identity named as a *reason* in a comment rejects nothing; only a registered, running enforcer that names the identity in what it emits counts as enforcing it, and an unregistered body fences nothing ([**FP-M25**](../false-positive/check-verification-rules.md)). (c) "Unfenced" is a routing fact, never a quality verdict — the heaviest obligations in a kit are unfenceable by definition (**KIT-LIM-3**), so an unfenced rule is never a deletion or retirement candidate on that ground ([**KIT-RET-2**](kit-rule-retirement.md)(c)). |
| **KIT-ENF-7** | A fence EXISTING does not prove its SCOPE — measure what it runs over, or do not claim the class is enforced. "Enforced" is a coverage claim, and a claim with no measurement behind it is exactly the silent gap **KIT-ENF-6** exists to remove, wearing that fence's name. The two failures it hides are the same size: a lock pinned to one hand-listed file and a lock covering the whole tree read identically, and a registration whose scope resolves to nothing at all reads as a running fence — a pattern that never matches is not an error in any linter, so the gate stays green while the lock governs zero files. Four obligations follow. (a) Scope is measured, not read off the declaration. Derive it from the resolved configuration over the real file tree, never from the scope pattern alone: where a profile disables a family for a subtree and a later profile re-enables part of it, the pattern alone reports a scope wider than the one that runs. (b) The measurement is carried into the check's own header ([**ENA-R1**](../enforcement-architecture/enforcement-authoring.md)) and into the rule that cites the check: a narrow scope is stated, so the next reader cannot mistake a pinned lock for coverage. Narrow is not a defect verdict — a single-authority file is correctly fenced in one place — it says only that "the named files are fenced", never "the class is fenced". (c) Zero measured scope is a finding. Whatever the measurement cannot reach — typically checks whose subject is decided inside their own body at run time, with no declared scope to read — is stated as unmeasured, never as narrow, because inventing precision about an unmeasured fence is the same defect one level up. (d) WHEN a fence runs is decided by its inputs, not by a fixed command list. A check that runs only in the full pre-push gate is invisible to the commit gate: the defect it decides is committed under a green commit gate and surfaces a round later. The answer is the path trigger ([**ENA-G3**](../enforcement-architecture/enforcement-authoring.md), [**ENA-PL1**](../enforcement-architecture/enforcement-gates-and-lifecycle.md)) — the check declares its input paths and runs whenever they change — never a list of commands an author has to remember. |
