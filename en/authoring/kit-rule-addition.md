# Adding a rule to the standards kit (procedure)

```kit-cover
type: normative
part-of: README.md
binds: the executable steps for adding a rule to this kit
open-when: signal:kit-rule-change, signal:standards-change
skip-when: signal:no-kit-change
owns: KIT-ADD-1, KIT-ADD-2, KIT-ADD-3, KIT-ADD-4, KIT-ADD-5, KIT-ADD-6, KIT-ADD-7, KIT-ADD-8, KIT-ADD-9, KIT-ADD-10, KIT-ADD-11, KIT-ADD-12, KIT-ADD-13
```

**Keywords:** kit change, new rule, part file, file size guidance, rule identity, cover block, index regeneration

Scope

- Included: Adding a rule to this kit — what may be written at all (**KIT-ADD-12**), choosing the owning topic and part file, keeping files readable, choosing the identity, writing the row so it reads as a definition, keeping the cover block true, regenerating the derived indexes, and the commands run before the change is committed.
- Excluded: What a rule says (domain content belongs to the topic that owns it); the shape of Markdown deliverables ([markdown-authoring.md](markdown-authoring.md)); changing, moving or deleting an existing rule, and fencing a rule mechanically ([kit-rule-change-and-enforcement.md](kit-rule-change-and-enforcement.md), banded with [kit-stated-limits.md](kit-stated-limits.md)); the structural invariants these steps exist to protect ([kit-structural-invariants.md](kit-structural-invariants.md), the KIT-INV family).
- Document type: Normative — the KIT-ADD step family.

Binding principle: The steps below are executable, not advisory: each names the command that decides it. No gate re-checks them after the fact ([**KIT-LIM-12**](kit-stated-limits.md)), so the author runs the named command and review holds the rest. Skipping a step is a bug.

Routing: an addition that is only a new hub row, a pointer, or a link is not a rule addition — it is routing text, and only the cover block and index steps below apply.

References: [README.md](README.md); [kit-structural-invariants.md](kit-structural-invariants.md) (KIT-INV); [markdown-authoring.md](markdown-authoring.md) (bare-identifier limit, deliverable rules); [kit-rule-change-and-enforcement.md](kit-rule-change-and-enforcement.md) (KIT-CHG, KIT-ENF); [kit-stated-limits.md](kit-stated-limits.md) (KIT-LIM); [**SSG-M8**](../ssot/ssot-principles-and-precedence.md) (one authority, no parallel path); [**FP-M18**](../false-positive/check-design-rules.md), [**FP-M19**](../false-positive/check-design-rules.md), [**FP-M20**](../false-positive/check-verification-rules.md); [agent-planning-procedure.md](../agent-planning/agent-planning-procedure.md) (the reading path this kit is shaped for).

## Procedure

| ID | Step |
|----|------|
| **KIT-ADD-1** | Name the problem class, then find the owning topic from the generated index — not by browsing. Read the topic table in [`en/README.md`](../README.md) and the problem-class row in [decision-matrix.md](../decision-matrix/decision-matrix.md). Do not open hub READMEs to orient yourself; the reading path forbids it and a hub carries no rule text anyway ([**KIT-INV-1**](kit-structural-invariants.md)). If no topic owns the concern, and only then, the addition is a new topic folder — the one genuine last resort. A new folder **MUST** get a hub `README.md` whose cover block says `part-of: self` in the same change, and its slug **MUST** be added to the published census group list in the same commit; the topic-index generator (**KIT-ADD-9**) fails loud on a folder with no hub or with two. |
| **KIT-ADD-2** | Pick the part file by its declared ownership, not by its name. The right file is the one whose cover block already `binds` this obligation class and whose `owns` already carries this rule family. Resolve it from the identity lookup at the kit root — `grep "^FP-M20\t" rule-id-index.tsv` (a literal TAB; the anchor is what stops `M1` matching `M12`) — or, for a family, `grep "^FP-M" rule-id-index.tsv`. A family is never spread across two files unless it was deliberately banded (**KIT-ADD-4**). |
| **KIT-ADD-3** | Look at the size before writing, as a reading signal — not a gate. `wc -c <file>` plus the size of your addition, against the guidance value in [**KIT-INV-5**](kit-structural-invariants.md). Above it, the file is a candidate for a conceptual boundary (**KIT-ADD-4**) when that boundary exists; if none exists, write the rule where its subject belongs and let the file be long. Nothing fails because a file is large, no file is ever "full", and making a rule smaller to fit is never an option. |
| **KIT-ADD-4** | A long file with a clear subject boundary is split into a sibling part file in the same folder; a rule family moves whole; every part carries the family's opening token; only the topic's entry file lists the parts. A family that reads comfortably in one file may be merged back. No rule is narrowed, hedged or dropped to make a file shorter, and moved text is unchanged ([**KIT-CHG-1**](kit-rule-identity-and-relocation.md)); a file with no subject boundary stays long. A rule never moves to another topic's folder or takes another prefix for size (**KIT-ADD-5**(b)). No band note, byte count or split history is written into a kit file. |
| **KIT-ADD-5** | Take the identity from the lookup, never by eye. `grep "^BE-M" rule-id-index.tsv` lists the family's live numbers; the next free one is the highest plus one. Three prohibitions bind. (a) A gap left by a deleted rule is never back-filled — the retired-identity ledger lists every permanently taken number ([**KIT-RET-5**](kit-rule-retirement.md)); a back-fill silently re-points every historical citation of the deleted rule at a different obligation. (b) Nothing is ever renumbered — a renumber is a rule-identity change, not a rename ([**KIT-INV-4**](kit-structural-invariants.md)). (c) No new bare identity family — a new family takes a hyphenated prefix that is unique in the kit ([**KIT-INV-7**](kit-structural-invariants.md)). |
| **KIT-ADD-6** | Write the row in a definition form, and cite every other file's rule in link + ID form. A rule is defined by a **MUST** / **MUST NOT** table row whose first cell is the bare identity. The census extractor reads exactly that shape, so the same shape used for a *citation* silently creates a second definition site: a bare identity in a row's first cell, or at the head of a list line (`- **ID** — …`), is a definition. Cite as `[SSG-M8](../ssot/ssot-principles-and-precedence.md)` instead ([**KIT-INV-3**](kit-structural-invariants.md)). |
| **KIT-ADD-7** | Let the extractor write `owns`; never hand-type it. The `owns` field **MUST** equal, as a set, what the published census extractor finds in that file. Write your best guess, then regenerate the identity lookup (**KIT-ADD-9**): it fails with `RULE_INDEX_OWNS_DISAGREEMENT` and names, per file, the definitions `owns` does not declare and the declarations with no definition — take that list as the authority. A glob (`RDS-M*`) is legal only when every matching identity in the whole kit is defined in that one file. |
| **KIT-ADD-8** | A new file declares itself completely. Six keys, in the fixed order, on line 3, no blank line inside the fence, one line per key, no markdown link in a value. `part-of` **MUST** resolve, relative to the declaring file, to a hub `README.md` that exists — a grammatically perfect path to a missing file is the defect this step exists for. `type: routing` implies `binds: nothing` and `owns: none` ([**KIT-INV-1**](kit-structural-invariants.md)). Every empty value has exactly one spelling: `nothing`, `never-by-default`, `none`; a missing key is an error, not an empty set. |
| **KIT-ADD-9** | Regenerate the derived indexes by command; never hand-edit them. The topic-index generator rewrites the committed topic region of [`en/README.md`](../README.md) and fails loud on a folder with no hub or two hubs; the lookup generator writes the identity index, the routing vocabulary and the synonym table at the kit root (`rule-id-index.tsv`, `routing-vocabulary.tsv`, `routing-synonyms.tsv`), derived on demand from the tree; its `--check` mode reports whether existing copies still match the tree. The kit itself carries no drift gate ([**KIT-LIM-12**](kit-stated-limits.md)): the topic region is regenerated in the change that adds, removes or renames a hub, the lookups are regenerated in the change that alters an identity or a cover block, and a hand-edited row is the drift the generators exist to remove. *(Kit tools: `node tools/kit-index.mjs`; `node tools/kit-lookups.mjs`, with `--check` to verify freshness.)* |
| **KIT-ADD-10** | Before the commit, run the lookup generators whenever the change added, moved or deleted an identity or edited a cover block, then the repository gate the adopting project's root agent-rule file requires. The generators are the cheapest structural check left: they fail loud on an `owns` set that disagrees with the file's definitions, an unknown shape, or a token with no phrase, and name the file. They are not a gate, and the kit ships no guard that runs in any gate ([**KIT-LIM-12**](kit-stated-limits.md)); a documentation-only commit under an exception the adopting project's change policy grants runs no gate command at all. Every kit obligation still binds and is held by review. A generator failure is fixed at its source, never by editing the generator to accept it. |
| **KIT-ADD-11** | The rule, its `owns` update, the regenerated topic region (when a hub changed) and any admitted fence land in the SAME change. A commit in which the tree and a generated artefact disagree is a parallel state, and the generators exist precisely to make that state impossible ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)); lookups regenerated from the tree in the same change (or confirmed fresh with `--check`) cannot disagree with it. If the rule's enforceable part passes the admission test, the fence is part of the same work — see [**KIT-ENF-1**](kit-rule-change-and-enforcement.md). |
| **KIT-ADD-12** | The kit receives only a genuinely new, reusable rule — written as **MUST** / **MUST NOT** and a short reason (a rule enforced by a check names it; otherwise it is review-held, **ENA-GV3**) — and it lands in the same commit as the change that settled it. A fix that applies an existing rule adds nothing to the kit. **MUST NOT** be written into the kit: how one change applied a rule, measurement logs, "measured in this project" stories beyond one sentence, dated clarification / amendment / history paragraphs, commit hashes or chains — the code, the commit message and version history carry them, and in the kit they bury the rule a search should hit first and go stale. A separate follow-up documentation commit is not used. Done means: (a) the root cause is corrected; (b) a new rule, if one was settled, sits in the relevant existing location by these steps; (c) the authority registry is current ([**SSG-R6**](../ssot/ssot-registry-rules-and-protocol.md)); (d) every part the admission test admits is fenced and proved, every other part follows ENA-GV3 ([**KIT-ENF-1**](kit-rule-change-and-enforcement.md), [**ENA-GV3**](../enforcement-architecture/enforcement-admission.md)); (e) the repository gate is green when the project's change-class policy requires it. |
| **KIT-ADD-13** | Bold marks only **MUST** / **MUST NOT** keywords and rule identities in prose. Machine-read markers and code literals retain their required syntax. A Verify cell names how a row is checked — static inspection or real-run observation — never a test to write. Bold spread over ordinary words hides the obligation a reader scans for, and a test recipe in a Verify cell instructs an artifact the adopting project's verification policy may forbid ([**M12**](../agent-planning/agent-planning-obligations.md)). |
