## **MUST**

**MRP-M1**: API request, response, and shared domain DTO types consumed by both client and server must live in the architecture-defined shared types root. [Consequence: STOP — do not ship duplicate competing DTO definitions for the same endpoint contract] [Verify: Review consumers and confirm their imports resolve to the shared authority]

**MRP-M2**: Runtime schemas used for the same payload on client and server must live under the architecture-defined shared schemas root and be imported from both sides; do not fork schema copies for the same field set. [Consequence: STOP / merge blocked if duplicate or drifted schemas are found] [Verify: Review shared imports and schema entry points]

**MRP-M3**: Shared utilities must contain only pure or environment-agnostic helpers suitable for every consuming tier; document the allowed utility surface in architecture. [Consequence: STOP — move I/O or platform-specific behavior to its owning package] [Verify: Review helper behavior and imports]

**MRP-M4**: Contract-first minimum: a change that introduces or changes a cross-boundary API contract must land the shared type or schema updates in the same merge series as the first consumer (client or server) that depends on it — no consumer merged with only ad hoc local interfaces for that contract. [Consequence: Merge rejected — review / CI fails (missing shared export or import from shared)] [Verify: Static PR diff / CI import lint]

**MRP-M5**: Breaking changes to exported shared types or schemas must surface as TypeScript errors in all dependent packages before runtime (strict compilation in CI for affected workspaces). [Consequence: Build fail in CI — must not merge with silent contract drift] [Verify: tsc / workspace build in CI]

**MRP-M6**: Client code that performs HTTP or API calls must type requests and responses using exports from the shared types and schemas roots (**MRP-M1**, **MRP-M2**) — not ad hoc parallel `interface` files in the frontend package for the same endpoint. A request whose required members a shared request schema declares is built through that schema — parse the members with it, or type the call argument as its inferred type. An inline `params` / body literal is a second, unchecked copy of the field set: a required member dropped from it type-checks and then fails on every use as a server-side validation rejection, whereas a schema-built request fails at the call site (compile error for a missing member, parse error for an empty one). The client must not guess or default a missing member to make the call succeed — the server contract stays fail-loud. When the schema transforms wire values, the outbound assembly is typed by the schema’s input type, not its parsed output type; query strings and Boolean/domain output values are not interchangeable. A type-only inference preserves the existing transport encoding without introducing a second field list or executing normalization twice. Whether the chosen view really describes the wire remains a review obligation; the type system holds required member and field-name completeness after the inference is connected. [Consequence: STOP — bug / must fix before ship; merge blocked if **MRP-M11** flags the pattern] [Verify: review shared imports and run the project’s configured type and boundary checks. Stated limit (**ENA-GV3**): where the compiler already surfaces drift loudly (a new wire field does not type-check against a local copy, **ENA-A4**) and the harm is developer friction, not data, a dedicated local-interface check is not admitted. The schema-built-request clause is likewise held by review unless a recurring defect class is measured (**ENA-A1** (a)), since the server’s own parse of the same schema rejects the omission loudly]

Nested request-metadata application (**MRP-M6**). A nested metadata object’s type is inferred from the accepting shared schema, not a local index-signature object. A validator that strips unknown keys does not prove preservation: a locally declared field may type-check, be sent and accepted, then disappear before its downstream derivation reads it. Keep the live producer fields explicit in the shared schema and derive narrower event-specific views by type projection from that same contract. The input/output distinction already required above also applies to a branded field: the outbound producer carries the schema’s wire input, while the validated brand belongs to successful parser output. Requiring the output brand on an existing raw-wire producer does not add validation; it creates a false type incompatibility and **MUST NOT** be cured with an assertion or a second local DTO. Schema-derived producer views are the stronger mechanism for explicit-field drift (**ENA-A1**(c)); no general local-interface check is admitted. Stated limit: a check would additionally need the actual key/value provenance carried by a dynamic object spread across producer and transport call sites. The producer’s static member list does not encode that provenance; a producer accepting an extensible parameter object is a live spread surface, and unsupported keys remain subject to the server’s stripping policy. Completeness and semantic preservation of that spread are review obligations, not a claim made by a green type check.

Note on **MRP-M15** (stricter requests): making a request stricter — a new required field, a tighter limit, a removed enum value, a renamed key — while old app versions are still supported **MUST** either accept the old shape with a default provably equal to that user's intent, or reject with a registered "update required" code; it **MUST NOT** answer with a generic validation `400` and **MUST NOT** use a guessed default. A generic `400` shows an installed client a failure it cannot explain or recover from, and a guessed default silently writes data the user never chose. Review-held: deciding which clients are still supported needs release history, like [**DCD-M8**](../dead-code/dead-code-rules.md).

**MRP-M7**: Document a compatibility/versioning policy for shared packages in architecture; identify which contract changes are breaking and require coordinated releases. [Consequence: STOP — document the policy before a shared contract change] [Verify: Architecture and release-policy review]

**MRP-M8**: Circular dependencies involving shared must fail the configured dependency-graph check (**MRP-M11**) or package-manager/bundler resolution; do not merge if detected. [Consequence: Merge blocked / build fail] [Verify: Run the dependency-graph or build check selected by the adopting project]

**MRP-M9**: Shared packages must not depend on deployable application packages; dependency direction is inward to shared, not outward. [Consequence: Merge blocked / build fail] [Verify: Review the workspace dependency graph]

**MRP-M10**: Production frontend bundle must not ship backend service implementation modules (controllers, repositories, raw DB clients) — verified by the same boundary tooling as **MRP-M11** plus, where available, bundle analysis on client build output documented in architecture. [Consequence: Merge blocked / release blocked — bug if found post-merge] [Verify: Static + bundle inspect (tooling per stack, documented in architecture)]

**MRP-M11**: Boundary enforcement must run in the adopting project's mandatory pre-merge gate using a documented mechanism appropriate to the workspace (for example, import-boundary linting, dependency-graph checks, workspace constraints, or compiler project references). It must encode MRP-N / MRP-M import rules and fail on illegal cross-imports rather than report warnings only. [Consequence: Merge rejected — boundary check failure] [Verify: Confirm the selected gate is required and returns failure for a prohibited edge]

**MRP-M12**: A shared runtime response schema's successful output must be assignable to its exported shared DTO under the project's strictest supported optional-property semantics. When a validator accepts an explicitly `undefined` optional property but the DTO means “key absent or concrete value,” normalize at the shared schema boundary by omitting that key; do not weaken every consumer's DTO to permit explicit `undefined`, and do not hide the mismatch with a cast. [Consequence: Runtime/schema and static-contract drift — must not ship] [Verify: strict TypeScript compile including exact optional-property semantics where supported + runtime parse of an explicit-undefined optional key]

**MRP-M13**: A closed domain enum used across client and server must have one runtime schema authority in the documented shared schemas root. Its static type must be inferred from that schema, and iterable option lists must be derived from the schema's own options API; UI label text may remain local only as an exhaustive `Record` keyed by the inferred type. [Consequence: STOP — duplicate enum values can drift between validation, persistence, API clients, and UI] [Verify: single-file AST lint rejects exact duplicate literal unions, enum arrays, option-object arrays, and parallel runtime validators outside the authority]

## **MUST NOT**

**MRP-N1**: Shared layer must not contain database queries, ORM/ODM calls, or raw SQL execution. [Consequence: Bug — must fix; merge blocked if **MRP-M11** covers shared package imports] [Verify: Review imports or use a configured forbidden-import check]

**MRP-N2**: Shared layer must not import or export UI components, UI hooks, or platform-specific UI runtime. [Consequence: Bug — must fix; merge blocked with **MRP-M11**] [Verify: Check the architecture-defined shared root for UI-runtime imports]

**MRP-N3**: Shared code must not embed secrets (API keys, database URIs, private tokens). Use the adopting project's approved secret-injection mechanism in deployable packages. [Consequence: Security bug — must not ship] [Verify: Apply the project's secret review/checks and **MRP-M11**]

**MRP-N4**: Backend or server packages must not import from frontend application roots (UI trees and screen modules, as named in architecture). [Consequence: Merge blocked / build fail] [Verify: Static boundary review and type-check paths]

**MRP-N5**: Client application packages must not import server-only implementation modules (such as service, controller, repository, or data-model implementations under the architecture-defined server root). [Consequence: Merge blocked / build fail] [Verify: Static **MRP-M11** boundary check and type-check paths]

**MRP-N6**: Client applications must not import shared-package subpaths outside the surface allowed by the architecture (for example, types, schemas, and documented pure utilities); barrels must not re-export forbidden dependencies. [Consequence: Merge blocked / bug if shipped] [Verify: Static barrel review and **MRP-M11** boundary check]

**MRP-N7**: Shared must not import from backend or frontend application packages (only apps may depend on shared). [Consequence: Merge blocked / build fail] [Verify: Static **MRP-M8** / **MRP-M9** / graph tool]

**MRP-N8**: Do not disable or make boundary checks warn-only in the adopting project's required merge gate without a documented, time-limited exception with an owner. [Consequence: Process violation — restore fail-on-error for illegal imports] [Verify: Review the configured merge gate and exception record]

**MRP-N9**: A consumer must not restate every member of a shared closed enum as a local TypeScript literal union, Zod enum, string array, option-object array, or equivalent comparison chain. A local element-type annotation binds member type, not completeness. Import the inferred type, runtime schema, or schema-derived options instead; an exhaustive label `Record` is not a second value authority because its keys are compile-time completeness consumers. [Consequence: Bug — remove the parallel authority in the same change (**SSG-M8**)] [Verify: **MRP-M13** AST enforcement + source inventory]

**MRP-M14**: The server contract exists before the client that consumes it. For a feature slice crossing the FE↔BE boundary, the endpoint, its request/response schema and the persistence shape are defined first; client code is written against a contract that already exists, not against one the author intends to write next. **MRP-M4** binds the shared type to land in the same merge series; this row binds the order inside it, and the two are not the same obligation — a slice can satisfy M4 and still have been built client-first. The reason is not tidiness: a client written first encodes the shape its author *assumed*, and every later correction to the real contract is a change to code that already works, so the assumption survives instead of the contract. Where a client is genuinely blocked on an undecided contract, the decision is taken and recorded first (the same STOP as a matrix conflict), never approximated with a placeholder shape (**SSG-M17**). [On violation: rework, not a patch — the client's assumed shape has already spread to its callers] [Verify: for each slice, the contract definition precedes the client commit in history, or the deviation is recorded with the decision that unblocked it]

**MRP-M15**: A response schema compiled into a released client binary must be forward-compatible with additive server fields. Any schema the client uses to validate a server *response* must ignore unknown keys, never reject them; a request/command payload schema stays closed, because there an unexpected key is a real error. The directory does not decide — being compiled into the binary does. A response schema hand-written inside the client application tree carries the identical failure as one in the shared root, so enforcement scoped to the shared root alone leaves the client leg of this rule unenforced. The complement also holds: a closed schema whose writer *and* reader are the same binary (device-local persistence, form input) is outside this rule and stays closed. When the same field list also backs the server's own outbound self-assertion, derive two views from one shape declaration (**SSG-M8**): a closed producer view — a permissive producer parse silently *strips* a field the server meant to publish, so it must stay closed — and a forward-compatible read view for the client. A breaking change to a compiled response contract is made only behind a versioned endpoint or an oldest-supported-version gate; while such a gate is temporary, its removal condition is recorded with the decision. A new member of a discriminated union is a breaking change, not an additive one, and permissiveness does not rescue it. Ignoring unknown *keys* is what a permissive object parse does; a union discriminated on a field's *value* rejects an unfamiliar value outright, and the whole response falls with it — so the one mitigation the rest of this rule prescribes is structurally unavailable here, while the change still reads as "just adding a case" in review. Where the server must express a new class of the same fact, prefer carrying the distinguishing information as an additive optional field on an existing arm, which old binaries drop and new ones read; the server may keep the finer classification in its own persistence and derive the wire arm from it. Take the versioned-endpoint or version-gate route only when the new class cannot be expressed that way, and record with it what a released client renders for the new value. **MRP-M14** does not cover this gap: it orders contract-before-client *inside one merge series* and says nothing about binaries already in the field — those carry their own compiled copy of the schema, and no server deploy can update it. [Consequence: STOP — every installed client on the old binary rejects the *whole* response, so a paid entitlement reads as absent and the feature looks broken to users who already paid] [Verify: single-file AST lint over every tree compiled into the client binary — the shared schemas root and the client application tree alike — rejecting a closed-object modifier inside a client-read response schema declaration, plus release-order review for response contract changes. A lint scope that names only the shared root satisfies half the rule and reads as full coverage; state the scope explicitly. What such a lint cannot decide from one file: whether a schema truly parses a server response — the predicate rests on a naming convention, so a response schema named otherwise is not seen (naming a client-read schema with `Response` is part of the rule's review), and only the closed-object *modifier* forms it enumerates are recognized (an equivalent catch-all rejection is not)]

**MRP-M15** note (a request schema the client parses before sending): A shared request schema that the client parses before sending is that client's send gate as well as the server's input gate, and every installed binary runs the copy it embeds. (a) Loosening it **MUST** ship in a client release as well as in the server deploy; where the parse runs in the first session after a store install (install-time capture, onboarding), that release **MUST** be a store build rolled out to the whole production track ([**PAN-RN-M11**](../analytics-rn/analytics-rn.md): the first session runs the embedded bundle). (b) A bound on a value the client copies verbatim from a third party (install referrer, deep-link or URL parameter) **MUST** be derived from that provider's published format, or a measured real value, with the derivation stated at the bound. Reason: one over-bound optional field fails the whole parse, so the client sends nothing and the entire record is lost, not the one field, and the loss never reaches server logs. [Example: a provider’s encrypted install referrer can exceed a guessed fixed length bound, so every install from that source is dropped on the device.]

**MRP-M15** note (a growable value set in a response): A new non-discriminant response field whose value set the server is expected to grow (a store, a provider, a channel) **MUST** be read in the client-read schema as a string mapped to the closed set plus an explicit `unknown` member, never as a closed enum, and the consumer **MUST** render `unknown` as "could not be read". Reason: a closed enum rejects the whole response on the first new value, exactly like a discriminant; designing the `unknown` member in from the first release is the only point at which it is free. [Verify: review — whether a set will grow is a product fact no single-file check can read]

**MRP-M16**: Widening a required response field to nullable is a wire-contract change, and only the released client's own gate decides whether it breaks. "The field is declared non-nullable, so the new value breaks installed binaries" is a type-level claim, not a measurement — a released binary does not re-check the declared type at runtime; it runs the gate it compiled. Prove or refute the break by reading the shipped consumer code: (a) enumerate every consumer of that field in the oldest supported client, (b) state the exact server-side condition under which the new value appears, (c) test whether that condition is biconditional with a sibling field the consumer already gates on. Where it is — the new empty value arises exactly when a sibling the consumer already refuses to proceed without is also empty — the widening is invisible to the released binary, and adding a *parallel optional field* instead would be strictly worse: the old binary keeps rendering the wrong value it renders today, and the contract gains a second name for one fact (**SSG-M8**). Where it is not biconditional, the widening is a break and **MRP-M15**'s routes (versioned endpoint or oldest-supported-version gate) apply. The measurement cuts both ways: it never licenses keeping the declared type by inventing a stand-in value for "unknown" — a fabricated number is a wrong answer, not a compatible one. [Consequence: STOP — either an installed client silently renders a fabricated value, or a compatible change is refused and the contract grows a duplicate field for one fact] [Verify: Static review of the oldest supported client's consumer code for the field plus the server condition producing the new value; record the biconditional (or its absence) with the decision. No single-file lint can decide this — the evidence spans the server derivation and a client tree at a different release]
