**Keywords:** lint rule authoring, files glob scope, syntactic prefilter, table-driven rule, rule message, rule header limits, three proofs, runtime budget, row-scoped suppression, guard authoring, path-triggered guard

Scope

- Included: The obligations on a check after it passed [**ENA-A1**](enforcement-admission.md): a syntax-tree lint rule (ENA-R) and a cross-file guard (ENA-G).
- Excluded: Whether the check should exist ([enforcement-admission.md](enforcement-admission.md)); predicate-design detail ([check-design-rules.md](../false-positive/check-design-rules.md)); the project's suppression token spelling (its root rules); gate placement ([enforcement-gates-and-lifecycle.md](enforcement-gates-and-lifecycle.md)).
- Document type: Normative — **ENA-R1**–**ENA-R8**, **ENA-G1**–**ENA-G6**.

Binding principle: An admitted check is still a cost. Each row below keeps that cost small and visible: narrow scope, cheap rejection, one table per question, a header that says what the check cannot see, and a measured budget.

References: [README.md](README.md); [**FP-M19**](../false-positive/check-design-rules.md) (empty derived set fails loud); [**FP-MS10**](../false-positive/check-verification-rules.md) (scope by decision site); [**FP-M21**](../false-positive/guard-runtime-rules.md) (a suppression reason is verified, not read); [**IV-M13**](../implementation-verification/change-acceptance-bar.md) (stated-limit shape); [**ENA-N14**](enforcement-anti-patterns.md) (option replacement).

## Writing a lint rule

| ID | Rule |
|----|------|
| **ENA-R1** | Scope the rule with file patterns to the decision site, never the whole tree by default. Bind it to the layer allowed to make the mistake ([**FP-MS10**](../false-positive/check-verification-rules.md)(a)), measure the resolved scope (files the rule actually runs on) and record the count in the header. A rule that guards one authority file but runs on every file pays whole-tree cost for a one-file question. |
| **ENA-R2** | Reject cheaply before doing anything expensive. A rule first tests a syntactic trigger — the import, callee name, member or literal its predicate needs — and returns early when the file cannot contain the pattern. Type-checker queries, scope analysis and cross-node traversal run only on nodes that survived the prefilter. A type-aware rule without such a prefilter is rejected ([**ENA-N7**](enforcement-anti-patterns.md)). The prefilter tokens state the same trigger set as the predicate and are derived from the predicate's own definition, never written as a second list: when the predicate learns a new trigger (a renamed or added callee) and the token list does not, the rule goes silently blind on exactly the files that moved to the new form. Not mechanically checked (**ENA-GV3**): comparing a free-form predicate with its token list needs the predicate's semantics, which no check has; review and the positive proof on a migrated file hold it. |
| **ENA-R3** | A family is one rule with one shared table. The rule identity names the question ("module owner boundary", "single writer field", "gate dominates effect"); each member is a row with a stable row id, its own file patterns, the forbidden surface and the authority to use. The table lives in one module the rule imports, and the rule is registered once ([**ENA-N14**](enforcement-anti-patterns.md)). Adding a member is a one-row change. Table-rule pattern: (a) a row carries its id, its kind-specific match, its own scope and owner globs, a message naming the authority (**ENA-R4**) and its normative reference; (b) the table is validated when the rule loads — unique ids, every scope and owner glob reaching a real file, a kind-specific shape check — and fails loud rather than running a dead row ([**FP-M19**](../false-positive/check-design-rules.md)); (c) the registration scope is derived from the union of the rows' scopes, so no row can sit outside the files the linter runs it on ([**FP-M37**](../false-positive/check-verification-rules.md)); (d) the index — one combined text prefilter over every row's tokens — is built once per process and each file is scanned once (**ENA-R2**); (e) one rule asks one question: a member that belongs to another table rule's question (for example a persistence write offered to a usage-boundary table) is refused at load, so two table rules never host the same surface ([**ENA-N18**](enforcement-anti-patterns.md)); (f) the shared machinery — row validation, prefilter, row-scoped allows (**ENA-R8**), and the engine that interprets a row — is one internal module used by every consumer, never a copy; while a family migrates, an old rule identity may survive only as an adapter that feeds its single row to that engine, and it is deleted when its member becomes a row; (g) a family whose question none of the general tables asks (for example "log, then raise" or "which hook position may throw") is merged into its own question-named table rule built on one shared arm engine — each row names a kind, the kind is a small predicate, and validation, prefilter, row scope and row allows come from the engine — never into a general table whose question it would bend ((e)). The arm engine is a consumer of the shared machinery in (f), not a second copy of it: it adds only the kind dispatch (row kind → predicate) and takes row validation, glob reach, the derived registration scope, the prefilter and the row-scoped allows from the same internal modules the general tables use, and its rule identities join the same table-rule list the suppression audit reads (**ENA-R8**). |
| **ENA-R4** | The message names the authority to use, and the row. "Use `<authority>` instead of `<surface>` (row `<id>`)" — never only "do not do X". A finding a reader cannot act on without opening the rule source costs review time on every hit. |
| **ENA-R5** | The rule header carries its admission record ([**ENA-A6**](enforcement-admission.md)) — the header, not a separate document, is where the next author looks. |
| **ENA-R6** | A new or changed check is verified by three proofs over real files, with no test artefact, and its coverage is measured, not read off the configuration. (a) Positive: the check flags the pre-fix code of the real defect, recovered from history and placed outside the working tree. Where the tool refuses outside input — it reports "file ignored" as a warning and still exits clean — the specimen goes in-tree at a path the gate traverses, created and removed in the same step, never over an existing file, with a clean `git status` recorded; a whole pre-fix revision is exported as its own untracked root with the changed check copied in. A stream-input channel is forbidden ([**FP-N15**](../false-positive/check-verification-rules.md)). (b) Negative: zero findings across the whole governed tree under the production configuration; a genuine finding is fixed at its source, a confirmed false positive gets an inline reasoned suppression or a narrower predicate — never a branch in the check that special-cases that finding. (c) Binding and ratchet: the check is registered at blocking severity in a block whose file pattern, expanded to its final value, matches the real path of a target file, and the gate command's path list reaches that file — both gates measured; then a temporary violation makes the gate fail, it is reverted and the diff is empty. A row added to an existing table-driven check needs (a) and (b) only; the ratchet in (c) is required when the check itself, its registration, its file pattern or the gate path list changes — the table's own load-time row validation already binds a new row. Any proof missing means the check is unverified and a coverage claim resting on it is void. When a proof misbehaves, suspect the predicate before the code. |
| **ENA-R7** | Each rule has a runtime budget. Its per-rule time from the linter's timing output over the full governed tree is written at admission ([**ENA-A5**](enforcement-admission.md)(i)) and re-measured only when its gate exceeds its budget or the rule's scope widens. Over budget: narrow the scope (**ENA-R1**), add or sharpen the prefilter (**ENA-R2**), or remove the rule — never raise the budget for one rule. |
| **ENA-R8** | A suppression carries a reason, and a table rule's suppression is row-scoped. The form properties of **ENA-G5** bind lint suppressions too; the reason is mandatory and a reasonless directive is rejected. Because a linter's disable directive silences every message of the rule on that line, a generic directive naming a table rule is forbidden (by the directive restriction below) and the table rule honours instead a row-scoped allow comment naming the row id and the reason; an allow comment naming no row, or a row that does not fire there, is itself a finding ([**ENA-N15**](enforcement-anti-patterns.md)), and so is an allow without a reason. The allow token is per rule (`<rule>-allow [ROW-ID] -- <reason>`), so an allow written for one table rule never excuses another. The directive restriction cannot live inside the table rule. Linters apply disable directives after rules report, so a block directive at the top of a file — naming the table rule, or naming no rule at all — swallows the rule's own report of that directive (measured: a rule-less next-line directive fully hid a money-row finding, and a first-line block directive swallowed the rule's "forbidden directive" report). The restriction is therefore one project-wide check whose findings no directive can silence: a directive-reading rule that rejects any disable directive naming no rule and any disable directive or inline rule configuration naming a table rule, run over the whole linted surface, plus a post-directive step that clears the suppression mark from that rule's findings and fails the file when the rule did not run there (inline configuration switched it off). Where the linter offers no such step, the check runs outside the linter as a source scan, and the kit says it gates later. Where row scoping is not available, rows that would otherwise share a line stay distinct rule identities. |

## Writing a guard

| ID | Rule |
|----|------|
| **ENA-G1** | A guard is only for a fact no single file can decide — cross-file, registry, parity between formats (data file, source, document), aggregate — and only after [**ENA-A1**](enforcement-admission.md) admitted it. Decompose the intended check into its smallest independent conditions; "it spans lines", "it needs context" or "it reads the whole file" are not reasons for a guard, because a syntax tree sees the whole file. Every single-file condition becomes a lint rule or a row, and is deleted from the guard in the same change — two mechanisms for one condition are forbidden ([**ENA-N18**](enforcement-anti-patterns.md)). A file format the production linter configuration does not parse is residue for the guard; that is read from the configuration, not assumed. |
| **ENA-G2** | A guard does not re-run the linter or resolve its configuration per file ([**ENA-N9**](enforcement-anti-patterns.md)). If it needs a lint-scope fact, it reads one resolved summary once per run, or the question moves into the linter's own configuration. |
| **ENA-G3** | A guard declares its input paths and runs only when one of them changed — or is cheap enough to run always. The gate compares the change set with the guard's declared inputs (paths, globs, and where relevant the set of tracked file extensions, so a new source class also triggers it). A guard whose answer depends on which files exist — a scope, coverage or dead-address check — declares the file set itself as an input: any added or deleted file of its source classes triggers it, even when no configuration file changed, because a deleted directory leaves a configured address dead without touching the configuration. The change set is the outgoing range against the remote mainline plus the working tree, so a pre-push run on the integration branch sees every merged branch. A guard that is within budget (**ENA-G6**) may run unconditionally; an expensive one that runs on every change regardless of its inputs is rejected. |
| **ENA-G4** | A guard does not require a committed, regenerated artefact. It derives what it needs in memory on each run. A committed generated file is legitimate only when a product or build step reads it at runtime and it changes rarely ([**ENA-N11**](enforcement-anti-patterns.md)). |
| **ENA-G5** | One central suppression authority; a suppression is a written, attributable statement at the finding's own line. The token spelling is declared once and resolved by one shared module every source-scanning check consults. (a) Placement: on, or immediately above, the line the check reports — never at file or directory scope; proved by re-running the check with the token moved away and seeing the finding return. (b) Attribution: it names the check's exact identity; an identity-less, wrong-identity or foreign-engine token suppresses nothing, and several tokens on one line are allowed only when each names its own check and reason. (c) Reason: mandatory, and the engine rejects a reasonless token. (d) Anchor one-to-one: where a check supplies the line for a file-level absence, that line belongs to that one finding; a line several findings share makes every token there blanket, so such a finding is reported without a location. (e) Lookup: the token is resolved from the finding's own line index, never by searching a range or the whole file; a helper that receives only text cannot honour it. (f) Line-attributable findings carry their line and resolve through the authority, emitting an audit record in place of the finding; a check that drops the line leaves a confirmed false positive no legal exit. (g) Growing a check: a predicate added as an arm of an existing identity inherits that identity's standing suppressions, so they are measured against the new arm first; where one would silence it, the arm takes a separate identity. An aggregate finding with no source line keeps its exceptions in the guard's own configuration, as a list that only shrinks; adding an entry to turn a genuine finding green is forbidden ([**FP-N19**](../false-positive/guard-runtime-rules.md)). Enforcement: (b) and (c) are fenced by a lint rule that parses every token through the authority, only over the trees the linter reaches; a tree outside lint scope relies on the resolver alone. Stated limit: placement, the one-to-one anchor and arm inheritance are not lint-checkable — where a finding is, and which arm a token was written for, only the producing check knows — so (a), (d) and (e) are held by the resolver's line-exact lookup and review, and (g) by the author's measurement. |
| **ENA-G6** | A guard has a runtime and memory budget, and fails loud rather than passing silently. Standalone wall time and peak memory are measured at admission and audit ([**ENA-A5**](enforcement-admission.md)(i)); guards sharing one expensive graph share one process. A derived required set that reads empty fails ([**FP-M19**](../false-positive/check-design-rules.md)); a missing external input (a sibling checkout, an environment path) fails with a named setup error, never a pass. |
