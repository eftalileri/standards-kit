# Android native configuration (theme and Activity)

```kit-cover
type: normative
part-of: README.md
binds: native theme and Activity obligations - styles.xml, the values-v34 split below targetSdk 35, MainActivity edge-to-edge, and the opt-out ban for new work
open-when: shape:frontend-heavy, signal:android-manifest, signal:android-native-theme, signal:edge-to-edge
skip-when: signal:backend-only, signal:ios-only-change
owns: AEE-M20, AEE-M21, AEE-M22, AEE-M23, AEE-M24, AEE-N20, AEE-N21
```

Scope

- Included: `res/values/styles.xml`, `android:statusBarColor`, `values-v34` split when `targetSdkVersion` ≤ 34, custom `MainActivity` `enableEdgeToEdge`, `windowOptOutEdgeToEdgeEnforcement` ban for new work.
- Excluded: Gradle version catalog outside theme / Activity — see [library-upgrade-policy.md](library-upgrade-policy.md).

Document type: Normative part — **AEE-M20**–**AEE-M24**, **AEE-N20**–**AEE-N21**.

Environment: The app-owned Android Gradle module, whether checked in or generated by the selected framework.

Binding principle: Violations are bugs — must not ship ([android-edge-to-edge.md](android-edge-to-edge.md) **AEE-C4**).

References: [README.md](README.md); [android-16-behavior.md](android-16-behavior.md) **AEE-N30**; [decision-gates.md](decision-gates.md).

## **MUST**

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **AEE-M20** | The application theme's `res/values/styles.xml` (or documented equivalent path) **MUST NOT** define `android:statusBarColor` when `compileSdkVersion` / `targetSdkVersion` is ≥ 35 (edge-to-edge default model); for API 35 and later, an opaque status bar color is not the layout strategy. If the project targets API 34 or lower, a required legacy value is isolated with an API-qualified resource (`res/values-v34/` or equivalent) and does not appear in the default `values/styles.xml` that applies to API 35+ builds. | Bug — system-bar appearance or content layout is wrong; must not ship if a single opaque bar color remains the layout strategy for API 35+. | Inspect the resolved theme resources for every supported target SDK (target ≥ 35: the attribute is absent from the default styles; target ≤ 34: it appears only in the qualified resource) and confirm that app content uses the inset rules in [safe-area-ssot.md](safe-area-ssot.md). |
| **AEE-M21** | If the application defines a custom `MainActivity` (not the default generated one only), its `onCreate` **MUST** call `enableEdgeToEdge(...)` from `androidx.activity` (or a documented framework wrapper) and **MUST NOT** call `setStatusBarColor` / `setNavigationBarColor` on the window. | Bug — must not ship. | Review the custom activity's initialization (it contains `enableEdgeToEdge` and no color setters) and verify the resulting system-bar layout on a supported device. With no custom subclass this check passes. |
| **AEE-M22** | When an application uses the unmodified native activity template supplied by its selected React Native/Expo version, do not add redundant activity code; track upstream in [library-upgrade-policy.md](library-upgrade-policy.md). Re-evaluate this assumption when upgrading the framework template. | No additional action while the template remains unchanged (informational). | Compare custom native code with the versioned upstream template when the native project is generated or upgraded; if the activity matches the template only, **AEE-M21** custom checks are skipped. |
| **AEE-M23** | Failure path: if a native theme or activity violates the edge-to-edge requirements (for example `styles.xml` still sets `android:statusBarColor` for an API 35+ target), STOP merge — resolve the native configuration before shipping dependent screen changes. | STOP until corrected or a scoped exception is approved. | **AEE-M20** verify; review the affected native resources and activity. |
| **AEE-M24** | New work **MUST NOT** add `android:windowOptOutEdgeToEdgeEnforcement="true"`; existing uses must be removed per [android-16-behavior.md](android-16-behavior.md) **AEE-N30**. If a supported target temporarily requires an opt-out, record its owner, affected scope, rationale, and removal condition; check current Android target behavior before carrying it forward. | Bug — must not ship a new or stale opt-out. | Review the manifest and the current Android behavior documentation for the target API; any remaining legacy use is tracked in the project's exception record with a removal date. |

## **MUST NOT**

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **AEE-N20** | Rely on opaque `android:statusBarColor` in the default `values/styles.xml` for `targetSdkVersion` ≥ 35. | Bug — must not ship. | **AEE-M20** verify. |
| **AEE-N21** | Call `setStatusBarColor` / `setNavigationBarColor` inside custom `MainActivity`. | Bug — must not ship. | **AEE-M21** verify. |

## Generated native tree reading — [**AEE-M20**](android-native-configuration.md) binding reading (no new obligation)

A transparent value is not an exemption. **AEE-N20** names an *opaque* color because that is the failure it describes: a bar color used as the layout strategy. **AEE-M20**'s Rule and Verify columns are unconditional and bind the attribute's presence, whatever value it carries; a Consequence column grades the severity of a breach, it never narrows the obligation. Above the edge-to-edge enforcement threshold the attribute is inert, so a transparent value is not a weaker strategy but dead configuration that reads as one — and dead configuration is what the next reader mistakes for the layout authority. Removal is still not automatic: the project **MUST** first name the runtime path that writes the equivalent value on every supported API level, including those below the threshold where the theme attribute is still honored. Where no such path exists, removing the attribute loses a real guarantee and the correct fix is the API-qualifier split **AEE-M20** already describes, not deletion.

Where the obligation binds when the native tree is generated. Under Continuous Native Generation — the native tree is produced by a prebuild step and is not tracked in version control — `values/styles.xml` is an artifact, not a source file, and two readings follow.

1. Editing the artifact does not satisfy **AEE-M20**. The generated copy is rewritten by the next prebuild, so a hand edit is lost and cannot even be committed. The obligation binds the single source authority that produces the theme: the project's own config plugin. Where the upstream framework plugin writes the system-bar color items unconditionally and the application configuration exposes no switch for them, the only conforming implementation is a step of the project's own plugin that removes those items and is registered so that it runs after the upstream step. Mod ordering is a property of the plugin system, so derive it from the mod chain and then measure it against a real prebuild output — a read of the ordering code is a hypothesis until the generated file is read back.
2. The removal step, not the artifact, is what a check can hold. Whether the plugin carries the removal step and covers every governed attribute name is decidable from that one file's syntax tree, so it belongs to a narrow check bound to the plugin, not to a repository-wide guard.

An artifact-side check is not the answer where the generated `values/styles.xml` is ignored by version control and no workflow runs a prebuild: such a check would measure nothing on every run. An environment-conditional artifact check is forbidden as well — a check that fails where it can read the artifact and passes where it cannot makes its green a coverage claim in precisely the environment with no coverage. The artifact side is measured by running the prebuild and reading the output, as part of the change that touches the plugin.
