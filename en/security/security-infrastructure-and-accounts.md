## Rules

| ID | Rule | Verify |
|----|------|--------|
| **SEC-INFRA-1** | Only a service whose purpose is to answer the public **MUST** have a public endpoint. A database, cache, queue, worker or internal administration service **MUST NOT** be reachable from the internet: it sits on the platform's private network, or, where the provider offers only public endpoints, behind an address allowlist naming each permitted source with a comment, never an open range. Where an edge (CDN, firewall, proxy) enforces security rules for a host, that host's origin **MUST** accept traffic only from the edge, so the rules cannot be bypassed by calling the origin directly. Reason: an exposed data store is reached without passing any application control, and an origin that answers everyone makes the edge optional. | Real-run observation of each platform's endpoint and allowlist listing, recorded with its date on the project's security page. A repository check is declined: exposure is console state no tracked file carries. |
| **SEC-INFRA-2** | A container image that runs in production **MUST** be referenced by an immutable content digest, and its process **MUST** run as a non-root user. Reason: a mutable tag lets an upstream change ship without a reviewed diff, and a root process turns any code-execution bug into control of the container. | Static inspection of the image definition. |
| **SEC-INFRA-3** | A DNS record **MUST** be removed or repointed in the same change that deprovisions or renames the resource it points at, and every record of a production zone **MUST** be listed with its live target at each periodic audit. Reason: a record left pointing at a released hosting name, bucket or platform app lets whoever claims that name serve content under the organisation's domain. | Real-run observation: zone export compared with the live targets. |
| **SEC-INFRA-4** | A domain that sends mail **MUST** publish a DMARC policy of `quarantine` or `reject` with an aggregate-report address that someone reads, alongside the authentication **EMP-M7** requires. A domain or subdomain that sends no mail **MUST** publish an SPF record permitting no sender and a DMARC policy of `reject`, unless a parent policy that covers it already rejects. Reason: without an enforcing policy anyone can send mail that receivers show as coming from the organisation, which is the usual carrier of credential phishing against its users. | Real-run observation of the published DNS records. |
| **SEC-INFRA-5** | Every stateful store whose content cannot be rebuilt from another store **MUST** have automated backups with a retention that matches the data-retention policy, and a restore into a non-production target **MUST** be exercised and recorded at least once a year and after any change of provider, plan or backup method. Backup copies **MUST NOT** leave the provider's controlled storage except to a location with equal access control and encryption. A store whose loss loses no data (a cache, limiter counters) states so on the project's security page instead. Reason: a backup that has never been restored is an assumption, and a copy taken outside the provider escapes every access control on the original. | Real-run observation: backup policy listing and the dated restore record. |
| **SEC-INFRA-6** | Every account that can change production — code host, hosting, database, DNS and registrar, app stores, update service, error tracker, mail and SMS provider, payment and entitlement provider — **MUST** require multi-factor authentication for every member; the registrar **MUST** hold a transfer lock on each production domain; and every API token **MUST** carry the least scope and, where the platform allows, an expiry. The list of these consoles with their members, factor state, lock state and token holders **MUST** be kept in one inventory on the project's security page and re-checked at each periodic audit. Reason: a console account is a production credential that bypasses every code review, and an unlisted console is never re-checked. | Real-run observation in each console, recorded in the inventory with its date. |
| **SEC-INFRA-7** | The application **MUST** connect to each database and cache as its own principal holding only the rights it uses on the data it owns — no administrative role, no access to another product's data — and people and tools **MUST** use separate principals from the application. Where the cache supports access-control users, each service gets its own. Reason: a leaked application connection string then exposes only what the application could already do, and an action is attributable to the principal that took it. | Real-run observation of the principal listing in each store's console or read-only API. |
| **SEC-INFRA-8** | A release signing key (store upload key, distribution certificate, update signing key) and a publish credential (store service account, update-service token) **MUST NOT** be held in the repository or its history, **MUST** each have one named holder recorded in the security-page inventory, a written recovery path that does not depend on the holder's one device (the store's key-reset procedure, an escrowed copy in a secret manager), and the least scope and an expiry where the platform allows. A key that was exposed **MUST** be replaced through the platform's reset procedure, not only removed from the tree. Reason: these credentials let their holder ship code to every user, so their loss or theft is a release-integrity incident, not a configuration slip. | Review-held against the inventory; history exposure is found by the repository's secret scanning. |
| **SEC-INFRA-9** | Where an application can receive code over the air, every update **MUST** be code-signed end to end — signed with a key held outside the repository and the update service, and verified by the installed client before it runs — wherever the update service supports signing. Until signing is enabled the gap **MUST** be a **SEC-NA-1** record naming the compensating controls, which at least are multi-factor authentication on every update-service account (**SEC-INFRA-6**) and publish rights held by a named minimal set that publishes only through the project's single publish command. Reason: an unsigned update is trusted on the strength of one account password, and whoever publishes it runs code with the signed-in user's tokens on every device. | Static inspection of the client's update configuration; the record's review date under **SEC-NA-2**. |
