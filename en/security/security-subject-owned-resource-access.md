## Subject-owned resources — delegated access

SEC-M-SUBJ-1: A delegated actor accessing another subject's resources **must** be limited to subjects that actor is authorized to serve, according to the product's documented relationship. Define the applicable owner and delegate roles, and record the access decision in one documented authority; any narrower or tiered variant (for example restricting a tier to the records it created, or limiting only writes to money fields) is a product decision recorded with that authority, and only that one decision function applies it. Apply the decision to every list, detail, create, update, and delete path of a subject-scoped endpoint. [Consequence: Security defect — IDOR class] [Verify: Static route-to-target and authorization-path inspection]

For a subject-owned entitlement, account, or ledger write, tenant membership alone is insufficient. The server **must** load the target row within the tenant, use the resolved tenant actor, and apply the same documented write rule to every public route that can change the row; a money-field gate names the work to be done as a closed operation set, so a new money writer **must** first become a member of that set. A route that creates such a row is one of those routes, including a creation nested inside another command that creates the record as a side effect: the single creation core takes the resolved actor as a required input — an optional actor turns the gate into a conditional one that every caller omitting it bypasses silently — and names the work from the value the write will apply, not from which fields the request sent. When a transaction writes the row, evaluate ownership from its transaction read; when an idempotency claim precedes the handler, reject before the claim as well. Client visibility is only an affordance. Enforcement limit: whether a route reaches a particular money or entitlement writer and whether the row was read in the transaction are cross-file/runtime facts; a single-file AST rule cannot establish the complete path. A required actor parameter makes an actor-less creation call a compile error, but whether the caller passed this request's resolved actor rather than another one is data flow. Review the route-to-writer graph and the transaction boundary. [Consequence: Critical cross-subject resource or ledger write] [Verify: route chain, target query tenant filter, actor/owner decision, alternate route, transaction read]

For a batch command that changes several subject-owned records, authorize every target before the idempotency claim or replay and re-read and authorize each target in the write transaction. A simultaneous write to a shared tenant resource is a different scope: require the tenant-wide management authority before changing that shared record. Each branch **must** keep its own permission contract. The complete route-to-branch-to-writer relationship and the transaction's fresh rows cross files, so this remains an explicit review obligation rather than a claim that a single-file lint rule proves it.

Broad financial list/read permission does not grant a subject-owned write. For a command that can settle either a child ledger or its parent ledger, authorize each selected row against its own current owner using the corresponding decision authority. Authorize against the ledger the command actually writes: an operation that writes only the parent ledger is decided by the parent's write rule for that operation, and the child subject is checked only where the child's own ledger is written. Where the product declares recording a collection exempt from a money-field gate, any delegate may record it on another's record — the actor class and tenant are still checked, and the choice between the two rules is read from the same stored parent reference in the pre-claim gate and in the write transaction. A batch with one unauthorized row is rejected before any row is written; a replay **must** repeat the same live authorization check before returning a stored success. [Consequence: Cross-subject financial mutation] [Verify: read permission and write permission are separate; enumerate all ledger writers and all selected item kinds]

SEC-M-SUBJ-2: An unauthorized attempt **must** return the documented denial status and semantic error outcome, and **must** be recorded for audit where required by policy. Do not reveal whether an unauthorized target exists. [Consequence: Security defect] [Verify: API behavior and audit-record review]

Implement the decision through one server-side authority that answers whether an actor may perform an action (update, delete) on a subject-owned record, with the action as a parameter; helper names and data models vary by project, and SEC-M-SUBJ-1 still binds. When a product decision widens the served-subject set, the decision function records it and the superseded helper is deleted rather than kept as a plausibly named alternative ([DCD-M9](../dead-code/dead-code-rules.md)).

## Subject actors — own-record scope

SEC-M-SUBJ-4: A subject actor's row scope **MUST** be keyed by the caller's own subject-record identities from the single resolver of those identities, and **MUST NOT** compare the caller's account id with a delegate-owned field (creator, assignee, seller). Reason: one account can carry a delegate history in the same tenant — a demoted delegate, a recycled identity — and that comparison returns the records it created for other subjects. An empty identity set matches nothing. [Consequence: Bug — cross-subject read] [Verify: review of every scope branch that admits the subject class]

## Skippable gates — the evidence contract

SEC-M-SUBJ-3: A gate the caller may SKIP **must** be skipped by handing over the gate's EVIDENCE, never a caller's assertion. A batch caller that legitimately proved a subject once will want the per-item gate to stand down; expressing that as a boolean (`skipCheck: true`) hands the gate's own question to the caller and keeps no trace of what was actually proved. Three consequences follow. (a) A caller that never ran the gate passes the same flag, so the protection is available to precisely the code that did not earn it. (b) The flag has no scope, so the proved set and the written subject may drift apart — the batch verified one set and the loop writes another — and nothing anywhere compares them. (c) Review cannot distinguish the two, because both read as `true`. The obligation: the skip path carries the verification's result as data — which tenant, which subject identifiers — and the consumer, before acting, asserts that this evidence covers *this* tenant and *this* subject, rejecting when it does not. The consumer thereby keeps answering its own question ([SSoT](../ssot/ssot-principles-and-precedence.md) SSG-M8); it merely stops re-reading. This is the skip-path complement to SEC-M-ZT-6(g) in [security-actor-class-gates.md](security-actor-class-gates.md): there the gate's result **must** become the operation's target, here it **must** become the *successor* gate's input. Where the evidence value can be constructed by any module, the type system closes the remainder that a check cannot. Brand the evidence with a symbol the authority does not export, so no other module can produce a value of that type: this answers *who may mint a proof* exhaustively and at compile time, where a lint rule answers it only for the production shapes it was taught to recognise. Check reach: a brand proves where a proof was minted, never that the read behind it was correctly scoped; that the minting authority's input came from a tenant-filtered query stays a contract written at the mint site. [Consequence: Critical security bug — cross-tenant write on the skip path] [Verify: Enumerate every skip site; confirm each passes evidence whose coverage the consumer asserts, and that the evidence type cannot be constructed outside its authority]
