## Rate limiting

SEC-M-RL-1: Backend **must** enable global rate limiting; authenticated traffic keyed by stable user id where available; public endpoints keyed by IP (and User-Agent where policy says); health endpoints exempt per documented list. A token-guarded infrastructure endpoint (a metrics scrape) **may** sit on that list only when its token check is constant-time with no store I/O and an absent or under-strength token closes it (the shared standing-secret byte floor, [SEC-M-JWT-5](security-cryptography.md) (a)) — a limiter in front costs each flooded request more than that rejection, and only the token's strength bounds guesses there. An address-keyed limiter whose key reads no body **must** be mounted before every body parser it covers, path-specific raw-body/webhook parsers included — otherwise a rejected request still costs a full read and synchronous parse, so the limit bounds nothing an unauthenticated flood spends. [Consequence: Bug — **must** fix] [Verify: Middleware config review]

Enforcement of SEC-M-RL-1: review-held; a text check that the entrypoint mentions a limiter was retired because it passed on the limiter's import alone and the class has no recurring defect outside the one mount surface ([ENA-A1](../enforcement-architecture/enforcement-admission.md)(a), [ENA-A2](../enforcement-architecture/enforcement-admission.md)).

SEC-S-RL-2: SHOULD: body size limits, slow-read / timeout limits, stricter limits on heavy routes — values in security note (TM-6 hardening). A limiter's budget **MUST** be sized against its window algorithm's worst case: a fixed window admits up to twice its budget within one window length straddling the reset, so a budget whose harm is a short burst **MUST** use a sliding-window or token-bucket store or be sized at half, and instantaneous capacity **MUST** be bounded by a concurrency cap, never by a request-rate window — the boundary burst is invisible in a config review. [Consequence: Roadmap item; a burst budget sized as if the window were sliding is a bug] [Verify: Architecture note; limiter config review]

SEC-M-RL-3: An identity-keyed limiter **must** be mounted where the identity actually exists, and a shared-network (IP) bucket **must** never be the only budget for a per-target protection. (a) *Mount-order proof:* a limiter keyed on `request.user` (or any authenticated identity) is only real if it runs after the authentication middleware. A limiter mounted application-wide before route/auth middleware always sees an empty identity, so its "authenticated" branch is dead code and every request silently falls into the IP bucket — the key generator **must not** carry a branch its mount point can never reach (SSG-M8). (b) *Shared-network reality:* behind carrier-grade NAT / office NAT, many unrelated users present the same public IP, and mobile clients of the same app present near-identical User-Agents; an IP(+UA) bucket is therefore a coarse volumetric shield only. Sizing it as if it were per-user is an availability defect — the first user exhausts the window and every other user on that network is locked out. (c) *Per-target budgets:* protections whose real subject is a specific target — OTP/SMS send (the recipient number), verification attempts, login brute force (the account) — **must** carry a budget keyed on that target, with the IP bucket retained as the secondary ceiling. (d) *Client-supplied keys are never sole authority:* a key read from the request body (phone, installation id) can be rotated by an attacker, so it may only add a layer on top of the IP ceiling; it **must** be normalized to a bounded, charset-restricted segment before entering the store key, and fall back to the IP key when absent. Server-verified identity (a validated token subject) is not client-supplied and may stand alone. (e) *Revocation-before-budget:* when identity validity depends on mutable server authority (session generation, account activity, membership, or equivalent), that current authority **must** be checked before the identity-keyed bucket is consumed. Signature-valid but revoked credentials **must** terminate before they can spend a legitimate principal's quota; otherwise an old long-lived token becomes an account-specific denial-of-service capability. [Consequence: Availability bug — legitimate users locked out of login/OTP or their authenticated account; or bypassable per-target protection] [Verify: mount-order trace from app bootstrap through current server-side identity/revocation validation to the limiter; stale/revoked credential terminates before limiter invocation; key-generator branch reachability; per-target bucket present on OTP/login routes]

(f) of SEC-M-RL-3 — where the request SPENDS MONEY and the caller is authenticated, the recipient is not the only subject: the SPENDER **must** be bounded too. A target-keyed bucket under (c) answers *"is this recipient being bombed"*. On an endpoint where each accepted request triggers a billed external command — an SMS or voice code, a paid lookup, a metered send — it does not answer *"how much can one caller spend"*, because the target is a request-body field the caller chooses freely: rotating it leaves every target bucket empty while the bill grows, and (d) already forbids treating a client-supplied key as the sole authority. The IP ceiling cannot stand in either (b). So a cost-bearing endpoint that runs behind authentication **MUST** carry a budget keyed on the server-verified identity, and an application-wide authenticated ceiling does not discharge it — that bucket is shared with every other call the app makes, so it is sized for traffic, not for spend. The narrow budget rides on top of the coarse one (a), and the two are orthogonal: the target bucket protects one recipient from many accounts, the identity bucket protects the bill from one account.

(g) — a pre-authentication EXISTENCE ORACLE needs its own source budget. An unauthenticated "does this identifier exist" endpoint is enumerable: the caller rotates the identifier, so a (c) target bucket opens fresh per request, and an IP bucket shared by many routes (b) admits thousands of probes a day. Where the product keeps such a surface, it **MUST** carry a source-keyed budget used by no other route, with a short and a daily window, mounted before the shared buckets so rejected probes do not spend neighbours' login budget; values come from measured legitimate traffic, and its rejection metric is the enumeration signal.

(h) — a GUESS BUDGET is decided in the same atomic step as the guess. Where an application-owned counter caps how many times a secret (a one-time code, a fixed accepted code) may be tried, the "budget left?" check and the comparison **MUST** be one indivisible step in the shared store: either the comparison runs inside the store's atomic script that also counts the failure and locks at the threshold, or a slot is reserved atomically before comparing and refunded only on success. Reading the counter in one command, comparing in application code and counting the failure in a later command **MUST NOT** be used: every concurrent request that read the pre-lock value gets a full guess, so the cap multiplies by the attacker's parallelism. A fixed accepted secret that bypasses a provider's attempt cap **MUST** carry such a budget of its own. When the store cannot confirm the budget, the guess is refused (fail closed) — this counter is the guess limit itself, not the ordinary request limiter that (RDS-M8) fails open. When the guess arrives in a provider delivery that is redelivered after a retryable failure, the budget **MUST** be keyed by the provider's message id inside the same atomic step (the same message holds its one slot), never re-counted per delivery: otherwise an outage the sender does not control spends their budget once per redelivery.

(i) — a SPEND CEILING on an unauthenticated billed command. Where an unauthenticated surface belongs to one tenant (a public page reached by that tenant's own key) and an accepted request triggers a billed external command, that tenant **MUST** be bounded as the spender under (f), next to the global and per-destination ceilings. When the store cannot confirm a spend ceiling, the billed command **MUST** be refused through a registered error with an alarm (fail closed) while non-billed paths continue, because failing open removes the only bound on money; this differs from the ordinary request limiter that (RDS-M8) fails open.

(j) — a FIRST-PARTY SERVER CALLER pools every end user behind its own address. Where the application's own server (server-side rendering, a same-origin route that holds a cookie) calls the backend on behalf of visitors, the address the backend resolves is that server's egress, and any client address it forwards is caller-controlled (SEC-M-RL-5). Budgets on those endpoints **MUST** key on the server-verified caller plus the request's target (resource key, intent id, token hash), never on the address; an application-wide address bucket in front of them **MUST** either be sized for the aggregate first-party volume or key a signature-verified first-party call on its caller identity. Why: keyed by address, one busy page exhausts the bucket and every visitor is refused at once.

(k) — a DAILY SPEND CEILING on every billed message send. Per-source and per-target buckets bound one caller and one recipient; neither bounds the bill when a caller rotates both (SMS pumping into expensive destinations). Every billed send **MUST** therefore reserve a slot in a global and a per-destination-country daily ceiling held in the shared store, through one authority that every send path calls before the provider command: the check and the increment of both scopes are one atomic step (a full scope increments nothing), the destination is read from the address itself — never from a request field — and a refusal sends nothing. The refusal is a registered expected error; the first refusal per scope and window raises exactly one alarm while every refusal stays counted, because a ceiling nobody hears about silently stops sign-in. When the store cannot confirm the slot the send is refused (fail closed), as under (i). Reason: without it the bill has no upper bound per day.

(l) — fire-and-forget BEHAVIOUR TELEMETRY spends its own per-user bucket. An authenticated telemetry ingest (screen views, form events) **MUST NOT** share the per-user API bucket; it **MUST** be keyed on the same verified identity, behind the same session gates, in its own store namespace with its own ceiling. Reason: telemetry volume grows with how actively the user works, so the busiest legitimate user exhausts the shared bucket with their own telemetry and their business writes are rejected.

(m) — a SHARED PROVIDER QUOTA is a cross-tenant resource. A request path whose purpose is a provider call the client can repeat at will (a verification, registration or lookup) against a provider whose quota every tenant shares (one key, project or server address for all tenants), and that does not read through a shared cache, **MUST** carry a per-actor bucket keyed on the server-verified identity, mounted after the gate that admits the actor to the call, and a global budget in the shared store, one bucket for every caller on every instance, sized below the provider quota for the calls one request can make under the window's worst case (SEC-S-RL-2). Both **MUST** run before the request's durable side effects (idempotency claim, cache invalidation, the provider call), so a refusal changes nothing. Quota exhaustion — the global budget refusing or the provider answering with its rate-limit status — **MUST NOT** revoke an entitlement already granted: the entitlement authority never derives a revocation or "no entitlement" from a refusal — it serves its cached state while that is valid and otherwise fails loud as provider-unavailable — and a client that receives the refusal waits out its `Retry-After` before repeating the call, never repeats it at once. Reason: the generic per-actor ceiling is sized for traffic, so a few looping accounts drain a quota that every tenant's entitlement reads depend on. A path whose per-actor ceiling across every plausible actor stays far below the quota is outside this clause.

Enforcement of SEC-M-RL-1 and SEC-M-RL-3: review-held, with a route census against (a)–(m) as the verification; a route-level rate-limit declaration in the boot route walk was declined — address coverage fails [ENA-A1](../enforcement-architecture/enforcement-admission.md)(a) (no route outside the documented exempt list has been found off a limited prefix), identity coverage fails (c) (the identity bucket runs inside the authentication gate itself, so no authenticated route can lack it), and the class-specific budgets that do recur fail (d)(iv) because the class is what the handler spends, which no stack shape shows, so the check would rest on a per-route self-declaration that the very omission defeats.

SEC-M-RL-4: A rate-limit rejection is an ordinary registered error and **must** leave through the single error boundary. The limiter's exceeded-handler **must not** write its own status/JSON envelope; it raises the registered code and lets the boundary derive status, category, user message, correlation id, and retry hint — see [error policy](../error-policy/transport-i18n-and-classification-rules.md) M28. The limiter **must** also emit a standard retry hint header (`Retry-After` or the documented equivalent) and route its own store/configuration failures to the project logger, never to `console`. [Consequence: Bug — expected throttling reported as a crash; client cannot tell the user how long to wait] [Verify: limiter config review; 429 response contains the envelope fields; store-failure log path]

## Client-address authority

SEC-M-RL-5: Every IP-keyed control reads the client address from exactly one derivation, and the proxy trust boundary behind it is a measured decision, not a default. (a) *One authority:* a single function derives the client address from the framework's trust-boundary-resolved value; limiter key generators, audit logs, geolocation and outbound attribution all call it. Reading the socket peer, the forwarded-address headers (`X-Forwarded-For`, `X-Real-IP`, CDN client-address headers) or the framework's resolved field anywhere else is forbidden — a "fall back to the socket" branch silently counts the proxy as the client, and two derivations drift apart (SSG-M8). (b) *Trust boundary from measurement:* the trusted-proxy list names every hop the hosting edge uses to reach the process, in every address family the process accepts — an IPv4 range does not cover the same platform's IPv6 private-network proxies. It is derived from the platform's documentation and a production observation of the socket peer and the forwarded chain. An uncovered hop resolves the proxy's address as the client, so unrelated clients pool into one bucket and a client whose requests alternate between covered and uncovered paths is counted in two — every IP budget is silently multiplied or shared. Trust only the platform's proxy hops, never "trust everything": anything left of the trusted hops is caller-controlled. A platform edge may append its own public address after the client (`client, edge-node`); a range-only trust list then resolves the edge node as the client, pooling users per edge node and counting one user in as many buckets as there are nodes. Where the edge's public addresses are undocumented and rotate, the boundary is expressed by position: the socket hop **must** be in the platform's proxy range, and only then is the one measured edge hop trusted; the platform's single-value client header (such as `X-Real-IP`) is the runtime cross-check. (c) *The collapse is loud:* the authority classifies each distinct chain shape (socket-peer class, forwarded-hop classes, resolved class) and logs it once per process — never a client address, only infrastructure prefixes; in production a resolved address in a non-public class, or one that disagrees with the platform's client header, is a WARN naming the hop shape. (d) *Proof after any boundary change:* one IP-keyed limiter blocks at exactly its configured budget in production, from one client. [Consequence: Bug — IP budgets multiplied or pooled across users; audit/geolocation attribute the proxy] [Verify: single-authority check where the adopting project has one; boundary list cites its measurement; post-deploy exact-budget probe]

Enforcement limit of SEC-M-RL-5: (a) can be fenced by a single-file check, where the adopting project has one, that forbids resolved-address member reads on request-shaped objects, socket-peer reads and forwarded-address header names outside the authority file. The entrypoint's trust setting (one framework trust-proxy setting bound to the authority's boundary policy constant) has no shape lock: one would pin one file's internal shape (ENA-N4, ENA-A1(d)), and a blanket trust-everything setting would let any caller choose its own rate-limit identity, in the one file that owns the application object ([ENA-A2](../enforcement-architecture/enforcement-admission.md)). (b) and (d) are runtime facts of the hosting platform that no checkout contains, so they are proven by measurement; (c) is the runtime signal that makes an uncovered hop visible instead of silent. Use the enforcement mechanism the adopting project documents, and record its actual scope and limits.
