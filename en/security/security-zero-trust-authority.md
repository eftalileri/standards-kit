## Zero trust — server authority

SEC-M-ZT-1: Protected APIs **must** validate identity and authorization on the server; **must not** trust client-supplied role, isAdmin, or query flags as authority. [Consequence: Bug — privilege escalation class] [Verify: Authz review]

SEC-M-ZT-1 note (provider-backed possession proof): When an authentication flow delegates issuance and verification to an external provider, accept only the provider's runtime response as proof for the exact subject and submitted code. Every subject **must** use the canonical provider send/check path. Hard-coded subjects or codes, local allowlists, fake provider identifiers, environment/test-account labels, and any branch that synthesizes issuance or successful verification without the provider call are forbidden in every deployable build. [Consequence: Critical authentication bypass] [Verify: Full send/check control-flow review]

SEC-M-ZT-1 note (server-issued one-time code): When the server itself issues the code and a provider only delivers it, exactly one server authority **MUST** own generation, storage, check and consumption: the code comes from a CSPRNG; only a keyed hash of it is stored, in shared state with an explicit lifetime; check and consumption are one atomic step; wrong tries are capped per code, after which the code is dead; the record is keyed by purpose as well as subject, so one flow's code never completes another; a new send replaces the previous code; and a store outage refuses both the send and the check. A delivery channel **MUST NOT** check a code, and a second channel is an adapter of the same authority, never a second checker — two checkers are two proof paths with different fences. [Consequence: Critical authentication bypass — replayable, cross-flow or unbounded-guess code] [Verify: Full issue/check control-flow review]

SEC-M-ZT-1 note (store-review possession exception — owner decision only): A product whose only sign-in factor is a provider-delivered one-time code cannot be reviewed by an app store whose reviewers receive no message on the subject they are given, so at most two named fixed-code subjects MAY be exempted from the possession proof above (provider-checked or server-issued): one store-review subject and one internal-test subject. The internal-test subject **MUST** be a different subject from the store-review one and **MUST NOT** be given to store reviewers, and internal testing **MUST NOT** use the store-review subject — where an account holds one session at a time, internal sign-ins on the review subject evict the reviewer mid-review and raise session-takeover alarms that look like an attack. Each subject is exempted ONLY on an explicit, recorded owner decision — never on an agent's or a plan's initiative — and ONLY while every bound holds for that subject: (a) the subject and its accepted code come from runtime configuration, never from literals in the source tree, so the tree carries no gate and the exemption closes without a deploy; (b) a half-configured state opens nothing, and each subject's pair is independent (removing one pair closes only that subject); (c) the scope is the named subjects — every other subject, and a subject's wrong code (including the other subject's code), still take the normal proof path unchanged; configuration naming one subject for both fails parsing; (d) both formats are validated where configuration is parsed, fail-fast, so a typo cannot silently half-open it; (e) the code comparison is constant-time, because the accepted value is long-lived; (f) one named interpreter is consumed by both the issuance and the check path (SSG-M8) — a second literal comparison is a parallel proof path; (g) an issuance identifier returned without a provider call **MUST NOT** imitate the provider's identifier format, so logs and support review stay able to tell the two apart; (h) every use is logged at WARN naming which subject was used, and the accepted code is written to no field; (i) each subject carries its own wrong-code budget in shared state, decided atomically with the comparison ([SEC-M-RL-3](security-rate-limiting.md) (h)) — the normal path's per-code attempt cap does not apply to a fixed accepted code, so without this budget a short accepted code is guessable without limit. This does not reopen the note above: an exemption missing any bound, or carrying no owner record, IS that banned class and is deleted on sight; and removing a recorded one needs the authority that created it, so the record is what stops the next reader from reading a deliberate decision as a defect. It is also not the environment-flag failure below: the predicate is *"is this exact subject one of the recorded fixed-code subjects"*, evaluated identically in every environment, and configuration supplies the subject's identity — not a deployment label that decides whether the check runs at all. [Consequence: Critical authentication bypass when any bound is missing] [Verify: Full issuance/check control-flow review + configuration parse review]

SEC-M-ZT-1 note (no identity precondition is not a hole): An endpoint consuming a single-use possession proof before any identity exists (sign-up code verification) cannot take an identity gate — the caller has no account yet. Legitimate while three properties hold, written at the route declaration. (a) The control is a budget, not an identity: attempts are capped per target subject as well as per source, plus a replay fence: guessing is bounded by the thing attacked, not the attacker. (b) The openness is declared with its reason, else it looks like a forgotten gate. (c) Sibling flows do not consume each other's proof — each reaches the provider by its own path. A review finding closes as a recorded exception, not as work: write the three properties and the deciding authority at the registry row, or a bare "review" reads as debt. [Consequence: Bug both ways — forgotten gate read as design, or deliberate endpoint re-litigated] [Verify: declaration reason; per-target + per-source budgets; replay fence; two proof paths traced separately]

SEC-M-ZT-1 note (a closed sign-in closes the session): Every account-state predicate the sign-in authority requires (active, not suspended, not deleted) is also a predicate of the per-request session gate, read from the same authority with the same polarity — a record whose flag is anything but the value sign-in accepts (false, missing, wrong type) is closed. Otherwise a long-lived credential minted before the state changed keeps passing a gate the account can no longer enter (SSG-M8: one authority, two answers). Three bounds. (a) Distinct state, same client contract: the gate names the closed state separately from "record absent" and "no session anchor" (SSG-M19) and checks it before the session-anchor comparison, but answers with the credential-invalid code clients already treat as sign-out — a new code that shipped clients do not act on strands them in a 401 loop; the distinction travels as a diagnostic cause at WARN, not a crash report. (b) Every writer that closes the flag invalidates the session accelerator after commit ([RDS-M6](../redis/redis-connection-keys-and-authority.md)(b), [RDS-M17](../redis/redis-degraded-mode-and-invalidation-ordering.md)); widening the cached state bumps the envelope's semantic version, never the key text (RDS-M3). (c) Revoke by rotating, never by clearing: where absence of the session anchor means "not enforced" (a migration-safe branch), a deactivation that **must not** let reactivation resurrect old credentials rotates the anchor to a fresh unguessable value; clearing it opens the gate to every credential. Enforcement: the gate's closed union with an exhaustive `never` default makes an unnamed state a compile error; (b)'s presence is a single-file lint rule (write sets the flag to anything but the accepted literal, file lacks the invalidator). Check reach: that the invalidation targets the same identity after commit, computed/spread update documents, and document-instance writes where no type information exists are not decidable from one file's syntax tree; (c) is review-only because "rotate vs clear" depends on the branch semantics of another file. [Consequence: Critical security bug — deactivated account keeps an authenticated session] [Verify: gate union + projection review; lint rule; review of every deactivation writer]

SEC-M-ZT-1 note (a stored contact address is not possession proof): A stored email address or other contact handle **MUST NOT** serve as proof of identity — account recovery, sign-in, or any flow that hands an account to whoever controls that channel — unless possession of the address was proven by a single-use code delivered to it. The proof is a marker with one writer, the possession-proving flow, written in the same write as the address it proves; any other path that sets or changes the address leaves it unproven, and a copy of the whole record keeps address and marker together. Records written before the marker existed count as unproven. An unproven address answers a recovery lookup exactly like an unknown one, so the distinction leaks nothing, and re-proving the same address is allowed. Reason: an address typed during sign-up is the user's claim, not evidence; trusting it hands the account to whoever owns that mailbox. [Consequence: Bug — account takeover through a mistyped or foreign address] [Verify: review — the trust decision has one authority and every identity-proof consumer calls it]

SEC-M-ZT-1 note (a proven claim displaces an unproven holder): When a subject proves possession of a contact address that another account holds unproven, the proof **MUST** win: the address is removed from the unproven holder in the same unit of work that binds it to the prover, and the holder is told through a channel it has proven — never the removed address, which now reaches the prover — by a durable notice written in that same unit, so a lost prompt message cannot leave the removal unexplained. An address uniqueness constraint **MUST NOT** let an unproven holder block the proven owner — at registration or at address change. A proven holder is never displaced this way. An unproven claim — an address typed at sign-up — **MUST NOT** displace anyone and **MUST NOT** fail the sign-up: the account is created without the address, with the same answer whether the holder proved it or not, so the response never reveals another account's proof state; the claimant proves the address later through the possession-proving flow. Reason: an unproven address is only a claim, and letting it lock out the mailbox's real owner turns a typo into a denial of the owner's own account. [Consequence: Bug — the real owner cannot verify or recover with their own address] [Verify: review — the displacement is one transactional write in the address-proof authority]

SEC-M-ZT-1 note (subject-sent message proves its sender only): Where possession is proven by a message the subject sends to the platform (a prefilled chat message carrying a code), the proven identifier **MUST** be the sender the provider asserts on the signature-verified callback; the code only binds that message to one pending intent, is single use and consumed on the first match. A number the client typed or the page holds **MUST NOT** be the identifier marked verified, nor be compared with the sender to decide it — a typed number is a claim, and a sender who forwards the code proves only their own number. [Consequence: Critical — an identity or resource bound to a number nobody proved] [Verify: review the callback handler — the verified identifier is read from the authenticated provider payload, never from intent or request fields.]

SEC-M-ZT-2: When an untrusted client command writes a backend projection of state owned by an external provider (for example purchase, entitlement, product, transaction, or environment state), a client-supplied provider identifier is intent only, never authority. The server **MUST** obtain fresh runtime-validated provider evidence, exact-match the intent to the corresponding provider-owned item, derive the write value only from that matched item, and reject non-production/ambiguous environment evidence in production before access or user-initiated writes. A separately authenticated, runtime-validated provider webhook is a distinct provider-owned evidence path and need not repeat the client-command fresh-read gate, but it **MUST** enforce the same runtime environment policy before any access, trial, reward, lifecycle, or durable projection side effect. Provider environment provenance **MUST** be preserved when a reusable credential/reference is stored, and current runtime compatibility **MUST** be asserted again before every later live provider operation; a historical acceptance does not authorize a reference forever. Authenticated unknown event kinds are audit-only and **MUST NOT** feed known-event projections or credentials. Apply [error policy](../error-policy/provider-contract-and-webhook-errors.md) M20–M22 and [SSoT](../ssot/ssot-must-provider-projection.md) SSG-M9/SSG-M11. [Consequence: Bug — forged/stale purchase projection, sandbox reference, or unknown event accepted for production side effects; **must not** ship] [Verify: Runtime gates at evidence ingest and later provider calls + review; use the enforcement mechanism the adopting project documents for direct raw-intent-to-writer, missing environment-gate, and unknown-event-ingest flows, and record its actual scope and limits]

SEC-M-ZT-2 note (a provider-signed object is trusted by its channel): A provider-signed object (for example a JWS transaction) inside the body of a response the server itself fetched over TLS from the provider's API with its own credential is provider evidence by that channel; it MAY be decoded and runtime-validated without verifying the embedded signature, so no verification dependency is owed for it. The same object arriving by any other channel — a client request, a forwarded or stored copy, a webhook body whose transport is not itself authenticated — **MUST** have its signature verified to the provider's published root before it feeds any projection. The decoder that skips verification therefore **MUST** stay private to the pull client and **MUST NOT** be exported. Reason: reused on an inbound path, an unverified decoder accepts a forged purchase.
