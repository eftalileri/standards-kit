# Security — what may serve as an authorization predicate (SEC-M-ZT-1 applications)

```kit-cover
type: normative
part-of: README.md
binds: the shapes in which a server-side authorization predicate is derived from something that cannot carry it -- a runtime capability object with no issuer-owned provenance, a scoped role gated by allowlist instead of deny-by-default, a scope-resolving helper that narrows a view instead of deciding entry, a deployment-environment flag standing in for an authorization fact, an internal-only command flag accepted by the public request schema, one actor's persisted model-prompt history reaching another actor, and a withheld feature (dark launch, pilot, kill switch) hidden by the client instead of refused by the server

skip-when: signal:no-auth-surface, signal:client-only
owns: none
```

Part of: [Security — zero trust: server authority and provider evidence](security-zero-trust-authority.md). SEC-M-ZT-1 itself — the obligation to validate identity and authorization on the server and never to trust a client-supplied role or flag — is defined there and is not restated here; this file carries only its applications, so the rule keeps exactly one definition site ([KIT-INV-3](../authoring/kit-structural-invariants.md)).

Why these are a file and not a paragraph: each note below describes a defect that survives review because the thing standing in for the predicate looks like an ordinary implementation detail — an internal object, a role label, a helper that returns a filter, a deployment flag. They are the cases in which citing SEC-M-ZT-1 alone is not enough to recognise the defect, which is why they are written out rather than summarised.

References: [Security — zero trust: server authority and provider evidence](security-zero-trust-authority.md) (SEC-M-ZT-1 and its possession-proof notes, SEC-M-ZT-2); [security-actor-class-gates.md](security-actor-class-gates.md) (SEC-M-ZT-6 — the actor-class gate the scope-resolving helper note is the entry-side half of); [security-tenant-scope-gates.md](security-tenant-scope-gates.md) (SEC-M-ZT-3, SEC-M-ZT-5, SEC-M-ZT-8); [security-global-identity-lookup.md](security-global-identity-lookup.md) (SEC-M-ZT-4); [security-backend-controls.md](security-backend-controls.md) (RBAC and the failure path); [ssot-principles-and-precedence.md](../ssot/ssot-principles-and-precedence.md) (SSG-M8 — one authority per question); [kit-structural-invariants.md](../authoring/kit-structural-invariants.md) (KIT-INV-8 — naming the enforcing check).

## Applications of SEC-M-ZT-1

SEC-M-ZT-1 note (runtime capability provenance): A server-internal object that authorizes a protected terminal effect **MUST** carry issuer-owned runtime identity that an outside module cannot mint, copy, serialize, or recover from a leaked object's fields. A TypeScript interface, private/unique-symbol brand, cast prohibition, object shape, identifier name, or caller-supplied property is compile-time/documentary evidence only and **MUST NOT** be the runtime acceptance predicate. The issuer keeps nominal membership in module-private state, freezes the public carrier, exposes no identity factory/serializer, and the terminal seam validates membership before reading carrier fields. A transaction-bound capability additionally binds the exact tenant, session, epoch/version, expiry and current retry/transaction attempt; reusing the same session object **MUST NOT** let a capability from an aborted, committed, or superseded attempt pass. Unknown runtime identity or unavailable attempt evidence fails loud; no structural compatibility fallback is permitted. [Consequence: Critical authorization bypass — cast/object-literal/clone or retry leakage mints a valid-looking terminal authority] [Verify: Issuer/terminal source review plus a real-source static ratchet proving structural tokens and non-canonical writers are rejected]

SEC-M-ZT-1 note (scoped role — deny-by-default + migration-safe): When a role is granted access to only a SUBSET of an already-authenticated surface (e.g. a read-only / limited admin role that may see one section but not the rest), enforce the scope on the server as a single centralized gate that ALLOWLISTS the permitted surface and DENIES everything else by default — so a newly added endpoint is automatically closed to the scoped role unless it is explicitly opened (never a per-route "remember to add the guard" blocklist). Client-side nav/route hiding is UX only, never the boundary (a hidden link's API **must** still 403). The converse also binds: the client's role-scope mirror **MUST** be a subset of the server gate at the granularity it exposes — a page, tab or control shown to a role whose request the gate denies for that role (a page whose data 403s, a write button on a read-only role) is a defect, fixed by hiding it in the single client access authority, never by widening the gate. When the allowlist is a path prefix, a route's path is its access decision: mounting under the prefix opens the route to the role, mounting outside closes it; choose the path from the intended access, and a route that replaces one the role reads today keeps that role's access unless a recorded decision removes it. Roll the new role out migration-safe: restrict ONLY the explicit new role value; treat an absent/legacy role claim as unrestricted, so already-issued tokens are not mass-locked-out. A source-level check can help ensure the gate remains in each route chain; where the codebase has no such check, review route registration and handler coverage whenever routes change (removal or misorder is a privilege-leak regression). [Consequence: Bug — privilege escalation / scope-leak class] [Verify: Authz review + mount guard]

SEC-M-ZT-1 note (scope-resolving helper — ask "who may enter", never "whom do I narrow"): A helper that computes how far an actor's view is narrowed (an owner/team scope resolver, a row-filter builder, a "which subset may this caller see" function) is an authorization boundary, not a convenience. Its predicate **MUST** be phrased as an entry allowlist over the permitted actor classes — every class that is not explicitly permitted is rejected, loudly, with a registered error. The inverse phrasing is the defect: a chain of *narrowing exceptions* (`if (role === 'staff') narrow(); if (role === 'restricted') narrowFurther();`) silently means "anything I do not recognize gets the widest scope", so an unrelated actor class — a subject-class session, a role added later, a corrupted claim — falls through into organization-wide data, and every downstream ownership check that depends on the produced narrowing filter never runs at all. Three consequences bind. (a) Unknown class = deny, not default. Absence of a narrowing rule is absence of permission; it **MUST NOT** be read as permission to see everything. (b) The rejection belongs to the helper, not to its callers. Once the helper denies, a caller-side copy of the same predicate is a second authority (see [SSoT](../ssot/ssot-principles-and-precedence.md) SSG-M8) — and copies drift in the dangerous direction: a caller-side copy that *returns an empty/absent filter* instead of throwing re-creates the exact widest-scope fallback the helper just closed, because "no filter" and "no narrowing needed" are usually the same value downstream. Delete the copies; keep one denial. (c) A permitted class **must** still pass unchanged. Converting the predicate to an allowlist **MUST NOT** silently remove access from a class that legitimately holds it today — enumerate the permitted classes from observed behavior, not from intuition. Closing the helper is necessary but not sufficient: it protects only the surfaces that call it, so it does not replace the centralized deny-by-default gate of the preceding note. [Consequence: Critical security bug — unrecognized actor class receives organization-wide scope and ownership checks are skipped; **must not** ship] [Verify: For each scope-resolving helper, assert the first branch is an explicit permitted-class check that throws a registered denial; grep for duplicated copies of that predicate at call sites and assert none of them returns a "no narrowing" value for an unknown class]

SEC-M-ZT-1 note (a deployment-environment flag is not an authorization predicate): A deployment-environment flag (`NODE_ENV`, a stage label, an `isProduction` boolean) MAY short-circuit developer convenience — an index-topology probe, a diagnostic log, a relaxed rate limit. It **MUST NOT** short-circuit an authorization check, and it **MUST NOT** be the sole controlling test of an early return that skips one. *"Is this deployment production?"* and *"is this runtime authorized to write the data it is connected to?"* are two predicates over two different subjects; making the first the gate of the second collapses them into one authority that answers neither (see [SSoT](../ssot/ssot-principles-and-precedence.md) SSG-M8). The resulting failure is silent and reachable by ordinary operations: a process whose flag says non-production while its datastore credential points at production passes the gate entirely, so a local shell, a staging instance, a migration script or an ad-hoc worker performs the irreversible write the gate exists to fence — a grant, a credit, an identity rewrite — with no error and no log. This is worse than an absent check, because at the call site it reads as though a check is present; and where the flag is parsed permissively (an enum that silently falls back to a development default on any unrecognized value) every gate written this way opens at once, from a typo. Two properties bind. (a) The shortcut is decided from durable state, not from the flag alone. Name what the shortcut actually claims — it is almost always *"the data I am about to write is not governed by this gate"* — and decide that from the data: if the datastore carries the gate's own governance record, the authorization predicate is evaluated in every environment, and only the record's genuine absence opens the shortcut. The flag MAY remain as an additional narrowing term, so that production stays fail-closed when the record is absent; it may never be the only term. (b) One named authority owns the shortcut. Every path that may take it calls that single predicate, so a second copy cannot drift open (SSG-M8), and no outer boundary re-decides the shortcut without having read the durable state. [Consequence: Critical security bug — a non-production runtime holding a production datastore credential performs an authorized-only irreversible write; **must not** ship] [Verify: for each environment-flag early return, name the check it skips; where that check is an authorization / ownership / tenant predicate, or fences an irreversible effect, the return **must** additionally require durable proof that the gate does not govern this datastore. Separating "skips an authorization check" from "skips a dev-convenience probe" requires knowing what the skipped callee does, which is a cross-file consumption fact: the two shapes can be byte-identical early returns inside identically named assertion functions, with the authorization predicate several files and call hops away, so no single-file syntax check distinguishes them. A rule banning the shape outright is decidable but fires on the legitimate convenience cases too, so it can only be introduced as a staged ratchet over a recorded baseline.]

SEC-M-ZT-1 note (the environment flag's own parse **MUST** fail loud): The note above bounds *what* a deployment-environment flag may gate; this one bounds *how its value is obtained*, because the parse is where the whole class becomes reachable from a single typo. A configuration schema that maps any unrecognized value to a default — a validation library's failure-swallowing combinator (`enum(...).catch('development')`), a `try`/parse wrapper, a lookup with an `??` tail — converts a configuration fault into a legitimate absence. Those are two different facts and **MUST** stay separable: absence is a normal operating state that a *declared* default may legitimately serve, while a value that was supplied and did not validate is a fault whose only correct response is refusing to start. What makes this outrank ordinary input hygiene is blast radius: one misspelled deployment variable moves every branch reading that field to the permissive side at once — request-origin admission, rate budgets, whether crash reporting initialises, whether the process is allowed to create database structure, and every gate written per the note above — with no error and no log, so the deployment looks healthy while running in the wrong mode. Two properties bind. (a) Only absence may be defaulted. Use the combinator that handles `undefined` alone, never the one that handles *failure*; a supplied value that does not validate **MUST** raise. This costs nothing in ergonomics — a runtime that never sets the variable keeps the previous behaviour exactly — so there is no trade to weigh. (b) The refusal **MUST** land at process start, before the process can serve. Parse the whole configuration on the startup path, ideally in the module preloaded ahead of the application entry, so a misconfigured replica never binds a port, never admits a request, and fails its deployment health gate instead of degrading silently; a parse deferred to first use turns a start-up refusal into a random request-time error. [Consequence: Critical security bug — one typo in one deployment variable opens every environment-gated branch simultaneously and silently; **must not** ship] [Verify: single-file AST — a schema chain rooted at the validation library's own import binding **MUST NOT** use the failure-swallowing combinator; the library binding is what separates it from an unrelated promise `catch`, so no naming heuristic is needed. Plus a start-up trace proving the parse executes before the listener binds. Unlike the review-only limit of the note above, this half is mechanically decidable, so use the enforcement mechanism the adopting project documents and record its actual scope and limits. Check reach: such a rule sees only the direct chain; a schema first bound to an intermediate variable and swallowed later needs variable tracking a single-file AST cannot give safely, so that form stays review-bound.]

SEC-M-ZT-1 note (a persisted model-prompt history belongs to one actor): Free text one actor stored — a question to a language model, the model's answer — **MUST NOT** enter a prompt, or a cached model response, served to a different actor. Scope the history read and the response-cache key to the actor verified in the current request (the account identity, not only its role), and give rows that carry no actor to nobody. A shared history lets a lower-privileged role plant instructions in a higher-privileged actor's advice and read that actor's questions back; a "this is data, not instructions" line in the prompt is not a boundary. [Consequence: Bug] [Verify: the history query and the cache key both take the verified actor; a row without the actor field matches no read.]

SEC-M-ZT-1 note (an internal command flag is not a wire field): A flag only a server-internal caller may set (skip a materialization step, bypass a side effect) **MUST NOT** be accepted by the public request-body schema. The wire schema is the public contract; the internal command schema extends it. Accepted on the wire, any client can switch the server's decision off — for example, a create request could suppress a server-owned materialization step. [Consequence: Bug] [Verify: the flag is absent from the body schema and present only in the command schema.]

SEC-M-ZT-1 note (a withheld feature is refused by the server, not hidden by the client): When a feature is withheld from some tenants — dark launch, pilot only, kill switch — every server route that serves it **MUST** refuse a tenant it is not offered to, through the one offer authority the client also reads to decide what to draw; hiding the entry point in the client is a display choice, not enforcement, because any authenticated caller can call the route directly. (a) The refusal runs after the route's actor-class gate, so it never answers for a tenant the caller may not enter, and before any persistent side effect (an idempotency claim, a write); it is one registered code. (b) Only the reads the client decides from stay open — the offer answer and a view that explains a paused state — and they hand out nothing the feature delivers (no artefact, no write). (c) A field of the feature on a general-purpose writer (a flag on a shared record) stays writable while it is inert until a gated surface uses it; refusing it would break the shared writer for every tenant. [Consequence: Bug — the feature is usable before it is offered] [Verify: review — every route of the feature's router calls the gate or is one of (b).]
