## **MUST** / **MUST NOT** — cryptography policy

| ID | Rule | On violation | Verify by |
|----|------|--------------|-----------|
| **SEC-M-CRYPTO-1** | TLS for production traffic: TLS 1.2+ minimum; preferred version and cipher policy documented in project security note; weak suites disabled. Outbound fallback requests and redirect destinations are part of the same transport obligation: a failed TLS provider response **must** never trigger a plaintext request. Where a secure fallback has no verified transport contract, return the documented unavailable result; disable automatic redirects when the destination protocol is not independently enforced. Enforcement limit: provider transport configuration and indirect redirect/fallback chains remain review-bound; a one-provider defect inside the sole authority does not establish recurrence for a new static check ([ENA-A1](../enforcement-architecture/enforcement-admission.md)(a), [ENA-A2](../enforcement-architecture/enforcement-admission.md)). | STOP — not shippable for external APIs. | Infra review + scan. |
| **SEC-M-CRYPTO-2** | Password storage: Argon2id (preferred) or bcrypt; cost / parameters version-controlled in security note; migration from legacy hashes documented if applicable. Plain-text password storage forbidden. The cost parameter has one source read by every writer of a hash and by the sign-in check. A password sign-in **MUST** do the same hashing work whether or not the account exists: an unknown, inactive or hash-less account is compared against a dummy hash of the same cost before it is rejected with the same code as a wrong password. Returning before the hash comparison makes response time an account-existence oracle that the identical error code does not hide. | Bug / breach class. | Schema + auth code review. |
| **SEC-M-CRYPTO-3** | Application-level field encryption (when required): AES-256-GCM or equivalent AEAD; keys in KMS / vault / platform secret — not in source. Nonce/IV unique per encryption. Every stored copy of a bearer capability whose primary store keeps only its hash (a link or code that grants an action) — in a queue or outbox payload, a replay body, a conversation or cache record — **MUST** be such an envelope, bound by its associated data to the record or recipient it was written for (so an envelope copied elsewhere does not open), and opened only in memory where it is delivered or sealed into another such copy; a failed open is a SYSTEM error, never a send without it. Reason: one clear copy turns read access to that collection into the capability the hash-only store protects. Where a later read must answer such a value in clear (a status or resume read), a key name **MUST** carry it only as a digest and every answer **MUST** be rebuilt from that one envelope by the value's original builder — never a second clear or derived copy (reason: a key listing otherwise hands out live capabilities, and a stored derived copy drifts from its builder). | Bug. | Crypto review. |
| **SEC-M-CRYPTO-4** | Key derivation from password or shared secret: Argon2id, scrypt, or PBKDF2 with documented iteration/work factors; HKDF where protocol requires; salt per record; randomness from CSPRNG (e.g. `crypto.randomBytes`). | Bug. | Code review. |
| **SEC-N-CRYPTO-1** | **Must not** store passwords with MD5, SHA-1/256 alone, fixed salt, ECB mode, predictable IV, or use `Math.random` for secrets/nonces. | Merge blocked / bug. | Static patterns + review. |
| **SEC-M-CRYPTO-5** | A configured standing secret — one that stays the same across every attempt — **must** be compared in constant time, **must** never reach a log field, and **must** have exactly one reader. These three travel together because they describe one object: a value an attacker may probe repeatedly. (a) `===` on such a value exits at the first differing byte, so the value is measurable character by character; length is eliminated first, then the bytes are compared with the platform's constant-time primitive. A per-attempt secret (a one-time code) does not carry this property, which is exactly why the *standing* case is the one that **must** be fenced. (b) The use of the gate is logged (a WARN-level metric, so an exception left open is visible); the secret itself is not — once written, it stays readable for the retention window and only rotation undoes it. (c) One interpreter reads the configuration. A second reader is a second gate that carries none of the first's fences, and a half-configured exception **must** open nothing rather than a partially-guarded path. | Security bug — a standing secret becomes measurable, durable in logs, or reachable through an unfenced parallel gate | Single-file AST rule: the configuration identifiers readable only in the interpreter and its contract; inside the interpreter, the secret's read forbidden as an equality operand and inside any observability call. The equality and logging arms are narrowed to the interpreter file — the same field name is legitimate everywhere else. |
| **SEC-M-CRYPTO-6** | Field encryption of data kept at rest **MUST** use a dedicated key with exactly one reader, **MUST NOT** derive it from a session or token signing secret, and **MUST** store the key version with every sealed value; a missing or malformed key **MUST** fail closed with a registered error — never a fallback key and never a clear-text write — while the rest of the service keeps running. Reason: rotating a signing secret would silently make every stored record unreadable, and a fallback key splits one data set across two keys that no rotation can reconcile. Short-lived envelopes (cursors, replay seals) may still use a signing-secret subkey (**SEC-M-CRYPTO-5** (c)). | Security / data-integrity bug — stored data becomes unreadable on rotation or is written under a key nobody owns | Crypto review: the env key has one reader that validates its length, the seal path stores the version, and the absent-key path raises the registered SYSTEM code. |
| **SEC-M-CRYPTO-7** | An access token a provider issues for a stored third-party credential, when it is cached outside process memory, **MUST** be sealed with that credential's own at-rest key and bound (AAD) to the stored credential's revision, so a replaced or removed credential leaves no token a reader can still use; **MUST NOT** be cached in clear text or keyed by tenant alone. Reason: a tenant-keyed cache serves the previous credential's token after a re-link, and a clear-text token in a shared cache is a credential at rest outside the field-encryption boundary. | Security bug — a re-linked or unlinked account keeps acting with the old credential, or a usable credential sits unsealed in the cache | Crypto review: the cache write seals with the credential key and an AAD carrying the revision, and the read treats a revision mismatch or failed open as a miss. |

## JWT and signing (normative minimum)

| ID | Rule | On violation | Verify by |
|----|------|--------------|-----------|
| **SEC-M-JWT-1** | Token signing algorithms and keys are owned by one server-side authority; weak algorithms and mismatched symmetric/asymmetric key modes are forbidden. A short-lived assertion signed locally from a standing credential is minted from the current credential for each operation and is never stored in a general shared cache. A token issued by an external authorization server may be cached only when its response is runtime-validated and its cache honors credential rotation, audience, scope, and expiry. | Security defect — stale or cache-injected credentials remain usable after key rotation. | Authentication service and cache-boundary review. |
| **SEC-M-JWT-2** | Access token maximum lifetime (the `exp` span or equivalent server-enforced cap) **must** be documented as a concrete bound in the project auth/security note; changes **must** pass GSEC4. | Bug / audit gap. | Auth note + diff review. |
| **SEC-M-JWT-3** | If the server issues refresh tokens, refresh rotation and reuse / replay handling (one-time use, detection, or documented alternative) **must** be documented, or N/A per SEC-NA-1 (e.g. no refresh-token model). | Session fixation class if omitted. | Auth service doc. |
| **SEC-M-JWT-4** | When an untrusted JWT's unknown `kid` would cause an outbound JWKS refresh, the refresh **must** pass a provider-global, cross-instance atomic cooldown gate (scoped only to trusted configured provider / issuer / JWKS-endpoint identity), implemented by the project's selected shared coordination authority, before any network call. The authority **must** support an atomic claim with an explicit bounded TTL. Derive its key only from trusted configuration; never include attacker-controlled `kid` or other token data. If Redis is the selected coordination authority, use `SET NX` with an explicit TTL as its atomic-claim example and follow the applicable [Redis](../redis/redis-degraded-mode-and-invalidation-ordering.md) RDS-M16 requirements. The winner may perform one controlled refresh and update the shared JWKS cache; losers may re-read that cache but **must not** issue another refresh. If the selected authority cannot confirm the claim, or cross-instance coordination is unavailable, fail closed for the unknown-key path without making a network call; a cached known-key verification path may continue. Do not fall back to a process-local or per-instance cooldown. Denial / degraded diagnostics use a bounded reason and **must not** interpolate, log, or capture the unverified JWT or attacker-controlled `kid`. | Security / availability bug — unauthenticated outbound request amplification, provider exhaustion, or attacker-controlled observability cardinality. | Two-instance unknown-`kid` burst and coordinator-outage observation; inspect the selected coordinator's atomic claim / TTL configuration and the resulting logs or crash events. |
| **SEC-M-JWT-5** | A symmetric session-token signing key is one authority with three fences. (a) One reader, one strength bar: the key's configuration is read by exactly one interpreter, which rejects an absent value, a value under 32 UTF-8 bytes (RFC 7518 §3.2 — an HMAC key at least as long as the hash output), and any placeholder the repository itself publishes (example env file, setup docs) — a published placeholder passes a length check and is a key everyone knows. The byte floor is one shared derivation for every standing symmetric secret, never re-typed per secret. It is not an entropy proof; it rejects only what is certainly too weak. (b) Boot, not first use: the server entry point runs the interpreter's assertion before it starts listening, so a missing or weak key stops the replica before traffic instead of surfacing as a 500 on the first login. The general env schema only *declares* the key, because offline scripts that never sign parse the same schema. (c) Algorithm explicit on both sides: signing names the algorithm instead of inheriting the library default, and verification passes an explicit allow-list, both read from one constant, so the two sides cannot drift and a token cannot choose its own algorithm. No development carve-out: the same bar binds every environment. | Security bug — a guessable or absent key is discovered only under live traffic, or verification trusts the token header. | Single-file AST rule: the key's configuration read only in the interpreter; every sign/verify call carries an explicit algorithm option (no `none`), which **must** be the interpreter's constant when the key comes from the interpreter; the entry file calls the assertion before `listen`. Check reach: a key passed in from another file as a parameter is seen only by the explicit-algorithm arm; a whole env object handed to another function and read there is not seen; a second server entry point is not covered automatically. |
| **SEC-M-JWT-6** | A provider's credential rejection (`401`) of an idempotent read authenticated by a locally signed bearer **MUST** be retried exactly once with a freshly minted bearer before it is classified. A standing credential that is really wrong rejects every attempt; a one-off rejection (a provider node whose clock trails, a propagation hiccup) passes on the second. Classifying the first `401` as a defect pages crash reporting for noise the retry would have separated. (a) One place: the retry lives in the single request authority for that provider, never per operation. (b) Reads only: only `GET` / `HEAD` or a documented idempotent read; a write, a `403` or any other status is never retried this way. (c) Bounded: exactly one extra flight inside the call's one absolute deadline ([BHE-M10](../backend-http-efficiency/outbound-call-time-budget.md)); no loop, no backoff ladder. (d) Classified after the retry: recovered → `WARN` + a closed-label metric, never crash reporting; rejected again → the provider's `SYSTEM` misconfiguration code ([M19](../error-policy/provider-contract-and-webhook-errors.md)); any other result keeps its own classification; the error context records which of the three happened. (e) No cross-run escalation is owed: a persistent credential defect fails the retry in its first run, and a recurring recovered rejection is the metric's rate. (f) Scope: a cached provider-issued access token (SEC-M-JWT-1's exchange case) is not covered — the provider validated it at issue, it carries no signer issue time, and no sporadic rejection of one is documented; extend this row only on that evidence. | Bug — sporadic provider-side rejection reaches crash reporting as a credential defect, or a write is replayed. | Inspect the single request authority for each provider: no other module calls the provider host directly, each call carries an explicit method, a read has the one `401` branch that re-mints, and a write has none. Use the adopting project's documented check where one exists and record its reach; a host constant imported from another module, a non-`fetch` client, and a minted credential serving exactly one flight stay review-bound. |
| **SEC-M-JWT-7** | When a provider contract validates `iat` / `exp` for a locally signed bearer, issue both claims from one captured clock value and follow only its documented, bounded clock-skew allowance. Do not backdate `iat` unless the provider permits or requires it. Keep `exp` within the provider's maximum lifetime as measured by that contract; where the cap is measured from `iat`, account for any permitted backdating so `exp - iat` never exceeds the cap. If the provider does not define relevant `iat` / `exp` constraints, this row is N/A per SEC-NA-1. | Security defect — provider rejection, or a bearer whose accepted lifetime exceeds the provider's cap. | Compare the signer with the provider's documented claim rules; use a controlled clock to verify skew and expiry boundaries, including that `exp` remains within the provider cap. Static source review cannot establish the provider's actual clock or undocumented validation behavior. |
| **SEC-N-JWT-1** | **Must not** operate a refresh-token model without documented rotation/reuse policy — SEC-M-JWT-3 or SEC-NA-1 required. | Bug. | Auth review. |
| **SEC-N-JWT-2** | **Must not** let each unknown `kid` directly trigger JWKS fetch, create a cooldown key per attacker-supplied `kid`, use an in-process / per-instance cooldown, perform the outbound refresh when the selected shared atomic coordination gate is unavailable or unconfirmed, or include the unverified JWT / raw `kid` in errors, logs, or crash events. | Security bug — bypassable cross-instance amplification control or attacker-controlled observability data. | Static key/call-flow review + runtime burst/log observation. |
| **SEC-N-JWT-3** | **Must not** verify a self-issued session token without an explicit algorithm allow-list, sign it on the library-default algorithm, read its signing key outside the one interpreter, make the key required in the shared env schema that offline scripts also parse, or defer the key's validation to the first sign/verify call. | Security bug — SEC-M-JWT-5 fences bypassed. | Same rule as SEC-M-JWT-5. |

## Failure path (normative)

| Situation | Required behavior |
|-----------|---------------------|
| Undocumented TLS termination or cipher policy | STOP — document before prod exposure. |
| Password path violates SEC-N-CRYPTO-1 | STOP — fix hashing before ship. |
| JWT lifetime / refresh policy change without GSEC4 / docs | STOP — see [decision gates](security-decision-gates.md). |
| A locally signed assertion is found in a general shared cache | Remove the cached assertion and mint it from the current credential for each operation; do not extend or namespace a replayable assertion to work around rotation (SEC-M-JWT-1). |
| Unknown JWT `kid` misses the shared JWKS cache | Acquire the provider-global, cross-instance atomic cooldown claim through the selected shared coordination authority before one refresh (Redis `SET NX` + TTL when Redis is selected); no claim or unavailable coordinator → reject the unknown-key path without an outbound request (SEC-M-JWT-4). |
