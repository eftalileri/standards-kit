## Zero trust — globally keyed identity lookup

[SEC-M-ZT-4](security-global-identity-lookup.md) application — aggregate-only operator metrics. An operator's permission to read platform-wide or selected-tenant metrics does not prove membership in each subject tenant. A metric consumed only as a total therefore carries the validated aggregate alone; internal joins may prove which records belong in that total, but names, account identifiers, tenant identifiers and per-subject event rows never become the response. Narrowing the wire output **must** preserve the population filter and stored-fact integrity checks; removing the detail is not permission to silently count invalid facts. A deprecated collection field retained for independently released consumers may remain only as an explicitly empty collection, never as a second detail authority or a compatibility exception to the disclosure prohibition. Its removal still owes the released-consumer horizon of [DCD-M8](../dead-code/dead-code-rules.md). A closed empty-tuple response type makes accidental row return fail compilation. No additional syntax lock is admitted where that stronger contract already excludes the leaking payload ([ENA-A1](../enforcement-architecture/enforcement-admission.md)(c)). Operator exception: a platform surface **MAY** return per-subject rows to the top operator class (for example a platform super administrator) alone, when the adopting project's owner has recorded that decision, but only when the single actor-class gate rejects every other class — delegated read-only operators and automated agents acting under their credentials included — with the registered forbidden code before any data or cache read, and the subject identifier is masked server-side (display name or a partial mask, never the raw identifier, in neither response nor log); such a mask is still personal data under the pseudonym clause below, which is why no other class may receive it.

[SEC-M-ZT-4](security-global-identity-lookup.md) application — the subject's own data copy (access/portability request). The copy reads the globally keyed identity record, so its subject **MUST** be the verified session identity alone — a request parameter naming the subject is forbidden even for the caller's own id, because that parameter is the enumeration seam. Fields **MUST** be an explicit allowlist: serialising the whole record ships internal fences, session and push tokens, credential hashes and attribution context the subject never gave. Records a tenant keeps about the subject as controller (its own subject card, orders, payments) **MUST NOT** be pulled across tenants into the copy; only the link itself (tenant name, relation, the name that tenant shows) travels, and the tenant answers for its own ledger. The response carries `Cache-Control: no-store` and an identity-keyed rate budget ([SEC-M-RL-3](security-rate-limiting.md)): a stolen session must not turn the copy into a cheap bulk exfiltration loop.

SEC-M-ZT-4: A globally keyed identity collection — one whose primary key is not tenant-scoped, and especially one whose key is a guessable real-world identifier (phone number, email, national id, sequential counter) — **MUST NOT** be queried with caller-supplied identifiers inside a tenant-scoped path. The identifier **MUST** first be proven to belong to the acting tenant (membership row, ownership field, or an equivalent tenant-join), and only the proven subset may reach the global lookup. A tenant id passed as a *parameter* is not scoping: scoping exists only where it appears in the executed filter or in the proof step that narrows the id set. This binds even when the surface is display-only (labels, chips, report headers, autocomplete): a resolved name, email, or avatar returned for an unproven id is a cross-tenant disclosure oracle, and a guessable key makes it enumerable. When one helper resolves an identifier through several sources, EVERY branch carries the scope — a single unscoped branch defeats the scoped ones, and it silently wins whenever its result takes precedence. A cross-subject ranking, feed or comparison surface is the inverted case and **MUST** be read the same way: it returns rows for subjects whose tenants the caller has proven nothing about, so no per-subject attribute may travel on the wire at all — the aggregate fact the surface exists for (position, count, tier) is the whole permitted payload, and the caller's own row is marked by a server-computed boolean, never by echoing back the identifier the server compared. There is exactly one bounded exception to that clause, and it is not a product decision this rule already permits: a tenant-published profile, where the subject tenant itself recorded a revocable opt-in to publication — its five conditions bind together and are defined by [SEC-M-ZT-7](security-tenant-published-profile.md); where any one of them is missing, this rule applies unchanged. Deriving a "pseudonym" from a subject identifier is not anonymisation. A truncation, suffix or substring publishes the identifier's own bytes, so where the identifier is a real-world one (phone, email, national id) the surface leaks personal data under an anonymous-looking label; a hash removes the bytes but leaves a stable correlation oracle over an enumerable identifier space. Where a human-readable label is wanted, it comes from the consumer's own message catalog, not from the subject's record. The WRITE side is the same obligation with a stricter deadline, and it is the half that persists the damage. Where a caller-supplied identifier of one record is stored INTO another tenant-scoped record — a membership array, an owner or assignee field, any foreign-key column — the tenant proof **MUST** be produced BEFORE the first persistent write, not merely somewhere on the path. Structural validation ("is it a string, an array, non-empty") is not proof: a non-existent id and an id belonging to a DIFFERENT tenant both pass it, and once written the record carries a cross-tenant link that later reads faithfully resolve. Three properties bind. (a) One authority, before the write: the proof comes from the single tenant-membership authority for that entity, and a second verification path on the same write is forbidden (SSG-M8) — a delegate preparation step may hold the proof, but then the delegate is the authority and the write path **must** consume it unconditionally on every branch. (b) Missing means refuse, never filter: when any id fails the proof, the operation fails loud with a registered code; silently dropping the unproven ids and persisting the remainder is forbidden, because the caller is never told the record they saved is not the record that was stored. (c) Deny uniformly: an id belonging to another tenant and an id that does not exist **MUST** return the identical outcome — a distinguishable response is an existence oracle over the other tenant's data. [Consequence: Critical security bug — cross-tenant PII disclosure / enumeration oracle on the read side; a persisted cross-tenant data link on the write side; **must not** ship] [Verify: For each caller-supplied id reaching a global-identity read, trace the tenant-proof step; assert every branch of a multi-source resolver is scoped. Single-file AST rules generally CANNOT see the READ side (the proof is data-flow across the id set, not a sibling key in the filter object) — enforce by review and by keeping the tenant proof inside the shared resolver rather than at each call site. The WRITE side is decidable from one syntax tree (the persisting shape and the awaited proof call are both visible), but decidable is not admitted: a fence exists only where [ENA-A1](../enforcement-architecture/enforcement-admission.md) passes. The stronger rung is a proof type the persisting write requires (a branded value only the proof authority can mint), which makes the unproven write fail to compile ([ENA-P1](../enforcement-architecture/enforcement-admission.md) rung 1). A new tenant-scoped foreign-key field is held by review until it carries a proof type or earns an admitted row.]

[SEC-M-ZT-4](security-global-identity-lookup.md) application — the result side of a tenant read. The shared read seam that binds populated references to the row's own tenant **MUST** also compare each returned row's own tenant field against the executed filter's tenant condition (one tenant or the gated set), remove a row outside it from the answer and report it once under a registered SYSTEM code at fatal level; the comparison is a field check on rows already read, never an extra query, and it lives only in that seam. Reason: a filter assembled by spreading a caller object can overwrite the tenant key, and the database then faithfully returns another tenant's rows that no later layer re-checks.
