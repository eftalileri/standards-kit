## **MUST** — **REP-M-23**, **REP-M-25**, **REP-M-32**, **REP-M-33**

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **REP-M-23** | The acceptance criterion for an irreversible data operation **MUST** be an invariant derived from its authority, never only a point-in-time count of a population that changes independently. A changing count can differ between observation and execution for legitimate reasons. Treating every difference as a blocker can prevent a valid operation indefinitely; dismissing it as noise can hide a real change in scope. Use an invariant the operation is intended to establish or consume, such as exact topology, a versioned marker, or a declared policy value. Record volatile counts as observations, not as the gate. If a fresh observation differs from the recorded value, explain the difference structurally before proceeding — name the mechanism whose cadence produces it and prove from the authority that the affected rows are outside the declared policy; stop if it cannot be reconciled against the authority. | Bug — an irreversible operation is either permanently blocked by a moving count or proceeds after a real scope change is dismissed as noise. | Review + evidence: the acceptance criterion names an authority-derived invariant; the dry-run reports the same values; volatile counts are labeled as observations; unexplained differences block apply. Review is required because source code may not distinguish a gate from a reported observation. |
| **REP-M-25** | The target of an irreversible operation **MUST** be named explicitly on every run, and a missing target **MUST** stop the run rather than resolve to a default. This applies to every predicate that bounds the blast radius, such as owner, record key, or time range. A default silently makes the source author, rather than the operator, choose what is destroyed; neither a confirmation flag nor a dry run corrects an unnamed target. The rule binds identically in a one-off maintenance script, which carries the same authority as the production write path with none of its review. Operator input is the single authority for the target ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)); a literal fallback is a second one and commits a live record key to version control. Where sibling operations already fail loudly on a missing target, converge on that existing shape. Examples may show only clearly synthetic values. | Bug — an irreversible operation destroys data nobody named, reports success, and leaves a record that reads as a deliberate choice. | Review + evidence: every irreversible entry point resolves and validates all targets from operator input and raises on absence or malformed values before any connection is opened; the failure names what to supply. Static analysis may catch literal defaults but cannot generally classify target dataflow through helpers. |
| **REP-M-32** | A declaration that a stored field was removed is NOT a measurement of the records, and destroying that field's values **MUST** be gated by a read-path proof taken at THREE levels: (1) no query predicate names it, (2) no response projection or transformer copies it, and (3) no consumer outside the inspected source boundary can reach the store directly. These are independent; none implies the others. A schema-aware mapper may strip undeclared fields from hydrated records while raw/lean reads bypass that filter, so an interface omission does not prove the value cannot leave the system. An explicit field-by-field allowlist transformer makes the proof possible; a spread of the fetched record makes it impossible, because every undeclared field the store still carries rides out with it. Evaluate nested fields by full path rather than bare name: a same-named field under another path is a different subject, so the verdict is taken per path and the removal set is written as paths. The third level cannot be answered from the inspected tree: it closes only by showing the out-of-tree consumer has no direct store access (a separate application reading exclusively through a controlled API, with no database driver among its dependencies, is such a proof); a shared store means the removal must be treated as a wire change ([**DCD-M8**](../dead-code/dead-code-rules.md)). The measurement itself **MUST NOT** disturb neighboring maintenance: a filtered count over the field can select an index whose own removal entry point gates on that index's usage counter being zero, so the counts are pinned to the primary-key index ([**REP-M-31**](repository-topology-excess-and-verdict-severity.md)). A field measured absent from every record is left out of the removal set — carrying it inflates the audit count the operator approves with a line that can never change. | Bug — a field the model calls removed still leaves on a raw-read response, a removal reports success while a released consumer keeps reading it, or a hygiene count blocks a correct structure removal by moving the counter that gates it. | Cross-file evidence: for each full field path, the query-predicate scan, the response transformer's shape (allowlist or spread) and the out-of-tree consumer's store access, all three recorded; the removal set written as paths, not bare names; the dry-run reporting per-field and union counts over the same predicate the write uses; measurements read-only and pinned to the primary-key index. The third level is not in the inspected source tree, so this row is enforced by the recorded measurement and a single-file check cannot prove it. |
| **REP-M-33** | A declared index that is a redundant prefix of another index **MUST** be removed only on a topology invariant read fresh immediately before the drop, never on a usage counter: (a) the target carries no behavior-changing option (unique, partial, sparse, TTL, collation, hidden); (b) the covering index is live, carries none of those options either, and holds the target's key as a strict prefix in the same order and direction; (c) the model no longer declares the target and still declares the covering index, with declared names read from the ODM's own index list (field-level declarations included); (d) after the drop, a fresh read shows the target absent and the covering index still standing. The removal changes the model declaration first and drops afterwards. | Bug — the target is the planner's current choice, so a zero-usage gate never opens; a partial, sparse or collated "cover" leaves part of the target's queries without an index; a constraint is lost to a usage argument; or a target still declared is reported missing on every start. | Review + evidence: the explicit migration's dry-run lists each target with its covering index, the apply re-reads after every drop, and the final dry-run reports zero remaining. |
