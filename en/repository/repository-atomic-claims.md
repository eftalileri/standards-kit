## **MUST** — **REP-M-13**, **REP-M-14**

**REP-M-13**: A durable inbox/outbox worker claim **MUST** be one atomic persistence operation with an expiring lease. The claim filter selects only documented eligible states (such as pending, retryable failure, or processing with an expired lease). The same atomic update records a unique lease owner, future expiry, processing state and start time, and increments the attempt-start counter. A successful typed claim returns the canonical persisted replay payload; the worker **MUST NOT** depend on an HTTP or request-memory copy. Long-running workers renew only through an owner/state/unexpired-lease compare-and-set. Completion, failure, and renewal return typed outcomes such as `applied` or `lease_lost`. Finalization **MUST** match the record, current owner, processing state, and unexpired lease so a stale worker cannot overwrite the current owner; that terminal compare-and-set is its own lease check, so a renewal immediately before it **MUST NOT** be added (one more write, no added guarantee). An exhausted stale-processing record also requires a newly acquired lease before terminalization; a scan result alone is not write authority. The repository returns persistence outcomes only; payload validation and retry/terminal-state policy remain in the service layer (**REP-N-2**). Candidate scans need an index aligned with their eligibility predicates. Where automatic index creation is disabled, change the predicate and its index through an idempotent migration with live topology verification before deploying the new worker. Keep field names explicit and consistently owned. [Consequence: Duplicate processing, stale-worker overwrite, or an unbounded retry scan under backlog.] [Verify: Atomic claim filter/update; canonical payload in the successful result; unique event identity; candidate-query index and live migration evidence; atomic attempt increment; owner/status/unexpired-lease predicates for renewal and finalization; and a leased terminalization path for exhausted work.]

Single-drainer application (how this row is met, not an exemption): a durable queue's enqueue shape and the predicate its drainer matches are one contract. The eligibility fields must be set by a shared persistence seam, not retyped independently by each producer; otherwise a successful write can create a row the drainer never selects. Before consolidating producers, compare their written field sets. Preserve genuine differences as explicit branches and keep distinct terminal outcomes named, even when they share an implementation. [Verify: Enqueue and due-read use one authority; producers agree on eligibility fields or differences are explicit; outcome wrappers preserve their meaning.]

Lease clock frame (a premise of this row, not an exemption): a lease expiry written and compared with the process clock is correct only while measured inter-process drift stays far below the lease margin (TTL minus renewal interval); the measurement method, the measured values and the redesign trigger are stated once, beside the scheduler lease, in [scheduled-work-boot-arming.md](../logging-policy/scheduled-work-boot-arming.md) ("Clock frame of the durable lease and the occurrence hold").

**REP-M-14**: A domain singleton ("at most one record for this natural owner/scope") **MUST** be claimed by its canonical natural key in one atomic persistence operation and backed by a unique constraint on that same key. A read-before-create followed by insert is not idempotent: concurrent writers can both observe absence. Use an exact natural-key claim/create path with insert-only semantics and return the winning persisted record without overwriting existing authority. If a generated surrogate also has a uniqueness constraint, retry surrogate collisions with a bounded new candidate; resolve a natural-key duplicate only by re-reading that exact key. Classify duplicate errors using allowlisted structural driver fields, never raw messages or key values that may contain sensitive data. Adding a constraint to existing data requires an idempotent duplicate preflight that fails loudly without deleting, merging, or guessing the winner, followed by creation and live topology verification. A model declaration is not production evidence when automatic index creation is disabled. [Consequence: Split authority, duplicate side effects, or nondeterministic reads.] [Verify: Unique-key declaration; atomic natural-key create-or-read; concurrent claim behavior; duplicate classification; migration preflight and live constraint topology.]

**REP-M-14** zero-valued singleton application: A stored numeric zero does not establish that its owning record is absent. A balance/counter cell is acquired by its exact natural key; an additive write updates an existing zero-valued cell and creates only on the documented positive initialization path. Insert-only identity fields never overwrite the winner. A quantity projection that coalesces absent to zero may remain a read derivation, but cannot select an insert branch. One measured defect inside the single writer is closed by its natural-key update API and transaction serialization, so no further lint or guard is required. A live-topology receipt names the actual namespace from the model's explicit collection binding, the ordered key and unique/partial/sparse/collation options, observation time and duplicate-cell/document-overage counts. An inferred plural collection name is not evidence. Zero duplicates in an empty collection proves no existing-row behavior; it does not discharge a live-write outcome or concurrent-writer claim. A timestamped observation closes only the previously unmeasured topology at that instant, never substitutes for current boot proof or authorizes index installation. Retain these limits with the recorded result; no identifier or raw natural-key value belongs in the measurement output.

**REP-M-13** enqueue-deduplication application: Duplicate suppression for a durable outbox row belongs to enqueue as well as to the drainer claim. A second queued row may cause a second irreversible effect when the destination does not suppress duplicates. The deduplication key **MUST** be required by the producer type, identify the business event rather than an attempt, and avoid storing raw personal identifiers when a digest or opaque identifier suffices.

Use two layers where needed: a logical pending-row check avoids ordinary duplicate writes and prevents resetting retry backoff; a database unique constraint over the same key and pending-state predicate closes the concurrent-writer race. The constraint must allow legitimate re-enqueue after a terminal row and must not let a missing key collide as a null value. Classify its duplicate error separately from store failures; treating every driver error as "already queued" hides outages.

Where an ORM/ODM schema declares document-level validation hooks that a query-level upsert bypasses, use a document-validated create path and rely on the unique constraint to close the race. Otherwise the canonical atomic create-or-read form in **REP-M-14** remains available. State the invariant that requires document validation at the write authority. [Consequence: Duplicate irreversible effects, valid re-enqueue blocked by a terminal row, a store outage disguised as deduplication, or a declared persistence invariant that is never enforced.] [Verify: Required event key; pending-scoped unique constraint verified against live topology; duplicate-key path separated from other driver failures; and a document-validation-preserving write wherever the schema depends on document hooks.]

**REP-M-14** once-mark application: A once-per-subject mark guarding an external send to a destination that collapses repeats by a deterministic business-event id, written by a single leased sender that processes a set, **MUST** be written after the provider call (one set write whose filter re-asserts the send gate) and only for items the provider path actually took; a claim written before the send is required only where the destination does not collapse repeats. Reason: a failure between a pre-send claim and the send loses the event for good, while a failure between the send and a post-send mark leaves a resend the destination absorbs. Review-held.

Stated enforcement limit: whether a write path targets a schema with document-level hooks can cross model and repository modules, and static checks may not resolve this reliably in every stack. Keep the write-form decision explicit at the single authority and review it against the schema's declared invariants.
