<a id="rep-m-28-clauses"></a>

## Single gated entry point clauses — [**REP-M-28**](#rep-m-28-clauses)

- (a) One entry point. An irreversible maintenance operation **MUST** be reachable through exactly ONE runnable entry point, and that entry point **MUST** refuse to do any destructive work until the operator has declared the run's mode — a rehearsal that writes nothing, or an explicit confirmation token compared to a fixed value. Two entry points for one destructive operation are two authorities for one question ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)), and the danger is not the duplication itself but its asymmetric decay: hardening lands on the path being read at the time — a gate here, a narrowed scope there — while the other keeps whatever shape it had, so the documented path grows safer and the *runnable* path stays weak.
- (b) Retirement is a deletion. Annotating the retired path as deprecated does not retire it. A comment changes what a reader believes, not what a runner can execute; while its command alias exists the second path is fully live, and the alias — not the file — is the operator surface. Retirement therefore removes the entry point, its command alias, and every citation naming it as a way to run the operation in the same change ([**DCD-M2**](../dead-code/dead-code-rules.md)), with the surviving authority's own header stating that it is now the only way. A completed one-shot data migration is retired the same way once a read-only measurement of its own candidate predicate on the live target returns zero and no runtime path depends on a rerun: a rerun was designed for the data it first met, not today's. A non-zero measurement instead converts it to the explicit-mode contract (**REP-M-15**) before any run. This does not soften [**DCD-M8**](../dead-code/dead-code-rules.md)'s additive migration for a wire surface: that branch exists because a frozen, already-shipped consumer can still call the old name, whereas a maintenance command's only consumer is an operator running the repository at that commit, so alias and script die together and the compatibility alias would preserve exactly the second path this row removes.
- (c) The mode has no writing default. The mode is an input with no writing default, and it is not the same question as the target (**REP-M-25**): the target says *what* would be destroyed, the mode says *whether this run destroys at all* — so absence of a confirmation **MUST** stop the run rather than be read as permission, and the rehearsal **MUST** be wired to something (a branch that returns before the first write, or a mode carried into the executor), because a mode that is declared and then consumed by nothing is a gate in name only.
- (d) One parser, typed store identity. The mode is spelled once, through the canonical explicit-mode parser of [**REP-M-15**](repository-index-migrations-and-validated-reads.md), and the confirmation token is that parser's writing mode — not a second input beside it. The operator names the writing mode together with the identity of the store the run connects to, compared exactly to the configured identity before any connection; that typed identity is the token. A rehearsal flag or a confirmation token read from the environment is a second spelling of *whether this run writes* — two authorities for one question ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)), and an exported variable outlives the run it was set for — so it does not satisfy this row; nor does a literal word beside the targeted mode, because a word fixed in the source is identical in every environment, whereas the configured identity also refuses a run pointed at the wrong store. The typed identity binds *which store*; *what inside it* is destroyed stays the operator-named target of **REP-M-25**.
- (e) Further inputs in the same parser. An operation that needs more inputs than its mode — a scope, a deployment or cohort proof, an operator attestation — declares them per mode in that same parser: `--name=value` arguments after the mode, validated by that mode's schema before any connection, with unknown, duplicate or non-canonical arguments refused. A multi-input command is never a reason for a second parser, and an attestation is a fixed-value argument the schema checks, not a presence flag whose misspelling reads as absent.
- (f) The declared scope bounds every phase. A run the operator scoped to one tenant, owner or key that still sweeps records outside that scope has a scope declaration in name only, and the surplus deletion is invisible in the way irreversible work always is — it reports success. A phase that cannot be expressed inside the declared scope is skipped and the skip recorded, never quietly executed at full breadth; the audit count reported for a scoped run is computed over the same scoped set the write uses, or the operator's decision rests on a number that does not describe what will happen.
- (g) The writing run destroys the reviewed set, not a fresh one. When the rehearsal shows the operator an exact record list, the writing mode **MUST** require a token derived from that list (record identities and versions, scope, store identity) as a declared argument (e), recompute it inside the write's atomic unit, and refuse on any difference before the first write. A writing run that merely re-audits deletes whatever matches at that instant — records created or changed after the review included — while its log reads as the approved list.

<a id="rep-m-28-verification"></a>

### Verification — [**REP-M-28**](#rep-m-28-clauses)

- Static (single-file analysis): in the adopting project's maintenance entry-point locations the **REP-M-15** mode check applies — the canonical parser called on the process argument slice before any connection, and no second mode spelling; any remaining debt sits in a shrink-only baseline. Use the enforcement mechanism the adopting project documents, and record its actual scope and limits: a reference to a check is not evidence that it exists or covers the full rule.
- Transition, and how it ends: where a project uses a transitional check, while a location still holds an unconverted entry point it keeps its old check so that it is not left ungated meanwhile — a call named with a destructive verb needs the rehearsal binding, a confirmation binding compared to a fixed value, a raising branch testing both before the first destructive call, and the rehearsal consumed outside that branch. That check fences debt, not a second conforming contract: a converted entry point leaves that location for one the parser check covers, and a new one is written to the parser. When the last unconverted entry point in a fenced location is converted or retired, the transitional check is DELETED and its scope is handed to the parser check in the same change. Both halves are load-bearing. Deleting it is required because a check whose subject population is empty reads as coverage while proving nothing ([**FP-M18**](../false-positive/check-design-rules.md)) and the shape it looks for is no longer permitted, so the only thing it could still do is bless a second mode spelling. Handing the scope over in the same change is required because removing the fence alone leaves that location ungated for the next entry point written there — the freed location is exactly where a new maintenance script lands by habit.
- Widening is bounded by subject, not by convenience: the parser check is given the locations where maintenance entry points live, not a recursive sweep of everything beneath them, because a read-only gate script that takes a reporting flag declares no mode and a recursive scope makes it a false subject.
- A module header declaring an executable entry point deprecated is the shape of a retired-but-runnable second path; when a transitional check that reported it is deleted, that arm **MUST** move to the surviving check in the same change, or the guarantee is lost while every gate stays green.
- Runtime/evidence: the surviving entry point's log records mode and resolved scope; skipped phases appear with the reason; a source scan after removal returns zero references to the deleted entry point and its alias.
- Check reach ([**IV-M13**](../implementation-verification/change-acceptance-bar.md)): (a) destructiveness is read from the called name, so an operation hidden behind a neutrally named surface is not classified — an under-catch, not a false positive; (b) the static half proves the mode is *read* before connection, not that every write sits behind it — that needs flow-sensitive analysis; the parser stops a run whose mode or store identity does not match, before any connection; (c) "a second script doing the same job under a different name" is not decidable from any single file, and no source tree carries a machine-readable inventory of irreversible operations to compare against, so only the annotated-retirement shape is mechanical.

## Context-gated authority a maintenance runtime cannot call — [**SSG-M8**](../ssot/ssot-principles-and-precedence.md) application

No identifier is added; [**SSG-M8**](../ssot/ssot-principles-and-precedence.md) keeps its single definition site.

A maintenance runtime **MUST** use the existing domain authority, never copy its body or make its required execution context optional. Decide the atomic unit through [TX-G1](../transactions/transaction-decision-gates.md): when ledger/history decisions and dependent erasure must commit together, maintenance **MUST** supply the same required transaction session and budget the complete unit under TX-M-13. Being a maintenance command does not exempt it from atomicity; dependent-first ordering alone cannot prevent a racing child insert or history write.

Only when TX-G1 is NO may an authority expose a separately named context-free arm over the same body; fence that arm out of context-holding callers at import level. Long teardown uses the durable closing/resume authority under [TX-M-12](../transactions/transaction-long-hard-delete.md), rather than an unbounded transaction or a partial history-delete loop. **REP-M-28**'s rehearsal, named-target and scoped-count obligations remain binding on every destructive arm.
