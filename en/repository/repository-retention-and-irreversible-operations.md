## **MUST** — **REP-M-22**, **REP-M-24** and **REP-M-27**

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **REP-M-22** | Exactly one mechanism **MUST** enforce a given retention or cleanup window, and that mechanism is the durable store's own expiry facility; reducing two mechanisms to one is an ordered operation ([clauses](#rep-m-22-clauses)). | Bug — the effective retention window is whichever writer fires first rather than the declared policy; and if the intermittent writer is removed before the store-native one is proved live, the window stops being enforced at all, silently. | Static: a single-file AST rule rejects an application-layer delete whose filter is *only* an open-ended time comparison, which is the collection-wide sweep shape; a delete that also carries an identity/tenant equality is a latency repair on a claim path, not a retention writer, and is not matched. Runtime/evidence: the live topology read back after the change shows the declared window and no narrowing predicate; the removed job appears in no scheduler inventory; a source scan for the removed symbols returns zero live references. Check reach: whether the collection being swept *also* has a store-native expiry is cross-file — it needs the model/migration topology declaration — so the enforceable half forbids the sweep shape outright. |
| **REP-M-24** | A runtime or start-up cleanup **MUST NOT** be able to remove a structure that a declared persistence authority still produces, and a hand-maintained obsolescence list is safe only while it is provably disjoint from every authority-produced name. A schema declaration plus its explicit migration on one side, and a start-up "drop these" list on the other, are two writers of one truth pointing in opposite directions ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)): the migration creates the structure, the next start removes it, and neither side reads the other. The failure is silent in the worst possible place — the migration's own post-apply read-back succeeds, because it reads at its own instant; the operation therefore reports success, every gate stays green, and the regression exists only at the *next* start, when nobody is collecting evidence. A usage statistic **MUST NOT** condemn a constraint-bearing structure. Zero reads is legitimate evidence that a *performance* index earns nothing, and no evidence at all about a uniqueness or partial-uniqueness constraint, whose product is an integrity guarantee rather than latency: it does its entire job while never being read. Condemning it by usage is exactly the error [**REP-M-23**](repository-irreversible-operation-evidence.md) names — a criterion that is not an invariant derived from the authority. Disjointness **MUST** be established against what the authorities actually produce, not against their most visible declaration sites: an ODM derives structure names from field-level options as well as from explicit declaration calls, and from constants referenced rather than inlined, so a scan that reads only the obvious call sites under-counts the authority set — and the name it misses is precisely the one that gets destroyed, because a name nobody noticed is a name nobody protected. Finally, reducing two mechanisms to one (**REP-M-22**) is complete only when the surviving authority's existence is verified at runtime: once the redundant mechanism is gone, the single remaining one can disappear without anything failing, which is the same silence wearing a different costume. | Bug — a declared, migrated structure is destroyed on every deployment while the migration reports success and every gate stays green; and a constraint condemned by a usage count removes an integrity guarantee that was doing its job precisely by never being read. | Static (cross-file): intersect the start-up drop list with the set of names every schema authority produces — field-level options and explicit declaration calls alike, resolving constant references — and fail on any intersection; also fail on a drop entry whose collection resolves to no authority, since an unmeasured entry would otherwise pass as clean. Check reach: "declared but absent in production" is a runtime fact no source scan can see ([**REP-M-15**](repository-index-migrations-and-validated-reads.md)), so the static half proves only that source contains no second writer; proving the structure is live needs the live-inventory read-back, and keeping it live needs the runtime readiness check this row requires. |
| **REP-M-27** | A retention window **MUST** be scoped to ONE retention class, and a record of a different class **MUST** be exempted by a discriminator the class authority writes — never by a negated expiry filter and never by enumerating the complement. One store routinely holds records of more than one class: short-lived behavioural telemetry alongside financial, contractual or audit records that carry a different legal basis and a longer, sometimes indefinite, obligation. An expiry keyed on a timestamp every record carries silently applies the *shortest* class's window to all of them, and the loss is invisible in the way **REP-M-22** already names — nothing fails when a deletion merely happens. The class boundary **MUST** come from the single authority that already answers "which records belong to this class" for reads ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)): the retention path consumes that authority, in the write path and in the migration alike. A second, hand-written "which records are exempt" predicate living in the expiry declaration is a second writer of one truth, and it is the copy that will go stale. The mechanism is forced, not chosen: store-native partial-expiry filters typically accept only *positive* predicates — equality, existence-true, comparison, type — and reject negation, so *"everything except class X"* is not expressible as a filter at all; a filter that instead enumerates the complement (*"all types except X"*) is forbidden even where the operator set permits it, because a class added later falls outside the enumeration and stops expiring with no signal. What remains is a dedicated retention-clock field written only to the records the window governs: a record without it — or carrying a non-date value there — is never reaped, which is the documented, guaranteed behaviour rather than a filter edge case. That field is a discriminator, not a duplicated timestamp: it answers *"when did this record's retention window start"*, a different question from *"when did the event happen"*. Adopting this on a populated store is an ORDERED, fail-safe operation: drop the old expiry first, backfill the clock field second, create the new expiry last, so that any interruption leaves *"nothing expires"* and never *"the wrong class expired"*. Backfill completeness is then measured and fail-loud ([**REP-M-20**](repository-historical-adoption-and-readiness.md)): a record left without the clock field has silently left the retention window forever, which is this rule's own failure mode pointing the other way. | Bug — a financial, contractual or audit record is destroyed on a telemetry schedule, or, after a half-applied cutover, behavioural records stop expiring and data minimisation silently ends; either way every gate stays green because no operation fails. | Static: the operator-set rule on partial-expiry filters mechanically rejects the negated form, so the forbidden shape cannot be written. Runtime/evidence: the live topology read back after the change shows the expiry keyed on the clock field; the dry-run reports the exempt population and the remaining backfill count, and the apply path fails loud on a non-zero remainder. Check reach: *which* records constitute a distinct retention class is a legal and domain judgement carried in no machine-readable form in a source tree — no check can derive that two kinds of record answer to different obligations — so the class assignment itself, and the correctness of the authority the retention path consumes, are review-bound. |

## Single retention mechanism clauses — [**REP-M-22**](#rep-m-22-clauses)

- (a) One writer of the window. A database-native expiry (a TTL index or equivalent server-side reaper) and a scheduled application-layer purge that deletes on the same time predicate are two writers of one truth, not a primary and a backup: neither reads the other, so the window that actually applies is whichever fires first, and the declared policy stops being the answer to *"when is this row deleted?"* ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)). Redundancy is not the justification it appears to be — a purge cannot cover a missing expiry index (it would have to read the index topology to know), and an expiry index does not need covering.
- (b) The store is the authority. Durability is the store's property, not the scheduler's: a scheduler that is paused, unleased, undeployed or crash-looping silently stops enforcing, while server-side expiry keeps running and is directly observable by reading the live topology ([**RDS-M5**](../redis/redis-connection-keys-and-authority.md)). The window's value stays one named constant that the topology declaration consumes, so the policy and its enforcement cannot drift apart ([**SSG-M1**](../ssot/ssot-must-authority-and-derivation.md)).
- (c) Ordered reduction. Reducing two to one is an ORDERED operation and the order is part of this rule: bring the store-native expiry to the declared window first, prove it live by reading back the full topology, and remove the scheduled purge only after that read-back succeeds. Removing the purge first — or in the same deployment, before the read-back — leaves an interval in which no mechanism enforces the window, which is a regression even though every gate stays green, because nothing fails when a deletion merely does not happen. Removal is then complete in the same change: the job registration, its boot call site, the executor, any helper left consumerless by it, and every scheduler-inventory or mutation-allowlist entry that named it ([**DCD-M7**](../dead-code/dead-code-rules.md)).
- (d) Stated consequences. Two consequences of store-native expiry **MUST** be stated rather than discovered: it fires no application code, so any derived cache previously invalidated by the purge now needs its own bounded expiry, and any evidence that must outlive a deleted row **MUST** already live outside it; and it reaches only rows whose expiry field carries the required type, so the count of unreachable rows is measured and reported, never assumed ([**REP-M-20**](repository-historical-adoption-and-readiness.md)).
- (e) Coverage, not only shape. A live replacement expiry proves SHAPE, not COVERAGE — that needs a population count, not a topology read. It reaches only rows carrying the field, so retiring the superseded window has a second gate after the read-back: rows missing the field **MUST** count zero. Reaching zero needs the write path to put the field on every transition that keeps a row alive, then one superseded horizon after that deploy: a coverage repair is not retroactive. The authority writing the row's state writes the clock, on every such transition: a field written only on *terminal* transitions, or removed on re-lease or takeover, leaves a class no expiry sees — and a zero live count does not prove that class empty when every row passes through it. A class left uncovered on purpose — age-based deletion would re-run a paid side effect — is declared at the field's own write site.
- (f) Shared horizon. Where ONE field and ONE index carry both the abandoned-row horizon and the replay window, take the longer; shortening a horizon in the change that removes the mechanism guaranteeing it is a regression, not a cutover.
- (g) Changing the window. A new value reaches the live expiry in place — `collMod` on the existing index, run by the explicit migration that recognises the documented previous value — never by drop and recreate. Lengthening is not retroactive: rows the old window already deleted stay gone, so "complete since `now − window`" becomes false for one old-window length. Every reader that needs "since when is this data complete" **MUST** read one horizon derivation kept beside the window constant — the later of `now − window` and a named floor no earlier than (apply instant − old window), which the apply asserts before it writes — and a period starting before the horizon reads as unavailable, never as zero — or, where the answer stays meaningful for a sub-period, it is measured over the retained part only and the response carries the measured start (complete / partial / unavailable from that same derivation), never silently clipped; a quantity that divides a full-period figure by a retained-part figure (a per-member average) stays unavailable, and a long range is never rejected merely because it reaches past the horizon; a reader computing its own cutoff from the constant is a second derivation ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)). Where a start-up gate compares the exact live option, apply before the code declaring the new value deploys, because every instance booting against the old value reports the structure missing. Shortening deletes the backlog at once, so its dry run reports that count before apply. A published privacy disclosure that states the window changes in the same release.

## Reading notes (non-normative)

- "Two mechanisms" is not always two writers. The test is whether both decide the *same* question. A store-native expiry that owns the window, plus a delete that removes one identified row whose expiry has passed so a fresh claim on the same natural key can be written, are not in conflict: the second is a latency repair scoped by identity, and it makes no policy decision. That distinction is what keeps **REP-M-22**'s static half free of false positives, and it is why the enforceable predicate keys on *filter scope* rather than on the presence of a time comparison.
- The observability that store-native expiry does not give you is a metric, not a second deleter. Losing a purge's "rows deleted" log is a real loss and it is the one argument for keeping a scheduled job. The answer is something that *reads*: a counter, or a periodic topology and population observation. Restoring a writer to regain a log re-opens **REP-M-22**.
