Scope

- Included: Server-side repository modules that encapsulate database access (queries, commands, cursors your stack uses). Layering: HTTP route / handler → input validation (a schema validator at the boundary) → service (business rules, error mapping, authz orchestration) → repository (persistence only).
- Excluded: Route or handler validation schemas; HTTP error mapping; authorization decisions; business invariants; client code; semantic API error code assignment.
- Decision gates: The topic does not select between client/server stacks; wrong-layer mistakes are covered by its **MUST NOT** rows and cross-links.
- Environment: Repository seams run wherever the server process runs; host and logging constraints follow [logging policy](../logging-policy/logging-policy.md) and [error policy](../error-policy/error-policy.md) at caller boundaries.

Binding principle: The repository is a thin persistence seam. Violations are architecture / security class bugs — merge blocked until fixed or standards amended.

## Agent execution contract

C1: This document is mandatory for server persistence code in scope.

C2: [Shared agent contract C2](../_meta/agent-contract.md).

C3: Precedence: Where the error policy defines repository, transaction, and error layers, repository-layer rules in this file define what counts as correct repository behavior; transaction policy defines session participation (**REP-M-8**, **REP-N-8**); error shape and HTTP mapping remain error policy at service / route layers.

C4: Non-compliance -> bug / must not ship; STOP and fix code or standards.

C5: [Shared agent contract C2](../_meta/agent-contract.md); no Active Record substitutes, no direct model access from controllers for runtime CRUD paths covered here.

C6: Change impact: If repository rules change, list affected security, forms, transactions, and error documents; resolve conflicts before merge.

Enforcement: Stop release for violations of **REP-N**-* or applicable security-boundary requirements.

## **MUST NOT**

**REP-N-1**: Must not perform input validation duties of the route layer (the boundary schema validator, or manual shape checks for transport payloads) inside the repository. [Consequence: Layer violation bug.] [Verify: Inspect repository paths for transport-schema parsing or duplicated payload checks.]

**REP-N-2**: Must not encode business rules, workflows, or domain decisions (pricing, eligibility, state machines) inside the repository — service layer owns those. [Consequence: Architecture bug.] [Verify: Design review.]

**REP-N-3**: Must not map database or driver failures into HTTP-facing semantic error codes or API response DTOs — that mapping belongs in service / route per error policy. [Consequence: Layer violation bug.] [Verify: Code review.]

**REP-N-4**: Must not perform authorization decisions (authorization scope or role checks) inside the repository; callers pass scoped keys or enforce authz before invoking the repository (see security backend **SEC-D3** where applicable). [Consequence: Security bug.] [Verify: Code review.]

**REP-N-4a**: Any caller-provided authorization scope **MUST** be part of the query filter, not checked only after the read. Reading a scoped record by primary key alone and comparing its scope in memory splits the authorization decision in two ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)): the query may return a record the caller was not authorized to access, and the in-memory check can drift or disappear. If "absent" and "out of scope" produce different outcomes, the response may also disclose the record’s existence. Put the scope in the filter so absent and unauthorized records produce the same result and no second scope derivation can drift. [Consequence: Security bug — unauthorized read or existence disclosure.] [Verify: For each scoped primary-key read, assert the scope is part of the query filter; document and review any intentionally broader administrative read.]

Enforcement, and the predicate trap it carries. Where query shape is statically visible, a project may lock this rule with a scoped check whose entity membership comes from the consuming schema or another declared authority, rather than a hard-coded model list. The check **MUST NOT** accept a post-read comparison as proof of safety: syntax shows that a comparison exists, not whether the branches produce the same response. The one sound exemption is a key derived from the scope identifier (for example a composite key prefixed with the scope id): the documents it can address are the scope's by construction. A genuinely cross-scope read — where the request cannot prove a scope at all, such as an invitation accepted by someone who is not yet a member — is NOT scoped blindly to satisfy the rule, which would break the operation. Split the seam: keep the unscoped half for that path behind an inline suppression naming the real gate (subject identity, not scope), and move every scope-proving caller to the scoped twin. Silencing the check per file instead lets the next ungated sibling added to that file inherit the exemption unnoticed. For a legitimately broader administrative read, document the authorization boundary at the call site and keep it narrow; avoid file-wide suppressions that can hide unsafe sibling reads. [Consequence: Security bug — out-of-scope read or existence disclosure.] [Verify: For each scoped primary-key read, assert that the scope is in the filter; review any exception against its authorization boundary.]

**REP-N-4b**: The scoped key a scoped repository accepts **MUST** be a type only the scope authorities can produce — never the raw identifier type. **REP-N-4** says the caller passes a scoped key; with a plain string parameter nothing distinguishes a key that passed the membership and actor-class gate from a path parameter, a body field or a resolver's *requested* value, so the gate's presence is decided by review alone. Brand the key, and bind eight details.

- (a) Exactly two doors mint it, both in the scope authority's module. The request door is the scope object's scope-key field — membership and actor class answered in the same call, whatever the identifier's source: the request surface, an explicitly requested identifier (membership validated), or the subject's own default scope derived from their membership records (the derivation is the membership answer, so it is not asked twice). The non-request door serves work that has no request actor (scheduled jobs, queue/outbox workers, verified provider events, scope creation), and a subject-gated request whose actor is not yet a member of the scope it acts on (an invitee answering the invitation addressed to them): no scope door can admit a non-member, so after the subject gate the identifier is read from the stored record the subject was matched against — never from the request, which carries only that record's key; the subject gate and the mint live together in one small function, which is the owner (f). A platform operator who acts on a scope without being its member takes the same door: the membership door can never admit that actor, so its origin is the operator actor class itself, checked inside one narrow file against the class the operator-authentication authority read from the operator's own current record on this same request — through a request-keyed carrier only that authority writes, never the token's claim or a request field an earlier layer also writes — so that the mint refuses when that authority did not run, and is never inferred from the route it arrived on. The admitted class set is per operation and declared in that file: an operation that writes to or acts for the scope admits only the full operator class; a read-only platform surface that the router also opens to a narrower read-only operator class admits that class for that read, the set taken from the class authority's own closed list rather than re-enumerated. A narrower read-only class with no scope relation of its own is a platform-wide viewer, so its filter admits any scope identifier by design; one that is tied to a subset of scopes must have that subset checked inside the same mint. A fence on which call sites use the wider read mint is not required where the router's deny-by-default class gate already keeps the narrower class off every write and non-read endpoint. The request schema bounds the filter identifier with the identifier's own shape authority, so an over-long value is a validation rejection, never a fail-loud mint error. The door takes the identifier's origin from a closed set plus a non-empty operation name, and fails loud on a non-canonical identifier instead of turning it into an empty read — on an erasure or cleanup path too, where an empty read would report the person's data gone while the row stays; the loud failure leaves the idempotent run re-runnable once the record is repaired. Mint at the point the identifier is read from the stored record, per item, inside the per-item failure boundary, and thread the branded value down. For a verified provider event that point is where the event's subject is matched against the scope authority's record: the door takes that record's identifier, never the candidate parsed from the payload (parsing is not authorization), and the verified-identity carrier holds the branded value for every downstream effect. An entitlement gate that reads a scope-keyed entitlement ahead of the handler takes the request door itself with the least class requirement (any member): it asks membership, not actor class — the class refusal stays with the endpoint's own requirement — so a non-member is refused by the scope before the entitlement is read, and the entitlement never answers for an unverified identifier. The per-request cost such a gate adds is budgeted: the membership reads it shares with the endpoint's own scope go through the request-scoped memo, so the gate adds no second read of the same key. A population or audience computation (a platform metric over the scope population, a notification or segmentation audience whose subject is not the request actor) takes the non-request door from the record it enumerates: the listed scope row's own identifier, or — for an audience subject — the subject's own stored membership record that matched the candidate scope, never the candidate; the enumerating read and the mint sit together in one narrow file that the broad consumers call. A request-time population read may fail loud for the whole list on a corrupt stored identifier; a batch job mints per item inside the item's failure boundary. A population unit that any scheduled job also consumes — directly or through a shared metric — is batch work for this purpose: it mints per row, records a failed row once by category and leaves it out, because a single corrupt row must not silence the job for every other scope on every run.
- (b) A format brand is not the scope brand. A schema's validated-shape brand says the identifier is well formed; a well-formed identifier belongs to nobody yet.
- (c) Trimming or re-parsing drops the brand. The doors emit the canonical form, so a consumer passes the branded value itself; a schema that re-parses a context object is re-joined with the branded field from the door's output, never re-minted. A shared cross-tier input type keeps the raw identifier; its server consumer declares a local view with the branded field, as (g) does for the actor.
- (d) Not every row keyed by a scope identifier is scope-owned. A row owned by a subject (a person's own rating of a resource, a membership probe that answers whether the subject belongs to the scope, including the persistence read the scope door itself asks) keeps the raw identifier, because its gate is subject identity or the membership question itself — name that at the function (the cross-scope split of **REP-N-4a**), do not brand it blindly. When such a subject-owned write must still take a scope-wide guard that requires the brand (a closure fence every scope write passes), the subject gate runs first and the brand is minted afterwards from the record that gate required (the subject's own membership or ledger row), in a narrow owner file — never from the request's identifier; the subject-owned repository itself stays raw. The same holds for a counterparty scope reached through a public key (a sharable code owned by another scope) and for a public listing read: the acting subject is not a member there, so the counterparty's identifier stays a stored lookup and the listing takes no scope key at all — only the acting scope's identifier, the value the write records, is branded. The probes the doors themselves ask stay raw for the same reason: the scope's own open/closing/existence probe, the ownership probe that resolves the scope's actor, and a completion probe that must still answer after the scope is gone. So do the scope reads a door asks to decide an actor-class requirement after membership but before the mint (does the requested record, or the record behind a requested child row, belong to the acting subject?): the mint depends on their answer, so they cannot take the brand. Give each such read its own repository function that answers only the gate's question — a boolean or the owning key, never a document — is called only by the door, and names that at the function; the general scope read of the same row then takes the brand. A general read shared by the door and by ordinary consumers is the defect this prevents: the door's raw call holds the whole function, and with it every consumer's chain, raw. Only-the-door is review-bound (a second caller of a probe compiles); the narrow return shape is what keeps a probe from serving as a general read. Two consequences follow. A path that must reach a scope the membership door rejects by design (resuming a half-finished closure of a scope that membership already treats as closed) keeps the ownership probe as its gate and mints from the matched record's own identifier in a narrow file — never from the probed input. And an endpoint whose released client contract rests on a probe's error code keeps that probe first and mints the scope after it: the scope is the brand's only source and cannot fail once the probe passed, the probe's result is never branded, and the client keeps the code it already handles. Where the scope door can still refuse after the probe passed (a member leaving a scope the membership door already treats as closed), the two consequences combine: the probe stays the gate and its code the contract, and the brand is minted from the record the probe matched — its own scope field, in the narrow file — never from the requested identifier.
- (e) Conversion is whole per repository function. A function is converted together with every caller chain up to a door; an assertion at an intermediate layer is a forged brand, and a half-converted chain is the defect in a new place. When a function's callers run deep into another subsystem (a scheduling or recurrence engine, a sale flow), the whole function waits for that subsystem's conversion slice and stays raw until then — converting it for its shallow callers only is exactly the half-conversion this detail forbids. A unit that serves both a request path and a scheduled path and receives a stored record takes the branded key as a parameter, so each caller brings it through its own door (the request its scope, the job its stored-record mint); inside, it compares the record's own scope reference with the key and fails loud on a mismatch — it neither re-derives the scope from the record (a second source for the same fact) nor trusts the pairing silently.
- (f) Both escapes are fenced. The brand's assertion escape is fenced by a producer-only assertion check, as for every brand. The non-request door is the same escape in call form — a function that turns any string into the brand — so its call-site set is closed: calls are rejected outside an owner list that names each caller file (not a directory, because a directory of scheduled jobs can still be imported by a request handler), and a new non-request caller joins that list through review. An owner entry exempts every present and future call in that file, so the owner is the narrowest file: when a broad request-reachable file needs a stored-record identifier, the stored-record read and the mint move into a small function in a file that does only stored-record work, and that file is listed — never the broad one. Nor does an owner export a function that turns a caller-supplied identifier or record into the brand: every importer could call it, which re-opens the closed call-site set one level up. An exported owner function either performs the gate and the stored-record read itself and returns the brand of that gated record, or downstream code selects the brand from the gate's own branded output (for a multi-scope subject panel: the membership set the subject gate resolved and minted) rather than minting it from a row it was handed.
- (g) An actor carries the brand only through the scope. Where decisions take a resolved actor whose record names its scope and that actor type is a wire contract the client also parses and builds, the server brand stays out of the shared type — the client would have to imitate a door it does not have. The scope authority mints a server-only view instead (the shared actor with its scope field branded) together with the scope: scope kinds that decide on the actor carry it, the route gate publishes it, and a scope without an actor obtains one for that same scope through one function that takes the scope itself, never a raw identifier, and refuses scope kinds that already carry an actor (one path per actor). A unit that must re-verify an actor-gated scope's actor inside its own transaction snapshot (a money write that re-checks membership and role after the pre-claim gate) takes the scope itself — never a subject identifier beside the scope key — and re-verifies through one scope-authority function that takes the scope and the session: it reads the subject the scope's actor names in that session, re-resolves the actor for the scope's key, re-applies that scope kind's gate and binds the result to the same scope. It accepts only scope kinds whose gate it can re-apply from the scope alone; a kind whose gate needs the original requirement's parameters joins only with a branch that re-applies that gate, never as a gate-less "fresh actor" path. Binding checks that the actor was resolved for the scope's key and fails loud otherwise. A resolver that answers membership but no declared actor-class requirement never mints the view — that would be a door around the scope. A function that reaches a scoped repository with the actor's scope key takes the view alone, never a second scope parameter beside it; the view's assertion escape is fenced like the key's, because a narrowing assertion from the shared actor compiles clean.
- (h) A free-form parameter carries the brand as a required top-level field. A repository function that takes a query-filter object or a create payload instead of discrete parameters types that object so its scope field is required and branded — one scoped-filter type laid over the free filter (the multi-scope form is a set of branded keys) and one scoped-payload type over the free payload; the rest of the object stays as free as before. The top-level key suffices because a document filter's top-level fields are AND-ed: a nested condition on the same field can only narrow the match, never widen it past the branded key. A composer that wraps the filter (a cursor continuation placed under a conjunction) repeats the branded key at the top level, and a payload rebuilt from an ORM document re-joins the branded key instead of trusting the document's plain field ((c)). A platform-wide scan (a scheduled sweep that mints per item) declares the key absent in its filter type, so a raw identifier cannot enter it; a free filter over subject-owned rows (a recipient's own notifications, an invitee's own invitations) stays raw per (d) and is named at the function — or, better, becomes a typed signature whose subject key cannot be omitted. An identifier-only update or delete of a scoped row takes the key in its filter as well, even when a scoped read preceded it (**REP-N-4a**).
- Check reach: whether an owner file's call launders a request-surface identifier is a data-flow question no single syntax tree decides — review-bound; so is whether a population or audience unit is reached only from population and audience work (a member request that called the audience gate with its own subject would get the same answer the membership door gives, through a second door); so is whether an operator door's per-operation class set matches the surface it serves (a read-only class set wired to a writing handler compiles); the scoped-filter type checks only the top-level key, so a nested condition on the scope field is untyped (it can only narrow); an object literal that spreads a free record (an index-signature type — a parsed query string, a JSON body, an untyped map) AFTER the branded key compiles, because the record's type names no scope field, yet a scope field inside it overwrites the key at run time — spread a free object only before the key, never after; and a service that reads a scoped model directly instead of through the repository bypasses the brand entirely — the repository-only persistence rule (**REP-M-3**) is what closes that path, and any direct-model-access fence decides it only where that fence is enabled, so elsewhere those reads are review-bound. Use the enforcement mechanism the adopting project documents for the brand, the assertion escape and the call-site closure; a reference to a check is not evidence that it exists or covers the full rule, so record its actual scope and limits.

[Consequence: Security bug — an ungated scope identifier reaches a scoped read or write with no type error.] [Verify: Every scoped repository parameter carries the brand; every non-request-door call site names a stored-record or provider origin, never a request field; every actor whose scope key reaches a scoped repository is the scope's server-only view, not the shared actor.]

**REP-N-5**: Must not use Active Record-style pattern where domain entities perform their own persistence for paths covered by **REP-M-3**; must not bypass the repository layer for convenience. [Consequence: Architecture bug.] [Verify: Architecture review.]

**REP-N-6**: Must not import or depend on client libraries (client state-management libraries, UI hooks, browser-only APIs). [Consequence: Build / boundary bug.] [Verify: Dependency and import audit.]

**REP-N-7**: Must not validate caller arguments with ad hoc argument validation that duplicates the transport boundary schema — missing or malformed identifiers are rejected before the repository (**REP-M-2**). Repository may still return null for honest "not found" on well-typed lookups per error policy M8. [Consequence: Layer violation bug.] [Verify: Code review.]

**REP-N-8**: Must not start or end database transactions or sessions at the repository layer (transaction/session lifecycle operations (such as begin, commit, or abort, or their equivalents)) — service owns lifecycle per transaction policy **TX-N-1**. [Consequence: Architecture bug — merge blocked.] [Verify: Grep transaction APIs under repository paths.]

**REP-N-9**: Must not let a read mode that bypasses object hydration depend on schema defaults, getters, virtuals, or setters. ORM/ODM plain-object, raw, or projection modes may return only stored fields, while hydrated objects can synthesize defaults or derived values. A field added after existing records were written may therefore be absent from storage even when a hydrated read appears complete. The schema declaration alone does not prove that persisted rows contain the field. (a) Type projected reads to allow fields that may be absent and decide the missing case explicitly at the read seam — partition it or return a named integrity gap the caller can handle. (b) Substituting a schema default for an absent stored field fabricates data and may turn “record predates this field” into an apparently authoritative value. Where a validated reader requires the field, [**REP-M-16**](repository-index-migrations-and-validated-reads.md) binds the return type as well. A checker for this relationship needs both the schema declaration and the read projection; a local syntax check may not establish the intersection. What can be checked at the consumer is that missing persisted values are handled explicitly and are not silently defaulted after the read. [Consequence: Fabricated measurement presented as stored fact, or a whole read path failing on one legacy record.] [Verify: For each hydration-bypassing read, list projected paths with schema defaults and confirm the seam handles absence explicitly; assert that application code does not reapply a default after reading.]

**REP-N-9** application — implicit identifier type. A model's type declaration **MUST** give the document identifier the type the store actually holds: an ODM-generated identifier is an object-id type, so declaring it a string without a string identifier path in the schema is forbidden. The compiler then passes the object into string fields and the first string method on it throws an unregistered `TypeError` far from the read. Where a string form is needed, derive it once at an identity seam that proves the stored type and raises a registered carrier otherwise; call-site `String(doc._id)` copies are a second derivation ([**SSG-M8**](../ssot/ssot-principles-and-precedence.md)). Held by the type system once declared truthfully; new declarations are review-held.

**REP-N-10**: Must not make a database query fail on purpose by embedding an always-invalid literal in a server-evaluated expression. A query planner may evaluate the expression before reading any document, turning a row-specific data problem into a failure for every tenant. Emit the fault as data: project a row-level verdict, lift it through the aggregate, and raise the registered error in application code; ensure later filters retain rows carrying the verdict. Where a database expression supports explicit conversion-error behavior (for example MongoDB `$convert.onError`), specify that branch rather than relying on an invalid conversion to fail the whole query. A focused static rule can enforce the conversion error branch; lifting the verdict across the stage builder and all consumers remains review-bound. [Consequence: Data-independent outage with an unclassified driver error.] [Verify: Inspect conversions for an explicit error branch; run the query with a filter matching no documents; name the row-level verdict and caller that raises the registered error.]

**REP-M-3** application — existing seam reuse. When relocating a direct read, first check whether a typed, scoped repository method already performs the same read. Reuse it only after comparing the filter, hydration, projection, order and session contract with the original call. Otherwise add a narrow method to the owning repository. A caller whose whole file has migrated can then be included in the direct-model-access fence; verify the check against known-safe and known-unsafe cases using the consuming project’s verification policy. This is a call-site and cross-file equivalence review: syntax alone cannot decide whether two query results mean the same thing.

**REP-M-3** application — one guarded update, one definition. A second write shape for a guarded field (by id; every row holding a previous value) joins the seam owning the first and reuses its update definition; an inlined copy re-decides the guarantee (companion counter, validators) per call site. Declare the guarded field read-only on the document type where the language allows it, so a direct assignment on a loaded document fails to compile in every file; a syntax-tree write-ownership row keyed to the model can only see files that name the model, while the loaded document usually reaches other layers through a repository, so the most common escape is exactly that assignment. A project may enforce this shape at its canonical write seam.
