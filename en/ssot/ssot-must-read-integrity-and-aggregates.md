**SSG-M18** application — counting unit and retained evidence. A subject-acquisition aggregate counts the recorded subject birth/conversion, not the number of devices, sessions or retry records later linked to it. Select the established writer-owned markers, not a client-sendable event-type string alone; deduplicate the subject before period and parent-source filters. State the recorded timestamp anchoring the cohort and revenue windows. Earliest eligible immutable evidence is a derived observation: evidence captured after the anchor cannot invent its source, conflicting equal-earliest facts stay unclassified, and an earlier genuinely late-linked fact may correct the view. Do not claim a frozen device pointer where none was recorded. Missing eligible evidence is an explicit unclassified result; a malformed required anchor remains a typed failure. A finite retention boundary belongs to the derivation and uses the existing retention authority: an expired history window is unavailable, never measured zero. Preserve independently available metrics. Inclusive N-calendar-day intent has one timezone-specific derivation shared by default, selection and prefetch, not N subtracted days plus two included endpoints. Identity scope is declared with the aggregate: an explicitly authorized global subject-portfolio report may include that subject's facts across organizations; this does not authorize a tenant-request reader to drop its tenant association.

**SSG-M18** application — monetary unit integrity. A unit is part of a monetary quantity. Its identity and missing-unit count come from the exact same facts and period as the amount; a dominant or arbitrary representative unit is not association proof. Validate required monetary facts and unit identity before combining amounts, partition sums by unit, and never sum or divide incompatible units without one separately established conversion authority. Such an authority **MUST** freeze each record's rate at that record's own payment moment, stored on the record beside the unchanged original amount and unit, and every aggregate **MUST** read the converted view through one shared projection; a record not yet converted keeps its own unit and stays in the mixed-unit outcome — no rate is guessed or taken from the read time. Reason: a rate applied at read time silently rewrites every past total each day the rate moves. An actually empty income population may have no unit; a monetary record with a missing unit is a failure. A revenue/spend ratio with incompatible or unknown units remains explicitly unavailable while valid count and non-monetary denominator dimensions survive. Query/API shape and the shared invariant authority are stronger than a new syntax rule; whether they cover the same fact population remains cross-file review (**ENA-P1**, **ENA-A1**(c)).

**SSG-M18** application — the name states the measured fact. A reported figure's name — its response field, its screen label, and any alert, verdict or recommendation text built on it — **MUST** name the fact its derivation actually measures. A proxy (an account deactivation standing in for an uninstall, a sign-up for an install, trailing billings for recurring revenue, inactivity for a subscription loss) **MUST** carry its own name and definition, and a decision that consumes it (a kill switch, an alert rule, a recommendation) **MUST** read it under that name, never under the target fact's. Where the target fact has no measurement, the target-named figure is absent, never filled by the proxy. Reason: the reader acts on the name; a proxy published under the target's name passes review because its arithmetic is correct, and every decision taken from it is wrong for as long as the two facts diverge.

**SSG-M18** application — forecasts and outcomes. A forecast amount **MUST** be shown as a labelled estimate range derived from one registered rate, replaced by the subject's own measured rate once its sample reaches the registered minimum, never as a best-case total; an outcome reported after a suggested action **MUST** be named an association inside one registered attribution window, never a cause. Reason: a best-case total and causal wording are read as promises, and a money decision taken from them is wrong by the gap.

**SSG-M18** application — persisted snapshot meaning. A persisted snapshot of a reported aggregate **MUST** store the version of its derivation's meaning, written by the snapshot's single writer; every reader **MUST** admit only rows of the current version, and a change of the derivation's meaning **MUST** raise the version and rebuild the older rows through the same derivation and writer (dry run, apply, read-only verification). Reason: an old row read beside new ones shows a figure of another meaning under the same label, and nothing on the screen tells them apart. Review-held (**ENA-GV3**).

**SSG-M18** application — configuration valid at the time. A historical aggregate that depends on a configuration (working hours, prices, thresholds) **MUST** read the configuration in force in each period, or exclude the periods before the configuration's last relevant change as stamped by that configuration's single writer; today's configuration **MUST NOT** be projected onto past periods. Reason: projecting current settings onto history fabricates past capacity or price, and a settings edit silently rewrites the past.

**SSG-M18** application — filter bounds within the source window. A user-editable filter evaluated over a derived per-subject summary **MUST** bound every day and window field to the windows that summary actually covers, and its schema **MUST** reject a request beyond them; it **MUST NOT** answer from the covered part, and a filter field whose fact does not yet exist **MUST** evaluate as absent with the subjects it removes counted in the response. Reason: a count over a window the source never read, or a constraint that silently empties the list, is shown to the user as a measured fact. Review-held (**ENA-GV3**).

**SSG-M3**: If the project defines an SSOT helper for a derived value, application code outside documented exceptions must not re-derive the same semantic from raw DB queries or stale denormalized copies alone — use the helper or documented read path. When that helper reads a sibling value (for example a label, amount, or status) from a snapshot/denormalized entity selected for an expected identifier, it **MUST** first prove the snapshot row's canonical identifier exactly matches that expected identifier; a non-empty sibling value alone is not association proof. This applies equally to single-object and array/union branches. Missing or mismatched identity/value fails loud without an unrelated-row, raw-identifier, or guessed-value fallback; diagnostics follow the logging/security policy rather than interpolating identifiers into free text. (Primary enforcement: review per **SSG-P2** table.) [On violation: Bug — wrong-entity derivation / review rejection / must fix] [Verify by: Helper branch review: exact identity match dominates sibling-field return; mismatch/missing runtime path; static guards where configured]

An edit preview of an existing operation must use the same exclusion context as its canonical write predicate. A caller-supplied record identifier is only a lookup candidate: resolve it inside the authorized tenant scope, derive any session/relationship exclusion from that stored record, and pass the identical verified scope to both the availability predicate and its displayed occupant list. Creation without edit context keeps its own scope. A read-only preview never takes the write claim. This cross-file contract is review-owned; a scoped query and shared predicate prevent parallel derivation, while a single-file check cannot prove that every caller supplies the correct edit record (**ENA-GV3**). The preview must resolve the same target resource owner as the writer too. For an edit with no explicit new assignee, derive the target resource owner from the tenant-verified stored record when the writer preserves that owner; do not substitute the inspecting actor. An explicit assignee still passes the existing resolver, and create keeps its existing fallback. Boolean occupancy and visible occupants consume the same resulting target and verified exclusions. A malformed stored owner uses the established invariant-error boundary. This read/write target parity remains cross-flow review-owned; no new writer or scope authority is introduced.

For a multi-tenant event or metric join, exact association proof includes every authority dimension that identifies the fact (at minimum the tenant/organization and subject when both are present); subject-only matching is forbidden. If a durable state flag semantically requires a companion anchor (for example an activation timestamp), its single writer **MUST** co-write both values and every metric/read boundary **MUST** validate the anchor before admitting that row to either numerator or denominator. The same obligation covers a companion quantity the flag asserts was granted (duration, amount or capacity): a projection retains the raw missing value and the read validates its declared range; a zero substituted inside an aggregate is a fabricated quantity, and the current clock substituted for an absent historical anchor is a fabricated event time. A missing or malformed required anchor or quantity fails loud through the typed error policy; warning-and-skip, guessed defaults, and denominator retention are forbidden because they manufacture a metric from internally inconsistent facts. Stated enforcement limit: selecting which stored field is required by a state assertion and whether a metric joins every identity dimension are cross-file semantic questions; the named invariant authority and scoped persistence API carry the guarantee, with review of their use. No new syntax rule is admitted when those stronger mechanisms already apply ([**ENA-A1**(c)](../enforcement-architecture/enforcement-admission.md)). [On violation: Bug — cross-tenant attribution or corrupted metric] [Verify by: Compound join predicate/key on both sides + paired writer + raw projection + pre-denominator runtime invariant + static enforcement where configured]

For a persisted configurable setting with a product default, the default **MUST** have one named authority consumed by every schema default and insert/upsert initializer; repeating the literal at those write surfaces creates parallel default authorities. A create-only default applies only when the inbound field is absent/`undefined`: a valid explicit falsy value (for example numeric `0` or boolean `false`) **MUST** survive unchanged, while `null` follows the boundary contract and **MUST NOT** be silently reclassified as absence. If an ODM schema default can also run during hydration, update, or upsert and thereby mask a missing field on an existing row, the create-domain writer **MUST** resolve the default explicitly and the persistence schema **MUST** retain validation without that hydration-capable default. After a settings row exists, its persisted field is the effective read authority: readers **MUST** validate and use that value, not silently replace it with the default or a local literal. A missing existing row is not permission for a lazy create/backfill; it fails loud unless a separately authorized repair/migration owns that operation. Missing, malformed, or out-of-contract persisted configuration fails loud through the typed error policy so corrupted state cannot be masked as a legitimate default. Stated enforcement limit ([**KIT-INV-8**](../authoring/kit-structural-invariants.md)(b)): only the single-writer half is mechanically fenceable — a cross-file check can restrict the persistence seam to the create-domain authority, and that is the half a repository should fence. The absence-versus-truthiness test itself is review-only, because the two single-file shapes that a syntax tree *can* decide do not isolate the defect: a truthiness fallback onto a named default (`x || DEFAULT`) is decidable, but where the adopting project's tree and history show no occurrence a rule for it would name no regression ([**FP-M17**](../false-positive/check-design-rules.md)) and could produce no real positive specimen ([**FP-M20**](../false-positive/check-verification-rules.md)(a)); and "a persistence-schema field declaring both a required validator and a default" is decidable but fires on the legitimate server-owned majority of such fields, which are not this defect. What a check would need is the one fact no file declares: which schema fields are caller-supplied create-only input whose default a create-domain writer already resolves. Deriving that would require a hand-maintained field list, which is itself a second authority for the same question ([**SSG-M8**](ssot-principles-and-precedence.md)) and is therefore not the answer. [On violation: Bug — configuration drift, explicit-value loss, or hidden corruption] [Verify by: One exported default constant + exact-absence resolution in the create-domain writer + all creation surfaces delegate to it + lean/raw persisted read where hydration would inject defaults + no update/lazy-ensure default writer + runtime invariant + any admitted cross-file seam check]

When one command derives eligibility, classification, amount, and a durable mutation from persisted configuration, every pre-mutation derivation **MUST** consume the same validated configuration snapshot; independently re-reading or locally copying one threshold can mix policy versions inside one decision. The durable mutation boundary **MUST** re-read the authority in its transaction/atomic consistency scope and prove the supplied snapshot still matches by canonical version plus every decision-bearing field (or by an equivalent collision-resistant canonical fingerprint) before writing. A mismatch is a precondition failure and triggers fresh evaluation, never a best-effort merge. Likewise, when several derivations in one decision require the same mutable fact set, load that fact set once and pass the exact snapshot; sequential independent reads are not one decision proof. Historical audit values already written under a valid snapshot remain historical facts and **MUST NOT** be rejected merely because current configuration later changes. [On violation: Bug — mixed-version decision, read-race, or retroactive reinterpretation] [Verify by: One config/fact snapshot passed through the decision graph + transaction-bound exact snapshot comparison + no duplicate source read/local threshold + static enforcement where expressible]

**SSG-M18**: A reported aggregate — a figure computed over a period from many records, such as a summary total, a utilisation ratio, or a ranked bottleneck — **MUST** have one named derivation, and every consumer **MUST** read it from there: the screen, the export, the scheduled summary, and any persisted snapshot of it. Three properties are declared with the derivation, never left to each caller. (a) The period's boundaries and the timezone that owns them. A period is a pair of instants, and which instants a label such as "this month" denotes depends on a timezone; that timezone **MUST** be the one owning the measured subject (the tenant's — not the server's and not the reader's), resolved through the project's single timezone-resolution authority and failing loud when it cannot be resolved. Two consumers computing their own boundaries produce two different numbers for one label, and neither looks wrong from where it stands. A ratio or share over time (utilisation, fill, empty capacity) presented as a finding **MUST** be computed over closed periods only: a window containing a future instant counts time that has not happened as an observed zero. A running total labelled as period-to-date is not such a finding. (b) The time basis. The derivation states which timestamp of a record places that record inside the period — created, occurred, completed, settled — and every consumer plus every cross-period comparison uses that same basis; a comparison whose two sides use different bases is not a comparison. (c) The empty and insufficient outcomes. "No records in this period" and "too few records for this figure to mean anything" are explicit results the caller handles. A zero substituted for an absent value is indistinguishable from a measured one; a ratio over an empty denominator **MUST NOT** be emitted at all rather than defaulted. Where a minimum window or sample size is required, that threshold belongs to the derivation and is named once, never repeated at a call site, and the insufficient result **MUST** carry its progress (the sample held and the sample needed) so the reader sees how far the figure is from meaning something. (d) The population — whose records the figure counts. A record's tenant key answers *which tenant's data this is*; it does not answer *which class of actor produced it*, and an aggregate about one class that filters only by tenant silently counts every other class sharing that tenant — the customers, guests or external parties attached to the same organisation. The shape survives review because the filter looks complete: the rows really do belong to the tenant, the total really is a total, and nothing is missing; the figure is simply about a larger population than its name claims, so it reads as correct from every side. Three obligations. (1) The producing class is a stored discriminator written at record birth, never a read-time join. Class membership is a point-in-time fact — a subject may move between classes (a customer becoming staff, a trial becoming a payer) — so re-deriving it at read time from today's membership re-labels every historical record and corrupts precisely the transition such a figure often exists to measure. The write path takes the class as a required parameter from the one classifier: a defaulted parameter reintroduces the defect the first time a new write site omits it, and the fact, once unrecorded, cannot be recovered later. (2) Records predating the discriminator are an explicitly named class, not a silent default. Their class is unknowable; the derivation names that legacy class, states which side of the boundary it falls on, and justifies the choice by measurement rather than assumption — the two candidate rulings differ by the entire history, so one keeps the defect for old rows while the other empties the series and reads as a regression. (3) The class filter is one exported predicate every reader spreads. Written once as a named match fragment, the ruling on the unlabelled class has a single site; spelled out per reader, its inverse is one keystroke away and reverses that ruling silently. Limit of mechanical enforcement (stated, not left to read as coverage): a single-file rule can require the predicate only where the filter is an object literal at the query call; filters assembled into a variable across statements, or built by a helper, escape it, and no single-file tree can tell which aggregates are *about* one class. Those stay review obligations. A persisted snapshot of an aggregate is a cache of that derivation, never a second authority: it is written only by recomputing the same derivation, and a reader that finds it missing recomputes instead of inventing a value ([**SSG-M8**](ssot-principles-and-precedence.md)). [On violation: Bug — two screens report different numbers for the same period, a defaulted zero is read as a measurement, a figure named for one actor class silently counts another, or a snapshot becomes a parallel authority that silently ages] [Verify by: One exported derivation with every screen/export/job consumer importing it; period boundaries built from the subject-owning timezone through the single resolution authority; the time basis named at the derivation; closed periods only for a finding; explicit empty/insufficient result types carrying progress rather than zero or null defaults; the producing class stored at write time through a required classifier parameter, the pre-discriminator rows ruled on by name, and every reader spreading the one exported class predicate; the snapshot writer calling the same derivation]
