Part of: [SSOT principles and precedence](ssot-principles-and-precedence.md). **SSG-M1** is defined here and only here; its measured shapes are listed below with a one-sentence test each. **SSG-M3** and **SSG-M18** are in [read integrity and reported aggregates](ssot-must-read-integrity-and-aggregates.md).

**SSG-M1**: For every protected datum, operation, or canonical derivation in scope, the design must identify exactly one authoritative source (write path, function, or read helper per KAT); parallel unauthorized writes or unsanctioned duplicate call sites are forbidden. Implements **SSG-M0** per semantic — not one file for all semantics. An access authority owns permission to materialize now; it does not thereby own durable business intent or the lifecycle of existing domain resources. A denial **MUST NOT** terminate, delete, or rewrite them unless a separately registered terminal command owns that mutation. A provider-facing identity **MUST NOT** be derived from a mutable field. Where an external provider keys its subscriber/customer/tenant record by a value the application computes from a user-editable attribute (phone number, e-mail, username), every change to that attribute orphans the identity on the provider side: the local projection can be re-keyed but the provider's record cannot, so the next lookup asks for a record that does not exist. Local re-keying is therefore the cause of the divergence, not evidence against it — and a read that cannot resolve the identity **MUST** fail loud rather than degrade to a default/entitlement-free state, because a silent default is indistinguishable from a genuine absence of entitlement. The authority for a provider-facing identity is an immutable opaque value minted once; migrating an existing derivation needs the provider's own alias/transfer operation and is never a local-only change. [On violation: Bug — must fix; CI fail when guards cover the rule] [Verify by: Guard / config / review; for the provider-identity half, grep the identity builder's inputs for fields the domain permits editing, and confirm the unresolved-identity branch raises instead of returning a default]

An authority's output **MUST** already be canonical, and a consumer **MUST NOT** re-canonicalize it. Naming one owner for a datum is only half the rule; the other half is that the owner returns the value in its final form — trimmed, normalized, with "absent" expressed once (`undefined`/`null`, never a sentinel the caller has to re-interpret). When the authority returns a raw-ish value and leaves the last normalization step to whoever called it, the single authority has silently forked into as many normalizations as it has consumers, and the split is invisible in review because every call site still calls the right function. It fails asymmetrically: consumers that normalize and consumers that do not derive different identities for the same input, so a cache key, an authorization gate and a persisted record can each target something different within one request. Two consequences. (a) Every reshaping step belongs inside the authority — including the last one, the one that looks too small to matter; the caller uses the returned value as-is and tests absence, nothing more. (b) The forked normalization is not a style issue, it is a second authority and is removed under the no-parallel-path rule, in the same change as the fix. This is mechanically enforceable per authority: the caller-side re-normalization (`f(x)?.trim()`, `f(x) ?? ''`, `f(x) === ''`) is decidable from a single file's AST once the call is resolved to the authority by import provenance. A pure type adaptation that does not change the value (`?? null` to satisfy a `T | null` signature) is not re-canonicalization and is not the target. [On violation: Bug — one input yields two identities inside one request; must fix at the authority] [Verify by: read every consumer of the authority and confirm none reshapes the returned value; single-file AST rule flagging a normalizing operator applied to a provenance-resolved authority call]

A context that cannot raise **MUST** read the already-resolved value, not re-run the resolver. Some consumers run where throwing has no receiver — a hook that runs after the response is sent, a `catch` block assembling diagnostic context, a teardown path. If the authority validates its input and can raise, calling it from such a place manufactures a new failure class: after the response, an exception has no boundary left to catch it; inside a `catch`, it replaces the original error with its own. The answer is neither to copy the authority's parsing inline (that is a second authority) nor to swallow its exception (that is a fallback). The authority records what it resolved into the request/operation-scoped context that already exists, and these places read that record through a non-raising reader which returns the resolved value or nothing — never a re-parse of the raw input, never an invented default. A value absent there is honest information: it means resolution never happened on this path. For a tenant identifier the non-raising reader **MUST** return the membership-proven value ([**SEC-M-ZT-5**](../security/security-tenant-scope-gates.md)(2)); a resolved-only record may reach diagnostics only under a field named as requested, never as the tenant the effect is attributed to — a resolved scope is what the caller asked for, not what it may reach. Do not open a second per-request carrier for it — the record belongs in the one the runtime already threads. [On violation: Bug — an unhandled exception in a post-response hook, or an original error replaced by the resolver's] [Verify by: for each authority that can raise, list its call sites and confirm none sits in a post-response hook, `catch`, or teardown path; the non-raising reader has no branch that parses raw input]

A derived field **MUST NOT** remain writable in an inbound contract. When a value is computed from other state by a single derivation (`isActive = remainingSessions > 0`, `total = sum(lines)`, a status computed from a lifecycle), the request/DTO/command schema that accepts the entity **MUST NOT** expose that field as an input — accepting it creates a second writer for a datum that already has an authority, and the two writers do not merely conflict, they conflict silently and asymmetrically: whichever runs last wins, so a value the API confirmed as saved is reverted at the next event that re-runs the derivation, with no error and no trace. Four obligations follow. (a) Direction is one-way. The field stays in the response (it is read); it leaves the request (it is not written) — and that contract is expressed in the schema, not in prose. (b) Ordering is not a fix. Running the derivation after the request write makes the derivation win, which merely converts silent data loss into a silent no-op; logging the contradiction beats losing it, but the API still advertises an input it does not honor. (c) An unused input is still a defect. Measure consumers before deciding: a writable derived field with zero callers is a latent trap, and dropping it is a documentation change; once a client depends on it, removal is a breaking change. (d) If the field genuinely must be settable, it is not derived. Then the derivation is the thing that must go — one authority either way; what is forbidden is keeping both and picking a winner at runtime. When a contract field is removed for this reason, record why in the schema itself so the next author does not "restore the missing field". [On violation: Bug — the API confirms a write it will silently revert; must fix before ship] [Verify by: For every field written by a derivation, assert the inbound schema does not declare it; consumer count of the removed input recorded in the same change; single-file AST rules can flag a request-schema key whose name matches a known derived field where the project maintains such a list]

A closed membership over a vocabulary is a DERIVATION from that vocabulary, never a second list of its members. When a union or enum already names a closed set of values, a per-value decision over it — which members a gate accepts, which route one way and which another — **MUST** be written as a total map keyed by the vocabulary (`Record<Union, …>`), and any runtime set or list **MUST** be derived from that map. A hand-written list of the same literals is a second, type-independent declaration: adding a member produces no mismatch, because there is nothing to mismatch — the compiler sees two unrelated definitions. The new member falls outside the list and the path carrying it drops to the "unknown" branch with no error and no warning — only missing behaviour, found from a user report. The total map inverts this: the member cannot be added without the compiler demanding a decision for it. The exclusions are the point — a member left out of a list is indistinguishable from a member forgotten, whereas an explicit `false` records the deliberate "no". A coarser VIEW of that vocabulary is the same derivation. A collapsed copy stored beside the authority (a three-way role beside the four-way one) is a second writer, and its name must say which scope it collapses — an unqualified name is read in the other scope. Derive it; where a released wire contract still carries the copy, keep it as a one-writer alias. [On violation: Bug — a new vocabulary member silently loses its behaviour] [Verify by: single-file AST rule rejecting a bare literal list whose members all belong to a vocabulary declared in the same file; a vocabulary declared in another file needs type information and stays with review]

A narrowed read that feeds a derivation takes its projection from one field list, and the derivation's input type is locked to that list. When a derivation (or a cache it fills) is fed by a projected read instead of the whole record, a field the derivation reads but the projection omits arrives as "absent" and yields a wrong answer with no error. Declare the selected fields once as a constant, build the projection from it, and make the derivation's input type fail compilation for any key outside it (for example an intersection that turns every such key into a required `never`). A hand-written projection string beside a hand-written input type is two lists of one fact. [On violation: Bug — a new derivation input silently reads as absent] [Verify by: the compiler, once the lock exists; whether a projected read feeds a derivation at all is review]

A record created in a practice (training, sandbox) scope **MUST** carry one persisted marker, and the marker **MUST** have one decision authority. (a) It is stamped at a single model-level choke point every create path passes; a path that bypasses the persistence layer's middleware calls the same authority. (b) A client-declared scope is a claim: the authority validates it against the authenticated actor, the record's tenant and the scope's live state on every stamped write and refuses otherwise — a dropped claim would write a real record. (c) A practice record **MUST NOT** link to a real money parent, nor a real record to a practice parent: erasing it would rewrite the real parent's derived state; children born later inherit the parent's marker. (d) Every derivation that reaches real end users, money, quota, analytics or other actors **MUST** exclude marked records inside its own authority through one shared predicate; reads that show the record itself keep it. (e) Erasure **MUST** select by the marker only, never by a time window or name, and runs as the separately chosen full money scope (PAY-M11). (f) The client that declares the claim **MUST NOT** send a write while the scope's state for the write's tenant is unknown (cold start, tenant switch, evicted cache): it reads the state from the server first and does not send the write when that read fails. (g) Behaviour events the actor causes while in scope carry the same marker, stamped by the event writer from the validated claim, and self-driven metrics (engagement, understanding, activation scores) exclude them. (h) Whether a scope kind marks at all is one total map over the scope kinds, read by the client that declares the claim and every surface that announces erasure, and a guided first use of the real product is never a practice scope — its records are the user's real first records. The marker authority marks what a valid claim names and **MUST NOT** reinterpret a claim by its scope kind: a released client that still claims a kind announces that scope's erasure in its own copy, and turning its records real would leave practice data the user was told is erased. Why: a missed path or a per-screen filter turns practice data into real notifications and revenue. [On violation: Bug — practice records reach real end users, money totals or metrics, or erasure misses/oversteps] [Verify by: review]

A failed join **MUST NOT** delete the row, and a deleted referent **MUST NOT** be replaced by a fabricated record. A join/populate result is a derivation; the identity of a row is the reference the row's own record carries. An ORM that resolves a reference in place expresses "target not found" by writing `null` over the very field that held the reference, so a consumer reading the joined object can no longer tell "this row has no reference" from "this row's referent was deleted" — and the usual reaction, dropping the row, silently deletes real history from every surface that reads through that path, including surfaces carrying money. Three obligations. (a) Recover the identity from the record, not from the join. The raw reference is still obtainable — from an un-joined read, or from the ORM's own record of what it substituted — and each row must keep its own key: grouping by the joined `target._id` collapses every unresolved row into one bucket or drops them all, while the record's own reference keeps each deleted referent distinct. (b) A deleted referent is a data STATE, not an authority failure. Where the domain has decided that history survives the record — the ordinary decision wherever money or completed work is attached — "the referent is gone" is the authority's answer, not its silence, so the fail-loud obligation for an authority that *cannot* answer does not reach it. Model the state instead: the event-moment frozen label where one was captured, otherwise an explicit "record deleted" marker resolved from the display catalogue in the surface's own language, one resolution per report rather than per row. (c) Never mint a substitute entity to satisfy a required field. When the consumer's type demands more fields than the surviving evidence carries, that is the signal that the field must become optional, not that the missing values may be invented; a fabricated referent is indistinguishable from a real one at every later read, and a lossy identifier (a slug, a normalized key) is never reversed back into the value it was derived from. The genuinely reference-less row — no key at all — stays fail-loud, because that one *is* a pipeline defect. Stated enforcement limit. A consumer's falsy value alone cannot show whether it was written by a failed join or was absent all along: the join is declared in the repository/query layer while the falsy test is written in the consumer layer, and the ORM's substitution is a runtime fact that leaves no textual trace at the test site. A single-file syntax-tree rule therefore cannot soundly recognize the condition: a broad predicate ("a loop that skips a row on a falsy check") matches many legitimate sites and is born red, while a narrow single-file variant ("a file that both joins `p` and tests `!p`") finds no reliable evidence, because the pattern this rule exists for typically spans files. A cross-file guard would need the value's data flow from query to transform, which no grep-level check resolves soundly. The fence that would close the gap is a repository-layer convention that returns the raw reference alongside the joined object, making the distinction a field rather than an inference; until such a field exists, this obligation is enforced by review. [On violation: Bug — rows silently disappear from every surface reading through the join, or a fabricated referent enters durable output] [Verify by: for each join on a reference whose target may be deleted, confirm the consumer takes identity from the row's own reference and models the deleted state explicitly; review, per the stated limit above]

**SSG-M1** shapes — name and test. Each is an application of **SSG-M1**, not a separate rule; when a test answers *yes*, the linked example file shows the measured case and its fix.

- Frozen copy — does a later derivation about an existing record read the live catalog instead of the copy the record froze? → [wrong derivation source](ssot-must-derivation-source-applications.md)
- Provider money — is any money field of a provider event (amount, unit, withheld share, environment) chosen by its name instead of by one named derivation over the provider's published contract? → same file
- Absent input — when its input could not be read, does the derivation write a neutral-looking value instead of answering *unknown* or withholding the record? → same file
- Past instant — does a derivation date a lifecycle transition from a current-state field that later writes overwrite, instead of from the transition history? → same file
- Caller-supplied fact — does a derivation take, as a parameter, a fact another of its parameters already determines? → [the fact supplied by the caller](ssot-must-derivation-source-applications-2.md)
- Guarded arithmetic — is a formula re-spelled without the condition that makes it valid, instead of calling the derivation? → [re-spelled derivation](ssot-must-derivation-respelled-applications.md)
- Scale twin — do a per-item and a bulk implementation of one measure both exist? → same file
- Partially gated copy — when a copy is reduced, is its divergence measured against the datum's contract, not only against the other copy? → same file
- Polymorphic carrier — does a call site re-spell the normalisation of a value that can arrive as identifier, resolved document or driver object? → [re-spelled derivation (2/3)](ssot-must-derivation-respelled-applications-2.md)
- Seam-row adapter — does a call site turn seam rows into the derivation's input instead of passing the rows as loaded? → [re-spelled derivation (3/3)](ssot-must-derivation-respelled-applications-3.md)
- Named per-record decision — is a named decision about one record (settings selector, fallback between two references, class membership, row validity) copied at a consumer instead of called? → same file
- Linked-identity population — does a membership derivation filter before resolving every authoritative alias of the same subject? → same file
- Required-contribution integrity — does an aggregate report a failed required contribution as a smaller successful population? → same file
- Insufficient classification predicate (also **SSG-M8**) — is a fact with more than two classes decided by a comparator or an equality chain, or does a classifier have an output member no branch produces? → [classification predicate](ssot-must-insufficient-classification-predicate.md)
- Aggregate gate state — is a state that stops per-member generation (pause, suspension) of a group programme stored on the group, instead of on each member record with the group answer derived by one shared function? Store it per member: every generation gate already reads the member record, and a group-level copy would be a second answer every gate must also read.
- Provider cache, wrong subject (also **SSG-M19**) — does a branch the authority does not own fall through to a third-party client cache instead of returning the empty answer? → [provider cache, wrong subject](ssot-must-provider-cache-subject-mismatch.md)
- Deadline state — does any reader decide that a record whose live state ends at a stored deadline is still live from its stored status alone? Every reader **MUST** use one predicate over status ∧ deadline > now; an expiry job only materializes the terminal state and its effects and **MUST NOT** be the boundary readers depend on, because a late, failed or stopped job would otherwise keep expired records in force.
- Measured quantity — is a non-money measured quantity (volume, mass, length, dose units) stored as a non-integer, converted at more than one site, or rounded on input? It **MUST** be stored as an integer in one closed base unit per dimension, every input and display unit **MUST** convert through one shared table keyed by the unit vocabulary, and an input whose base value is not whole **MUST** be refused visibly, never rounded or truncated: a second conversion site or a silent rounding makes two readers report different quantities for one ledger. Money scale is [PAY-D8](../payment-ssot/rules.md).
- Free-text selector — does a stored field whose value selects arithmetic, conversion or routing (a unit, a package kind, a movement purpose) accept free text? It **MUST** be a closed vocabulary validated at the boundary: free text cannot be converted or aggregated, and it forks the field's meaning per record.
- Observation baseline — does a correction that sets a ledger to an observed value (a physical count) post `observed − balance at commit`? Each observed line **MUST** record the balance read when it was observed and post `observed − balance at observation`: movements between observation and commit would otherwise be erased or counted twice.

**SSG-M2**: Cross-domain effects on one field or operation must name a single primary owner (the registry authority of its KAT row or lint registration) and must grant other domains access only via explicit writer files / owner globs with narrowest scope (prefer file- or function-level paths over whole trees unless architecture documents a wider path). [On violation: Merge blocked (**SSG-P1-2**)] [Verify by: Review of the row / registration]
