Part of: [SSOT principles and precedence](ssot-principles-and-precedence.md). This file defines provider-evidence and ordering obligations; [entitlement lifetime and capacity-gated admission](ssot-must-provider-entitlement-and-capacity.md) covers what the projection entitles and for how long.

**SSG-M9**: When an untrusted client command initiates a projection write of externally owned state, client input may express only intent or an expected identifier; it is never proof of external state and never the write value. Before writing, the server **MUST** obtain a fresh, runtime-validated provider record, require an exact match between the client intent and the provider-owned item when the command names an expected item, and derive the persisted value only from that matched record. A stale cache, client assertion, receipt text, UI message, locally remembered selection, or a different active provider item **MUST NOT** authorize the write. Missing, mismatched, or environment-incompatible proof fails closed with no projection write. A preflight or eligibility endpoint MAY establish that an external action is currently allowed, but **MUST NOT** persist the anticipated outcome or trigger outcome-dependent access, lifecycle, or durable side effects: permission is not evidence that the user completed the action. Only later matching runtime-validated provider evidence may project that outcome. An authenticated provider webhook is a distinct evidence path; it need not make a redundant provider read solely to satisfy this client-command rule, but it **MUST** pass runtime environment policy before any side effect. [On violation: Critical SSoT/security bug] [Verify by: client intent → fresh provider read → exact item match → write, or provider authentication → runtime validation → environment gate → write; static enforcement where a single-file check can prove a bypass]

**SSG-M10**: A stateful third-party SDK whose configuration or active identity affects later operations **MUST** have exactly one session-orchestration authority. Keep raw configuration and identity mutators behind documented low-level adapters; application consumers invoke only the authority. It serializes identity changes with dependent operations, deduplicates concurrent setup for the same target, and verifies the SDK's post-mutation identity when the SDK exposes readback. Matching identity alone does not prove provider-state freshness: before publishing readiness with a derived snapshot, reconcile a fresh provider snapshot even on the same-identity path. If a mutator can partially change SDK state before reporting failure, keep that scope unavailable until a subsequent provider verification tied to the same scope proves the resulting identity and state; unrelated refreshes or login/logout actions must not clear unresolved scope state. Route later provider updates through one identity-checked reconciliation action. A UI store may publish only derived readiness/view state; it is never a second persisted or SDK writer. Reject every single-file import/call bypass of the authority. [On violation: Critical cross-scope/session or stale-state bug] [Verify by: import/call boundary; serialized mutation and dependent operations; post-condition and fresh-read gate; per-scope failure isolation and recovery; one update-reconciliation action; review of the configure → identity → dependent-operation sequence]

**SSG-M11**: Provider-owned environment provenance and event kind are part of the external evidence, not incidental metadata. A production runtime **MUST** enforce its environment policy before persisting any reusable provider credential/reference and **MUST** preserve that provenance in the durable projection. A previously accepted stored reference is not permanently blessed: every later live provider operation or irreversible side effect that consumes it **MUST** re-evaluate the stored provenance against the current runtime policy before the call. An authenticated but unknown/forward-compatible event kind MAY be retained for audit, but **MUST** remain no-op for known-event projections, credentials, access, lifecycle, or other domain side effects until it becomes an explicitly runtime-validated known kind. [On violation: Critical SSoT/security bug — sandbox evidence or unknown event mutates production state] [Verify by: Runtime gates at evidence-ingest and later side-effect boundaries + durable provenance review + single-file AST dominance/known-event rules where expressible]

**SSG-M12**: A durable projection from concurrent/out-of-order provider events or reconciliation reads **MUST** carry a provider-owned monotonic token (sequence, revision, purchase/renewal time, or predecessor/supersession link) and use one conditional writer that cannot replace newer evidence with older evidence. For predecessor chains, the durable current head is authority: initial write requires no head, refresh may match the head, and advance requires exact provider predecessor = current head. A mismatch does not prove staleness; when gaps are possible it **MUST** be durably retained unresolved before acknowledgement. Every head advance **MUST** run a bounded deterministic drain of exact successors and **MUST NOT** delete unresolved mismatches. If the bound ends with another successor, preserve a durable continuation trigger or return retryable failure through a path proven to resume from the new head; triggerless success is forbidden. Distinct children of one predecessor, disagreeing simultaneous predecessor sources, or equal-token conflicting identity/value **MUST** retain evidence and fail loud. Arrival/local time, lexical order, duplicate-key failure and last-writer-wins **MUST NOT** choose direction. Replacement **MUST NOT** use `upsert` as an ordering detector; upsert is only for a separately proven initial insert. In a shared cache generation protocol, current-generation acceptance **MUST** dominate storing/returning that cache snapshot; mismatch/indeterminate coordination makes it unusable and requires bounded authority reread or loud failure. Cache generation **MUST NOT** authorize or veto durable/irreversible database effects because TTL, eviction, restart or outage can create ABA. A fresh provider read reaches a durable projection only through the monotonic writer and, where tenant authority change must fence materialization, the persistent database epoch/transaction fence in **RDS-M21**/**TX-M-12**. A status derived from a live provider snapshot **MUST** take every provider-owned attribute it reports (for example the plan tier of the active product) from that same snapshot through the canonical parser, and **MUST NOT** require the durable projection of the same evidence as a precondition: the projection lags the provider, so its absence or older value during an ordering window is not an invariant violation and must not become a server error or a stale capacity. The projection serves only where the snapshot carries no classifiable value. When the snapshot holds several concurrently active products, a capacity-bearing attribute **MUST** be the most permissive value among the runtime-allowed active products, never the provider's single representative product: the user is paying for every active product at once. [On violation: Critical stale-projection/liveness bug — delayed evidence can downgrade or disappear, a rejected snapshot can escape, or ephemeral coordination can become authority] [Verify by: Provider token/edge + conditional writer + unresolved retention + bounded drain/continuation + ambiguity fail-loud + cache-acceptance dominance + separate durable writer/epoch review; a single-file AST check where single-file proof is possible, cross-file/runtime review otherwise]

**SSG-M12** note (a push channel that can miss the fact): When the provider documents that its push channel (webhook, notification) can omit a change of a money or entitlement fact, a scheduled pull of the provider's record of state **MUST** be the authoritative detector of that fact, and every push channel is a fast path only. All detectors write through the one writer under one dedup key built from the provider's own identity of the fact (order or transaction id), so whichever detector arrives first records it once and the rest are no-ops. The pull's candidate identifiers come only from durable rows of the subject, never guessed; where one unknown identifier fails a whole provider batch, the batch is split until the failing identifier is isolated, so one bad row cannot block the rest. The pull **MUST** read each candidate's own provider record (per-order or per-transaction state); a provider change list bounded by a lookback window or filtered by an access action (for example a voided-purchases list that keeps a limited history and lists only refunds issued with revocation) is a fast path like a push channel, never the authoritative detector, because the facts it omits are the ones the pull exists to catch. Reason: a push-only design silently loses exactly the facts the provider said it would not push (for example a store refund issued without revoking access).

**SSG-M19**: A provider payload field's presence does not establish the category or class to which a record belongs. Classify provider-owned records only from the field the provider contract defines for that classification, using the exact published values. Do not substitute presence (`$exists`, `hasOwnProperty`, `in`, or key membership) of a different field; do not add undeclared case-folding, trimming, aliases, or defaults. When the same classification is expressed in both a persistence query and a runtime predicate, derive both from one named authority and ensure they describe the same set, including absent, null, empty, and unknown values ([**SSG-M8**](ssot-principles-and-precedence.md)). A record whose class cannot be derived from the declared field fails closed as *not this class*. Do not infer a class from an identifier's shape after its canonical parser rejects it: a suffix or prefix guess is the original guess with the contract removed, and it admits retired or foreign namespaces while reading like a parse. The weaker sibling never anchors at all: a predicate that splits an identifier on a separator and validates only the segment at a fixed index asks *shape* and never *namespace*, so every foreign string sharing that shape classifies, and nothing in the path ever refuses it. A classifying predicate **MUST** match the identifier against the published namespace contract start to end; the segment vocabulary is a check applied after the namespace matched, never instead of it, and a namespace the canonical parser does not yet recognise is added to that parser rather than served by a private positional copy beside it. A fail-closed result also has a display obligation: a surface that previously showed the guessed class **MUST** make the unknown state visible — omit the label *and* say the class could not be read — because replacing a wrong value with a silently blank one moves the defect instead of removing it; reuse an existing unavailable-data string rather than inventing one. A provider may encode a category as a value on a shared event rather than in a category-specific event kind, so the absence of a category-named kind from a handled list is not proof the system cannot learn about it; the audit question is whether the contract-defined classification field is reachable, because a validation schema that omits it leaves the value in the raw record yet invisible to every typed consumer, collapsing two categories into one branch. [Example: a cutover fence treated the presence of a nullable, channel-neutral transaction-identifier field as proof of one channel; every event of the other channel carried it too, so the fence selected the whole population instead of its own subset.] [On violation: Critical misclassification bug — records from another class enter a scoped decision or irreversible side effect] [Verify by: provider-contract ownership for each classification field; the same named constants/derivation for query and runtime predicates; no presence-only or rejected-identifier fallback; visible unknown display state] [Stated enforcement limit: a static check can detect presence-only conditions and duplicated expressions, but cannot prove which field the provider contract assigns to a category; that fact requires current provider documentation or a versioned contract declaration. A literal-ban rule is also unavailable when the published values are not namespaced — it fires on unrelated placeholders and sibling constants sharing a value — so such a vocabulary is fenced by one classification function returning a closed union, not by a literal rule.] [Stated enforcement limit — the numeric-range sibling: deriving a class from a quantity (a duration in days standing in for a billing period) is the same guess-from-shape defect and is decidable from one file, yet a gate for it cannot be born green while the range rule itself is an open product question; the gate lands with that decision, and until then the obligation is carried by review and the absence is stated rather than left to read as coverage.]

**SSG-M19** note (a provider's own count of an outcome this system also measures): A provider-reported result (for example an ad platform's attributed installs, purchases or conversion value) is a separate data piece whose authority is that provider. It **MUST** be stored and shown under its own label and **MUST NOT** be summed with, substituted for, or used as numerator or denominator of a first-party outcome metric: the two answer different questions under different attribution rules. Counting it **MUST** select exactly one provider key per business event, by the exact published value: providers report one event under several alias keys (per surface plus a deduplicated aggregate), and a system that sends two event names for one transaction (a purchase and a subscription start) appears under both, so summing aliases or both names double-counts. One stored column uses one time basis (conversion date or interaction date) for every provider, or its window sums mix days. Two providers that count the same outcome for the same subject (an ad platform and an app store for one campaign) are two data pieces: each **MUST** have its own stored field, its own writer and its own label, and neither is written into, summed with or substituted for the other — one field with two provider writers per subject silently turns a comparison into a double count. A privacy-thresholded or noised provider aggregate (rows below a minimum group size withheld, random noise added) **MUST** be read as such: an absent row is unknown, never zero; a sum of the returned rows is a lower bound and is labelled as one together with the provider's stated noise; and ingestion **MUST** use the coarsest provider granularity that still answers the question, because the threshold applies per row and finer rows are withheld first.
