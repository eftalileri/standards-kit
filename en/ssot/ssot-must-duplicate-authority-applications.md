## The substituting twin

**SSG-M8** substituting-twin application: Two accessors that answer one question and differ only in what they do when there is no answer — one substituting a value, one returning the absent case — are a duplicate authority, and the substituting one **MUST** be deleted rather than corrected. The pair looks harmless because both are "correct" in isolation, but which answer the product gives is then decided by which name a call site happened to import, and that is not a decision anyone made. The substituting twin also wins by ergonomics, which is why it spreads: its name is the shorter, more obvious one, its return type is non-nullable so no call site is forced to handle anything, and a reviewer reading the call site sees no branch to question — the fallback is invisible at exactly the place it does its damage. Two obligations follow. (a) Reduce to the accessor that reports absence, then make each call site handle it explicitly — the point of removing a substitution is that the empty case becomes visible, so replacing it with a different silent coercion (`?? ''`, `?? 0`, a coalesce at the call site) reinstates the defect one layer out. (b) De-fallbacking is not the fix when it leaves two identical functions. Stripping the substitution from the twin produces a byte-equivalent duplicate, which is the same violation with the evidence removed; converge on one and delete the other in the same change ([**DCD-M2**](../dead-code/dead-code-rules.md)). Where several call sites then repeat the same "is this value usable here?" combination — an absence check plus a validity check — that combination is itself one derivation and is named once ([**SSG-M1**](ssot-must-authority-and-derivation.md)), not re-spelled per call site. [On violation: Bug — the product's answer depends on which of two imports a call site chose, and the substituted value is indistinguishable from a real one] [Verify by: one accessor per question, with the absent case in its return type; no second accessor differing only in fallback behaviour; call sites branching on the absent case rather than coalescing it away]

## The trigger flag

**SSG-M8** trigger-flag application: When one field is the sole input of an engine and other fields are meaningful only while that flag is set, the flag and its dependent fields have ONE writer — a path that writes the flag alone is a second authority, even though it writes only one field. The shape is easy to miss because the second writer looks minimal rather than duplicative: it sets the flag correctly, and the defect is entirely in what it did *not* write. Clearing the flag while leaving the dependent fields in place produces a record in a state the domain has no name for (for example, an inactive item that still carries active configuration), and the next reader — a repair script, a report, a re-activation path — has to guess which of the two halves is the truth. Three obligations follow. (a) The authority owns the whole transition, not the flag — its write sets the flag *and* clears or populates every dependent field in the same operation, so no caller can produce a half-state. (b) The prohibition is on the UPDATE surface, not on reading or on creation. Filtering by the flag is a read; writing it as part of creating the record is the flag's birth, and the record is complete by construction. Fencing those too buys nothing and produces false positives that erode the rule. (c) A repair/migration script is a consumer, not a co-authority. "It runs once, under supervision" is the argument that reintroduces the parallel writer; a one-off script calls the same authority the runtime calls, and its scope must therefore be inside the fence, not exempted from it. This is mechanically enforceable from a single file's syntax tree: a property whose key is the flag, appearing under a persistence-layer update operator, in any file other than the authority. [On violation: Bug — durable records enter a state the domain does not define, and the engine's behaviour stops being derivable from the flag] [Verify by: single-file AST rule scoped to update operators, with the authority file as the only exemption and repair scripts inside scope; every non-authority path calling the authority instead of writing the flag]

## The materialised eligibility flag

**SSG-M8** materialised-eligibility application: A flag materialised onto a record so a query can filter on it, but whose truth is the PRODUCT of several inputs held elsewhere, has exactly one writer, and that writer recomputes the whole product from the authorities on every write — it never patches the flag from the body of the event that woke it. That distinction is the rule: incremental patching drifts permanently on a single missed event (one dropped webhook, one failed retry, and the stale value survives forever because nothing later disagrees with it), whereas full recomputation is self-healing — any later trigger repairs it, so a missed event costs latency, not correctness. Four obligations follow. (a) One writer, and it takes no answer from its caller. Where the writer must be told something it cannot read where it runs (a provider/cache read forbidden inside a transaction callback), the input arrives as an opaque, module-issued carrier, not a bare boolean: a boolean parameter is a place for the caller to lie, and the classic regression is passing the value that was true when the job was queued. (b) The input authority has one read path too — the same rule one level down. A second module reading it directly is a second writer by proxy: it can read where reading is forbidden, and it bypasses the carrier's freshness and identity seal. Same predicate family, so it belongs in the same check; a separate rule would be a second authority over one question. (c) Removal is synchronous, acceptance may be deferred. Where the inputs include a withdrawable consent, removal happens inside the withdrawal's own transaction — a scheduled job's waiting time is the exact size of the violation — while acceptance may wait, because arriving late costs a delay, not an exposure. Corollary: since the product short-circuits, a withdrawn intent must not require the paid/remote input to be reachable, or a provider outage keeps a non-consenting subject published. (d) Birth and in-memory reflection are NOT writes. The flag in the object literal that creates the record is its birth (born closed — the absence of the fact, not a decision); assigning the reconciler's returned value onto an in-memory object carries a read result, not persistence. Excluding both is what makes the check false-positive-free: the fence is the persistence-layer update operator, nothing else. [On violation: Bug — a withdrawn subject stays exposed, or an ended entitlement keeps its benefit, with no signal either way] [Verify by: single-file AST rule over update-operator payloads naming the flag, with the persistence seam as the only exemption; the same rule's second predicate restricting the input authority's import to the carrier-issuing module; birth and in-memory assignment deliberately out of scope]

## The relation-derived counter cache

A counter derived from a countable relation **MUST NOT** be written back into the document that owns that relation as a time-to-live (TTL) copy. The copy is a second representation of a value whose only authority is the relation itself; unless it is invalidated by every writer that changes the relation, it drifts inevitably — and the drift is silent, because a stale number is a structurally valid number that raises no error and can keep feeding capacity, quota, billing, or eligibility decisions long after it stopped being true. A TTL does not make this safe: it only bounds how long each divergence lasts, and any relation writer added later (or any write path the original author did not enumerate) reopens the gap without touching the counting code. Membership churn is the specific killer — a delete followed by a re-create of the same logical member is two relation writes that a TTL window can straddle, so the copy can be refreshed at the exact moment the relation is momentarily empty and then stay wrong. The required design is a self-healing derivation: recompute the counter from the authority on every read, so divergence is structurally impossible and no invalidation obligation exists at all. This is normally cheap — the count is an index-covered read on the relation's owning key, and it replaces a write (the copy update) on a read path. Prove the index exists and state the per-request read count rather than assuming cost. If measurement proves recomputation is genuinely too expensive, the cache **MUST** live outside the owner document in a store shared by all instances (a document-embedded cache is itself a second writer of the authority record and diverges across instances), **MUST** carry an explicit TTL, and **MUST** be invalidated from every relation writer — and that obligation **MUST** be recorded where those writers are defined. Removing the persisted copy is not complete until the field is dropped from the schema and from every cross-boundary contract, transformer, and DTO that echoed it; a contract field may be kept only when a consumer is proven to read it, and that consumer must then be served from the derivation, never from the stored copy. [On violation: Bug — a silently stale derived counter drives a business decision] [Verify by: Grep every assignment of a `*Count`-shaped field on a persisted entity plus every `$set` of one, and prove its value is not derived from a count/aggregate over the owned relation; index evidence for the recomputation; single-file AST lint where the derivation and the write are visible in one function]

## The gate that re-derives what it was given

**SSG-M8** re-deriving-gate application: A gate that canonicalises the identifier it was handed before matching on it, while its caller returns the raw argument, holds two derivations of one identity — and the caller **MUST** return the identity the gate matched, canonicalised at exactly one point. The shape hides because both halves are individually correct: the gate is *more* careful than its contract requires, and the caller reads as a pass-through (`gate(x); return x`). The damage lands one consumer later: the value that was authorised and the value that then builds a query filter, a cache key with its invalidation twin, an idempotency scope or a log field are different strings, so a request is granted on the canonical entity and served beside it. The grant/use split is what makes this worse than an ordinary duplicate; a *deny* would be safe. Three obligations follow. (a) Canonicalisation has one site, the outermost one on the path. Pushing it into each gate only makes the gates agree with each other. (b) A caller **MUST NOT** canonicalise its own argument before handing it over — that second normalising call is the duplicate re-appearing at the call site, and it diverges the day the canonical form gains a rule. (c) Canonicalising is not validating. Where a fan-out of arms produces different error codes for a malformed value, one validation gate in front of them changes those codes; the canonical step must therefore hand on a value the arms still reject exactly as they did. [On violation: Bug — an actor is authorised against one entity and served against another, with no error on either side] [Verify by: the caller returning the value it passed in, with one named canonicalisation applied before the first gate call, and no normalising call on that identifier at any call site. Stated limit: not decidable from one file's syntax tree — the canonicalisation lives in the callee's body, and the faulty and the fixed caller have identical trees; enforcement is review plus keeping one canonicalisation entry point]

## The partial writer of a materialised derived value

**SSG-M8** partial-writer application: A value stored on a record but derived from other fields of the same record (a per-unit value materialised from a total and a count), together with every stored rule whose validity is bounded by that value (a fixed allocation capped at the per-unit value), has ONE write seam: every path that changes any input field calls it, and the seam re-derives the materialised value from the final inputs and re-validates the bound rules in the same write. The shape hides because each writer is locally plausible: the full edit command re-derives and re-validates, a narrower secondary writer (a bulk or cross-screen edit of the same record) sets only "its" input — one re-derives but skips the rule check, another sets the count and leaves the stored per-unit value computed from the old count — and when both inputs change in one request, the sequential partial writers derive from a half-updated record. Each partial writer is a second authority over the derived value and over the rule invariant, and the drift is silent: the stored value is structurally valid and feeds every later snapshot or allocation computed from it. Three obligations follow. (a) One seam owns inputs, derivation and bound-rule validation together; it mutates the loaded record and leaves persistence and the transaction boundary to the caller, so the full edit command and every secondary writer reach the same code with the same rejection code — a client that sees the rejection from one screen sees it identically from the other. (b) Several inputs arriving in one request are applied in one load and one write, never as sequential per-field writers. (c) Post-commit effects of the write (a cache invalidation of the record's listing) belong to each writer's transaction owner, not to the seam that runs inside the transaction ([**RDS-M20**](../redis/redis-prohibitions.md) (b)); a secondary writer that reaches the seam still owes the same post-commit effects as the full command. Creation is out of scope: a new record derives its value and validates its rules in its own birth path, and there are no stored rules to re-check. [On violation: Bug — a money value derived from a stale input, or an allocation rule the edit screen would reject, persists through a secondary path] [Verify by: one seam per materialised derived value, called by every update path of its inputs; no path assigning an input field and saving without it; the derived value re-computed from final inputs. Stated limit: not decidable from one file's syntax tree — an input field assigned on a loaded document looks the same inside and outside the seam's call graph, and the audit that recomputes the stored value against its inputs is a read-only data check, not a gate; review holds the obligation]

## The identity birth outside the match authority

**SSG-M8** identity-birth application: A record type whose instances stand for a real-world identity (a person by phone, email or tax number — and by normalized name where no stronger key exists) **MUST** be born only through one match-or-create authority, and every creation path — operator form, import, invitation, a record mirrored for a sibling entity — **MUST** call it. A path that inserts directly is a second identity decider and births a duplicate whenever its own lookup is narrower than the authority's. The authority resolves a weaker key to the existing record: a key-less create with the same normalized name returns that record, and a strong key arriving for a key-less record of the same name is attached to it instead of a second record being born, so a retried or re-entered form converges on one record. A channel whose input does not prove identity (a self-declared name on a public or self-service form) **MUST NOT** merge by that weaker key — the merge would bind a stranger to someone else's history — and declares this as an explicit policy argument of the same authority, never as a separate writer. Reason: per-path lookups of different strength duplicate records silently, and a merge driven by unproven input leaks data. Check: review-held — every call of the record type's insert seams lives in the authority's file.

## Sibling band

A duplicate authority can also be opened without storing anything, by two consumers each spelling one classification by hand. That shape is bound by [**MUST** — the insufficient classification predicate](ssot-must-insufficient-classification-predicate.md); it is not restated here.
