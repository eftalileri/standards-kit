## The fall-through that changes the subject

A derivation over a datum the authority owns **MUST** branch on the authority's declared source, and every branch the authority does not own **MUST** return the empty answer rather than fall through to a third-party client cache. The defect looks like graceful degradation and is the opposite of it. A stateful third-party SDK keeps a local cache describing its own subject — the store subscription, the payment order, the linked account it last saw on this device. When the authority says the record's source is not that provider, the cache is not stale and is not wrong: it is *correct about something else*. Reading it yields a well-formed, plausible value for a subject it was never about, and no field on either side records the mismatch, so nothing downstream can detect it.

Three obligations. (a) One named function answers the question and every consumer reads it. The shape is created by a second derivation, not by a bad line: two surfaces spell the same source-to-value mapping, they agree on the branches the authority answers, and they diverge only on the branches it does not — which is exactly where no one looks, because "both agree" is the property reviewers check ([**SSG-M8**](ssot-principles-and-precedence.md)). (b) The unowned branches are empty, not inferred. Where the authority declares the subject is in a state the provider does not describe — internally owned access, a locally granted entitlement, a grant made outside the provider, an unlinked subject — the honest answer is *unknown*, and a consumer predicate **MUST** turn unknown into no match, never into "any value" ([**SSG-M19**](ssot-must-provider-projection.md)). A derived read may not write back a class the authority does not hold ([**SSG-M1**](ssot-must-authority-and-derivation.md)). (c) Population size is not the risk measure. The window opens only while the authority and the device cache disagree, so the count on any given day is usually small or zero; it is the consequence that is severe, because these are typically money and entitlement surfaces and the user can be shown, or granted, a state that belongs to another subject. Measure the live count, report it, and merge regardless — a measured zero lowers urgency, it does not close the duplicate.

[Example: two surfaces derive the same provider-owned status from the authority's declared source. They match on the branches the provider owns; on a branch the authority declares as not provider-owned, one surface returns empty while the other falls through to the provider SDK's device cache. With one device cache holding an active entitlement for another subject, the falling-through surface shows that entitlement as the current one — a state the subject never acquired — while the provider-owned branch renders identically in both versions. The live count of subjects in the diverging shape may be zero on the day it is measured; the duplicate is removed anyway.]

Enforcement. The strongest available fence is not a lint rule: when the provider-cache reader has exactly one legitimate consumer, stop exporting it — a second consumer then fails to compile, which is stricter than any single-file AST rule and has no false-positive surface. Prefer that wherever the seam's consumer set is one module; where it is not, an import-boundary check over the named seam is the fallback, when one passes the project's enforcement admission criteria ([**SSG-M10**](ssot-must-provider-projection.md) already requires that shape for SDK mutators). [On violation: Critical entitlement/money bug — a subject is shown, or granted, a state belonging to a different subject] [Verify by: one named source-branching authority; every unowned branch returning empty; the consumer predicate proven to yield no match on empty; the provider-cache reader unexported or import-fenced; a traced before/after of what each branch renders] [Stated enforcement limit: unless the adopting project uses a branded type that binds cached provider data to its subject, no static check can decide that a cached provider record describes the same subject as the authority's row — that is a data-origin fact. The reachable mechanical half is the seam's consumer set (compiler or import rule); the branch-by-branch correctness stays a review obligation, stated here rather than left to read as coverage.]
