Part of: [SSOT principles and precedence](ssot-principles-and-precedence.md).

**SSG-M15**: When an actor class (session type, role, tenant mode) is not allowed to reach a class of resources, that restriction is one derivation and every layer that can start a call **MUST** read it from that derivation. A restriction enforced only at the outermost boundary (transport interceptor, HTTP client, gateway) while the layers that initiate calls (query/mutation/effect layer) use a *different* predicate — or none — is a two-predicate system, and divergence is not a risk but a certainty: the boundary rejects while the initiating layer keeps opening calls, so every attempt becomes a blocked request plus failure noise instead of a call that is never made. The derivation **MUST** be a single exported function; per-direction wrappers (read gate, write gate) are allowed only as thin delegations to it — a wrapper that re-states the predicate is a parallel authority (**SSG-M8**). Related-but-different predicates (is this identifier valid, is this feature entitled, is this actor an owner) **MUST** be AND-ed with the restriction, never substituted for it. Two further obligations follow: (a) the boundary's own "is this resource in the restricted class?" classification (for example a URL/prefix table) is itself an authority and **MUST** be registered, because adding an entry to it silently creates a new initiating-layer obligation; (b) an initiating call path that structurally bypasses the declarative gate — mandatory-fetch APIs, imperative prefetch/ensure/fetch, effects, listeners, background tasks — **MUST** read the authority at call time, not from a captured closure value, since an earlier effect in the same commit may already have invalidated it. The boundary's rejection is an expected authorization outcome, not a defect: it is classified through the client failure/severity authority at business/warning severity and **MUST NOT** be reported to the crash channel. [On violation: Systemic noise + false defect signal — every restricted-actor session produces rejected calls and the real defects drown in them] [Verify by: One exported derivation + delegation-only wrappers + registry entry for the boundary classification; AST ESLint that the initiating layer's gate expression resolves to that derivation, and that bypassing fetch APIs re-read the authority in-scope]

**SSG-M16**: When the definition of "valid for this field" lives in both an input schema (request validator) and a persistence schema (ODM/DDL constraint), those two statements are one rule and **MUST** derive from a single invariant — either by sharing one exported predicate, or by one side being provably a superset of the other, recorded as such. An optionality difference between the two schemas is not a redundancy, it is a latent outage: the input layer admits a value the storage layer rejects, so the request passes *every* validation gate and then fails at write time as a raw driver/ODM error — a throwable the error registry does not know, which the single boundary therefore cannot classify (unmapped → `SYSTEM` → 5xx → crash reporting) while the user's write silently never happens. Three obligations follow. (a) Watch the empty value, not just absence. Storage `required`/`NOT NULL` semantics frequently reject the *empty* value too (a common ODM rule is that a required string fails on `''`), so an input schema whose normalization emits `''` for an omitted field contradicts a required storage field even though both look "present". (b) A cross-field rule does not discharge a per-field constraint. "A or B must be filled" proves nothing about A alone; if storage requires A unconditionally, the pair is still divergent. Resolve it by relaxing storage to the pair-level invariant, or by tightening the input to the per-field one — never by leaving both. (c) Relaxation is a product decision, not a cleanup. Removing a validity constraint changes the product contract and needs the owner's decision; but once relaxed, every derived write path **MUST** stay honest — no layer may substitute a fabricated default (a placeholder name, `'unknown'`, a synthetic id) for the now-legitimately-empty value, because that converts a user's deliberate blank into invented stored data. When a field becomes optional, re-verify every derivation that consumed it (search keys, generated identifiers, display strings, uniqueness assumptions) for empty-input behavior. [On violation: Critical write-path outage — a fully validated request dies at persistence as an unclassifiable error, and the crash channel fills with what is actually a schema-contract defect] [Verify by: One shared predicate or a recorded superset relation; cross-file guard comparing each required persistence field against what the feeding input schema can emit (the empty value included) — a single-file AST cannot see the other schema; plus review of derivations after any relaxation]

**SSG-M16** ODM application: A cross-field persistence invariant **MUST NOT** use a path validator that returns success merely because its `this` value is a query. Run the shared invariant against the hydrated document in document-validation middleware. A query writer that changes any member field **MUST** either derive and validate the exact post-update state or route through the document/domain writer; indeterminate state fails loudly before persistence. If the audited query writers change only unrelated fields, record that bounded writer inventory and keep the invariant at the document/domain seams. **That inventory is a snapshot, so mechanize it rather than re-auditing it:** adding a query writer can bypass the invariant without looking different from legitimate query writes. A single-file check can recognize a member field under a persistence update operator when the call's receiver is the invariant's model; it can then exempt only the document/domain writers. **Anchor on the receiver, not the field name:** field names such as `relatedId`, `status`, or an `isEmpty` marker can recur on unrelated models. **State the reach:** a check that sees only inline update objects misses update documents built into variables; that form remains a review obligation unless the check resolves it.

**SSG-M16** clearing shape: "Cleared" is one state and **MUST** have one stored representation, so convergence on a single writer is incomplete until the writers also agree on the *shape* of the operation. Two writers that both clear a field — one by removing the key, the other by setting it to the store's null/empty value — leave the collection carrying two representations of one state, and the divergence is invisible from the write side because both calls "worked". It surfaces on the read side, differently per reader: a presence predicate (`key exists`) separates the two, while a coalescing read (`value ?? default`) merges them, so two correct-looking readers disagree about the same record and neither logs anything. Three obligations follow. (a) The authority declares the shape, not just the field. The one writer states which representation means "cleared" and converts the other form at its boundary — a caller that passes the null/empty form gets it normalized, never persisted as a second shape. (b) Convergence includes a census of the legacy shape. Retiring a parallel writer stops *new* divergence; it does not repair the rows the parallel writer already produced, so the count of records carrying the other representation is measured before the switch and recorded with the change — an unmeasured legacy shape is the same defect deferred, and every reader must keep handling both until that count is zero. (c) A presence-based index, unique constraint or query is part of the contract. Where any of those distinguishes absent from empty, changing the shape changes their result set; they are re-read before the shape is chosen, and the chosen shape is the one they were built for. [On violation: Bug — one logical state is stored two ways and independent readers disagree with no error surface] [Verify by: the authority's clear path normalizes to a single representation; the legacy-shape count recorded in the same change; presence-based indexes/queries over the field re-read and named. A single-file AST rule can flag a clearing write that uses the non-canonical shape once the project names the canonical one; it cannot see how many stored rows carry the other shape — that is a data measurement no source scan can supply]

**SSG-M16** external-value application: A value that enters the product from outside it — a third-party API response, a device/OS setting, an IP-geolocation lookup, a partner webhook — **MUST** pass the domain enum's own membership check before it is typed as a member, and a static cast is not that check. This is the blind spot of a request-boundary validation rule: the enum's runtime schema guards the *request* path, so a value that arrives on any other path reaches the enum-typed field with nothing between it and the field but a cast, which silences the compiler and validates nothing. The external validator upstream typically checks only *shape* ("two letters", "an ISO-looking code", "a plausible identifier") and cannot check *membership*, because it does not know the product's supported set; the two questions are routinely confused because the shape check looks like validation and passes. The failure is deferred and lands far away: the unsupported member surfaces as a missing key in a lookup map keyed by the enum, or as a storage-layer enum rejection at write time — the same unclassifiable write-path outage this rule exists to prevent, reached from the opposite direction. Three obligations follow. (a) The enum owns its membership predicate, and it lives beside the list. One exported narrowing predicate, declared in the same module as the closed set, so growing the set cannot leave a stale second answer to "is this a member?" elsewhere; every non-request path calls it, while request paths keep using the enum's runtime schema — both derive from the one list, so this is not a second authority ([**MRP-M13**](../monorepo/monorepo-rules.md)). (b) A non-member is treated exactly as an absent lookup, never as a new outcome. The path that already handles "the external source told us nothing" is the path an unsupported member takes; inventing a third branch, or substituting a default member, converts a known-unknown into fabricated data ([**SSG-M18**](ssot-must-read-integrity-and-aggregates.md) (c)). (c) Validate every field taken from that response, not the one that prompted the review. External payloads are read field-by-field and cast field-by-field; fixing one cast while its neighbour on the next line carries the identical defect leaves the outage intact and makes it look addressed. [On violation: Bug — an unsupported external value is typed as a domain member and fails later at a lookup map or a storage enum, as an error the registry cannot classify] [Verify by: one exported membership predicate co-located with the closed set; every non-request ingestion point calling it; no `as <EnumType>` cast on a value whose provenance is an external response. *Stated enforcement limit:* a single-file AST rule can flag the cast shape, but deciding that the cast's operand is externally sourced needs the provenance of the value across modules, which one file's syntax tree does not have — so absent that rule this row is review-bound at the ingestion points the project lists.]

**SSG-M16** tightening precondition: Closing an optionality gap by tightening storage is a change to existing rows, not only to future ones, so it **MUST** be preceded by a measured census of the stored corpus and **MUST NOT** be applied while any row cannot satisfy the new constraint. A row that predates the constraint does not fail on write of *that* field; it fails on the next write of any field, because document-level validation runs over the whole document — so the defect appears as an unrelated update dying at persistence, which is the least diagnosable form of it. Three obligations follow. (a) The census is a measurement, never an estimate, and its result is recorded with the change; "there probably are none" is not a precondition. (b) Where the field has no machine-derivable legitimate value, the repair migration writes nothing and fails loud instead. An absent value whose only honest source is a human decision cannot be backfilled: deriving it from a *related* stored field is fabrication whenever that field can be stale, and a fabricated value is worse than a missing one because it is indistinguishable from a chosen one. Such a migration is a readiness gate — it partitions the corpus, names the rows that cannot pass, and refuses the tightening — and an empty backfill is then a correct, complete outcome rather than a skipped step. (c) The gate outlives the measurement. It is kept and registered as a runnable entry point, because the next environment to receive the tightened schema (a second deployment, a restored dataset) has a different corpus and must produce its own evidence. [On violation: Bug — an unrelated update fails at persistence for rows the tightening left behind, or a fabricated value is stored as though a human had chosen it] [Verify by: the census result recorded in the same change as the constraint; the tightening and the census landing as separate, ordered changes; the gate registered as a runnable entry point that fails loud on a non-empty offending partition]

**SSG-M16** executed-validator application: A persistence constraint binds only where the write path runs it, so declaring one is half the change — the other half is proving the writers execute it. Common ODMs validate on create/save but skip validation on update/upsert unless the call opts in, so the omission is the silent default: a constraint added to a module whose only writer is an update call never executes once, yet it is reviewed, merged and thereafter believed — a false guarantee stops anyone looking further. Three obligations follow. (a) The constraint and every write touching the field are read together, and the opt-in is written at the call site. A default is not evidence. (b) The constraint's value set derives from the type's single authority — one exported list building both the type and the validator — since a hand-copied member list is a second writer of the same fact and decays unsignalled. (c) Where validator and writer share a module the omission is decidable from that module's syntax tree, so it belongs in a lint rule, not review, and that rule self-scopes on "this file declares a validating schema" rather than a path list, which empties silently the day the schema moves. [On violation: Bug — a value the schema forbids is written unchallenged while the declaration reads as protection] [Verify by: the opt-in flag at each update call in the declaring module; the validator's members derived, not copied; a lint rule keyed to schema declaration, not to a directory. *Stated enforcement limit:* a writer in a different module is outside a single-file predicate, and where most update calls carry no flag, extending the rule there is a per-field product decision, not a widening of this one — that surface stays review-bound until measured field by field.]
