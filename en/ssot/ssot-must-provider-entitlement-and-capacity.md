**SSG-M13**: When effective access expiry can be extended or combined independently from a provider's billing period (for example by an administrative grant, credit, promotion, or provider grace period), effective access end and provider billing-period end are distinct semantics and **MUST** remain separate explicit fields or canonical derivations. When the provider itself keeps access active beyond the regular billing-period end, the provider's documented access-granting end **MUST** extend the canonical effective-access window while the regular billing-period end remains unchanged. Multiple access sources **MUST** be composed only by their registered source precedence/composition rule; a generic maximum, minimum, or fallback **MUST NOT** be inferred from field names. Authorization/availability MAY use the effective access end; provider lifecycle decisions such as cancellation timing, scheduled plan-change timing, and renewal-boundary reconciliation **MUST** use the exact provider-owned period end or event timestamp. Unknown, malformed, or contradictory provider timestamps **MUST** fail loud rather than becoming inactive, normal, or a fallback value. A maximum/minimum/fallback across effective-access and billing-period semantics **MUST NOT** stand in for missing provider lifecycle evidence; the provider-lifecycle operation fails closed when its required provider period is absent or invalid. The same separation binds a capacity-bearing plan attribute: when an independent grant can raise capacity while a provider plan is active, the provider plan attribute and the effective capacity **MUST** be separate fields of the canonical status — capacity-gated admission reads only the composed capacity, while plan-change and downgrade decisions compare against the exact provider plan; collapsing them either hides granted capacity or lets the grant turn an upgrade into a "downgrade". Where the admission side's use of the composed capacity is visible in one file, the adopting project may fence it with a single-file check admitted under its enforcement policy. [On violation: Critical access/lifecycle projection bug — provider-granted access can be cut short, or an independent local access source can move or hide a provider billing transition] [Verify by: Contract/type distinction + authority registry + one canonical access-window derivation consumed by parser and access decisions + review of lifecycle consumers; runtime invalid/missing-provider-date gate] [Stated enforcement limit: types and module boundaries can force consumers through a named canonical derivation, but static analysis cannot prove an external provider's documented access-granting timestamp or the business precedence among independent access sources; those facts require provider-contract and authority-registry review.]

A cached time-dependent access decision is not evidence of current access. Re-evaluate the stored explicit entitlement period/grace evidence at the canonical current clock through the same access-window derivation before returning it to an access consumer. Cache TTL and generation prove retention/coherence, not passage of time. The read boundary and a shared runtime helper enforce this; whether every consumer reaches that boundary remains inventory/review, and no redundant syntax rule is added (**ENA-A1**(c)).

Persisted access-derived state (**SSG-M13** application). A stored value derived from a time-dependent access decision (an "active"/"published" flag gating a feature) is the same cached decision persisted. (a) It **MUST** have one writer that fully recomputes it from the access authority and the other inputs, never patched from an event body. (b) Besides the entitlement-change arm it **MUST** have a clock-driven reconcile arm, because a lapse by trial end, grant window or provider expiry produces no write and no event. When the entitlement-change arm is best-effort (it reports instead of failing a committed purchase), the clock arm's candidates **MUST** cover every subject whose value can change in either direction — every subject that asked for the state, not only those currently holding it — because the clock arm is then also the only repair of a failed activation. (c) It **MUST NOT** be the only access evidence for a write that consumes the entitlement; that write re-evaluates the live predicate at the current clock. Reason: an event-only, patched or flag-only design leaves a lapsed subject active with nothing left to correct it. [Verify: review — one writer, a declared clock arm, the live predicate on the consuming write]

Entitlement records **MUST** use a closed absent/present representation, with nullable timestamps only where the provider contract defines that meaning. Absent is inactive and never enters product or environment gates. Present with a null period means lifetime only when that state is explicitly defined by the provider contract. Missing required present fields or absent period/grace evidence **MUST** fail loud. Derive the shared union and one canonical parser/helper from the contract, then require present evidence before applying environment or product gates; where the type system enforces the union, a duplicate lint rule is unnecessary. Type checking cannot prove external provider semantics or validate untyped cache bytes; runtime validation and cache versioning remain required. [On violation: Critical false-access or environment-classification bug] [Verify by: closed evidence union; one parser/helper; present-state gate before environment/product decisions; runtime validation and cache versioning for untyped data]

**SSG-M14**: When a durable admission or creation is capacity-gated and is expected to remain valid across a future provider transition, a runtime-validated scheduled capacity reduction **MUST** constrain new admissions immediately. The decision consumes the verified target capacity and current capacity from the same canonical status snapshot and applies the target when that reduction is active; it **MUST NOT** re-read a raw persistence projection as a parallel decision source. Current access may remain available until the provider boundary, but code **MUST NOT** knowingly create durable state that is already invalid under the verified next capacity. A preflight or client selection alone is not a scheduled reduction and **MUST NOT** narrow capacity; only the provider-evidenced projection from **SSG-M9**/**M12** may do so. [On violation: Critical future-state integrity bug — a write accepted under expiring capacity is invalid at the known transition] [Verify by: Canonical status snapshot + provider-projection provenance + capacity decision review; a single-file AST check when the target→current precedence is visible in one file]

Subject cardinality — the provider's subject is a ceiling on the product's (**SSG-M14** application). **SSG-M14** bounds capacity in time; the same obligation binds in number. When the entitlement subject the product sells (for example a workspace, site or tenant) is finer-grained than the subject the provider bills (for example one account, one exclusivity group or one billing profile), the provider's subject is a hard upper bound on how many of the product's subjects may hold a paid entitlement concurrently, and that bound **MUST** be stated as a product constraint before the finer subject ships — not discovered by the first customer who needs two. Three obligations. (a) The bound is named where the catalogue is defined, because it is a property of the catalogue rather than of the code: if every purchasable product sits in one exclusivity group, one account buys one of them, and a second purchase under the same account is a change of the first, not an addition. (b) The collision is loud, never a silent handoff. A provider that resolves the conflict by moving the purchase to whichever local subject asked last leaves the earlier subject with no entitlement and no event of its own: the losing subject's status derivation simply reads "no active entitlement", which is indistinguishable from never having bought. At least one durable uniqueness constraint **MUST** make the second binding fail loud — the provider's immutable transaction identity, persisted once per subject, is the one key both sides already agree on. (c) The provider's conflict-resolution setting is evidence, not an assumption. Whether the provider blocks, transfers or shares a purchase seen under a second identity is a provider-side setting that no repository read can produce; it **MUST** be read from the provider's current configuration or documentation and recorded, and until it is, the transferring behaviour is the one to design against, because it is the only one that is silent.

[Example: the entitlement subject is one tenant, the provider account bills one subscription, and every catalogue product sits in a single exclusivity group. Event history shows one provider transaction seen under several provider customer identities belonging to one owner and to different tenants, the last identity carrying the subscription. The purchase moved, and nothing in the losing subjects' records says so; outside the transaction-identity uniqueness constraint it would leave no trace at all. A live count of zero affected subjects does not retire the obligation.]

Two reusable lessons about recording the (c) setting. A recorded setting **MUST** carry its label and its configuration path as of the reading date, because providers rename these fields: a reader hunting an old label finds nothing and may conclude the setting was removed, which is the opposite of what happened. Record also whether a per-environment override exists and its value, so it is known whether one behaviour governs every environment. And a transferring value confirms the design (c) already mandates rather than changing it: the transfer-event branch that re-derives both the losing and the winning subject, and the per-subject uniqueness constraint on the provider's transaction identity, keep their rationale unchanged and no code follows the measurement. It is the non-transferring value that is the expensive answer, because it forces both of those to be re-measured.

[On violation: Critical entitlement bug — a paid subject silently loses access when the same provider account buys for a second subject, with no error and no event] [Verify by: the catalogue's exclusivity grouping named in the product decision; one durable per-subject uniqueness constraint on the provider's transaction identity; the provider's conflict-resolution setting read from its current configuration and recorded with label, path and reading date] [Stated enforcement limit: no static check can decide this class — the provider's exclusivity grouping and its conflict-resolution setting live outside source code unless the project records them in a versioned contract, so an AST or cross-file rule has nothing to read. The reachable mechanical half is (b)'s uniqueness constraint, which turns the second binding into a loud persistence failure; the cardinality declaration itself stays a product-decision obligation, stated here rather than left to read as coverage.]
