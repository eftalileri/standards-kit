## The incomplete copy of a closed value set

A closed value set has one authority; a hand-written second list of the same values is a duplicate even when it is INCOMPLETE — and the incomplete one is the more dangerous half. Where a domain owns a fixed vocabulary (statuses, kinds, channels, tiers) behind one schema-and-derived-type authority, a literal union, enum call, or bare array that restates those values elsewhere is a second definition. The complete copy at least fails visibly when the two disagree on a value that exists. The copy missing one member never disagrees with anything: it is a structurally valid, independent type, so the compiler stays silent when the authority grows, and the surface built on it simply stops representing the record carrying the new value — no error, no warning, only an absence. Nothing on the missing branch ever runs, so nothing ever reports it.

A subset threshold must be justified, not guessed. Exact-set matching misses incomplete copies; matching any subset flags intentional views such as allowed states or report populations. If a project admits a mechanical threshold, measure legitimate subsets in that project's current source tree, choose the smallest threshold that separates them from duplicates, and record the evidence. An intentional subset above that threshold needs a documented exception; do not widen the predicate without new evidence.

The rule must not restate the vocabulary either. A check that embeds the value list becomes a third authority for it, and it drifts the same way — silently, and against the very thing it guards. Read the values from the authority file at rule-load time and fail loudly if they cannot be parsed exactly. Label maps are not copies: an exhaustive `Record<Vocabulary, string>` keyed by the derived type is *forced* to stay complete by the authority, so a predicate that inspects value lists — never object keys — exempts it by construction rather than by an allowlist. [On violation: Bug — a surface silently omits every record carrying a value its private copy never learned] [Verify by: single-file AST rule over literal unions, enum calls and bare arrays, its match set read from the authority file, its arity threshold documented with the measurement behind it]

## The copy that sits in the same file as the authority

When the second declaration of a closed value set sits in the same file as the first, the duplication is fully decidable and **MUST** be fenced; when the two are in different files, member equality alone is NOT evidence of duplication. Within one file, a union and a constraint listing the same members often define one contract twice: the compiler accepts according to one list while persistence accepts according to the other. Keep one immutable array authority, derive the type from it, and have the constraint consume that same array. File locality is the anchor. Across files, equal member sets can answer different questions; consolidating them based on equality alone would create a false SSoT. Cross-file similarity remains a review question unless the project declares that the sets answer the same semantic. [On violation: Bug — the type and persisted constraint disagree about a closed set] [Verify by: same-file value lists derive from one immutable authority; cross-file lists are not merged solely because their members match]

File locality is what makes the predicate safe, and it is not a convenience — it is the whole anchor. Within one file, a union and a value constraint that spell the same set are one contract written twice. Across files, identical members do not prove identical meaning: a type can be reused for distinct domains, or two domains can happen to share a vocabulary. Merging them without a declared semantic relationship would create a false SSoT — one authority for facts that are free to diverge. A cross-file equality check is therefore not a valid anchor. Where contracts genuinely cross boundaries, use the consumer's import of the producer's authority rather than comparing two independent lists ([**SSG-M1**](ssot-must-authority-and-derivation.md); see the monorepo type-placement rules).

Declared limit — the cross-file half has no mechanical enforcement, and this paragraph is its only coverage. The information a check would need is *intent*: whether two equal member sets answer one question or two. That is not present in either file's syntax tree, nor in a registry by default, and inferring it from naming would be the name-list anchor the false-positive rules already forbid ([**FP-M32**](../false-positive/check-verification-rules.md)). The single-file half is enforceable and must be enforced — the fix at each site is to make the set an immutable array authority, derive the type from it (`(typeof ARRAY)[number]`) and have the constraint spread that same array, leaving one writer. [On violation: Bug — the type and the persisted constraint disagree about a closed set, and neither the compiler nor persistence necessarily reports it] [Verify by: a single-file AST rule matching a value-constraint list against same-file literal unions by member-set equality, with no cross-file comparison and no name list; plus the declared limit above wherever the cross-file case is discussed]

A consumer-side import edge can provide a narrower check. In a file that already imports the union it constrains, verify that the constraint reuses the imported authority rather than spelling its members again. This check requires type resolution; before enabling it, verify the project's type-aware checks can resolve derived unions and will not flag correct code. [On violation: Bug — a consumer re-declares a contract it already imports] [Verify by: constraint consumes the imported value authority; any admitted check resolves the derived type]

## The consolidating authority narrower than the copies it absorbs

When many local copies of one derivation are reduced to a single authority, that reduction holds only if the authority can express every input the copies accepted; an authority whose parameter type is NARROWER than the widest copy is not a simplification but a silent loss of a declaration the tree already makes. The trap is that identical bodies invite a blind merge. Copies of a derivation converge on the body long before they converge on the signature, because each site widened its own input the day a real requirement demanded it — so the bodies compare equal while the accepted input does not, and the equivalence measurement ([**SSG-M23**](ssot-principles-and-precedence.md)) must diff the signatures, not only the statements. The loss then surfaces at the call site as a type error, which invites exactly the wrong repair: narrowing the *caller's* contract to match the authority. That trades a capability the caller earned for the convenience of the merge, and it is a regression whether or not any record exercises it today.

The widest copy is usually the correct authority, and the declaration that needs the width identifies it. When consolidating copies, compare signatures as well as bodies. A shared body can accept different inputs at different call sites; narrowing the canonical signature to the smallest copy may make valid callers unrepresentable. Prefer an upstream dependency's type over a hand-narrowed approximation when values originate there. [On violation: Bug — consolidation removes an input shape already declared by a caller] [Verify by: compare every copy's accepted inputs and preserve legitimate wider forms in the authority]

A deferred-work record's copy count is a floor, not the population. Each site can rename the duplicated function; searching only for the original identifier misses copies with different names. Derive the population from the computation's statement shape before trusting a count. If the measured population cannot be closed in the current change, state the open scope and count; do not present it as a technical limit when the predicate can be implemented after the copies are addressed. [On violation: Bug — renamed copies remain outside the consolidation or enforcement scope] [Verify by: recount copies by computation shape, not only by identifier]

Narrowness also hides in a guard, and whether the guard is necessary depends on input provenance, not only its declared type. A guard may be redundant when an operand is a local literal whose type already proves its shape, but load-bearing when the value comes from an unvalidated external input. Do not resolve the difference by widening the shared authority's parameter to an untyped form; that removes compile-time checking for every caller. Use a separately named variant over a shared implementation when call sites have genuinely different provenance. [On violation: Bug — consolidation drops a guarantee required by external input or removes type checking for all callers] [Verify by: trace each operand's provenance and retain an explicit variant for unvalidated inputs]
