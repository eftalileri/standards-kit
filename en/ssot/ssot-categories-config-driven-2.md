Scope: script and erasure consumers of KAT-3 model authority; [category definitions](ssot-categories-config-driven.md).

---

An operator or maintenance script is a consumer of a model's authority, never a writer (**SSG-M8** application). A hand-run entry point — a targeted delete, a cleanup, a seed — and its shared helpers call the same domain authority the application uses for that record: the subject delete, the account deletion, the member-departure unit, the record-creation service. A script that writes the record itself is a second writer that silently misses every protection the authority gains later. Typical shapes of the drift: a cleanup helper carries its own delete list and removes money-bearing records the authority would close while keeping the ledger ([**PAY-M10**](../payment-ssot/money-owning-record-teardown.md)), deletes rows a product decision retains, and skips a lock the authority enforces; another copies the account-deletion list without the downstream erasure request and session cleanup, and removes member rows without the departure unit's cache invalidation. Where the copy and the authority disagree, the authority's contract decides ([**SSG-M23**](ssot-principles-and-precedence.md)): a script-only effect the contract excludes by decision is dropped, and a genuinely missing one becomes a named mode of the authority — neither survives in the script. A step only the copy performed (for example removing a departing member's per-tenant settings row) moves into the authority, which also stops the application's own departure paths from leaving orphan rows. The rehearsal counts through the authority, never through a restated filter: the authority exposes a read-only count, or the filter definition its write step reads, and the rehearsal consumes that. A restated filter drifts and stops showing effects the real run performs. A refusal the authority can now return (a lock) is surfaced in the rehearsal and the row skipped with a record, so the rehearsal still describes the run ([**REP-M-28**](../repository/repository-irreversible-operation-entry-point.md)). Enforcement: use the enforcement mechanism the adopting project documents; the strongest single-file form forbids, over the script tree, any model-level write, driver-collection write or model construction on a receiver bound by import provenance to the model layer, with a closed per-file, per-model exception list derived from an empty-set run in which each surviving entry names the record's only writer or an open owner decision. Model-scoped seam rules keep no script allowance. A reference to a check is not evidence that it exists or covers the full rule; record its actual scope and limits. Stated limits ([**KIT-INV-8**](../authoring/kit-structural-invariants.md)(b)): a one-shot migration directory is outside such a rule, since bulk transforms no domain authority performs are its contract; hydrated-document writes and driver collections not bound to a model are invisible; a long ordered cascade whose writes stay explicit per-model calls (so model-scoped rules see each one) is summarised in the rehearsal, not derived — a data-driven step list would hide those writes; a restated rehearsal filter is review, since telling it from a legitimate scope read needs the authority's filter set, which no single file carries; and the rule proves only that the script does not write, not that the authority it calls is the right one — review.

Erasing an identity is a departure from every tenant it belongs to — the erasure authority runs the departure authority, never a partial copy (**SSG-M8** application). When an identity holding memberships in tenants it does not own is erased, each membership ends exactly as a voluntary departure would: the erasure authority calls the departure unit once per membership, before any de-identification, and deletes the identity record last, so an interrupted run leaves the identity in place and a re-run finds the remaining memberships. The identity record is never deleted while a membership bond still points at it — each bond is departed (erasure) or re-homed (identity change). History the tenant owns (its records about third parties) is not the erased subject's to destroy: only the bond goes. Typical drift: the in-app erasure leaves membership rows, pending assignments and a per-tenant settings row pointing at the erased identity while only an operator copy departs — two entry points, two end states; and an operator copy that also hard-deletes other tenants' records performs an effect the authority excludes, so it is dropped rather than carried over (**SSG-M23**). A cleanup keyed by a re-issuable identity reads membership absence in the same transaction snapshot as its delete: a departure that removes the membership first and dependent rows second leaves a window in which the same identity rejoins and receives a fresh row under the same key; one snapshot makes a rejoin committed earlier visible and a row born later invisible. Enforcement: use the enforcement mechanism the adopting project documents; the strongest single-file form requires a file that deletes the identity record to call the departure unit or the identity-change re-home before the delete. Stated limits ([**KIT-INV-8**](../authoring/kit-structural-invariants.md)(b)): source position is not execution order; such a rule proves the call exists, not that it runs for every membership; a delete reached through a parameter is invisible — review. The snapshot guard is code, not a rule: whether a filter key can be re-issued to a new member is a data-lifecycle fact no single file carries.
