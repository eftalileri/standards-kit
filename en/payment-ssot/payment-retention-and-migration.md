## MUST (normative) — PAY-M (retention band)

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **PAY-M15** | Every retained person-attributed financial row **MUST** store one durable financial subject key—an immutable key that survives later account-link, roster-membership, assignment, or relationship deletion—and, when a historical display label is required, one immutable event-time name snapshot under NCM-M10. A mutable current-membership row or login-account alias is only an ingress lookup aid, not the owner of retained financial history. Tenant-wide financial reads and exact settlement commands derive scope from authorized tenant-owned financial rows, so later roster removal cannot hide or make them unpayable; a selected/current-person filter may resolve an accepted current alias once at the authorization boundary, then query the exact stored subject. Only an omitted subject filter may mean tenant-wide: an explicitly present empty or malformed subject collection **MUST** fail loud or return an exact empty result, never widen to all subjects. The name snapshot is internal financial data and may be projected only by an explicitly authorized financial DTO/report surface; generic DTOs must omit it. Missing rollout snapshots require dry-run → apply → zero-missing post-proof before strict readers activate; runtime current-name/membership fallback is forbidden. During writer-first coexistence, idempotency/dedup keys **MUST** canonicalize every accepted legacy alias to the durable subject before comparison, so replay cannot append a second row for the same subject/source. | Hidden debt, cross-scope disclosure, unpayable retained rows, duplicate financial rows, or PII disclosure — reject / must not ship | Static: retained schema has required subject+snapshot; all-scope query has no current-roster membership list; explicit empty/malformed subject filters do not become tenant-wide; exact command groups stored subject; generic serializer omits snapshot; writer-first dedup normalizes legacy aliases. Migration: bounded dry-run/apply/post-check proves zero invalid retained rows. |
| **PAY-M17** | Deleting a subject entity that owns retained financial history is one ordered, transactional teardown — never a bare row delete. When an entity (party, member, account) is the *subject* of rows that carry money or history (collection lines, completed bundles or subscriptions, past records, accrued allocations), deleting that entity **MUST** route through one named teardown authority that performs, in this fixed order and inside one transaction: (a) run every deletion guard first, so no destructive step precedes a refusal; (b) stop the subject's automatic future production — every recurrence/renewal/scheduling intent flag the background engines read **MUST** be cleared, and the set of the subject's owning rows **MUST** be enumerated *inside* the transaction (enumerating outside leaves a race in which a renewal committed between enumeration and delete survives); the flag writer **MUST NOT** be gated on a liveness/active predicate that the background engines themselves do not apply, otherwise the exact rows that keep producing are the ones that cannot be stopped; (c) delete only pending, not-yet-consumed future rows — rows that carry money or history are kept (PAY-M10/PAY-M11); (d) freeze the event-time label on every retained row whose display name is derived from the subject, filling only absent labels and never overwriting an existing snapshot (PAY-M15, NCM-M10), from the same single derivation the write paths use — a second derivation makes one subject appear under two labels; (e) remove every membership/collection reference to the subject (arrays, join rows) through that reference's single writer, leaving no residue; (f) delete the subject row itself through a tenant-scoped, session-bound persistence call and fail loud when the delete count is zero; (g) re-assert the invariant that no future-producing flag survives, and abort the whole unit if any does. After commit, the caller **MUST** invalidate the tenant's affected read caches before the operation is reported complete, using the observable (non-failing) invalidation surface — a committed deletion **MUST NOT** be reported as failed because a cache generation bump could not be confirmed. The confirmation copy shown before the action **MUST** state, line by line, exactly what is kept and what is removed (PAY-M11). Subjects deleted before this teardown authority existed leave rows whose future-producing flag is still set — a backlog that keeps producing for an absent subject — so shipping the teardown **MUST** be followed by a bounded repair migration that resolves "the subject is absent" tenant-scoped (the subject lookup matches both the subject key and the owning tenant), writes only through the same single flag writer (a raw field update is a second writer and leaves the stale plan/schedule fields the writer clears), leaves every row whose subject still resolves — or whose subject cannot be resolved at all — untouched and counted rather than guessed, and proves zero remaining absent-subject flags with the same classification authority it used to select them (no second definition of "absent"). | Orphaned rows whose owner, amount, and label can never be resolved again; a background engine that keeps producing records for a deleted subject — irreversible and must not ship | Static: every delete site of the subject model routes through the one teardown authority (a delete-site allowlist and a companion-call check asserting that the stop-future and freeze-label steps accompany the delete, to the extent the adopting project's enforcement mechanism provides them; record its actual scope and limits); the owning-row enumeration is inside the transaction; the label writer targets only absent labels. Runtime: after deletion, queries for future-producing flags on that subject return zero, retained financial/history rows are still readable and still labeled, and no membership array still contains the subject. Migration: the legacy backlog repair runs dry-run → apply → zero-remaining post-proof through the single flag writer. |
| **PAY-M16** | A live migration that rewrites a retained financial subject, allocation identity, or settlement-relevant embedded row **MUST** share one durable database fence with every live settlement writer. When migration readiness has not yet been proven, application bootstrap provisions a missing fence with insert-only locked semantics and validates every existing state before serving it as an authority; it must not open an unproven migration window on a fence-aware instance. Each settlement writer touches that exact pre-existing fence record inside the same transaction as its ledger/entity writes; it **MUST NOT** upsert the authority. Apply **MUST NOT** start until deployment evidence proves every live settlement-capable instance runs the fence-aware writer; a rolling-deploy predecessor that does not touch the fence invalidates the concurrency proof, and any settlement it commits must remain a retained readiness blocker rather than be ignored. Only a valid locked state maps to the retryable maintenance response—missing, malformed, exhausted, or non-exact fence state is a system failure. Migration apply acquires a monotonically fenced lock before its first readiness count and re-validates exact ownership inside every repair transaction. If strict schema/readers depend on that migration, apply **MUST** keep the fence locked through the zero-remaining proof, final read-only proof, and deployment evidence for every strict-reader instance; an explicit release command then takes a newer revision, re-proves settlement/data zero, and opens the fence. If apply/release fails after acquisition, the fence remains fail-closed and resume must take a newer fence revision. Dry-run is read-only and reports both data and fence readiness. A before/after row count, a deployment-to-apply gap, an apply-to-strict-deploy gap, or an operational “quiet period” is not a concurrency proof. | Split-brain financial identity, hidden authority corruption, or partially migrated payout history — reject / must not ship | Static: bootstrap owns insert-only locked ensure+parse; all settlement commands delegate to one persistence seam containing a no-upsert transactional fence touch; migration repair transactions touch the same record. Runtime: deployment proof excludes predecessor writers; any predecessor-era settlement blocks readiness; from that proof through dry-run/apply/final-proof/strict-deploy/release there is no open settlement interval; release rechecks zero under a newer exact fence. A fence-aware writer receives a retryable maintenance response while the unproven/active migration lock exists—never interleaves silently; missing/malformed state reaches the system-error observability path. |
