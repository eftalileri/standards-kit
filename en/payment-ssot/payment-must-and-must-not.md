## MUST (normative) — PAY-M

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **PAY-M1** | For every transaction where PAY-D6 applies, the canonical response derivation **MUST** receive a finite `expectedTotalForStatus` before exposing payment state. | PAY-F2 | Review that all response paths load the required expected-total inputs. |
| **PAY-M2** | Every call to PAY-D4 **MUST** pass `totalAmountFieldPresent` explicitly, set from the persisted record shape (key presence, not value). | Bug | Review mapper inputs and key-presence handling; the flag tracks real key presence. |
| **PAY-M3** | Each read/transform path **MUST** call PAY-D4 exactly once for each serialized financial record (no second parallel derivation). | Bug | Review that no second derivation is added on the same response path. |
| **PAY-M4** | A cancellation **MUST NOT** infer the target record's paid state from money owned by a parent record or mirrored there (for example a bundle ledger or its mirror). The persisted target for a record carrying its own collected money is decided only by PAY-M24. | Bug | Review that cancellation reads only the owning record's own ledger and the explicit product policy. |
| **PAY-M5** | A completed payment entry **MUST** include its effective payment time in the canonical format (ISO UTC); validation **MUST** reject its absence, or assign it from the application's one server clock authority, so no completed row reaches persistence without it (PAY-F1). A request schema shared with a client is pure shape validation and **MUST NOT** fill an actual payment timestamp by reading the clock of whichever runtime parses it. Missing-field completion belongs to one backend input-normalization authority consumed by every applicable create/edit write path before payment acceptance/persistence. Where idempotency fingerprints the request intent, its input excludes server-assigned timestamp values. A valid timestamp explicitly supplied under the operation's existing contract is preserved; this missing-field obligation does not authorize silently overwriting historical payment dates. | Reject / ERROR | Review: shared/client schema generates no runtime payment time; applicable create/edit writers use the same backend normalizer before the canonical ledger write; raw-request idempotency excludes server-assigned values; completed output carries the time. Release review confirms clients running a retired clock-filling schema receive the update. |
| **PAY-M6** | Dashboard summaries and reports **MUST** use the same canonical financial projection as detail and list surfaces (PAY-O1), not ad-hoc status or total calculations. | Bug | Review shared projection use across read paths. |
| **PAY-M7** | Translation keys required by [ui-binding.md](ui-binding.md) **MUST** exist in every locale supported by the product; do not rely on fallback strings for those keys (PAY-N4). | Reject | Inspect the product's configured locales and required keys. |
| **PAY-M8** | `paymentStatus`, `paidAmount`, and `remainingAmount` **MUST** be written by exactly one response-mapping authority invoking PAY-D4. No secondary enrichment layer may author these fields for API clients. | Bug — PAY-C3 | Review for a single writer at the response boundary. |
| **PAY-M9** | Immediately before PAY-D4, normalize an omitted or null payment-entry collection to an empty array only when the contract defines that meaning (PAY-D7); a wrong type remains invalid (PAY-F1). A query-engine aggregation over persisted payment entries **MUST** use the one PAY-D7 shape adapter and may sum only its validated rows; list and total owners **MUST** translate its invalid marker to the registered invalid-payment-item error before returning. Refund netting follows PAY-M25. | Bug | Review normalization and aggregate consumers: a single normalize step before the mapper; the aggregate receives only the canonical adapter's validated path, and every aggregate output owner checks the invalid marker before shaping its result, so invalid input never yields a successful partial result. |
| **PAY-M14** | An operation that settles multiple financial rows **MUST** accept the actor's bounded PAY-D10 explicit item IDs as intent, authorize every item, and re-read every selected row from the authoritative store inside one service-owned transaction. The server **MUST** derive canonical amounts and grouping from those rows and persist the complete selection as one all-or-none command: every selected row commits exactly once or none commits. The client may display a derived preview total, but that value is never write authority. Apply [transactions/transaction-policy.md](../transactions/transaction-policy.md) and [idempotency/idempotency.md](../idempotency/idempotency.md) in addition to this rule. | Critical financial integrity bug — reject / must not ship | Static: request contract contains explicit item IDs but no authoritative amount/group; one domain command owns one transaction. Runtime evidence: persisted selected IDs and server-derived amounts correspond to one committed unit, with no partial success response. |
| **PAY-M18** | A fail-loud money authority **MUST NOT** be replaced by inline arithmetic: its missing snapshot/price/cancelled-input refusal is part of the derivation. Returning legal zero from incomplete inputs silently loses revenue. | Bug — silent revenue loss | Inspect, using the adopting project's enforcement mechanism, every inline re-computation of an authority's formula; a local rebinding of the same source followed by the same arithmetic and cross-file consumers require provenance review. Record the mechanism's actual scope and limits. |
| **PAY-M20** | Each stored money field **MUST** have one complete validity/normalization gate consumed directly by every reader. Caller presence/type/range pre-tests **MUST NOT** replace or precede the authority's judgement, including substituting a valid-looking value before its gate. Legitimate normalization (for example a stored date value to the contractual ISO string) belongs in the gate; sibling fields use the same gate shape, never private exceptions. | Bug — the authority's refusal cannot fire | Search the field's name for type/instance/presence branches outside the gate; inspect each consumer's direct delegation and sibling-field gate shape. |
| **PAY-M27** | Every writer that adds actor-declared collected money to a single record's ledger — a collection command's partial amount, a ledger-replacing edit, or a record birth carrying collected rows — **MUST** bound the added collected total inside the unit that writes it, against that record's remaining from its ledger's own remaining authority on the PAY-D8 scale (the ledger without the added rows, after any same-unit price write), through one amount decision shared by every ledger kind and writer; an amount above the remaining **MUST** be rejected with a registered business error code, never clamped or turned into the full remaining. A price edit below the received total adds no money and is not bounded by this row. The server that honours a new optional amount field **MUST** be live before any client sends it, because an older server's object schema strips the unknown key and books the full remaining. | Wrong money written — a partial request booked as full, or an overpayment | Review: one shared bound decision for every writer; release order is checked at deploy. A syntax check cannot establish whether a computation is a bounded collection; record any check's actual scope and limits. |
| **PAY-M28** | A tenant's money **MUST** live in exactly one currency: amounts are plain numbers read in the tenant currency, and a row that stores a currency label (an accrual, a payout) **MUST** carry that same code. A currency change after birth **MUST** go through one writer that requires the user's explicit "relabel without converting" consent and moves every stored label in the same transaction as the settings write, a unit bounded by TX-M-13 and never committed in chunks (a chunked relabel leaves readers on a mixed set); a reader that sums labelled rows **MUST** refuse a row whose label differs instead of adding two currencies. A derivation that can create a new fraction (percent, division, proration, parsed input) **MUST** round to the currency's own minor units from the one currency table; folds of stored amounts round on the storage scale, which is the finest minor unit in that table, and a proration's last share takes the remainder on the storage scale so the shares always sum to the stored total. A retired ISO 4217 code **MUST NOT** be offered or accepted as a new choice; once a count over stored data proves no row uses it, it is removed from the currency table rather than kept as a dead member. | Wrong money shown or refused — historical amounts relabeled silently, unpayable accruals, fractional amounts in a zero-decimal currency | Review: one relabel writer; readers delegate to one currency-match guard; one rounding authority. Whether a computation creates a fraction is not decidable from syntax, so a syntax check cannot replace review. |
| **PAY-M29** | A paid outbound channel (a metered message, a billed send) **MUST** be gated by one durable balance authority: every grant, debit, refund and operator correction is applied exactly once through a ledger keyed by its business event (purchase transaction, sent item, operator action), balance and ledger entry are written in one transaction, and the balance never goes below zero. Exhaustion **MUST** degrade the flow to its free path — the core action still completes and its result stays visible — and **MUST NOT** block it; the account holder is told once per exhaustion episode. Where the provider bills per delivered item, a debit taken at provider acceptance **MUST** be refunded under the debit's own ledger key when the item reaches a terminal failure without any delivered status; where the provider bills at acceptance, no refund is made — the balance pays what the provider charges, no more. | Bug — a purchase or message applied twice, a negative balance, or a core flow stopped by a spent balance | Review: one writer of the balance and its ledger, a unique ledger key, and the exhausted branch reaching the free path. "Is this send paid" is not decidable from syntax, so a syntax check cannot replace review. |
| **PAY-M30** | A consumable that pays a provider whose unit cost varies by destination **MUST** record on every grant the cost tier it was bought at, from the purchase's own market evidence and capped at the unit cost the price actually paid covers after tax and the distribution channel's share — never above the market's tier, and without the margin multiplier so rounding or currency drift never lowers an honest buyer's tier (a grant missing either fails loud, never a guessed tier), and **MUST** debit each send `max(1, ceil(destination cost ÷ tier cost))` units of one tier, read from the one rate authority that also prices the bundles; a send no single tier covers is refused like exhaustion (PAY-M29), never split or partially debited, and a take-back removes the granted value, not a unit count. | Bug — credit bought in a cheap market pays for an expensive destination at a loss, or a send is charged a fraction | Review: tier recorded at grant, one rate table read by debit and price suggestion, integer rounding up. "Does this provider cost vary by destination" is not decidable from syntax, so a syntax check cannot replace review. |

Timestamp provenance (PAY-M5): a valid supplied ISO value may be an explicit historical date or a released client's old default; the server **MUST NOT** guess its origin or overwrite an allowed date. Missing completed payment time is filled by the single backend normalization authority, separate from the pure shared schema. Installed-client compatibility closes through client release evidence, not a source gate.

## MUST NOT (normative) — PAY-N

| ID | Rule | Consequence | Verify |
|----|------|-------------|--------|
| **PAY-N1** | Frontend, mobile, or non-mapper backend layers **MUST NOT** compute `paymentStatus`, `remainingAmount`, or PAY-D3 independently for authoritative UI/API behavior. | Reject PR / bug | Static: search the client for payment status formulas; it must use API fields. |
| **PAY-N2** | Implementations **MUST NOT** infer collected money from a lifecycle status or from the creation of a bundled or prepaid product alone. | Bug | Review that collection is derived only from validated financial records. |
| **PAY-N3** | Implementations **MUST NOT** default missing persisted `totalAmount` to `0` in outbound API models when the distinction between PAY-D1 and PAY-D2 is required (forbid silent collapse to zero). | Bug | PAY-O2 audit. |
| **PAY-N4** | **MUST NOT** ship placeholder or fallback user-visible strings for mandatory PAY-M7 keys. | Reject | Locale files complete. |
| **PAY-N5** | When `totalAmountFieldPresent === false`, implementations **MUST NOT** emit `paymentStatus: 'paid'` solely because a numeric `totalAmount` field on the in-memory object equals `0`. | Bug | Inspection: absent key plus in-memory 0 is still unpaid. |
| **PAY-N6** | A client **MUST NOT** submit an authoritative amount or grouping for a PAY-M14 settlement, fan out one multi-row user action into multiple single-row mutation calls, or translate an "All" scope/filter into implicit select-all. A server **MUST NOT** settle rows discovered only from a mutable filter/range at execution time; the command is bound to the explicit IDs submitted for that action. | Reject — partial payment, stale amount, or unintended-row risk | Static: no client amount/group field and no mutation loop; contract: "All" changes read scope only; server: exact-ID validation precedes the single transaction. |
| **PAY-N7** | A retained financial row **MUST NOT** be filtered, regrouped, renamed, or rejected solely because its subject is absent from current membership or account-link state. Its immutable name snapshot **MUST NOT** be added to a broader response unless that surface is explicitly authorized to expose it. | Reject — retained history disappears or sensitive data crosses an authorization boundary | Review current-membership filters, exact settlement reads, and surface-specific response projections. |
| **PAY-N8** | A financial migration **MUST NOT** treat separate pre/post counts, process-local state, cache-only coordination, an assumed maintenance window, or a fence created opportunistically by settlement writers as a substitute for the pre-provisioned same-database transactional fence required by PAY-M16. It **MUST NOT** translate missing/malformed fence authority into an ordinary maintenance response. | Reject — a concurrent payout can commit between checks after earlier migration chunks already committed, or authority corruption can remain hidden | Review that migration and settlement share the same durable transactional fence in both write sets, and that losing or failing to parse it aborts before the next financial mutation through the system-error path. |
| **PAY-N9** | Money invalidity **MUST NOT** become legal `0`; represent allowed absence as `undefined`/absence, and required-field corruption by a registered error. The same prohibition covers in-range stand-ins such as an empty mandatory timestamp, epoch date or sentinel identity. | Bug — unknown becomes valid data without an alarm | Inspect money derivations and outputs for placeholder defaults and every required-field stand-in; see the placeholder-check limits below. |
| **PAY-N10** | An existing money record **MUST NOT** be repriced from the live catalogue without explicit user choice; the input and re-selection corollaries bind ([clauses](#pay-n10-clauses)). | Bug — a sale is silently re-priced, a typed amount is silently dropped, or the edit screen crashes | Inspect the input, write and read paths against the clauses below. |

<a id="placeholder-checks-pay-n9"></a>

## Placeholder checks — [**PAY-N9**](#must-not-normative--pay-n)

A static check can identify direct numeric fallbacks (a null-coalescing or presence-test default to `0`) on a money-named receiver and direct empty-string defaults on timestamp fields, while leaving a deliberate numeric clamp alone — the test's question, not the literal, separates them. Use the enforcement mechanism the adopting project documents for these forms; a reference to a check is not evidence that it exists or covers the full rule, so record its actual scope and limits.

These checks identify receivers and direct default expressions; a differently named intermediate or cross-call helper does not prove the persisted field's provenance, and checks on non-money fields may create false positives. Epoch/sentinel variants still follow PAY-N9's absence/fail-loud contract, and remaining call paths are reviewed.

<a id="existing-price-edit-clauses-pay-n10"></a>

## Existing-price edit clauses — [**PAY-N10**](#pay-n10-clauses)

An existing-record edit **MUST** seed money inputs from its stored sale price and leave them unchanged on unrelated edits (for example a quantity or duration change). The catalogue value may be shown beside it and, when different, **MUST** be visibly offered through an explicit labelled "apply current price" action. Only that choice writes a price override through the record's one writer. Stored price remains the default, catalogue is never silently applied/hidden, and direct price input remains available: a rule never removes a user capability — options are offered, not imposed. The catalogue is birth authority, not an edit writer ([PAY-R-D7](reporting.md)).

<a id="pay-n10-corollary--a-value-helper-carries-only-the-inputs-its-result-depends-on"></a>

<a id="value-helper-inputs-pay-n10-corollary"></a>

### Value-helper inputs — [**PAY-N10**](#pay-n10-clauses) corollary

A default-price helper that also takes a quantity "for validation" imports the range decision of the flow it was written for; reused in another flow whose range authority differs, it rejects values that flow permits. Each flow's range is decided by that flow's own range authority, once, and client and server read the same derivation of it.

<a id="pay-n10-corollary--one-input-per-money-fact-and-every-input-reaches-the-write-authority"></a>

<a id="one-input-per-money-fact-pay-n10-corollary"></a>

### One input per money fact — [**PAY-N10**](#pay-n10-clauses) corollary

A figure derived from others (outstanding = price − received) gets no input of its own on the same form: a second input for it is a second writer of the price, and when the write path reads only one of the two, the other is silently dropped. The server keeps accepting such a field while released clients may still send it ([DCD-M8](../dead-code/dead-code-rules.md)); the current client neither renders nor sends it.

<a id="pay-n10-corollary--a-stored-derived-money-value-is-written-by-the-server-and-only-when-a-pricing-input-is-re-selected"></a>

<a id="stored-total-writes-on-pricing-re-selection-pay-n10-corollary"></a>

### Stored total writes on pricing re-selection — [**PAY-N10**](#pay-n10-clauses) corollary

A record's stored total (the value a payment path reads as "expected") is not an edit input: an edit request carries the user's pricing *inputs* (line selection, kind, explicit price override) and the server derives the stored total from the record's frozen lines plus the override, in the same write as the line patch, only when one of those inputs actually changed — one shared predicate that the client preview reads too. A status, note, time or assignee edit leaves it untouched. A client that computes the total itself and sends it on every save is a second writer. Released clients that still send the retired field are accepted and the field is dropped at the request schema (the value reaches no write path; [DCD-M8](../dead-code/dead-code-rules.md) — no rejection of an in-field client). The same holds at birth: a create request carries the pricing inputs, never the stored total, and the create writer derives the total from the lines it freezes in that same write plus the override.

<a id="pay-n10-corollary--re-selection-is-per-line"></a>

<a id="retained-frozen-lines-pay-n10-corollary"></a>

### Retained frozen lines — [**PAY-N10**](#pay-n10-clauses) corollary

Adding or removing one line of a multi-line record does not re-price the lines that stay: each kept line keeps its frozen name, duration and price — and every other per-line term frozen at the line's birth, such as an allocation rule for that line — and only a newly added line is born from today's catalogue (PAY-R-D7 applies per line). The client's per-line display, its preview total and the server's line patch read the same merge.

<a id="pay-n10-verification-and-check-boundaries"></a>

<a id="verification-and-check-boundaries-pay-n10"></a>

### Verification and check boundaries — [**PAY-N10**](#pay-n10-clauses)

Inspect record-seeded money inputs, explicit catalogue offers, result-dependent helper parameters, and each money input's consumed request field. Existing/birth context, source provenance and selected server branches are cross-file facts that a single-file syntax check cannot decide. Types that exclude stored totals from create/update requests and internal create inputs hold the omission; predicate-only total writes and kept-line freeze require writer/merge review.
