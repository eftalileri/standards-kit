# Ad-platform install and conversion attribution -- normative

```kit-cover
type: normative
part-of: README.md
binds: capturing and attributing mobile-app installs and conversions from ad-platform signals - provider contract fidelity, lossless provider ids, partial validity, channel truth, closed capture outcomes, retry and lifecycle, drift observability, consent per signal, server classification authority, the web-to-app click-id handoff, pre-campaign verification and keeping provider contracts current; delivering conversion events so the platform attributes them to the ad - conversion definition, install anchor and send delay, app-event body, identifiers in the release build, per-event delivery record, attribution mirror, proof metric and its report field, optimization-event learning volume and ad-report retention
open-when: signal:analytics-attribution, signal:ad-attribution, signal:install-referrer, signal:conversion-events, signal:external-provider
skip-when: signal:no-attribution-change
owns: ADA-D*, ADA-M*, ADA-N*, ADA-S*
```

Scope: How an app (iOS and Android) learns, for each installation and its later conversions, which paid ad platform and campaign caused it, using the signals the operating-system vendors and ad platforms publish, plus click identifiers carried through a web landing page. Rules are stack-neutral; stack notes are isolated at the end. Excluded: SDK auto-collection flags and the consent applier ([analytics-rn.md](analytics-rn.md), **PAN-RN-M4**–**PAN-RN-M10**, **PAN-RN-M12**, **PAN-RN-M13**); product-event taxonomy (**PAN-RN-M1**–**PAN-RN-M3**); ad-spend import and reporting.

Placement: this part file extends the analytics hub because that hub already owns the ad/attribution SDK consent rules and the `signal:analytics-attribution` route; a separate topic would be a parallel authority for one data flow.

Reference companion (provider fact sheets for an Apple and Meta example set, verification and go-live checklists, sources): [ad-platform-attribution-provider-reference.md](ad-platform-attribution-provider-reference.md). The reference is an optional adapter: a project that uses other providers writes the equivalent fact sheet and keeps the rules below.

Currency: the provider facts in the reference describe the providers' documentation and observed platform behaviour on the date the adopting project last checked them. An agent applying them **MUST** first compare every provider fact it relies on with the provider's current official documentation and changelog; where they differ, the provider wins and the project's fact sheet is corrected in the same change (**ADA-M14**). A value described as measured is not provider-documented and is re-measured, not assumed.

Rules owned elsewhere and applied here, not restated: provider response validation at its owner path and its sealed-envelope, absence and timestamp corollaries ([M21](../error-policy/provider-contract-and-webhook-errors.md)); retryability split of provider failures ([M19](../error-policy/provider-contract-and-webhook-errors.md)); no stand-in values ([SSG-M17](../ssot/ssot-must-no-stand-in-data.md)); one authority per datum and the absent-input application ([SSG-M1](../ssot/ssot-must-authority-and-derivation.md), [absent-input application](../ssot/ssot-must-derivation-source-applications.md)); client classification and once-per-process reporting ([COB-RN-M6](../client-observability-rn/classification-authority-and-outbound-links.md), [COB-RN-M12](../client-observability-rn/absorbed-defaults-and-global-nets.md)); an impossible capability is not a failure ([COB-RN-M15](../client-observability-rn/outbound-link-ownership-and-visibility.md)); request-schema bounds on third-party values and forward-compatible response schemas ([MRP-M15](../monorepo/monorepo-rules.md)); first-session measurement needs a store build ([PAN-RN-M11](analytics-rn.md)); durable device identifiers ([SEC-M-STORE-5](../security/security-client-mobile-surface.md)).

## Definitions

| ID | Definition |
|----|------------|
| **ADA-D1** | Signal path: one provider mechanism that can attribute an installation. The closed set this file covers: (a) an operating-system attribution token exchanged for the ad platform's attribution record; (b) aggregated, signed install postbacks delivered to the ad network (and optionally a developer endpoint), never a per-install record on the device; (c) the store's install-referrer string, the transport for an ad platform's encrypted referrer and for web-landing parameters; (d) an ad-platform install referrer read from the ad platform's own apps through a content provider, encrypted the same way as (c); (e) click identifiers carried through a web landing page (platform click ids, UTMs); (f) server-sent conversion events (an ad platform's server-side conversion API for app events). |
| **ADA-D2** | Owner path: the single module per signal path that reads the provider's answer, validates it and hands typed fields onward. Client and server each have at most one per signal path, and both use the same shared schema module. |
| **ADA-D3** | Capture outcome: the closed per-signal-path fact sent with the install record -- `resolved` (the provider answered and the envelope is schema-valid, including a documented "no attribution" answer), `unavailable` (the signal cannot exist in this environment: unsupported OS or platform, simulator, no store, a documented feature-not-supported response, non-store install, ad-platform app not installed), `failed` (it could have answered and did not: transport error, provider outage after retries, expired token, envelope drift, decryption failure). A retry in progress is a state before the terminal outcome, not a fourth outcome. |
| **ADA-D4** | Authenticated payload: a provider answer whose origin is proven independently of its fields -- an encrypted referrer whose authentication tag verified under the app's key, or an attribution record returned by the operating-system vendor's endpoint for an OS-minted token. |
| **ADA-D5** | Channel verdict: the paid / organic / unknown decision plus source and campaign hierarchy for one installation, derived by one server classifier from all captured signals. |
| **ADA-D6** | Conversion event: a post-install action (registration, trial start, purchase) reported to an ad platform so that the platform attributes it to the install's ad and can optimize delivery on it. Its name is the platform's standard event the campaign optimizes for. |
| **ADA-D7** | Delivery record: the persisted per-event fact of one conversion send -- event id, subject, event name, attempt time, the action source the platform finally received, which matching signals were present (presence only, never values), and the platform's answer (status, events received, trace id, error codes, whether a retry is queued). |

## **MUST**

| ID | Rule |
|----|------|
| **ADA-M1** | **MUST** validate every provider answer at its owner path (**ADA-D2**) with a runtime schema that mirrors only the provider's documented guarantees: the documented type, documented required vs optional, documented values. **MUST NOT** add constraints the provider does not promise -- non-negative or range checks on ids, a guessed maximum length, seconds-precision on a timestamp the provider sends at minute precision, a closed enum the provider's changelog has already extended. Where the provider's documentation is silent on required-ness, the field is optional. Reason: an invented constraint turns valid provider data into "drift" and silently discards paid installs. This is the [M21](../error-policy/provider-contract-and-webhook-errors.md) contract applied per signal path. |
| **ADA-M2** | **MUST** parse provider JSON losslessly before any schema runs, and carry every provider id as its decimal digit string. Providers document ids as 64-bit integers with no range promise, and may quote them as strings in some samples and send them as unquoted integers above 2^53 in others -- the owner path accepts both encodings and keeps the exact digits. A default float parse (JavaScript `JSON.parse`, any `double`) has already changed a large id before the schema sees it, so the schema cannot detect it. Storage, warehouse columns and wire types are string or exact 64-bit integer, never float. The id rule itself is [M21](../error-policy/provider-contract-and-webhook-errors.md)'s sealed-envelope corollary; this row adds the parse-order obligation. |
| **ADA-M3** | **MUST** keep the install record when one leaf field is invalid: the field is omitted, the issue is reported (**ADA-M8**), the record still carries an honest capture outcome. **MUST NOT** truncate, clamp, round, re-case or synthesize a value to make it pass -- a truncated id is a different id, and a stand-in is forbidden by [SSG-M17](../ssot/ssot-must-no-stand-in-data.md). An invalid envelope field that the verdict depends on (the provider's attributed flag; a payload that fails to decrypt) makes the outcome `failed` for that signal path only; the other signal paths of the same record are unaffected. |
| **ADA-M4** | **MUST** derive channel truth only from evidence. (a) An authenticated payload (**ADA-D4**) proves the channel even when some of its ids are unreadable ([M21](../error-policy/provider-contract-and-webhook-errors.md) sealed-envelope corollary). (b) A missing, `unavailable` or `failed` signal is *unknown*, never organic or direct ([absent-input application](../ssot/ssot-must-derivation-source-applications.md)). (c) A provider's "no attribution returned" answer means only that; where the provider documents it is also returned for other reasons (for example privacy-threshold ad-group settings), it is not proof of organic and not even proof of non-paid. (d) An unauthenticated value (a `utm_source` value, a referrer whose tag did not verify, a landing-page parameter) is a hint the classifier may record, never a paid-channel proof; an ad platform may state that `utm_source` is not an indication of its install. (e) When several signals disagree, one documented precedence table in the server classifier decides. |
| **ADA-M5** | **MUST** report each signal path's capture outcome (**ADA-D3**) with the install record and compute capture-health rates as `resolved / (resolved + failed)` per signal path and platform; `unavailable` is excluded from the denominator and counted separately. Reason: a rate that counts simulators or non-store installs as failures pages on noise, and one that counts them as successes hides an outage. |
| **ADA-M6** | **MUST** retry only what the provider documents as transient, per the project's retry table (the reference shows one): a not-found within the token's documented validity window (at the provider's documented interval and attempt count), a provider server error, a network error, a disconnected store service. An invalid-token answer, a developer-error response and a schema failure of a provider-vouched answer are defects and are not retried as-is; an encrypted referrer whose tag does not verify is not retried either, and is a link-author input failure, not a defect (**ADA-M8**); a documented feature-not-supported or platform-not-supported response and a missing ad-platform content provider are `unavailable`. The HTTP client timeout to the provider's attribution endpoint **MUST** exceed the longest hold the provider documents before it answers not-found. A token past its validity window is replaced by a newly minted one, never re-sent. Classification follows [M19](../error-policy/provider-contract-and-webhook-errors.md), including its propagation exception for a not-found that can still become found. |
| **ADA-M7** | **MUST** capture once per installation and keep the raw provider inputs (store referrer string, encrypted ad-platform payload; for the operating-system token path, the ability to mint a fresh token) on the device until the server acknowledges the install record, retrying delivery across cold starts until it does. The server upserts idempotently by installation id: a resolved attribution field is first-write-wins and immutable; a later successful capture may fill only a slot that was never resolved. Login or account linking attaches the installation id to the account through the server; it **MUST NOT** reset, re-key or drop a pending capture. Reason: the store referrer stays readable for a bounded period and the OS token lives for a short one, but the install's first session is the only moment every signal is fresh. |
| **ADA-M8** | **MUST** route a provider-contract drift (an envelope or leaf outside the documented contract in an answer the provider itself returned) to the defect channel (`SYSTEM`). A referrer envelope that fails decryption is `BUSINESS` ([M21](../error-policy/provider-contract-and-webhook-errors.md) unauthenticated-link corollary): it reaches the app inside a link any author can write, so one failed tag is indistinguishable from a forged link; a wrong configured key shows only as that signal path's `failed` rate (**ADA-M5**), which the health reader alarms on. Route environment or user conditions (`unavailable`, offline, provider outage after retries) to the expected channel. Each distinct drift key `(signal path, field path, issue)` is reported at most once per process with the suppressed-repeat count kept ([COB-RN-M12](../client-observability-rn/absorbed-defaults-and-global-nets.md)(b)); an `unavailable` outcome is not reported as a failure ([COB-RN-M15](../client-observability-rn/outbound-link-ownership-and-visibility.md)). Evidence is structural only: field path, expected type, observed JSON type, length class, provider status code. **MUST NOT** log the raw payload, referrer string, token, decryption key, click id or any id value. |
| **ADA-M9** | **MUST** gate each signal path by its own documented consent requirement, from the project's single consent authority. Where the operating-system vendor documents that its attribution APIs may be called regardless of tracking authorization and do not engage in tracking as the platform's tracking-permission prompt defines it, a tracking-permission denial **MUST NOT** suppress them. Advertising-SDK collection keeps its own gate ([PAN-RN-M5](analytics-rn.md)); server events carry the live tracking-permission status and the regional data-use flags from the same authorities as the device ([PAN-RN-M7](analytics-rn.md), [PAN-RN-M10](analytics-rn.md)). Persisting an installation id or click id is a durable-identifier write governed by [SEC-M-STORE-5](../security/security-client-mobile-surface.md) and the project's regional regime. Attribution records hold provider ids, campaign metadata and outcomes only -- no name, e-mail, phone or raw advertising id -- and are deleted by the account-erasure authority with the account they were linked to. |
| **ADA-M10** | **MUST** keep the attribution verdict on the server. The client sends raw signals and capture outcomes, never a paid / organic verdict; the server re-validates with the same shared schema (**ADA-D2**), exchanges the OS token with the provider itself, decrypts the ad-platform referrer itself, and one classifier owns **ADA-D5** ([SSG-M1](../ssot/ssot-must-authority-and-derivation.md)). The decryption key and any provider credential live only in the server's secret store. Reason: a verdict or key in the binary is forgeable and cannot be rotated without a store release. |
| **ADA-M11** | **MUST** hand landing-page parameters to the app losslessly: each click id and UTM is copied byte-for-byte (case preserved where the provider documents its click id as case-sensitive), URL-encoded exactly once into the store `referrer` parameter, and decoded exactly once by the owner path. Where a provider documents no maximum length for its click ids, a bound is derived as [MRP-M15](../monorepo/monorepo-rules.md) note (b) requires (from measured real values, the derivation stated at the bound), set with wide headroom above the largest measured value and named at its definition as an abuse limit, not a format claim -- a bound at the observed maximum fails on the provider's next longer id -- and is identical in the landing page, client and server schema; a value over it is omitted and reported (**ADA-M3**), never cut. A click-derived cookie value the provider defines from the click id is built in the provider's documented format with the click id unmodified. A click id the platform accepts for a later conversion upload **MUST** be stored on the touch in a field named for it whenever it is present, whatever channel the verdict names, and carried onward under its real key; classifying on such an id while dropping its value is a defect, because the value cannot be recovered after the visit. |
| **ADA-M12** | **MUST** give each conversion event one event id, produced by one authority and sent identically by the on-device platform SDK and the server path, so the ad platform can deduplicate (typically on event name plus event id). Server events respect the provider's documented event-age window (a provider may reject the whole request if any event is older than it), so a late event is sent alone or dropped with a report, never back-dated. |
| **ADA-M13** | **MUST** pass every step of the pre-campaign verification checklist (the reference shows one; a project using other providers adapts it) for each signal path the project ships, with real-run evidence (a device, a store track, the real server schema in a scratch script), before the first paid campaign on that platform. No automated test artifact is written for it ([M12](../agent-planning/agent-planning-obligations.md)). |
| **ADA-M14** | **MUST** re-check each owner-path schema against the provider's current documentation and changelog at least quarterly, on every drift report, and on every provider SDK or library upgrade, and record the documentation date or version checked in the project's source list. Reason: provider contracts change without breaking the HTTP call (new fields, new enum members and new `false`-answer cases appear within a couple of years; a provider may mark referrer metadata "subject to change"). |
| **ADA-M15** | **MUST** report, per period, every measured paid touch whose full identity (channel, campaign, ad) matches no delivered ad row as its own count with its ids, and an alert on spend without measured outcomes **MUST** name which case it measured: touches arrived for the account's campaigns but their ad ids joined no ad (an id-mapping defect), or no touch arrived at all (capture or tagging, with the platform's own install claim beside it). Reason: a touch that is neither matched nor unattributed is counted nowhere, so a wrong stored ad id looks exactly like a capture that never happened and the fix goes to the wrong layer. |
| **ADA-M16** | **MUST** fire each conversion event (**ADA-D6**) from the one authority that creates the product state it names, at the moment that state begins, once per subject, with a deterministic event id (for example `<event name>_<subject id>`): when every new tenant starts its trial at creation, the tenant-creation authority sends the trial event. The sent name **MUST** be the platform standard event that the campaign's optimization event selects; verify the pair in the platform's campaign settings before spend. Reason: an event sent from a proxy moment, or under a name the campaign does not optimize for, gives the platform no usable signal while spend continues. |
| **ADA-M17** | **MUST** anchor a server-sent app conversion to an install the platform already knows. (a) The on-device platform SDK reports install / activation in the first session, before any user step; verify on a store build that this report leaves the device. (b) The server sends the conversion only after a delay that follows the device's install report (the adopting project **MUST** measure and document a finite value; a provider may document none), scheduled in a durable store so that it survives a process restart, retried with a bounded attempt count and backoff, and claimed atomically so that a reprocess never sends twice. (c) The event time is the send moment, never a back-dated value before the install report. Reason: a conversion that reaches the platform before or with the install finds no install to attach to and is counted as received but never attributed. |
| **ADA-M18** | **MUST** send an app conversion as a real app event: the provider's app action source; app-level data carrying the tracking-enabled flags that reflect the recorded consent fact and the provider's positional extended device info (platform version marker, OS version, empty strings for unknown positions); the SDK install id and the advertising id when permitted, in the form the provider requires (unhashed where it says so); and the client IP address and user agent taken from the device's own request. These come from a device context the app records on open under consent and that the server stores with the account. The dataset or pixel receiving the events **MUST** be linked to the app in the platform's events manager. Without a device context the event is sent under a non-app action source (not app-optimized), and every such fallback, and every app body the platform rejects, is counted and reported with the platform's error code. Reason: without the device fields the platform cannot match the event to the install's ad. |
| **ADA-M19** | **MUST** keep the attribution identifiers and the SDK's first-session install report alive in the release build: Android code shrinking (R8 / ProGuard) keeps the advertising-id client and SDK classes; the SDK app id and client token in a store build come from the one production authority, fail the build when missing or malformed, and are checked against the platform before the build ships ([BE-M32](../build-environment/build-environment-env-key-declaration.md)). Verify on the store artifact, never on a debug build. Reason: a debug build that attributes proves nothing about the shrunk, differently configured store binary. |
| **ADA-M20** | **MUST** persist a delivery record (**ADA-D7**) for every conversion send, written idempotently by event id, deleted with the account by the erasure authority and with the tenant by the closure authority. A failed write of the record **MUST** reach the defect channel carrying the complete platform answer and, for a validation failure, each rejected field path with its reason. Reason: without a per-event record a sent event and a lost event look the same, and the platform reports attribution only per ad and day. |
| **ADA-M21** | **MUST** run an attribution mirror: per ad-sourced subject, compare the delivery record with the platform's per-ad reported conversion count after the platform's attribution grace (the adopting project documents the value it measured), and classify every subject by one closed cause set -- no owning tenant, pending, not sent without consent, not sent without device context, not sent, sent unrecorded, platform rejected, sent without device context, platform count unavailable, install not attributed, delivered not attributed, attributed. Every failure cause raises one critical alert that lists each failing subject as one line (ad id, times, platform answer, signals, cause, fix); consent denial is counted and shown, never alerted. Reason: an attribution break otherwise surfaces only as spend without results, after the budget is gone. |
| **ADA-M22** | **MUST** measure success only as: of the first N real ad-sourced subjects that reached the conversion after a change, how many the platform's per-ad report counts. **MUST NOT** accept as proof an own-device test, a preview, or the platform's test-events tool -- that tool accepts bodies that attribution then ignores. The count **MUST** be read from the report field and key the project's fact sheet names for the optimized event (the reference gives a Meta example), and the read states field, key, attribution window and date range; a "not attributed" verdict needs the same read as an "attributed" one. Reason: the platform reports some standard events outside its general action list, so a lookup in the wrong field returns 0 for an event it counts, and spend is cut for a defect that does not exist. |
| **ADA-M23** | **MUST** keep the store of platform-reported spend, installs and conversions free of any default table, partition or dataset expiry, and the store's ensure step re-asserts no expiry on every run. Reason: an inherited sandbox expiry silently deletes the history the mirror (**ADA-M21**) and spend alerts (**ADA-M15**) compare against. |
| **ADA-M24** | **MUST** treat an ad platform that publishes no per-install server conversion upload as install-attributed only: a post-install conversion reaches it, if at all, only as an aggregated postback conversion value (one writer, **ADA-N2**). A project that wants such a platform to see trials sets the conversion value at the trial moment (**ADA-M16**); otherwise trial and revenue per campaign are joined on the server from the attribution record (**ADA-M10**), and no platform-side trial count is expected. |
| **ADA-M25** | **MUST** check before spend, and on every budget change, that the optimization event can reach the platform's learning volume per ad set: expected weekly events = weekly budget / expected cost per event (from the platform's own reported cost for that event, or the funnel's measured install-to-event rate times cost per install), compared with the platform's published threshold. Below it, the choice of a different optimization event, fewer ad sets or a larger budget is recorded as a decision with the computed number; keeping the event is allowed, but the plan states that delivery stays learning-limited. Reason: below the threshold the platform never leaves learning, so cost per result stays volatile however correct the event delivery is, and a delivery defect is wrongly suspected. |
| **ADA-M26** | **MUST** recognise a source's self-applied tag in the exact form the source emits (an AI assistant appends its own host as `utm_source`, so every assistant referrer host is also an accepted source value), and **MUST NOT** credit a host that a search engine shares with an assistant to the assistant (when one host serves both search and the assistant, it is organic search). Landing and server classifiers read one vocabulary source; any landing copy is verified as a whole-file mirror by the project's enforcement mechanism. Reason: an unrecognised explicit source is classified unknown before the referrer is read, so the channel vanishes entirely, while a shared host credited to the assistant inflates the assistant with ordinary search. |
| **ADA-M27** | **MUST** measure the consent rate of every consent-gated capture surface -- web banner: shown on its own, granted, declined, unanswered derived; app: the measurement answer of the period's new accounts -- as day totals that carry no visitor id and write nothing to the device, and **MUST** show it beside the channel counts that depend on it. A low rate is a coverage limit, not a pipeline defect: it is shown, never alerted. Reason: every consent-gated channel count is the real count times the consent rate, so without the rate a channel cannot be judged to work or fail. |

## **MUST NOT**

| ID | Rule |
|----|------|
| **ADA-N1** | **MUST NOT** treat aggregated install postbacks as per-install or per-user records, or join them to an installation or account. They are aggregated under the provider's crowd-anonymity tiers; they serve campaign-level reporting only. A developer copy of a postback is accepted only after its provider signature verifies. |
| **ADA-N2** | **MUST NOT** let two writers update the postback conversion value. One module (the app's own, or one chosen SDK) owns the conversion-value schema; a second writer overwrites the first and corrupts every postback ([SSG-M1](../ssot/ssot-must-authority-and-derivation.md)). |
| **ADA-N3** | **MUST NOT** decrypt the ad-platform referrer with a routine that skips authentication-tag verification (stripping the tag and decrypting as a stream cipher). The verified tag is what makes the payload authenticated (**ADA-D4**); without it any forged referrer becomes a paid install. |
| **ADA-N4** | **MUST NOT** count provider test data as production attribution. Providers return fixed test payloads in developer or test modes, and development postbacks may be signed with a separate key; the single channel classifier recognises the documented test payload (an older client that does not forward every id may send a partial payload) and produces no paid claim from it, so no metric can count it, or the server tags such records with their environment and every metric excludes them through one shared scope. |
| **ADA-N5** | **MUST NOT** send a server conversion in the same request, transaction or moment that creates the install or account on the device, and **MUST NOT** keep its pending send only in process memory or a fire-and-forget timer (**ADA-M17**). |
| **ADA-N6** | **MUST NOT** fake an app event: no app action source without a real device context, no invented extended device info, install id or advertising id, no hashing of ids the provider requires unhashed (**ADA-M18**). |
| **ADA-N7** | **MUST NOT** let a conversion path fail silently: a skipped send, a non-app fallback, a platform rejection or a lost delivery record each leaves a counted, alertable trace with its cause (**ADA-M18**, **ADA-M20**, **ADA-M21**). |
| **ADA-N8** | **MUST NOT** declare an attribution fix done from code review, a green gate or a test-events receipt; it is done when real ad-sourced conversions appear in the platform's per-ad report (**ADA-M22**). |

## SHOULD

| ID | Rule |
|----|------|
| **ADA-S1** | On Android, implement the store install-referrer path first; add the ad platform's content-provider path when view-through or cross-session click-through installs matter (where the platform documents that the store referrer carries neither), and deduplicate the two in the server classifier (for click-through installs a platform may document the two referrer values as identical). |
| **ADA-S2** | Prefer reading provider answers in the server runtime, where lossless JSON parsing and secrets are available, and keep the client owner path to transport (token, raw referrer string, outcome). |

## Stack notes (React Native / Expo)

- The OS attribution-token API, the store install-referrer client and the ad-platform content-provider query are native calls: they need a native module and, for the content provider, Android `<queries>` entries for the ad platform's packages. A native change reaches new installs only through a store build ([PAN-RN-M11](analytics-rn.md)).
- Do not parse provider JSON on the device unless the engine offers lossless parsing (a `JSON.parse` reviver with source-text access, or a lossless parser library); otherwise forward the raw text (**ADA-S2**).
- The shared schema module is the one the client parses before sending; its bounds follow [MRP-M15](../monorepo/monorepo-rules.md) note (b).
